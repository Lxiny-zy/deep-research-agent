# 10 系统设计、框架比较与压力题（10 题）

## Q91. SparkOffer 用 LangGraph，DeepResearch 为什么又自研工作流引擎？

**面试官为什么问**

这是简历上最自然的框架比较题。对方会判断自研是合理学习和定制，还是重复造轮子并夸大能力。

**30 秒口播**

SparkOffer 的目标是尽快把面试训练闭环做出来，LangGraph 的状态机、interrupt 和 Checkpoint 很适合，所以我直接使用成熟框架。DeepResearch 的目标之一是把 Agent Runtime 的关键原语做透，我需要工作流作为图数据落库、前端编辑、定义快照和自定义合并语义，因此实现了项目范围内的轻量引擎。它不是 LangGraph 的通用替代，只覆盖线性/DAG、条件、Join、反思、团队和恢复这些需求。

**深水区备料**

- LangGraph 优势：成熟生态、持久化、人机中断、图执行、社区维护，业务项目优先选它。
- 自研收益：数据模型、运行状态、前端画布、租约和证据链可精确对齐；代码可用于解释底层原理。
- 自研成本：并发合并、取消、Checkpoint 兼容、可观测、迁移和大量测试都要自己承担。
- 选择标准：已有框架能否满足持久化语义、扩展点、团队维护成本和上线时间，不以“自主可控”作为空泛理由。
- 如果公司已有 LangGraph 平台，你应优先融入而不是坚持重写。

**大概率追问**

- 你的引擎有哪些能力 LangGraph 已经有？
- 如果重做还会自研吗？
- 自研最大 Bug 是什么？

**坑**

- 不要说自研性能或能力超过 LangGraph，除非有同口径基准。
- 不要贬低框架来抬高项目。

## Q92. LangChain、LangGraph 和 LlamaIndex 各自适合解决什么？

**面试官为什么问**

简历同时写了三者。对方会检查你是否只是把流行库都列上去。

**30 秒口播**

我把它们看成不同层。LangChain 更偏模型、Prompt、工具和 chain 的通用组件；LangGraph 解决有状态、多步骤、可中断和可恢复的执行图；LlamaIndex 更偏数据接入、索引、检索和 RAG 组织。SparkOffer 里状态机用 LangGraph，知识库管线用 LlamaIndex，工具和模型适配会用 LangChain 的组件。实际项目不需要为了统一而把所有逻辑都塞进同一个框架。

**深水区备料**

- 三者边界会随版本变化，回答应以你实际使用的模块为准，不背官网口号。
- LangChain abstraction 多、升级快，核心业务可包一层自己的接口降低耦合。
- LangGraph 的 state schema、node、edge、checkpoint 和 interrupt 适合长流程，但业务权限和工具幂等仍需自己做。
- LlamaIndex 的 ingestion/retriever/index 能缩短 RAG 开发，但召回评测、数据版本和权限过滤仍是应用责任。
- 选型要看团队已有栈、可观测、部署、许可证和版本维护，而不是下载量。

**大概率追问**

- 不用 LangChain 能否直接调 SDK？
- LlamaIndex 和直接用 Qdrant 有什么区别？
- 框架升级导致接口变化怎么处理？

**坑**

- 不要把框架功能说成你自己的实现。
- 不要回答成三个官网定义，必须结合 SparkOffer 的实际分工。

## Q93. Function Calling、MCP 和 Skill 有什么区别？

**面试官为什么问**

这是当前 Agent 岗常见概念组合。对方想看协议、工具发现和可复用工作流是否被混在一起。

**30 秒口播**

Function Calling 是一次模型调用里描述工具 schema，让模型返回工具名和参数；MCP 是应用与外部能力提供方之间的标准协议，除了工具还可以暴露资源和 Prompt，并支持发现与连接；Skill 更像给 Agent 的可复用操作说明和工作流包，告诉它某类任务该按什么步骤使用哪些工具。三者可以组合：Skill 规定流程，MCP 提供远端工具，模型通过 Function Calling 选择具体动作。

**深水区备料**

- Function Calling 通常由模型 provider API 定义，执行循环和权限仍由应用实现。
- MCP 标准化 client/server 通信和能力发现，不自动解决业务授权、沙箱和可信度。
- Skill 可能只是文档、Prompt、脚本和模板集合，不一定是运行时协议；具体含义依平台而异。
- 工具数量多时要做分组、检索式发现或分层路由，不能一次把几百个 schema 全塞入上下文。
- 外部 MCP Server 的工具描述和输出都属于不可信输入。

**大概率追问**

- 18 个工具是否需要 MCP？
- MCP Server 如何鉴权？
- Skill 能否替代代码工作流？

**坑**

- 不要说 MCP 是“Agent 的 USB”后就停止，面试需要具体协议边界。
- 不要说 MCP 自动提供安全和跨租户隔离。

## Q94. 设计一个企业内部知识 Agent，你会怎么做？

**面试官为什么问**

这是 Agent 应用开发的标准系统设计题。重点不在画十个模型，而在权限检索、证据、更新和反馈闭环。

**30 秒口播**

我会先把它做成受约束的 RAG Agent，而不是自由自治。数据接入时保留文档版本、ACL 和来源，按权限切分索引；查询先做身份和意图判断，再用混合检索、重排和上下文预算找资料。模型回答必须带引用，写操作和跨系统工具默认关闭。运行层记录检索、引用、Token 和反馈，离线用权限泄露、召回和 groundedness 集评测，线上从少量部门 canary 开始。

**深水区备料**

- 接入：连接器 → 解析/OCR → chunk → metadata/ACL → embedding/index → 增量更新与删除。
- 查询：tenant/user ACL filter 必须下推到检索层，不能召回后再让模型过滤。
- 检索：BM25+向量、多 query、RRF、rerank；保留版本和文档级引用。
- Agent：先问答和只读搜索，复杂任务才启用计划与工具；最大步骤、预算和超时明确。
- 安全：Prompt Injection、越权检索、敏感字段、审计、DLP、外部模型数据策略。
- 评估：ACL 泄露 0 容忍、Hit@K、引用支持、用户解决率、P95 和每问题成本。

**大概率追问**

- 文档权限实时变化怎么办？
- 同一问题不同用户为何答案不同？
- 如何处理表格、图片和 PDF？

**坑**

- 不要把权限过滤放到生成后。
- 不要一上来设计多 Agent 群聊，先证明单 Agent RAG 的必要性和边界。

## Q95. 设计一个能执行写操作的业务 Agent，如何保证可控？

**面试官为什么问**

从知识问答升级到改工单、发邮件、退款后，错误成本完全不同。对方会看 human-in-the-loop 和事务设计。

**30 秒口播**

我会把计划和执行分开。模型先生成结构化 action plan，服务端校验权限、参数和业务规则；只读步骤可以自动跑，写操作先 dry-run，向用户展示对象、字段和影响范围，确认后再提交。每个动作带幂等键和审计记录，失败时按动作定义补偿，不让模型自由决定回滚。高金额或批量操作再走人工审批。

**深水区备料**

- 工具分级：read、reversible write、irreversible/high-risk；不同确认和审批策略。
- Plan 中引用稳定业务 ID，不使用模型生成的模糊名称直接执行。
- prepare 阶段再次读取最新数据，防止确认前状态变化；commit 时做版本/CAS 检查。
- 幂等 key、防重复提交、outbox 事件和补偿动作共同构成 effectively-once。
- 模型不能看到超出用户权限的数据，也不能通过工具结果扩大 scope。
- UI 显示原始结构化 diff，不只显示“我将为你完成操作”的自然语言。

**大概率追问**

- 用户确认后数据已经变化怎么办？
- 一组动作执行一半失败怎么办？
- 如何防止 Prompt Injection 触发写工具？

**坑**

- 不要把用户一句“可以”当对任何后续动作的永久授权。
- 不要让 LLM 自己判断事务是否成功或该如何补偿。

## Q96. 如果有 1000 个并发长任务，你会怎么扩展 DeepResearch？

**面试官为什么问**

考从单机演示到生产平台的演进。重点包括排队、worker、provider 配额、事件和数据热点。

**30 秒口播**

我会先把 API 和执行器拆开。API 创建 run 后通过 outbox 投递到持久队列，worker 按租户和优先级拉取，用数据库 lease 执行；模型和搜索调用走集中式限流与连接池，不能让 1000 个任务同时打 provider。事件写外部流，SSE gateway 按 run 订阅。数据库把事件、Checkpoint 和大原文分层存储，并对热点查询做索引和归档。扩容目标不是让 1000 个任务同时跑满，而是可控排队和公平调度。

**深水区备料**

- API：无状态化；run create、status、cancel、resume；幂等请求 ID。
- Queue：优先级、延迟任务、重试/死信、visibility timeout；按 tenant 做 weighted fair queue。
- Worker：不同模型/工具能力池，run 级租约，取消信号，最大并发和资源隔离。
- Rate limiter：全局、provider、model、tenant 四维 token bucket；根据 429 动态降载。
- Event：Redis Streams/NATS/Kafka；持久 seq，SSE gateway 可回放 offset。
- Storage：PostgreSQL 保存元数据，原始网页/报告放对象存储，事件冷热分层。
- 指标：队列等待 P95、运行 P95、provider saturation、租户公平、单位任务成本。

**大概率追问**

- 一个 run 是否可以跨 worker 执行？
- 如何避免数据库成为瓶颈？
- 用户取消排队任务如何处理？

**坑**

- 不要回答“多开几个 uvicorn worker”。
- 不要把并发任务数等同于同时发出的模型请求数。

## Q97. 模型供应商大面积故障时，Agent 如何降级？

**面试官为什么问**

Agent 流程可能依赖多个模型节点，简单重试会造成雪崩和费用放大。对方会看错误分类、熔断和质量边界。

**30 秒口播**

先按错误分类：超时、5xx 和限流是临时故障，有限重试并指数退避；认证和参数错误不盲重试。连续失败达到阈值后对 provider/model 熔断，让新请求快速走备用档案或降级工作流。降级必须保持 schema 和安全门，例如可以从强模型切便宜模型，但不能跳过证据验证。完全不可用时保存 Checkpoint，返回可恢复状态，而不是把半成品标成功。

**深水区备料**

- ModelProfile 路由可扩展健康分、优先级和 capability 标签；当前主要是角色绑定→默认→进程默认。
- circuit breaker 状态需要跨实例共享，并区分 endpoint、model 和 region。
- retry budget 限制一条 run 因多节点级联重试放大；对 429 尊重 Retry-After。
- fallback 模型应预先跑 schema/质量兼容测试，不在故障时临时选未知模型。
- 质量敏感节点可暂停等待恢复，而不是无条件降级；策略由任务 SLA 决定。
- 供应商恢复后半开探测，避免所有流量瞬间回切。

**大概率追问**

- 两个 provider 输出差异很大怎么办？
- 熔断期间正在运行的请求怎么办？
- 如何避免备用 provider 也被打挂？

**坑**

- 不要对 401 一直重试。
- 不要把 fallback 等同于无损切换。
- 不要在故障时关闭安全校验来保成功率。

## Q98. 把当前执行架构改成队列 + worker，如何保证数据库和消息一致？

**面试官为什么问**

这是 Q82/Q96 的深入版本。对方会指出 run 已落库但消息没发，或消息已发但事务回滚的双写问题。

**30 秒口播**

我会使用 transactional outbox。创建 run 和插入 outbox event 在同一个数据库事务里提交，独立 relay 扫描未发送事件并投递队列，成功后标记发送。消息可能重复，所以 worker 用 run 状态、lease 和幂等 consumer 去重；它不依赖“队列恰好只投一次”。执行事件同样可以先写数据库 outbox，再发布到事件流，保证状态和可见事件最终一致。

**深水区备料**

- Outbox 字段：event_id、aggregate/run_id、type、payload/version、created_at、sent_at、attempts。
- Relay 使用 `FOR UPDATE SKIP LOCKED` 批量抢任务，多实例并发不重复占用；即使重复 publish，consumer 仍需幂等。
- Worker 接到消息先 CAS/lease run；已终态直接 ack，其他 owner 持有则延迟或放弃。
- Inbox 表可记录消费 event_id；对高吞吐也可依赖业务状态机幂等而不逐条落 inbox。
- 取消、resume 和 schedule 也作为命令事件，按 run version 防止旧命令覆盖新状态。
- 事件总线是通知，数据库仍是 run 真相源，避免两个权威状态机。

**大概率追问**

- relay 发成功但来不及写 sent_at 会怎样？
- 队列消息顺序乱了怎么办？
- 为什么不用分布式事务？

**坑**

- 不要声称 outbox 消除重复，它解决丢消息，重复仍靠幂等。
- 不要让队列和数据库各自维护一套互相冲突的最终状态。

## Q99. 如果再给你 30 天，你会优先改什么？

**面试官为什么问**

看你是否能按风险和收益排优先级，而不是继续堆页面、角色和流行概念。

**30 秒口播**

第一优先是把执行器从 API 进程拆成持久队列和独立 worker，因为它决定系统能否稳定扩容。第二是补真实 provider 的 contract/nightly 测试和线上质量监控，解决离线 Fake 覆盖不到的漂移。第三是增强多租户治理，包括 RBAC、Secret Manager、审计和配额。研究质量方面再补真实关系标注集和报告后二次 claim 校验。我不会先增加更多 Agent 角色。

**深水区备料**

- P0 执行面：outbox、queue、worker、跨实例 event stream、幂等工具调用、取消。
- P1 质量面：真实 provider 小样本、人工 golden set、来源可信度、final report claim coverage。
- P1 安全面：强制鉴权、RBAC、租户隔离、不可覆盖 safety prefix、密钥托管。
- P2 产品面：冲突 diff/三方合并、用户反馈闭环、运行成本面板。
- 每项定义验收指标，例如 1000 排队任务不丢、provider 故障可恢复、跨租户泄露测试为 0。
- 优先级依据是架构上限和风险，不是实现有趣程度。

**大概率追问**

- 只能选一个会选什么？
- 30 天能做到什么程度？
- 哪项对求职展示最有价值？

**坑**

- 不要列一份没有顺序的 Roadmap。
- 不要为了展示新技术优先重写已稳定模块。

## Q100. 你使用 Claude Code、Codex 等工具，这个项目到底有多少是 AI 写的？

**面试官为什么问**

简历明确写了主流 AI Agent 工具，代码量又大。对方真正关心的是你是否理解、能否独立调试，以及项目事实有没有未经验证的生成内容。

**30 秒口播**

我确实使用 AI 编码工具提高检索、样板代码和测试编写效率，但需求拆分、架构取舍、验收标准和最终代码责任在我。我的判断标准不是“哪一行谁敲的”，而是我能不能解释状态和边界、复现 Bug、修改实现并用测试证明。比如并行三方合并、租约 fencing、证据门禁和意图单向约束，我都能从问题、代码到回归测试完整讲清。工具生成但我没验证的内容不会放进简历。

**深水区备料**

- 准备现场独立完成三类动作：追一条 run 全链路、修改一个节点策略、为并发 Bug 写最小测试。
- 说明工作方式：先写需求和不变量 → 让工具检索/生成候选 → 审查差异 → 跑测试/静态检查 → 人工验证边界。
- AI 常见失误：引用不存在的 API、破坏并发语义、过度重构、写只锁实现细节的测试、编造指标。
- 展示真实修复故事和负面边界，比声称“完全手写”更可信。
- 若被问某个陌生角落，不要硬装；可以现场读代码推导，但要区分“我主导”与“我知道仓库里有”。
- 开源贡献同样以 PR、review 和测试结果证明，不以生成工具作为贡献主体。

**大概率追问**

- 不用 AI 你能否从零实现？
- 如何发现 AI 生成代码里的问题？
- 哪个模块你最熟，现场能改吗？

**坑**

- 不要否认使用工具，简历已经写了。
- 不要回答“AI 只是辅助”后没有具体审查流程。
- 不要把未跑过的数字、未读懂的代码或工具生成的设计写成个人成果。
