# 08 评估、测试、观测与成本（10 题）

## Q71. 你如何评估一个 Agent 系统？

**面试官为什么问**

Agent 的“回答看起来不错”无法支撑上线。对方想看你是否把代码正确性、产出质量、安全、可靠性和成本分开测。

**30 秒口播**

我会分五层。代码和状态机用离线测试验证；最终报告用固定数据集和 LLM Judge 做相对质量对照；安全用注入、伪引用、矛盾和交叉印证红队集；可靠性用故障注入和恢复演示；线上再看成功率、P95、Token、工具错误和用户反馈。每层回答的问题不同，不能拿一个总分替代。

**深水区备料**

- 功能正确性：DAG、条件、状态合并、Checkpoint、API、SSE、Catalog，使用 Fake LLM/Search 可重复运行。
- 质量：coverage、groundedness、depth、coherence；同模型、同数据集比较 workflow 或 Prompt 版本。
- 安全：确定性门禁的拦截/放行与关系管线传播，成对报告攻击召回和正常误伤。
- 可靠性：kill process、租约接管、重复节点、恢复耗时和最终状态。
- 成本性能：Token、模型请求数、搜索数、墙钟、P50/P95、并发峰值。
- 在线：任务完成、引用点击、用户编辑/重试、人工抽检、投诉与回退率。

**大概率追问**

- 哪些指标进 CI，哪些不进？
- 如何建立 Agent 的 golden set？
- 一个总成功率是否可用？

**坑**

- 不要只谈 LLM Judge。
- 不要把离线测试数量当产出质量证明。
- 不要用不可复现的真实 LLM 数值锁死每次 CI。

## Q72. 用 Fake LLM 做 613 项离线测试，真的可信吗？

**面试官为什么问**

对方会质疑测试只是在验证你自己编的假行为，没覆盖真实模型随机性和 provider 协议。

**30 秒口播**

这些测试的目标是验证我写的确定性逻辑，不是证明模型聪明。Fake LLM 按请求 schema 返回可控计划、Finding 和反思结果，Fake Search 返回能被真实 EvidenceVerifier 校验的来源，所以 DAG、合并、恢复、预算和门禁都走生产代码。真实模型质量放到 eval 层测。局限是 Fake 和 provider 可能漂移，所以模型封装还要单独用模拟流式 chunk 和 usage 结构做协议测试。

**深水区备料**

- `tests/fakes.py` 只替换模型/搜索依赖；WorkflowEngine、Guardrails、Repository、API 仍是真实现。
- 假检索内容与 evidence quote 刻意逐字对应，既能测通过路径，也有对抗集测拒绝路径。
- 613 是默认排除 PostgreSQL marker 后的收集数；总计 614，不能混报。
- 真实 provider 风险：流式格式、usage 字段、错误码、JSON 遵循度、限流和连接行为。
- 补充方式：contract tests、录制回放、nightly 少量真实模型冒烟，不让随机性阻塞每次提交。

**大概率追问**

- Fake 写错了怎么办？
- 为什么不在 CI 调一次真实模型？
- 哪类 Bug 最难被 Fake 抓到？

**坑**

- 不要说“测试全绿所以系统没问题”。
- 不要让 Fake 绕过本应被测的护栏或状态代码。

## Q73. LLM-as-Judge 怎么设计，如何减少偏差？

**面试官为什么问**

简历写了多模型 Judge 和四维评分。对方会追问自评偏差、长度偏好和分数稳定性。

**30 秒口播**

DeepResearch 的 Judge 分 coverage、groundedness、depth、coherence 四个维度各打 1 到 5 分，不直接给一个模糊总分。评审温度设为 0，Prompt 明确不能因篇幅长就加分，每条数据还带判分要点。Judge 使用独立 Tracer，避免评审 Token 污染被测 Agent 成本。我只把它用于固定条件下的相对比较，不把绝对分当真值。

**深水区备料**

- 代码：`eval/judge.py::Judge`、`EvalScore`。
- 降偏方法：随机答案顺序、隐藏系统版本、多个 Judge/模型、人工标注校准、pairwise 比绝对打分更稳定。
- groundedness 最好结合确定性引用指标，不完全交给 Judge。
- Judge Prompt 和被测 Prompt 可能共享偏好；使用独立模型只能降低、不能消除相关偏差。
- 评审失败、格式错误和超时应单独记录，不能当低分。
- SparkOffer 的个性化收益应与仅主题/随机基线比较，并结合弱点覆盖和难度分布，而不是只看 Judge。

**大概率追问**

- 温度 0 是否就可复现？
- Judge 和生成模型相同怎么办？
- 为什么不用人工评审？

**坑**

- 不要说 LLM Judge 客观。
- 不要把四维平均掩盖某一维严重退化。

## Q74. 对抗评测为什么可信？哪些地方用了假 LLM？

**面试官为什么问**

当前输出多项 100%，很容易被质疑为脚本按答案返回。必须说清被测对象和假依赖边界。

**30 秒口播**

注入和伪引用两类直接调用生产的 SourcePolicy 和 EvidenceVerifier，都是确定性代码：当前固定集是 20/20 和 13/13，另有 2 条合法引用必须放行。矛盾与交叉印证需要关系模型，所以离线评测用脚本化假 LLM 按用例真值提出候选，再测试 claim ID、阈值、双向标记、独立发布方和冲突优先这些管线是否正确。因此 10/10、3/3、4/4 证明的是传播与门禁，不是关系模型在开放世界的识别率。

**深水区备料**

- 入口：`eval/adversarial.py`，用例：`eval/adversarial_cases.py`。
- 注入红队包含曾经漏过的 4 类绕过，修复后转成回归样本。
- 伪引用用例要求来源本身 policy=allow，确保拦截归因于 EvidenceVerifier，而不是前置规则碰巧拒绝。
- 合法对照防止系统通过“全部拦截”刷高攻击拦截率。
- 关系候选由假 LLM 给出，但 publisher domain、冲突覆盖佐证和最终状态由真实代码执行。
- 下一步应引入真实来源和人工关系标注集，测模型判别本身。

**大概率追问**

- 20 条注入是否太少？
- 如何防止对固定用例过拟合？
- 为什么语义验证也用假模型？

**坑**

- 不要笼统说“五项安全能力都是 100%”。
- 不要省略合法对照和脚本化关系模型的说明。

## Q75. 意图识别只有 78.7% 准确率，为什么简历还敢写？

**面试官为什么问**

这是典型压力题。对方要看你是否会隐藏不漂亮的数据，以及系统是否把分类错误限制在可接受范围。

**30 秒口播**

78.7% 是 L1 规则加 L2 本地模型在 75 条离线任务集上的准确率，不包含线上 L3 兜底。我保留这个数字，是因为它同时说明 81.3% 请求能零 Token 判定，也暴露了 14 条弃权和若干 badcase。系统不会强猜：低置信可以交给 LLM或回退默认 deep；真正安全相关的风险判断单独评测，当前是 18/20 拦截、0/24 误伤。这个模块优化的是成本和路由，不是用 78.7% 决定生死。

**深水区备料**

- 任务意图错路由的损失通常是工作流深度/预算不合适，而不是绕过证据门禁。
- 显式用户选择优先于推荐路由；unknown 使用保守默认。
- badcase 多为词表未覆盖导致 p=0，应增加训练数据、特征覆盖或 L3，而不是降低阈值强行接收。
- 风险评测和任务分类必须分开，不能用总准确率掩盖漏拦截。
- 线上应记录路由修改、用户重选工作流和澄清率，验证离线标签是否对应真实需求。

**大概率追问**

- 为什么不直接删掉本地模型？
- 误路由怎么被发现？
- 2 条风险待复核算不算漏拦？

**坑**

- 不要把 81.3% 说成意图准确率。
- 不要为了漂亮把待 L3 样本计入已拦截。
- 不要回避 badcase。

## Q76. 除了 Judge 分数，还有哪些确定性质量指标？

**面试官为什么问**

对方想看质量是否完全依赖另一个模型，以及指标能否在线稳定采集。

**30 秒口播**

我会直接从运行数据计算逐字验证率、语义支持率、报告准入率、引用快照覆盖率、独立发布方数、冲突和拦截数量，再配合 Token、搜索次数和墙钟。这些指标不判断报告“写得好不好”，但能稳定发现证据链断了、引用覆盖下降或成本突增。Judge 负责较主观的覆盖和深度，确定性指标负责工程回归，两者不能互相替代。

**深水区备料**

- 分母必须固定：例如验证率以提交校验的 Finding 为分母，不能只统计留下来的成功项。
- 语义支持率依赖验证模型结果，不是完全无模型；但统计逻辑确定且可回归。
- 严格双源开启与关闭时，报告准入率口径不同，仪表盘需要按配置切分。
- 引用快照覆盖检查 eligible Finding 是否有可审计 source snapshot/hash。
- 冲突数量上升可能是来源质量下降，也可能是检测变强，需结合版本与样本分析。
- 指标按 workflow、model profile、数据域和版本分桶，避免整体均值掩盖局部退化。

**大概率追问**

- 哪个指标最能代表 groundedness？
- 支持率提高是否一定是好事？
- 如何设回归阈值？

**坑**

- 不要把可计算指标叫事实准确率。
- 不要使用只有成功样本的分母刷高比例。

## Q77. Token 用量如何统计，为什么 Tracer 是单一事实源？

**面试官为什么问**

Agent 多节点、多模型、多次重试，Token 很容易重复计数或遗漏。对方会追问流式 usage、恢复和 Judge 成本。

**30 秒口播**

每次模型调用由 LLM 适配层拿 provider usage，并通过 Tracer 记录到对应 Agent 事件；TokenBudget 只读取 Tracer 的累计值，不再单独 charge，避免双重计数。累计 metrics 会写入 Checkpoint，恢复后继续累加。评估 Judge 使用独立 Tracer，所以报告生成成本和评审成本不会混在一起。provider 不返回 usage 时只能估算并明确标记，不能伪装成真值。

**深水区备料**

- 流式响应可能只在最后 chunk 返回 usage；客户端中断时可能缺失最终数据。
- TokenBudget 的 `update(max)` 防止重复事件让累计值倒退或重复加算。
- 需要按 prompt/completion、模型、角色、重试、缓存命中拆分，才能做成本归因。
- 金额计算还需模型价格版本和计费单位；Token 不直接等于成本。
- 恢复重放产生的新 Token 应计入同一 run 总成本，同时可单列 wasted/replayed usage。
- 工具、embedding、rerank 也有成本，不能只盯聊天模型 Token。

**大概率追问**

- provider 不给 usage 怎么办？
- 缓存命中如何计费？
- 用户断开 SSE 是否停止模型调用？

**坑**

- 不要从字符串长度随便推一个 Token 数当精确值。
- 不要把 Judge Token 混进被测工作流成本。

## Q78. 你做过哪些成本和延迟优化？

**面试官为什么问**

Agent 系统很容易通过增加模型调用换效果。对方想听结构性优化，而不是只说换便宜模型。

**30 秒口播**

我主要从减少不必要调用、缩短单次上下文和并发等待三方面做。意图级联让 81.3% 请求零 Token 完成前置判断；quick/deep 等工作流按任务选择，不让简单问题跑完整反思；角色级模型路由把抽取放到便宜模型；RAG 先去重再 Rerank，控制候选；独立子问题并发但用共享 Semaphore 限流；上下文按优先级裁剪并对稳定前缀做缓存。最后用质量、Token 和墙钟一起比较，避免只优化账单。

**深水区备料**

- 减调用：规则/本地模型、early stop、有界反思、工具结果缓存、重复调用检测。
- 减上下文：结构化摘要、只传依赖结果、引用 ID 代替重复原文、长期画像压缩。
- 换模型：按角色和难度路由，保留 schema 与质量门；失败时有限回退。
- 并发：multi-query、子问题、团队并行；关注 provider QPS 和 P95，不盲目拉满。
- 检索：hash 增量 embedding、候选裁剪、批量向量化。
- 端到端优化顺序先测阶段耗时，再处理最大项，不能凭感觉改 Prompt。

**大概率追问**

- 并发为什么可能让 P95 更差？
- 如何判断反思一轮值不值？
- Prompt cache 如何提高命中率？

**坑**

- 不要只说用了 asyncio 所以快。
- 不要以牺牲证据门禁为代价降低成本，却仍拿旧质量指标宣传。

## Q79. 上线后你会监控哪些指标和告警？

**面试官为什么问**

离线评测不能覆盖 provider 变化、真实用户分布和长尾故障。对方在看生产运维意识。

**30 秒口播**

我会按入口、执行、外部依赖、质量和成本五组监控。入口看请求量、拒识、澄清和限流；执行看 run 成功率、各节点 P50/P95、重试、恢复和队列等待；外部依赖看模型、搜索、数据库错误和 429；质量看引用准入、冲突、用户重试和人工抽检；成本看每 run Token、工具调用和租户预算。告警要带 workflow、模型和版本标签，才能定位是代码还是 provider 漂移。

**深水区备料**

- SLO 示例：run 成功率、首事件延迟、最终报告 P95、恢复成功率、SSE 断流率。
- Provider 监控：响应码、超时、JSON 解析失败、usage 缺失、fallback 比例。
- 质量哨兵：固定小样本 nightly eval、确定性证据指标阈值、人工抽样。
- 安全：注入命中类型、误伤申诉、异常工具调用、密钥轮换失败。
- 成本异常：Token/请求突增、重试放大、单租户并发、模型路由失衡。
- 日志与 trace 关联使用 run_id/node_id，但默认不记录敏感正文。

**大概率追问**

- 哪三个指标必须第一天就有？
- 质量下降如何自动回滚？
- 如何区分模型升级和代码回归？

**坑**

- 不要只监控 CPU、内存和 HTTP 500。
- 不要收集完整 Prompt 当默认日志来换可观测性。

## Q80. 如何做 Agent Prompt 或工作流的 A/B 测试？

**面试官为什么问**

想看你是否能把离线改进转成线上证据，并处理成本、用户差异和安全风险。

**30 秒口播**

先在固定数据集做离线回归，确定安全和成本没有明显退化，再把新版本以小流量 canary 发布。实验单位按用户或会话稳定分桶，避免同一用户来回切版本；主指标根据业务选任务完成、用户评分或弱点覆盖，护栏、P95 和成本作为不可突破的约束。高风险改动先 shadow 只记录结果不影响用户，达到样本量后再决定扩大或回滚。

**深水区备料**

- 版本对象应包含 Prompt、workflow definition、model profile、检索配置和代码版本，不能只记一个实验名。
- Agent 输出长且主观，常结合用户行为、人工盲评和 Judge；Judge 只作辅助。
- 分桶考虑新老用户、任务类型、语言和难度，防止 Simpson's paradox。
- 成本/延迟是 guardrail metrics；质量小幅提升但成本翻倍未必值得。
- 安全门禁改动不宜直接 A/B 放开，先离线红队和 shadow。
- 实验期间保留原始版本快照，支持问题 run 复盘。

**大概率追问**

- 用户评分样本偏差怎么办？
- 如何确定样本量？
- 多个组件同时变化如何归因？

**坑**

- 不要把两次手工体验对比叫 A/B 测试。
- 不要只看平均 Judge 分，不看成本、长尾和安全约束。
