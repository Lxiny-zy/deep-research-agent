# 09 后端、前端与工程落地（10 题）

## Q81. 为什么后端选择 FastAPI 和 asyncio？

**面试官为什么问**

简历两个项目都用了 FastAPI。对方想知道这是熟悉框架的惯性，还是与模型、搜索和 SSE 的 I/O 特征匹配。

**30 秒口播**

Agent 应用的大部分等待都在模型、检索和数据库 I/O，不是 CPU 计算，所以 asyncio 能在一个进程里并发承接多个长请求和子任务。FastAPI 还提供 Pydantic schema、依赖注入和 ASGI 流式响应，适合工具参数、结构化事件和 SSE。需要注意的是 async 不会让 CPU 密集任务变快，embedding 本地推理或大文件解析要放线程池、进程池或独立 worker。

**深水区备料**

- `httpx`、异步 SQLAlchemy、模型流式和搜索调用应全链路异步，任何同步阻塞都会卡事件循环。
- `asyncio.gather` 提供并发，不等于无限并发；Semaphore 和连接池仍需限制。
- FastAPI dependency 用于认证、Repository/Settings 注入，Pydantic 用于 API 契约。
- BackgroundTask 适合短生命周期收尾，不适合可靠长任务；当前项目使用 `asyncio.create_task` 加数据库恢复，仍有进程边界。
- CPU 密集操作可用 `asyncio.to_thread` 过渡，但持续高负载应拆 worker。

**大概率追问**

- 一个同步 Tavily SDK 会有什么影响？
- uvicorn 多 worker 后内存状态怎么办？
- async SQLAlchemy 有什么坑？

**坑**

- 不要说 asyncio 是多线程。
- 不要在 async 路由里直接调用耗时同步库。
- 不要把 FastAPI 的 BackgroundTasks 当持久任务队列。

## Q82. 为什么当前用进程内后台任务？什么时候必须换 Celery、Arq 或 Kafka？

**面试官为什么问**

这是架构规模边界题。面试官会检查你是否能解释先简后繁，以及何时现有方案不再成立。

**30 秒口播**

项目初期用进程内 asyncio 任务，是因为部署简单、调试链短，配合数据库 Checkpoint 和租约已经能演示恢复语义。但任务数量上来后，它缺少持久排队、独立扩缩容、跨进程取消和统一重试，EventHub 也只在本进程有效。出现多实例、高并发、任务积压或需要独立 worker 发布时，我会把 run 命令写入持久队列，API 只负责受理和查询，worker 按租约执行。

**深水区备料**

- 队列只传 `run_id` 和版本，不传巨大 Blackboard；worker 从数据库读取 definition/Checkpoint。
- 任务投递和 run 落库要用 outbox 或同库事务，避免“记录有了但消息没发”或相反。
- Celery 生态成熟但语义复杂；Arq 更贴近 asyncio/Redis；Kafka 适合事件流和高吞吐，不自动提供工作流语义。
- worker 心跳、可见性超时与数据库 lease 要统一，避免双重租约产生冲突。
- 取消通过持久状态和 worker 协作完成，不依赖 API 进程里的 task handle。

**大概率追问**

- 为什么已有数据库租约还需要队列？
- 消息重复投递怎么办？
- worker 怎么实时推 SSE？

**坑**

- 不要说“上 Kafka 就解决分布式一致性”。
- 不要为了简历从第一天引入复杂队列，却没有任务规模和运维需求。

## Q83. 为什么实时链路选 SSE，不选 WebSocket？

**面试官为什么问**

项目写了全链路 SSE。对方会从通信方向、代理兼容、重连和鉴权角度追问。

**30 秒口播**

运行过程主要是服务端单向推送事件和报告 Token，用户控制仍走普通 HTTP，所以 SSE 的语义更简单，也更容易穿过现有 HTTP 代理。浏览器端没有直接用 EventSource，而是用 fetch + ReadableStream，因为 EventSource 不能方便地带自定义 `X-API-Key`。代价是自动重连和 Last-Event-ID 要自己实现，当前主要靠事件回放和详情接口兜底。

**深水区备料**

- SSE 使用 `text/event-stream`，事件以空行分隔；代理需要关闭缓冲或及时 flush。
- 前端解析要处理 UTF-8 字符跨 chunk、CRLF、注释心跳和一个 chunk 多事件。
- fetch 方案可带 header 和 AbortController，但要自己处理 status、重连、offset 和终态。
- WebSocket 适合高频双向交互、协作编辑或实时控制；本项目控制命令频率低，HTTP 更易审计和重试。
- 客户端断开不应自动取消后台研究，除非产品明确将连接生命周期绑定任务。

**大概率追问**

- SSE 最大连接数如何处理？
- 代理 60 秒断开怎么办？
- 为什么不用轮询？

**坑**

- 不要说 SSE 自动保证不丢消息。
- 不要把 API key 放 URL query 来迁就 EventSource。
- 不要收到局部 Agent error 就关闭整个流。

## Q84. 前端如何维护 Agent 运行状态，避免事件乱序和终态覆盖？

**面试官为什么问**

实时 UI 常见问题是重连回放、重复事件和局部错误把页面误判为失败。对方会看前端是否理解后端状态语义。

**30 秒口播**

前端不会把每条事件直接随意改组件状态，而是先进入 reducer，按事件类型更新 run、节点、报告和统计。只有 ORCHESTRATOR 的 done/error 才是整次运行终态，单个 Researcher error 只标对应节点。终态一旦确认就冻结，后续同一 chunk 里迟到的回调会被 `terminal` 守卫忽略。重连时先拉详情或回放，再接实时事件，避免只依赖内存状态。

**深水区备料**

- Hook：`frontend/src/hooks/useResearchStream.ts`；事件聚合和进度逻辑位于前端 lib/reducer。
- fetch abort 只能阻止后续 read，同一 chunk 已同步分发的事件仍可能继续调用 handler，因此需要 disposed/terminal 双守卫。
- 进度是启发式估算：完成节点 + 活跃状态权重，done 才到 100%，不能伪装精确 ETA。
- token 增量丢失时最终报告事件和详情接口提供全量结果。
- 事件最好带 seq/id；重复回放可按序号去重，跨实例需要持久 offset。

**大概率追问**

- 事件乱序怎么办？
- 页面刷新后如何恢复？
- 局部失败为什么还能生成报告？

**坑**

- 不要用“收到任意 error 就关闭 SSE”。
- 不要让组件各自解析同一事件协议，应该集中归一状态。

## Q85. React Flow 工作流构建器如何保证用户画出的图可执行？

**面试官为什么问**

画布拖拽只是 UI。对方关心客户端交互校验、服务端安全校验和数据库版本冲突如何配合。

**30 秒口播**

前端先做即时反馈，例如禁止自环、检查端口和提示条件错误，但它不是真相源。保存时服务端重新解析 nodes、edges 和 Step，校验悬空边、环、条件语法、角色白名单、重试上界和唯一报告终端，再由拓扑结果重算 steps。更新带 version 做 CAS，冲突返回 409；编辑器保持本地草稿，让用户决定刷新还是覆盖。

**深水区备料**

- API 归一化：`deep_research/catalog_api.py::_normalize_graph_payload`。
- 只提交 edges/nodes/viewport 时合并 existing 字段；旧 steps-only 记录首次编辑可自动生成兼容图。
- 服务端不信任客户端同时提交的 graph 和 steps 一致，派生表示由服务端生成。
- 图校验还需所有分支汇入唯一报告终端，防止流程“成功”却没有 report。
- 409 后当前实现刷新 server version 但保留草稿，第二次保存是明确覆盖，不是三方 merge。

**大概率追问**

- 为什么不只存 graph？
- 多人同时改不同节点能否自动合并？
- 前端怎样展示非法路径？

**坑**

- 不要说前端检查能保证安全，API 可以被绕过。
- 不要把乐观锁说成实时协同编辑。

## Q86. 为什么同时支持 SQLite 和 PostgreSQL？迁移怎么管理？

**面试官为什么问**

看零配置体验和生产能力如何兼容，也会追问 SQLite 并发、异步驱动和 schema 漂移。

**30 秒口播**

SQLite 让个人用户和桌面版零配置启动，PostgreSQL 负责多实例、并发事务和生产部署。Repository 接口不依赖具体数据库，SQLAlchemy async 负责方言适配；schema 由 17 个 Alembic 迁移演进。验证链会跑 upgrade head、`alembic check`、downgrade base 和离线测试，既检查 ORM 与迁移是否漂移，也检查回滚能力。

**深水区备料**

- `deep_research/persistence/db.py` 根据 URL 创建 engine；SQLite 可设置 WAL 和启动 schema 准备。
- SQLite 写并发有限，不适合高并发多 worker；PostgreSQL 支持行锁、条件更新和租约事务。
- Repository Protocol 有 InMemory 与 SQL 实现，离线测试可不用真实数据库。
- 自动 `create_all` 适合测试/内存；正式 schema 演进必须走 Alembic，不能混用导致漂移。
- migration 需要 forward、backward、数据回填、默认值和锁表影响评估。
- PostgreSQL 特有的并发语义应有 `@pytest.mark.pg` 集成测试。

**大概率追问**

- SQLite 和 PostgreSQL 行为不一致怎么办？
- 生产迁移能否直接 downgrade？
- 如何做零停机加非空列？

**坑**

- 不要说支持 SQLAlchemy 就天然跨库一致。
- 不要在生产启动时无条件 `create_all` 代替迁移。

## Q87. OpenAI 兼容模型如何接入？参数和 provider 差异怎么处理？

**面试官为什么问**

“兼容 OpenAI”不代表所有端点行为一致。对方会追问结构化输出、stream usage、参数支持和重试。

**30 秒口播**

我把模型调用收敛到一个薄 LLM 接口，配置 endpoint、model、key 和参数模式。角色通过 ModelProfile 选择模型，Agent 不直接依赖某家 SDK。结构化输出使用 schema Prompt、JSON 提取和 Pydantic 校验，流式调用统一成 Token 事件。不同 provider 对 temperature、max tokens、usage 和错误码支持不同，所以参数模式和兼容测试必须显式处理，不能假设“接口长得像就完全一样”。

**深水区备料**

- 配置层级：环境变量默认 → runtime config 覆盖 → per-run 参数。
- `dataclasses.replace` 或 Pydantic 校验保证每层覆盖后重新检查范围。
- 模型档案允许 endpoint/model 级路由；同一 run 内按 profile ID 缓存客户端并在结束时关闭。
- provider 私有 structured output 可按能力开启，但基础路径保持通用解析。
- 错误分类：429/5xx/网络可重试，401/403 通常切凭据或失败，schema 错误走有限修复。
- 模型名称不代表固定权重版本；评测和 manifest 应同时记录 endpoint、参数、时间和配置 hash。

**大概率追问**

- DeepSeek 与 OpenAI 参数不兼容怎么办？
- provider 返回不了 usage 怎么统计？
- 模型客户端为什么要缓存和关闭？

**坑**

- 不要声称支持所有 OpenAI-compatible provider。
- 不要把所有异常统一重试。

## Q88. 搜索 key 池如何自动切换，为什么并发下容易出竞态？

**面试官为什么问**

简历写了检索 key 主备切换。面试官会用两个请求同时遇到配额错误的场景检查并发逻辑。

**30 秒口播**

key 按 priority 排序，池维护当前粘滞下标。每个搜索协程有自己的 tried 集合保证有限尝试，但每一轮都读取实时全局下标，避免另一个协程已经切换后自己还继续撞旧 key。遇到配额、429 或鉴权错误时，只有全局下标仍指向当前失败 key 才推进，防止两个协程互相把下标拨回；普通搜索错误直接上抛给步骤重试。

**深水区备料**

- 代码：`deep_research/tools/tavily_pool.py::TavilyKeyPoolSearch`。
- failover hints 当前来自错误文本/状态，生产可改成 provider 类型化异常。
- tried 集合保证每个请求最多尝试 key 数量，避免无限循环。
- 成功后把 `_idx` 粘滞到该 key，减少每次从首 key 重试。
- key 池只能解决单 provider 多凭据；provider 级故障需要跨搜索后端 fallback。
- 配额恢复、冷却时间和健康检查可作为后续演进，避免坏 key 每次都被重新尝试。

**大概率追问**

- 为什么非配额错误不切 key？
- 多进程共享 key 状态怎么办？
- 所有 key 都失败如何返回？

**坑**

- 不要把进程内下标说成跨实例全局状态。
- 不要遇到任何异常都轮换 key，可能放大请求和掩盖业务错误。

## Q89. Docker 和 PyInstaller 两种交付形态分别解决什么问题？

**面试官为什么问**

看你是否真正考虑用户如何运行，而不是只在开发机启动成功。

**30 秒口播**

Docker 面向服务器部署，把 API、前端静态资源、PostgreSQL 和持久卷按一致环境启动，适合多实例和运维；PyInstaller 面向不想装 Python 的个人用户，配合 SQLite 和本地配置做桌面式零配置交付。两者共享同一应用代码，但数据库、配置路径、迁移和静态资源定位不同，所以构建脚本和启动自检要分别验证。

**深水区备料**

- Docker 使用多阶段构建可先编译前端，再复制 dist 到后端镜像，减小运行镜像。
- 容器运行时配置通过环境变量和挂载卷，密钥不写进镜像层。
- 启动 PostgreSQL 前做健康检查和 Alembic upgrade；应用与迁移并发启动需避免多个实例同时升级。
- PyInstaller 需要处理 hidden imports、静态文件、证书、模型 JSON 和可写数据目录。
- SQLite DB、runtime config 和日志不能放进只读打包目录。
- 两种形态都要提供版本信息、配置诊断和升级/备份路径。

**大概率追问**

- 容器内如何保存 runtime_config？
- PyInstaller 如何做自动升级？
- 多实例谁负责跑 migration？

**坑**

- 不要把密钥烘焙进 Dockerfile 或 `.env` 提交仓库。
- 不要说打包成功等于跨平台都能运行，必须分别构建和测试。

## Q90. 你的 CI 和测试策略如何覆盖完整 Agent 产品？

**面试官为什么问**

前面可能谈了很多单点测试，这题要求把后端、前端、迁移、PostgreSQL 和 eval 机制组织成质量门。

**30 秒口播**

我把确定、快速、免费的检查放进每次 CI：后端 ruff、format check、mypy 和默认离线 pytest；单独用 PostgreSQL service container 跑数据库特有测试；前端跑 ESLint、TypeScript build 和 Vitest。Alembic 还要检查 upgrade、ORM 漂移和 downgrade。真实 LLM 质量分不锁进每次 CI，只测试评估器机制，并在手动或 nightly 任务里跑固定小样本。

**深水区备料**

- 后端当前默认 613 项，总收集 614 且 1 项 pg marker；前端 20 文件 139 项。
- 静态检查覆盖未使用导入、格式、类型和 asyncio 常见问题，但不能替代运行测试。
- 测试层次：纯函数/状态机、Agent 组件、ASGI API、Repository/恢复、前端 reducer/hook/page。
- 协议测试模拟 OpenAI 流 chunk、usage 和 SSE 分块；页面测试用 deferred promise 控制竞态，不靠 sleep。
- 对抗率值因确定性且免费可以进 CI；真实 Judge 数值有成本和方差，作为离线回归。
- 还缺的测试应主动说：真实 provider contract、长稳/负载、多浏览器和完整多租户隔离。

**大概率追问**

- 为什么没有 coverage 百分比？
- 哪部分测试最薄？
- 如何减少 flaky async 测试？

**坑**

- 不要编造覆盖率。
- 不要用 sleep 等并发时序，优先 Event、Barrier 和 fake clock。
- 不要把“测试多”替代关键性质说明。
