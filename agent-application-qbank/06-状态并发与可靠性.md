# 06 状态、并发与可靠性（10 题）

## Q51. Checkpoint 里具体保存什么？为什么要同时保存工作流定义？

**面试官为什么问**

“支持断点续跑”很容易停留在保存当前步骤。对方会检查恢复是否依赖后来已经变化的代码配置。

**30 秒口播**

Checkpoint 不只保存当前节点号，还保存完整 Blackboard、WorkflowRun/StepRun 执行状态、累计 Token/耗时，以及本次 run 的 workflow definition 和 Catalog 运行快照。保存 definition 是因为内置模板或用户流程以后可能被修改，恢复必须继续执行创建当时的语义。角色 Prompt 和模型非密钥参数也冻结，但密钥不进快照，恢复时按 profile ID 重新取当前凭据。

**深水区备料**

- `WorkflowEngine._checkpoint` 保存 Blackboard JSON 和 workflow definition；`orchestrator.py` 把运行设置、metrics、Catalog snapshot 放进 scratch。
- 写入点：线性步骤后、图层后，以及成功/失败/取消终态。
- definition snapshot 解决“历史流程变化”；Catalog snapshot 解决“角色 behavior/prompt 变化”。
- API key 不保存，降低历史记录泄密面；这也意味着 profile 被删除后无法保证完全相同的模型恢复。
- Checkpoint 是恢复状态，不是完整事件日志；事件另行持久化用于审计和回放。

**大概率追问**

- **为什么不每个 Token 都写 Checkpoint？**
  因为写 Checkpoint 是一次完整 Blackboard 序列化加数据库事务，按 Token 频率写会让数据库成为瓶颈，而且收益极小——恢复的粒度本来就是节点级，保存半个节点的中间状态没用，那个节点还是得重跑。所以写入点选在语义边界上：线性步骤后、图层后、终态时。代价是最多丢一个节点的工作量，这是我接受的粒度。

- **密钥不冻结还能叫可复现吗？**
  本来就不能叫可复现，我不会用这个词。冻结密钥反而是错的——历史记录里存密钥等于扩大泄密面，而且密钥轮换后旧快照会带着废密钥无法恢复。所以设计是按 profile ID 从当前 Catalog 取实时凭据。至于「可复现」这个说法本身，远端模型会升级、搜索结果会变，逐字节重放从来就做不到。快照保证的是执行语义一致，不是输出一致。

- **schema 升级后旧 Checkpoint 怎么办？**
  Blackboard 是 Pydantic 模型序列化的 JSON，加可选字段是兼容的——反序列化时取默认值即可。真正麻烦的是删字段和改语义，这时候只能给 Checkpoint 带版本号，恢复时按版本走不同的解释路径，或者干脆判定为不可恢复直接标 error，好过用错误语义续跑。这是我承认还没做完整的地方，目前只靠「加字段用可选」这个约定顶着。

**坑**

- 不要说能 byte-for-byte 重放。远端模型、搜索结果和密钥都会变化。
- 不要把 workflow 名字当作 definition 快照。

## Q52. 恢复时哪些节点跳过，哪些节点重跑？

**面试官为什么问**

这是恢复语义的核心。简单地“从失败节点继续”无法覆盖条件跳过、并行层和正在运行的节点。

**30 秒口播**

恢复时，已经 SUCCEEDED 的节点直接跳过；明确因预算耗尽而 SKIPPED 的节点也是终态。因条件暂时不满足而跳过的节点会重新评估，因为恢复后前驱状态可能变化。中断时处于 RUNNING、READY 或 RETRYING 的节点视为未完成，需要重跑。并行层里已经成功的兄弟结果已经合进 Checkpoint，所以不会因为一个分支失败把整层全部重做。

**深水区备料**

- 线性流程按稳定 `step-N` node ID 对齐历史 StepRun。
- 图流程需要恢复 active/successful 节点集合，并区分 skip reason。
- fail-fast 场景先合并已成功兄弟，再写失败 Checkpoint 和抛错。
- 外部工具若在中断前已经成功但状态未落库，恢复可能重放，因此需要工具层幂等。
- 取消状态通常不自动恢复，需用户显式 resume 或新建任务，取决于产品语义。

**大概率追问**

- **RUNNING 节点可能已调用成功，重跑怎么办？**
  会重跑，这正是 at-least-once 的来源。对纯检索和模型调用来说代价只是多花一次钱，可以接受；对有副作用的工具就必须靠工具层幂等——用 `run_id + node_id + action_index` 这样的稳定幂等键，工具侧按键返回上次结果而不是真的再执行。所以这不是编排引擎单方面能解决的，需要工具服务配合。我不会说重跑没有代价。

- **条件重评会不会改变原流程结果？**
  会，而且这是刻意的。条件跳过和预算跳过的语义不一样：预算耗尽是终态，不该重来；条件不满足只是「当时前驱还没产出这个字段」，恢复后前驱状态已经在 Checkpoint 里了，重评可能得到不同结果，这时候走新分支才是对的。混成同一个 SKIPPED 语义会导致恢复后流程停在半路。代价是恢复后的路径可能和原来不完全一致，所以事件里要能看出哪些节点是重评过的。

- **如何识别同一个节点？**
  必须用稳定 node ID，不能用数组下标。线性流程用 `step-N` 这种由位置推导的稳定 ID；图流程用用户定义的 node ID。用下标的问题在于用户改一下节点顺序，恢复时就会把 A 的历史记录对齐到 B 上——而且这种错不会报错，只会静默跑错。这也是为什么保存工作流时要校验 node ID 唯一。

**坑**

- 不要承诺 exactly-once。
- 不要只根据数组下标匹配图节点，用户图需要稳定 node ID。

## Q53. 多实例恢复为什么需要租约和 fencing？

**面试官为什么问**

只用一个 `locked=true` 无法防止旧进程恢复后继续写。对方会检查你是否理解脑裂和陈旧持有者问题。

**30 秒口播**

租约解决“谁现在有资格执行”，fencing 解决“旧执行者回来后还能不能写”。实例抢到 run 时写 owner 和过期时间，并持续续租；每次受保护的 Checkpoint 或终态写入，都在同一事务里锁 run 行并核对 owner。旧实例即使暂停后恢复，只要租约已经被别人接管，它的写入就会因 owner 不匹配被拒绝，并取消本地任务。

**深水区备料**

- 代码：`deep_research/persistence/sql_repository.py` 的 lease acquire/renew 与 owner 条件写。
- 只检查时间戳不够：两个实例时钟偏差或旧实例晚写仍可能覆盖新状态。
- owner token 可以是实例+任务唯一值；更严格可使用单调 fencing token 版本。
- 续租失败必须传播到执行协程，不能只记录日志继续跑。
- Checkpoint 写与 lease 校验必须同一事务，否则存在检查后失效的 TOCTOU。

**大概率追问**

- **数据库暂停导致续租失败怎么办？**
  续租失败必须传播到执行协程并取消本地任务，不能只打条日志继续跑。理由是续租失败意味着「我可能已经不是 owner 了」，这时候继续执行就是在制造脑裂——另一个实例可能已经接管。安全方向是主动放弃：宁可这次任务被别人接管重跑，也不要两个实例同时写。代价是数据库抖动会导致不必要的任务切换。

- **为什么不用 Redis 分布式锁？**
  因为多引一个组件就多一个可用性依赖和一致性边界，而我需要的保证恰好可以在已有的数据库里拿到——租约和 Checkpoint 在同一个事务里，天然没有跨系统的 TOCTOU。用 Redis 锁的话，锁在 Redis、状态在 Postgres，两边的原子性要自己缝，Redlock 的争议也不少。缺点是数据库要承受续租的写压力，QPS 上去以后这条会先撑不住。

- **进程暂停时间短于 TTL 会怎样？**
  没人接管，原实例醒来后继续跑，这是正常路径。危险的是暂停时间刚好卡在 TTL 边界——旧实例以为自己还持有租约，实际上已经被接管了。所以租约不能只靠 TTL 判断，每次受保护写入都要在同一事务里锁行核对 owner。这就是为什么我说租约保证的不是「只有一个进程在运行」，而是「旧 owner 写不回去」。

**坑**

- 不要把租约说成“保证只有一个进程运行”，网络和暂停下可能短暂双跑；保证的是旧 owner 写不回。
- 不要只讲抢锁，不讲每次写的 fencing。

## Q54. 你的恢复语义是 at-least-once 还是 exactly-once？

**面试官为什么问**

这是分布式任务经典压力题。任何轻率承诺 exactly-once 的回答都会被工具副作用反例击穿。

**30 秒口播**

当前更接近 at-least-once。数据库状态通过 owner fencing 防止旧实例覆盖，但节点在“外部调用成功、Checkpoint 尚未提交”之间崩溃时，恢复会再次执行。纯检索和模型调用通常只是增加成本，写操作就必须用幂等键、业务唯一约束或操作日志去重。Exactly-once 不是工作流引擎单方面能保证的，需要每个外部工具都参与协议。

**深水区备料**

- 典型不确定窗口：工具响应已返回，进程在保存 node success 前退出。
- 幂等 key 可取 `run_id + node_id + action_index`，工具服务保存处理结果并返回相同响应。
- 对不可幂等操作可使用 outbox、prepare/commit、人工确认或补偿事务。
- 模型调用无法真正去重远端成本，但可以缓存请求 hash，前提是输入和模型版本稳定。
- 报告和数据库写入可通过唯一约束实现幂等 upsert。

**大概率追问**

- **发邮件、付款这类工具怎么处理？**
  不能靠重试语义解决，必须在工具协议层解决。付款这类的标准做法是幂等键——调用方生成稳定的键，服务端按键去重并返回上次的响应。做不到幂等的就上 outbox 或者 prepare/commit 两阶段：先落一条待发意图，确认成功后再实际发出。最保守的是人工确认，把不可逆动作挡在自动重试之外。我的项目里没有这类工具，所以这条是设计判断不是已实现。

- **缓存模型响应有什么风险？**
  缓存键必须包含模型版本、参数和完整输入，任何一个漏掉就会返回不该返回的结果——比如模型升级了但缓存还给旧答案，用户会以为系统坏了。另一个风险是温度大于 0 时缓存等于把随机性冻住了，重跑不再是重新采样。而且缓存救不了远端的实际成本，只有你自己这边不再发请求才省钱。所以它更适合确定性场景（temperature 0、输入完全一致），不适合当通用优化。

- **能否做到 effectively-once？**
  可以逼近，但那是整条链的性质，不是引擎单方面能给的。做法是 at-least-once 的执行加上每个副作用点的幂等或去重，最终对外表现为只生效一次。前提是每个外部工具都参与协议——只要有一个不支持幂等键，这个保证就断了。所以我说的是「可以做到 effectively-once 的架构」，不是「系统已经是 exactly-once」，这两句话差别很大。

**坑**

- 不要把数据库事务扩展成对外部 API 的全局 exactly-once。
- 不要说“重试前查询一下状态”就总能解决，外部系统未必提供可查询 ID。

## Q55. Chaos 演示中的 1.8 秒和 75% 是怎么测的？

**面试官为什么问**

简历数字很亮眼，面试官会追问计时起点、终点、对照组和是否包含租约等待。

**30 秒口播**

脚本先用离线假后端跑一遍 deep 流程拿到 8000 Token 对照，再在第二次运行中间强杀 API 进程，等待租约可接管后重启。从重启到收到首个 `workflow.resumed` 事件是 1.8 秒；恢复后新增调用是 2000 Token，相比完整重跑少了 6000，也就是演示场景下 75%。这个 1.8 秒不包含前面的 TTL 等待，75% 也取决于杀进程的位置。

**深水区备料**

- 脚本：`scripts/chaos_demo.py`；测试：`tests/test_chaos_demo_hook.py`。
- fake backends 让演示可复现、零成本，测的是恢复管线而不是真模型质量。
- 指标应写清“重启后接管耗时”，不能称为总故障恢复时间。
- Token 节省按 tracer 模拟用量，真实模型各阶段 Token 分布可能不同。
- 需要观察已完成节点不重跑、resume 事件、最终报告和状态正确，而不只看耗时。

**大概率追问**

- **为什么要等 TTL？**
  因为进程被强杀不会主动释放租约——它没机会执行任何清理代码。新实例只能等原租约过期才敢接管，否则就是在赌旧进程真的死了。这个等待是租约机制的固有成本，缩短 TTL 能减少等待但会增加误判接管的概率（GC 停顿、网络抖动都可能让活着的实例续租晚一拍）。所以我报数字时会把 TTL 等待和接管耗时分开说，1.8 秒指的是重启后到收到 resume 事件，不含前面的等待。

- **如果在 Synthesizer 中间杀掉还能省 75% 吗？**
  不能，会明显更低。75% 是那个固定 chaos 场景的结果——杀在研究阶段之后，所以前面所有检索都不用重跑。如果杀在 Synthesizer 中间，前面已完成的节点照样跳过，但 Synthesizer 本身要整个重来，而它恰恰是最贵的一步。所以这个数字是位置敏感的，我只把它当「恢复机制确实生效」的证据，不当成本承诺。

- **fake backend 的数字有业务价值吗？**
  有限，而且要说清它测的是什么。fake backend 让演示可复现、零成本，它验证的是恢复管线本身——已完成节点确实跳过了、resume 事件确实发出了、最终状态和报告确实正确。它完全不能说明真模型下的质量或真实的 Token 分布。所以这些数字的定位是「恢复机制的功能证据」，不是性能基准，更不是成本预测。

**坑**

- 不要说“故障后 1.8 秒恢复”，要加“租约可接管并重启后”。
- 不要说所有运行都固定节省 75%。

## Q56. timeout、retry、backoff、fallback、continue 和 fail-fast 如何组合？

**面试官为什么问**

节点可靠性参数不是字段清单。对方会给出超时、部分写入和 fallback 失败的组合场景。

**30 秒口播**

一次主 Agent 尝试先受 timeout 约束，失败后按指数退避重试；所有主尝试耗尽才执行一次 fallback，fallback 也受同一超时限制。最终仍失败时，continue 会记录 FAILED 并让其他分支继续，fail-fast 则终止流程。每次尝试都在 Blackboard 深拷贝上运行，只有成功才提交，避免失败尝试留下半截状态。

**深水区备料**

- 代码：`workflow.py::_execute_with_policy` 附近的 candidate、retry 和 fallback 路径。
- 指数退避实际按 `retry_backoff * 2**attempt`；定义校验限制单步最多 5 次、全流程最坏退避不超过 120 秒。
- fallback 不进入主重试循环，避免故障时调用爆炸。
- `asyncio.CancelledError` 必须向上传播，不能被普通异常处理吞掉。
- fail-fast 并行层仍要保留已经成功兄弟的结果和 Checkpoint。

**大概率追问**

- **哪些错误应该重试？**
  只重试瞬时错误：429、5xx、超时、连接重置。参数错误、权限拒绝、schema 不匹配这类永久错误重试多少次都是同样的结果，只是把故障时间拉长、把成本翻倍。所以异常处理必须能分类，不能笼统 `except Exception` 然后重试。结构化输出解析失败是个特例——它可重试，但重试方式不同：要把具体校验错误回灌给模型，而不是原样重发。

- **fallback 是否用更便宜还是更强的模型？**
  取决于失败原因，但 fallback 的定位是「保住可用性」不是「提高质量」。如果主尝试是因为超时或限流失败，换个更强更慢的模型只会再超时一次，这时候该换更快更稳的。所以我倾向于 fallback 走更稳定的路径。关键设计是 fallback 只执行一次、不进主重试循环——否则故障时调用量会爆炸，本来是 5 次变成 5×5 次。

- **timeout 后底层 HTTP 请求真的停止了吗？**
  `asyncio.wait_for` 会取消协程，客户端这边确实停止等待，但远端服务器可能已经开始处理甚至已经完成了——它不知道你走了。所以超时不等于「这次调用没发生」，Token 可能已经计费、副作用可能已经产生。这也是恢复语义只能是 at-least-once 的原因之一。另外取消的 `CancelledError` 必须往上传播，不能被普通异常处理吞掉，否则取消传不下去，任务会变成幽灵。

**坑**

- 不要对参数错误、权限拒绝等永久错误盲目重试。
- 不要在原 Blackboard 上直接重试。

## Q57. 为什么并发限制要在整个 run 内共享？

**面试官为什么问**

嵌套 DAG、team_fanout 和 Researcher 内部都可能并发。各层各建 Semaphore 会把总并发放大。

**30 秒口播**

如果每个团队、每个图分支都各建一个 `Semaphore(5)`，嵌套后实际并发可能变成几十。我的做法是在 run 入口创建一把共享 Semaphore 放进 RunContext，所有昂贵的模型和搜索操作都使用它，嵌套工作流继续复用。team_fanout 外层不能持着这把锁等子流程，否则子流程内部再取同一把锁会自锁。

**深水区备料**

- 共享范围是单 run，避免一个大任务内部放大；跨 run 的进程总限流还需要全局池或 provider 限流器。
- 测试用峰值计数器断言多个团队和图节点组合时 `peak <= max_concurrency`。
- Semaphore 保护昂贵 I/O，而不是整个 Agent step；否则 CPU/状态处理也被不必要串行化。
- 并发数应结合 provider rate limit、连接池、平均延迟和内存动态配置。
- 公平性问题：单个大 run 仍可能占满进程资源，生产环境需要租户/队列级调度。

**大概率追问**

- 多个 run 同时执行如何限流？
- 为什么不用令牌桶？
- 怎么防止某个慢任务长期占槽？

**坑**

- 不要把 run 级 Semaphore 说成全系统限流。
- 不要在父流程持锁再调用需要同一锁的子流程。

## Q58. Token 预算为什么是软预算？会不会超支？

**面试官为什么问**

Agent 成本治理常见题。对方会检查预算检查点、终端报告和流式调用能否中断。

**30 秒口播**

预算在步骤边界检查，耗尽后跳过非终端步骤，但仍尽量让 Synthesizer 或 Aggregator 基于已有材料产出部分报告。这样用户不会因为最后一点预算耗尽而什么都拿不到。它会超支：当前步骤已经发出的模型请求不会中途硬切，终端步骤也允许执行，所以最坏多一个步骤加收尾成本。这个取舍是可用性优先，不是精确计费。

**深水区备料**

- `TokenBudget` 以 `Tracer.total_tokens` 为真相源，`update(max)` 保证单调，避免重复 charge。
- 累计用量随 Checkpoint 保存，恢复后预算不会清零。
- 终端角色集合不是只写死 synthesizer，Catalog 中 behavior=synthesize 的卡片也可能成为终端。
- 更严格预算可在请求前用 max_tokens、模型价格和输入长度预估，但无法精确预测输出。
- 对计费产品还需要货币预算、预留终端额度和用户确认，而不只是 Token 数。

**大概率追问**

- 如果 Planner 一步就打爆预算怎么办？
- 如何给终端报告预留额度？
- 流式模型能不能中途停止？

**坑**

- 不要说预算可以精确控制不超一 Token。
- 不要在恢复时忘记累计历史用量。

## Q59. Tracer、EventHub 和 SSE 是怎样串起来的？

**面试官为什么问**

看可观测性是否与业务执行解耦，也会追问慢消费者、断连和回放。

**30 秒口播**

Agent 和 WorkflowEngine 只向 Tracer 发结构化事件，Tracer 同时累计耗时和 Token，并把事件交给 sink。API 的 sink 一方面持久化关键事件，一方面 publish 到进程内 EventHub；SSE 订阅者先回放 buffer，再接实时队列。Token 增量只走实时流，完整报告和最终统计另有终态事件与详情接口兜底，避免数据库被高频 token 事件打爆。

**深水区备料**

- 代码：`deep_research/observability.py::Tracer`、`EventHub`。
- 订阅时“回放 buffer → 注册队列”之间无 await，在单线程事件循环下避免发布交错导致丢缝。
- 每个订阅队列有上界 1024；满时 publish 不阻塞执行，允许丢事件，close 哨兵必须腾格送达。
- 前端使用 fetch + ReadableStream 解析 SSE，便于带 `X-API-Key`，但失去 EventSource 自动重连。
- 跨实例时进程内 EventHub 不够，需要外部事件总线和 Last-Event-ID/持久 offset。

**大概率追问**

- 队列满了为什么丢而不是阻塞？
- 客户端断线如何补事件？
- Token 事件丢了界面怎么办？

**坑**

- 不要说 SSE 天然可靠、不丢消息。
- 不要把 EventHub 说成跨进程消息总线。

## Q60. 运行时快照和工作流乐观锁分别解决什么问题？

**面试官为什么问**

两者都与“配置变化”有关，但一个保护执行一致性，一个保护编辑并发。对方会用运行中修改和多人编辑追问。

**30 秒口播**

运行时快照解决的是 run 创建后控制面继续变化的问题：本次会用到的角色 behavior、Prompt、模型非密钥参数和终端角色被冻结，恢复也按快照重建。乐观锁解决的是两个用户同时编辑同一工作流：客户端提交 base version，数据库更新带 `WHERE id=? AND version=?`，只有一个能成功，另一个返回 409 并保留本地草稿。前者保证执行语义稳定，后者防止静默覆盖。

**深水区备料**

- 快照代码：`catalog/runtime.py::create_catalog_runtime_snapshot`、`load_catalog_runtime`。
- 只快照工作流可能触达的显式和隐式角色，控制 checkpoint 体积与暴露面。
- 密钥按 profile ID 从 live Catalog 获取，所以轮换可生效；profile 删除后可能回退默认模型。
- 乐观锁 API 有友好预检查，Repository 的条件 UPDATE 才真正封住 TOCTOU。
- 409 后前端只刷新 server version 并保留草稿，第二次保存仍是用户明确覆盖，不是自动合并。

**大概率追问**

- 409 后为什么不做自动 merge？
- 删除角色卡后旧 run 怎么恢复？
- 快照是否包含搜索 key？

**坑**

- 不要把乐观锁说成协同编辑或 CRDT。
- 不要声称快照包含密钥或保证外部服务完全复现。
