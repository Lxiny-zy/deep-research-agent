# Agent 应用开发岗位面试题库

> 适用岗位：Agent 应用开发、LLM 应用开发、AI 应用后端、多 Agent/RAG 平台开发。
>
> 这套题库以简历中的两个项目为主线：SparkOffer 负责证明你会使用 LangGraph、RAG、长期记忆和工具调用做产品；DeepResearch 负责证明你理解 Agent Runtime、工作流、证据约束、长任务恢复和工程化落地。DeepResearch 的答案均以当前仓库代码为依据；SparkOffer 只采用简历已经写出的事实，不虚构代码细节。

## 一、为什么重新做一套

旧的 `interview-qbank/` 更接近按代码模块整理的技术笔记，适合查实现，但不完全符合真实面试节奏。面试官通常从简历的一句话切入，先判断你是否真的做过，再逐层追到设计动机、实现细节、指标口径和残余问题。

因此本题库固定采用下面的结构：

1. **面试官为什么问**：告诉你对方在验证什么，不让回答跑偏。
2. **30 秒口播**：现场先说这一段，控制在 4～7 句。它必须像人说话，而不是背组件清单——先讲**为什么这么做**，再讲**大概怎么做**，最后点一句**出问题时怎么兜底**。一句话里堆五个类名、库名、缩写，等于没回答。
3. **深水区备料**：只有对方继续追问时再展开，包含代码落点、算法、边界和证据。这里可以出现类名、文件名和参数，因为对方已经决定深挖。
4. **大概率追问**：这是本题库和普通技术笔记最大的区别——**每一个追问都直接给出参考答案**，而不是只列一串问题让你自己猜。追问的答案通常两三句话，同样遵循“先原因、再做法、后边界”。
5. **坑**：指出容易夸大、混淆或自相矛盾的说法。

“30 秒口播”和“深水区备料”是同一答案的浅、深两层。不要一上来把备料全部倒完。“大概率追问”里的答案是第三层：它假设面试官已经追到这一步，你需要能立刻接住，而不是当场重新想。

## 三、简历事实口径

### SparkOffer

- 技术栈：FastAPI、LangGraph/LangChain/LlamaIndex、Qdrant、React 19、TypeScript、SSE。
- 三类 Agent 编排：简历面试五阶段状态机、专项训练流水线、带 18 个工具的 Function Calling 助手。
- 长期记忆：画像 ADD/UPDATE/IMPROVE/NOOP、向量去重阈值 0.75、14 天半衰期、单用户上限 500、SM-2 由确定性算法维护。
- RAG：多路并发查询、RRF `k=60`、0.85 语义去重、Rerank、哈希差量向量化；55 例人工集上的 Hit@1 76.4%、Hit@3 92.7%、Hit@5 100%、MRR 0.86、P50 230ms。
- 注意：本仓库没有 SparkOffer 源码。被追到类名、表结构或实现细节时，只回答你真实写过且能在 SparkOffer 仓库证明的内容。

### DeepResearch

- 产品公共模板收敛为 3 条：`deep`、`quick`、`hsi_review`。注册表仍保留 `brief`、`fact_check`、`monitoring`、`teams`、`auto` 和历史 `guarded` 等内部兼容流程，供旧 checkpoint、CLI 与 planner 使用；它们不在 UI 展示，也不承担安全门禁。意图/风险门禁由运行时在所有工作流启动前统一执行。
- 默认编排模式为 `planner-driven`：`framework/06_global_rules.md` 作为共享 system prompt 注入内置、自定义及 planner-authored 的每个 Agent，提示词和流程约束不再依赖某个单独的 workflow；`guarded` 仅作为历史兼容别名保留。
- 意图离线评测：75 条任务意图样本，L1+L2 准确率 78.7%，81.3% 请求零 Token 完成判定；风险请求拒识 18/20，正常请求误伤 0/24。剩余 2 条进入 L3 复核，不应说成已拦截。
- 安全离线评测：20/20 注入拦截、13/13 伪引用拦截、10/10 矛盾传播、3/3 有效交叉印证、4/4 同源或冲突伪佐证拦截。关系类指标使用脚本化假 LLM，证明的是管线传播，不是开放世界事实判断能力。
- 测试基线：后端默认离线 613 项，完整收集 614 项且其中 1 项为 PostgreSQL 标记；前端 20 个文件、139 项。
- Chaos 演示：1.8 秒是重启后到首次恢复事件的接管耗时，不包含等待租约 TTL；75% 是演示中避免的重复调用 Token 比例，不等同于所有场景都节省 75% 成本。

## 四、现场回答规则

1. 先回答“为什么这样做”，再说“怎么做”，最后补一句“出问题会怎样、怎么兜底”。只讲组件名、库名和流程图，不算回答。
2. 术语第一次出现先用一句人话解释再深入。说 RRF 先说“按名次融合多路结果”再甩公式；说 fencing 先说“旧进程回来后不许再写”再讲实现。
3. 数字必须带分母和评测范围。例如说“20/20 自建注入用例”，不要说“Prompt Injection 识别率 100%”。
4. 区分概率能力和确定性约束。模型负责生成、分类和提出候选；程序负责权限、状态、校验和终止性。
5. 区分三个状态概念：对话记忆、单次运行 Blackboard、可恢复 Checkpoint。不要把它们都叫 Memory。
6. 主动承认当前边界：后台执行仍在 API 进程内；不是完整分布式任务队列；恢复语义不是 exactly-once；自定义角色不是任意代码插件。
7. 一道题只讲一条主线。面试官没追问时，不主动展开五个旁支。
8. 追问的答案别背成稿子。记住每条“先原因、后做法、再边界”的骨架，现场用自己的话接住。

## 五、建议刷题顺序

- 第一轮：`01 → 02 → 03 → 04 → 06`，先把项目主线讲顺。
- 第二轮：`05 → 07 → 08 → 09`，补效果、安全和工程化。
- 第三轮：只刷 `10` 和每题的“坑”，训练压力追问。
- 面试前一晚：每个模块随机抽 2 题，只看题目先口答 30 秒，再对照口播版修正。
