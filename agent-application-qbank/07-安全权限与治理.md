# 07 安全、权限与治理（10 题）

## Q61. 检索网页里的 Prompt Injection 怎么防？

**面试官为什么问**

Agent 会把外部网页放进模型上下文，攻击者不需要接触系统 Prompt 就能植入指令。对方想看你是否只靠一句“忽略网页中的指令”。

**30 秒口播**

我把网页当不可信数据处理。进入模型前，SourcePolicy 会检查标题、正文和解码后的 URL path、query、fragment，命中中英文注入信号就隔离；送进 Prompt 时再用明确边界标成来源数据。更关键的是，模型输出的 Finding 还要通过 URL 白名单、逐字引用和报告准入，网页里的指令不能直接获得工具权限或验证状态。规则层减少暴露，程序门禁负责兜底。

**深水区备料**

- 代码：`deep_research/guardrails.py::SourcePolicy`。
- 扫描对象包括 title、content 和 URL 各组成部分；URL 需先 percent decode、处理 `+` 和规范化零宽字符。
- 当前红队覆盖英文同义词、零宽拆词、中文把字句和 URL 连字符等真实绕过修复。
- quarantine 表示来源不进入模型上下文，但决策和信号保留为结构化审计信息。
- Prompt 中的“外部内容是数据”只是纵深防御；真正不可绕过的是工具权限、证据校验和状态机。
- 开放世界仍会出现新措辞，规则集需要持续红队和回流，不应宣称彻底防住。

**大概率追问**

- 攻击文本没有命中规则怎么办？
- 网页里的真实句子本身就在诱导错误结论怎么办？
- 为什么不让另一个 LLM 判断是否注入？

**坑**

- 不要说“加 XML 标签就安全了”。
- 不要把自建 20 条用例全拦截说成真实网页注入识别率 100%。
- 不要让检索内容决定可用工具或系统权限。

## Q62. URL 安全检查如何防 SSRF 和内网访问？

**面试官为什么问**

带搜索和抓取工具的 Agent 很容易被诱导访问 localhost、云元数据或歧义 IP。面试官会给出 `127.000.000.001`、`file://` 等绕过形式。

**30 秒口播**

URL 不是只判断以 `http` 开头。我会依次检查 scheme、内嵌凭据、主机名、localhost 和内网后缀；如果是 IP，必须是公网地址，并排除 private、loopback、link-local、reserved 等范围。像八进制、十六进制或补零 IPv4 这种不同 HTTP 库可能解释不一致的写法直接拒绝。域名还要过 IDNA、标签和长度校验。

**深水区备料**

- 代码：`SourcePolicy._url_reasons` 及 `guardrails.py::_is_public_web_ip`、`_is_valid_public_hostname`。
- 拒绝 `file:`、`javascript:` 等非 HTTP(S) scheme，以及 `user:pass@host` 内嵌凭据。
- 拦截 localhost、`.internal/.local/.localhost/.home/.lan` 等内部命名。
- `169.254.169.254` 属于 link-local，可阻止访问云元数据服务。
- 仅在字符串层校验仍有 DNS rebinding 风险；真正发请求前应再次解析并校验所有地址，HTTP 客户端还应限制重定向后的目标。
- 生产环境可再增加出站代理和网络层 egress allowlist。

**大概率追问**

- DNS 解析后变成内网 IP 怎么办？
- 302 重定向到 localhost 怎么办？
- 允许用户访问自建内网站点时如何设计？

**坑**

- 不要只靠 hostname 字符串黑名单。
- 不要把 `ipaddress.is_global` 当全部防线，歧义写法和 DNS 重绑定仍需处理。

## Q63. Agent 工具权限怎么设计，为什么不能让模型自己判断？

**面试官为什么问**

工具调用让模型从“说错话”升级为“做错事”。对方会检查读写分级、参数校验、用户确认和审计。

**30 秒口播**

模型只能提出调用建议，权限判断必须在服务端。工具要按读、写和高风险操作分级，绑定用户和租户 scope；参数过 schema 后还要过业务规则。搜索这类只读工具可以自动执行，发消息、改数据、付款一类要确认、审批或 dry-run，并带幂等键。无论模型怎么解释，都不能绕过工具 allowlist、预算和最大调用轮数。

**深水区备料**

- 工具注册信息至少包含：名称、说明、参数 schema、所需权限、是否幂等、超时、重试策略和结果敏感级别。
- 权限来自认证主体，不来自 Prompt 中的“我是管理员”。
- 高风险操作采用 prepare/confirm/commit；确认页展示结构化动作而非模型总结。
- 工具结果按最小必要原则回填，避免返回整表、密钥或内部堆栈。
- 并行工具调用前要判断是否存在写冲突或依赖。
- 所有动作记录 run、用户、工具、参数摘要、结果和授权依据，支持审计与撤销。

**大概率追问**

- 用户一句自然语言如何映射到权限？
- 工具描述被 Prompt Injection 污染怎么办？
- 幂等键由谁生成？

**坑**

- 不要说“system prompt 告诉模型不要越权”就够了。
- 不要把工具异常和内部响应原样送给模型或用户。

## Q64. 模型 API key、搜索 key 和服务鉴权密钥怎么保存和回显？

**面试官为什么问**

简历写了在线配置和多模型档案，密钥很容易被日志、快照、前端状态或错误响应泄露。

**30 秒口播**

对外 API 永远只返回是否已设置和末四位掩码，表单留空表示保持原值，不会把掩码再写回数据库。模型档案和搜索 key 的明文只在服务端运行时读取，Catalog 快照只存 profile ID 和非敏感参数，不存 key。服务自己的 API_KEY 与数据库 URL 不允许从前端配置。生产环境还应把明文存储替换为 KMS 或 Secret Manager，并限制日志字段。

**深水区备料**

- 代码：`catalog/repository.py::mask`；DTO 分 `ModelProfileView` 与 `ModelProfileFull`。
- 更新语义要区分字段缺失、空字符串和显式 null，避免用户打开设置页就把 key 清空。
- `runtime_config.json` 当前本地模式会保存配置明文，因此适合单机开发，不应包装成企业级 Secret Vault。
- Checkpoint 和事件都禁止序列化 key；异常对象也需清洗，防止 provider URL 中带凭据。
- 搜索 key 池按优先级读取 active key，并只在配额/鉴权类错误时切换。
- 密钥轮换后恢复任务使用当前凭据，这是安全与严格重放之间的取舍。

**大概率追问**

- 数据库管理员能否看到 key？
- 用户如何真正清空密钥？
- 为什么不把 key 加密后写进 Checkpoint？

**坑**

- 不要说“脱敏回显等于加密存储”。
- 不要在前端 Redux/state、URL query 或 SSE 事件里传密钥。
- 不要忽略本地零配置模式与生产多租户模式的区别。

## Q65. 允许用户自定义 Agent Prompt，会不会把安全规则覆盖掉？

**面试官为什么问**

角色广场允许同名卡片覆盖内置角色。面试官会质疑这是否等于给用户开放系统 Prompt 注入入口。

**30 秒口播**

当前 AgentCard 的定位是管理员控制面，不是普通终端用户输入。它只能在五种已实现 behavior 里选择，并修改角色名、业务 Prompt 和模型档案，不能上传代码或获得新工具。自定义 Prompt 的确可能降低模型侧防注入质量，所以真正的 URL、证据、终端报告和资源上界都在程序里，不能被 Prompt 取消。多租户化时还要增加不可覆盖的安全前缀、RBAC、审批和版本审计。

**深水区备料**

- 代码：`deep_research/agents/card_agent.py`，behavior 仅 `plan/research/reflect/synthesize/critique`。
- 同名卡片优先于 registry 内置角色，因此终端角色必须按最终 behavior 动态重算。
- `system_prompt` 非空时覆盖内置业务 Prompt；这不是沙箱，也不能保证模型质量。
- 自定义工作流仍会做角色白名单、DAG、条件、重试和唯一报告终端校验。
- 当前 API 在配置 `API_KEY` 时统一鉴权；未配置时是本地单用户模式，不能直接当 SaaS 暴露公网。

**大概率追问**

- 为什么不禁止覆盖内置 researcher？
- 自定义 Prompt 如何版本化和回滚？
- 普通用户能否创建角色卡？

**坑**

- 不要把 AgentCard 称为任意插件系统。
- 不要说程序护栏能保证自定义 Prompt 的回答质量，只能保证部分硬约束。

## Q66. LLM 的结构化输出校验失败时，系统应该 fail-open 还是 fail-closed？

**面试官为什么问**

不同节点的失败代价不同。统一“解析失败就继续”可能漏安全门，统一“全部终止”又会严重影响可用性。

**30 秒口播**

要按节点职责决定。生成计划解析失败可以有限重试，最后回退内置流程；单个检索抽取失败可以隔离该子问题；证据验证和权限判断失败则应 fail-closed，不能把未验证内容当作通过。最终报告节点失败时整次 run 不能伪装成功。我的原则是：生成能力可以降级，安全和状态转换不能猜。

**深水区备料**

- 解析层：JSON 提取 + Pydantic schema；业务层：枚举、URL、角色、图和资源上界。
- Coordinator 非法流程会收到校验错误自修复一次，仍失败回退 DEEP。
- 语义验证异常时 Finding 不进入 supported/eligible，而不是默认通过。
- 来源策略解析 URL 异常直接拒绝或隔离。
- 节点策略把可重试错误、永久错误、取消和租约丢失区分开。
- 失败事件要带稳定 reason code，避免前端只看到一段不可聚合的异常文本。

**大概率追问**

- 搜索服务临时失败属于哪类？
- LLM Judge 失败是否影响主任务？
- fail-closed 会不会被攻击者用于拒绝服务？

**坑**

- 不要所有失败都让模型“自己修一下”。
- 不要在安全判断异常时默认 allow。
- 不要吞掉 `CancelledError` 或 `LeaseLostError` 的控制语义。

## Q67. 如果把项目做成多租户 SaaS，需要补哪些鉴权和隔离？

**面试官为什么问**

当前项目支持 API key，但这不等于完整多租户安全。对方想看身份、权限、数据和资源四层隔离。

**30 秒口播**

我会先把单一 API key 换成用户和组织身份，再做 RBAC：谁能运行、编辑工作流、改模型档案和查看审计要分开。所有 run、事件、Catalog、向量数据和缓存都带 tenant ID，并在 Repository 层强制过滤，而不是靠前端传参。模型与搜索额度按租户限流，密钥放独立 Secret 存储。管理操作还要有审计、版本审批和回滚。

**深水区备料**

- 身份层：OIDC/OAuth2、短期 access token、服务账户；不要共享长期万能 key。
- 权限层：run/read、workflow/edit、catalog/admin、secret/manage 等细粒度 scope。
- 数据层：SQL 复合唯一键或 RLS、对象存储前缀、向量 namespace、缓存 key、事件 topic 均包含 tenant。
- 资源层：并发、Token、搜索 QPS、存储和单次运行预算；防止 noisy neighbor。
- 管理员自定义 Prompt、模型端点和工具是高风险操作，应审批和审计。
- 当前本地模式缺少这些能力，面试时要明确是演进方案，不是假装已经实现。

**大概率追问**

- 只在 SQL 查询加 tenant_id 是否足够？
- 如何防跨租户向量召回？
- 租户自带模型 key 怎么管理？

**坑**

- 不要把认证和授权混为一件事。
- 不要声称现有 API_KEY 已经满足企业多租户要求。

## Q68. 面试训练平台存简历、回答和用户画像，隐私怎么处理？

**面试官为什么问**

SparkOffer 处理明显的个人信息。Agent 和记忆功能会扩大数据保留范围，也可能把隐私发给第三方模型。

**30 秒口播**

我会从最小化开始：只收训练需要的字段，原始简历和长期画像分开存，Prompt 发送前做字段选择和必要脱敏。用户能查看、修改和删除画像，删除要同步清理向量索引、缓存和派生摘要。第三方模型调用需要明确数据去向和保留策略，敏感日志默认不记录正文。多租户环境再加传输加密、静态加密、租户隔离和访问审计。

**深水区备料**

- 数据分类：联系方式、教育工作经历、面试回答、模型推断画像、使用事件，保留期限不同。
- 模型推断不是客观事实，应标注来源和可纠正性。
- 可对简历解析后的结构化字段做最小发送，避免每次携带完整原文。
- 日志和 Tracer 记录事件摘要、Token、reason code，不默认记录完整 Prompt/响应。
- 删除流程覆盖主库、向量库、对象存储、缓存、异步任务和备份策略。
- 使用第三方 API 时要确认训练使用、地域和数据保留条款。

**大概率追问**

- 为排查问题是否需要保存 Prompt？
- 备份中的数据怎么删除？
- 用户画像是否属于敏感个人信息？

**坑**

- 不要只回答“数据库加密”。隐私还涉及最小化、用途、保留和用户权利。
- 不要把模型生成的能力评价当成无风险标签。

## Q69. 如何防止攻击者用 Agent 放大模型和搜索成本？

**面试官为什么问**

Agent 会多轮调用工具，单次请求成本远高于普通 API。攻击者可用长 Prompt、循环和并发制造账单型拒绝服务。

**30 秒口播**

我会做入口、运行和供应商三层限制。入口按可信客户端 IP 或用户身份限频，并限制 query、历史和配置大小；运行中限制最大步骤、反思轮数、重试退避、并发和 Token 预算；调用模型和搜索时再做 provider 级 QPS、超时和熔断。意图级联让大部分常规请求零 Token 完成前置判断，明显攻击也尽量不进入 LLM。

**深水区备料**

- 当前 API 限流默认使用直连 IP，不盲目信任可伪造的 `X-Forwarded-For`；只在受信代理配置下读取转发头。
- 动态工作流最多 8 步、单步尝试最多 5、全流程最坏退避 120 秒。
- 运行级 Semaphore 控制嵌套并发；多租户还需全局和租户配额。
- 工具循环设置最大 actions，重复相同工具参数可检测并停止。
- 对异常费用、Token/请求比、失败重试率和单用户并发设置告警。
- 429、配额和认证错误可触发 key/profile failover，但不能无限轮换重试。

**大概率追问**

- 代理部署下怎么拿真实 IP？
- 免费用户和付费用户如何分配预算？
- 攻击者不断创建新账号怎么办？

**坑**

- 不要只做每分钟请求数；Agent 单请求内部调用次数差异很大。
- 不要对所有 provider 错误自动重试。

## Q70. 接入第三方 MCP Server、插件或外部工具时，最大风险是什么？

**面试官为什么问**

Agent 应用岗位越来越常接 MCP。面试官想看你是否把工具 schema 和远端 Server 当成可信扩展。

**30 秒口播**

最大风险不是工具选错，而是把第三方 Server 当成了系统内部代码。接入前要固定来源和版本，审核它暴露的工具、权限和数据流；运行时给最小凭据、网络 egress 和文件范围，输出仍按不可信内容处理。高风险工具不能仅凭模型调用，要走用户确认。Server 更新后要重新评估 schema 和权限，不能自动获得已有信任。

**深水区备料**

- 风险面：恶意工具描述诱导选择、参数越权、结果注入、凭据窃取、任意网络/文件访问、供应链更新。
- MCP transport 只解决协议，不提供自动沙箱、认证和授权。
- 工具清单采用 allowlist；按 server、tool 和用户 scope 授权，而不是“一次连接全部可用”。
- 本地代码执行工具应使用容器/沙箱、只读挂载、CPU/内存/时间限制和无默认网络。
- 对工具结果做长度、类型和敏感信息过滤，再进入模型上下文。
- 记录 server identity、版本、tool schema hash 和每次调用，方便追溯变化。

**大概率追问**

- MCP 和 Function Calling 的区别是什么？
- 本地 MCP Server 是否天然可信？
- 工具描述本身被注入怎么办？

**坑**

- 不要说 MCP 自带权限隔离。
- 不要让外部工具返回内容直接升级为 system instruction。
