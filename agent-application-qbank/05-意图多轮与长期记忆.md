# 05 意图、多轮与长期记忆（10 题）

## Q41. 为什么意图识别要做三级级联，不直接调用大模型？

**面试官为什么问**

简历把规则、本地模型和 LLM 写得很具体。对方想听成本、延迟和安全上的动机，而不是“多级更准确”。

**30 秒口播**

意图识别是每个请求都要经过的前置步骤，如果全部调用大模型，就给所有流量增加固定 Token 和秒级延迟。我的级联先用高精度规则处理明显模式，再用随包发布的本地分类器处理常规请求，只有低置信样本才交给 LLM。离线评测里 81.3% 的请求在零 Token 下完成判断。它本质上是成本阶梯，同时让明显攻击请求尽量在最前面被拦下。

**深水区备料**

- 代码：`deep_research/intent/cascade.py::IntentCascade`。
- L1 规则：稳定、高精度、可解释；L2 本地模型：字符 n-gram TF-IDF + 逻辑回归；L3：结构化 LLM 判断。
- 离线评测只运行 L1+L2：75 条任务样本，任务准确率 78.7%，明确路由覆盖 80.0%，全级弃权 18.7%。
- L3 不是为了覆盖一切，而是处理低置信和弱风险信号；失败时可以 unknown/default，不应放宽安全判断。
- 级联指标应报告每层分流比例、准确率、拒识和误伤，而不是只给总准确率。

**大概率追问**

- **81.3% 和准确率 78.7% 为什么不同？**
  两个指标问的不是同一件事。81.3% 是有多少请求在 L1、L2 就给出了判定、完全没花 Token，属于成本口径；78.7% 是这些判定里有多少判对了，属于质量口径。一个请求完全可以零 Token 完成判定但判错，所以两个数字不能互相替代，更不能只报好看的那个。

- **L1 规则会不会越来越难维护？**
  会，这是规则层的必然趋势——覆盖新表述就得加模式，加多了互相干扰还难以回归。我的控制办法是把规则限制在「高精度、可解释」的明显模式上，模糊地带交给 L2 和 L3，不让规则去追求覆盖率。真到了维护不动的时候，正确做法是把那部分能力迁移到模型层，而不是继续堆正则。

- **L3 不可用时怎么办？**
  按保守方向退，不能因为兜底层挂了就放宽。任务分类退回 unknown 走默认 deep 流程，风险判断保持前级已识别的结果不变——也就是说 L3 挂掉只会让系统更保守，不会让攻击请求趁机溜过去。代价是可用性下降，这是我接受的方向。

**坑**

- 不要说三级是为了“层层投票提高准确率”。前级高置信时后级根本不运行。
- 不要把零 Token 覆盖率说成准确率。

## Q42. 本地意图模型为什么不用 sklearn，自己实现 TF-IDF 和逻辑回归推理？

**面试官为什么问**

考依赖取舍和你是否真的理解模型推理。自己实现如果只是炫技，反而会被质疑。

**30 秒口播**

这里不做在线训练，只需要加载固定权重做轻量推理。自己实现的范围很小：字符 n-gram 特征、TF-IDF、L2 归一化、线性 logits 和 softmax，权重存成 JSON 随应用发布。这样桌面版和零配置部署不用额外带 sklearn，也方便在纯 Python 环境运行。训练脚本仍负责离线生成词表和权重；如果以后模型复杂化，我不会继续手写。

**深水区备料**

- 代码：`deep_research/intent/model.py`；模型文件：`deep_research/intent/models/query_intent.json`。
- 字符 2/3-gram 对中文无需分词，也能处理英文片段、拼写变化和零宽字符清洗。
- 推理步骤：normalize → feature counts → TF-IDF → L2 normalize → `W·x+b` → softmax。
- softmax 先减最大 logit，避免指数溢出。
- 自研代价：要自己保证训练/推理特征一致、模型版本兼容和数值测试。

**大概率追问**

- **为什么不用词级分词？**
  中文分词本身要带词典和分词器依赖，而且分错了下游特征全歪。字符 2/3-gram 不需要分词就能用，对错别字、空格插入和中英混写这些变体也更鲁棒——意图识别面对的恰好是这类不规范输入。代价是特征维度更大、可解释性差一些。

- **模型文件被篡改怎么办？**
  它是随包发布的资源，威胁模型和代码本身是一样的——能改这个 JSON 的人通常也能改代码，所以单独给它加校验意义不大。真正的兜底在于这一层只做路由和风险信号，最终的证据门禁和权限判断不依赖它，篡改它不能直接换来越权。要更严的话可以在打包时记录文件哈希并在启动时校验。

- **什么时候会切回 sklearn/ONNX？**
  当模型不再是线性分类器的时候。现在自己实现的推理就是 TF-IDF 加一层线性变换再 softmax，几十行能写完也好测；一旦要上树模型、深层网络或者需要量化加速，我不会继续手写，那时候依赖成本远低于自己维护数值正确性的成本。

**坑**

- 不要说“自研模型比 sklearn 快”，除非有基准。
- 不要把推理代码说成自己发明了逻辑回归算法。

## Q43. 本地分类器的置信阈值怎么定？为什么允许弃权？

**面试官为什么问**

看阈值是不是拍脑袋，以及系统如何处理不确定性。Agent 前置分类最危险的不是 unknown，而是自信地路由错。

**30 秒口播**

我在 dev 集上扫描阈值，选择“被模型采纳的样本精度至少 0.9”时覆盖率最高的点，再把阈值写进模型文件。低于阈值就弃权，不强行猜类别。因为 unknown 还能走默认流程或交给 LLM，错误路由却可能减少研究深度、漏掉时间约束，甚至把风险请求放过去。这里精度优先于覆盖率。

**深水区备料**

- 训练脚本：`scripts/train_intent_model.py` 中的阈值选择逻辑。
- 需要分清模型概率和校准概率；softmax 高并不自动代表真实置信度。
- 可以进一步做温度缩放、可靠性图和按类别阈值，当前实现是较简单的全局门槛。
- unknown 不等于失败：路由层可以 default deep，风险弱信号可以升级 L3。
- 数据分布变化后阈值需重新校准，不能永久固定。

**大概率追问**

- **为什么目标精度是 0.9？**
  这是个产品取舍，不是数学最优。定 0.9 是因为这一层错了的代价不对称——弃权只是多花一次 LLM 调用，判错却会让整个后续流程走错工作流。所以我选了「保证被采纳样本精度不低于 0.9 的前提下覆盖率最高」的那个点，把不确定的都推给后级。

- **每个类别是否应该不同阈值？**
  应该，现在只有一个全局门槛，这是实现上的简化。不同类别的样本量和难度不一样，共用一个阈值等于对稀有类别过严、对高频类别过松。要改的话就是按类别分别扫阈值，代价是要保证每个类别在 dev 集上都有足够样本，否则阈值本身就是噪声。

- **模型过度自信怎么办？**
  softmax 出来的值不是校准过的概率，训练数据少的时候尤其容易给出虚高的置信度。可以做温度缩放，用可靠性图看预测置信和实际准确的偏离，再校准。当前实现没做这一步，我只是把阈值定得比较保守，这是简化不是解决。

**坑**

- 不要说 0.9 是数学上最优值。
- 不要用测试集选择阈值后再在同一测试集报效果。

## Q44. “风险只能收紧，不能放宽”具体是什么意思？

**面试官为什么问**

这是意图模块最关键的安全设计。对方会构造“前级判危险、后级说安全”的冲突场景。

**30 秒口播**

风险判断读取的是攻击者可控输入，所以后一级不能推翻前一级已经发现的高风险信号。比如规则层命中 Prompt Injection，LLM 即使返回 safe，最终风险仍保持 injection。来源筛查和工作流路由也遵循类似单向原则：后续组件可以增加限制，不能取消已有门禁。这样即便 LLM 判定器被注入，最坏是误拦正常请求，不会把已经识别的攻击放进模型上下文。

**深水区备料**

- 代码：`intent/cascade.py::_tighten_risk`。
- 用户 query 与检索来源是两条不同通道；来源判定不能修改用户任务意图，只能收紧 source policy。
- 显式用户工作流选择优先于推荐路由，但风险拒识优先于所有工作流选择。
- 单向安全会增加可用性损失，因此必须同时评估拒识率和正常请求误伤率。
- 当前离线风险集：18/20 被拦、0/24 正常请求误伤，2 条弱信号待 L3 复核。

**大概率追问**

- **规则误判后用户怎么申诉？**
  当前没有申诉通道，这是明确的产品缺口。设计上应该给拒识返回稳定的 reason code 而不是一句笼统的拒绝，让用户知道被什么规则挡了；再配一个人工复核入口。技术上要注意的是申诉通道本身不能变成绕过门禁的后门，得走独立审核而不是让用户自己确认放行。

- **为什么不让更强的 LLM 纠正规则？**
  因为风险判断读取的是攻击者可控的输入——如果允许 L3 说 safe 就推翻前级的高风险结论，那攻击者只要构造一段能骗过 LLM 的文本，就能让整套规则失效。所以方向是单向的：后级只能加限制，不能减。代价是规则误判没法被模型自动修正，只能靠迭代规则本身。

- **误伤是否会积累？**
  会，而且单向收紧的设计天然让误伤只增不减，这是必须一起报的代价。所以我把拒识率和误伤率成对评测——当前离线集上是 18/20 拦截、0/24 正常请求误伤。真上线还要看用户申诉和放弃率，光看拦截数会自我感觉良好。

**坑**

- 不要说系统安全因此不依赖模型，模型仍参与未覆盖风险识别。
- 不要只报 90% 拒识，不报 0/24 误伤和 2 条待复核。

## Q45. 多轮追问中的“那第二个呢”怎么处理？

**面试官为什么问**

考对话上下文处理是否只靠拼接历史。指代消解错误会让后面的意图和检索全部跑偏。

**30 秒口播**

我先用规则判断当前 query 是否自足，像“那第二个呢”“前者怎么样”才进入消解；完整问题直接跳过，避免每轮额外调用。需要消解时，只取最近最多三轮相关历史，让模型改写成独立问题，同时保留原句和消解依据。消解结果仍要重新做意图、槽位和风险判断，不能因为它来自模型就直接信任。

**深水区备料**

- 代码：`deep_research/intent/context.py`，`MAX_HISTORY_TURNS = 3`。
- 规则同时识别指代词和自足句式；不能只看有没有谓词，例如“前者怎么样”仍依赖上下文。
- 历史渲染需要角色、顺序和长度限制，防止旧攻击内容长期污染。
- 解析失败或缺历史时保留原 query，并让 readiness/clarification 处理不完整信息。
- 不建立永久会话表也可由前端显式携带最近对话；但多设备和服务端连续性会受限。

**大概率追问**

- **为什么只取三轮？**
  因为消解依赖的是最近的话题焦点，不是完整对话史。带的轮次越多，模型越容易把指代绑到更早的实体上——「第二个」到底是上一轮列的第二个，还是三轮前那份清单的第二个，历史越长越容易搞错。同时上下文越长越贵。三轮是个经验值，不是最优解，真要定应该用带标注的多轮样本扫一下还原准确率随窗口大小怎么变。

- **历史里有 Prompt Injection 怎么办？**
  两道处理。一是消解的 system prompt 里明确写了历史轮次是参考信息、不是指令，其中的祈使句一律不执行；二是更关键的——消解结果不是终点，它出来之后还要重新走一遍意图、槽位和风险判定，而风险只能收紧不能放宽。所以就算模型被历史里的内容带偏改写出一个恶意 query，它照样得过前面那道风险关。另外窗口只有三轮，本身也限制了旧内容的驻留时间。

- **消解错了用户如何发现？**
  靠留痕。消解不覆盖原始输入，原句、命中的信号 code 和消解依据都保留下来，前端可以展示「系统把你的问题理解成了 XX」。这样用户在看到跑偏的报告之前就有机会发现理解错了。我不认为这个方案够好——理想情况应该是低置信消解直接转成一次确认，而不是先跑完再让用户回头看。

**坑**

- 不要把全部聊天历史直接拼进分类 Prompt。
- 不要把模型改写后的 query 覆盖原始输入而不留审计字段。

## Q46. 意图、槽位和澄清为什么要分开？

**面试官为什么问**

很多系统把“分类置信度高”当作“请求已经可执行”。对方会用“对比一下”这类缺实体问题检验设计。

**30 秒口播**

意图回答“用户想做哪类任务”，槽位回答“任务里的实体、时间、领域和侧面是什么”，readiness 才回答“信息够不够执行”。“对比一下”可能被高置信识别为 comparative，但没有对比对象，仍然不能开始研究。我会先规则抽槽位，必要时让 LLM 补抽，再检查缺口并最多澄清三轮；用户回答后合并槽位，重新组成完整 query，再创建 run。

**深水区备料**

- 代码：`deep_research/intent/slots.py`、`deep_research/intent/readiness.py`、`deep_research/intent/clarify.py`。
- 槽位抽取遵循“抽不到留空，不猜”；幻觉出的时间或实体会直接污染检索。
- 澄清在 run 落库前完成，避免历史中留下没有真正执行的垃圾 run。
- 选项优先用规则生成；只有规则无法覆盖时才用 LLM，控制成本。
- 用户可以选择“直接研究”，但风险请求不能通过该选项绕过拒识。

**大概率追问**

- **为什么最多三轮？**
  `MAX_CLARIFY_ROUNDS = 3` 是硬上限，到顶强制放行，带着已有信息去研究。定这个数的逻辑是代价对比：把用户问烦的代价，高于跑一次信息不全的研究。而且澄清必须能终止——如果靠模型自己判断「问够了吗」，它完全可能一直觉得还差点什么。所以终止性写在代码里，不写在 Prompt 里。

- **用户一直不给完整答案怎么办？**
  照跑。三轮到顶就用现有信息建 run，槽位缺就缺着，下游退回原始 query 的自由文本表达。另外每轮选项末尾都固定挂一个「直接研究」，用户任何时候都能跳过追问——他比系统更清楚自己要什么。风险请求不能通过这个选项绕过拒识，拒识优先级高于所有澄清路径。

- **槽位和 Prompt 参数如何连接？**
  槽位不是直接拼进 Prompt 的裸字段，而是先渲染成一段人类可读的约束摘要——研究对象、时间范围、领域、语料语言、关注侧面——再作为约束块进 Planner 的上下文，前端展示也复用同一份渲染。这样做的好处是抽不到的槽位自然不出现，不会在 Prompt 里留一串空值误导模型。原则是「抽不到留空，不猜」，一个幻觉出来的「2024 年」会直接污染整条检索。

**坑**

- 不要只用分类置信度决定是否澄清。
- 不要让澄清循环在后台挂起一个 run 等用户输入，当前设计是创建前交互。

## Q47. SparkOffer 的长期用户画像如何更新？

**面试官为什么问**

简历写了 Mem0 风格两阶段更新。对方会检查模型的角色、存储规则和错误记忆如何处理。

**30 秒口播**

我不会把每段对话直接写成长记忆。第一步让模型从本轮评价里抽取候选发现，例如某类问题持续薄弱；第二步把候选和已有画像一起交给模型，输出 ADD、UPDATE、IMPROVE 或 NOOP。程序再校验操作、去重并写入。模型负责语义归纳，数据库负责版本、权重、数量上限和删除，这样能减少一次偶然回答对长期画像的污染。

**深水区备料**

- ADD：新增稳定事实；UPDATE：修正旧描述；IMPROVE：记录能力改善；NOOP：证据不足不改。
- 候选记忆应保存来源回合、置信度、时间和证据摘要，方便纠错。
- 单轮结论不能无限提高权重；可要求多次观测或高质量评价才固化。
- 画像更新 Prompt 与出题 Prompt 分离，避免生成任务顺手篡改长期状态。
- 被追到具体 schema、事务或 Mem0 API 时，只按 SparkOffer 真实实现回答。

**大概率追问**

- **LLM 把用户能力判断错了怎么办？**
  这是一定会发生的，所以设计上不让单次判断直接固化。第二阶段的合并会拿候选和已有画像一起看，证据不足就输出 NOOP 而不是硬写；候选本身要带来源回合和证据摘要，事后能追到是哪次回答导致的这条结论。再加上用户可查看和修改画像，错记有人工纠正入口。真正的兜底是：单轮结论不能无限抬权重，需要多次观测才固化。

- **UPDATE 和 IMPROVE 有什么区别？**
  UPDATE 是修正——原来那条描述本身就不准，用新的替掉。IMPROVE 是记录进步——原来的判断在当时是对的，只是用户现在变强了，这是一次状态变化而不是纠错。分开的意义在于它们对下一轮出题的影响不一样：被 IMPROVE 的薄弱点应该降权、拉长复习间隔；被 UPDATE 的说明系统之前理解偏了，不该因此认为用户有进步。混成一个操作就丢掉了这个区别。

- **为什么不用纯规则更新画像？**
  因为「这道题答错说明他哪块弱」是语义归纳，规则写不出来。同一次错误可能是概念没掌握，也可能只是表述不清，规则只能看到分数看不到原因。但反过来也不能全交给模型——写入、去重、权重上限和数量上限必须由程序控制，否则模型一次抽风就能污染长期画像。分工是：模型负责理解，数据库负责守规矩。

**坑**

- 不要说“模型自动维护画像”就结束，程序写入门才是关键。
- 不要把用户原话和模型推断混为同等可信的长期事实。

## Q48. 0.75 去重、14 天半衰期、30% 权重上限和 500 条上限分别解决什么？

**面试官为什么问**

简历数字很密集，对方会逐个拆开检查它们是不是有明确作用和校准依据。

**30 秒口播**

0.75 语义阈值用于发现近重复记忆，避免同一个薄弱点换句话后不断新增；14 天半衰期让旧结论逐步减弱，适应能力变化；单条权重上限 30% 防止某一记忆支配整个出题上下文；500 条上限控制每个用户的存储和检索成本。它们都是治理参数，不是通用最佳值，需要结合重复率、画像稳定性和个性化效果做离线校准。

**深水区备料**

- 去重后不是一律丢弃，可合并证据次数、更新时间和置信度。
- 时间衰减可用 `weight * 0.5^(age/14d)`，但稳定事实与短期表现可以使用不同衰减策略。
- 权重上限是上下文采样占比，而不是数据库里只能占 30% 数量。
- 达到 500 条后可淘汰低权重、过期、已掌握或高度重复项，而不是简单删除最旧。
- 这些规则需要和用户“查看、修改、忘记我”能力配合。

**大概率追问**

- **0.75 如何选？**
  在重复率和误合并率之间校准的，不是通用最佳值。定低了会把「事务隔离级别不清楚」和「MVCC 原理不清楚」这类相关但不同的薄弱点合并掉，画像就变粗了；定高了换个说法就新增一条，同一个弱点能刷出十条记忆。校准方法是拿一批人工标注的「是不是同一个薄弱点」的记忆对，扫阈值看合并准确率。这个数字和 RAG 那边的 0.85 不是一回事，两边的对象和代价都不同。

- **用户长期没使用，所有记忆都衰减没了吗？**
  按 `weight * 0.5^(age/14d)` 这个公式算，权重会趋近于零但不会真的删除——衰减影响的是它在出题上下文里被采样的概率，不是存在与否。而且不同类型的记忆不该用同一种衰减：短期表现（这周做题状态差）本来就该快速衰减，稳定事实（本科专业、目标岗位）不该衰减。现在做得比较粗，是可以改进的地方。用户回来以后系统应该表现得像「记得你但不确定你现在什么水平」，而不是完全从零开始。

- **上限 500 是否会损失重要信息？**
  会，这是明确的取舍。500 条是为了控制单用户的存储和检索成本——每次出题都要检索画像，条数无上限地涨，延迟和费用都跟着涨。关键在于淘汰策略：应该淘汰低权重、已过期、已掌握和高度重复的，而不是简单删最旧的——最旧的很可能恰好是最稳定的事实。真要更稳妥，可以在淘汰前把一批相关记忆压缩成一条摘要，而不是直接丢。

**坑**

- 不要把 cosine 0.75 解释成 75% 语义相同。
- 不要把所有记忆用同一种衰减，稳定偏好和短期弱项生命周期不同。

## Q49. 为什么 SM-2 复习调度不用 LLM？

**面试官为什么问**

考你是否知道哪些决策应该确定化。复习间隔如果每次由模型自由生成，很难解释和回归。

**30 秒口播**

SM-2 的输入是掌握度或回忆质量，输出是下一次间隔和熟练参数，这类计算规则明确、需要稳定可复现，没必要交给 LLM。模型可以评价用户回答并提取能力信号，但真正的间隔更新由确定性算法完成。连续三次得分达到 7 分以上后，系统把薄弱点判为已掌握并移出重点题池。这样同样输入一定得到同样调度，也方便测试和解释。

**深水区备料**

- 模型评价本身有噪声，可做 rubric、校准或多轮平滑，不能把单次 Judge 分数当真值。
- SM-2 可维护 ease factor、interval、repetition count 和 next review time。
- “连续 3 次 ≥7”是产品规则，不是 SM-2 原始公式本身；要明确算法和业务门槛的边界。
- 已掌握不是永久删除，可降低权重或延长复习间隔，后续退化时重新进入。
- 对复习策略应测弱点覆盖、遗忘率和用户训练收益，而不只是出题数量。

**大概率追问**

- **LLM 评分不稳定会不会污染 SM-2？**
  会，这是这条链上最脆弱的一环——SM-2 本身是确定性的，但它的输入是模型给的回忆质量分。同样一份回答换个时间评可能差一分，间隔就跟着变。缓解手段是给评分定 rubric 而不是让模型自由打分，以及不拿单次分数做终态判定——「连续三次 ≥7 才算掌握」本质上就是在对噪声做平滑。我不会说这解决了问题，只能说降低了单次误评的影响。

- **为什么是三次、为什么是 7 分？**
  这两个都是产品阈值，不是 SM-2 公式的一部分，我不会把它包装成科学结论。选三次是因为一次可能是蒙对、两次还可能是同一批题重复出现，三次能挡掉大部分偶然；7 分是评分 rubric 上「答得基本完整」的位置。要验证得看被判为已掌握的薄弱点后来有没有大量退化回来——退化率高就说明门槛松了。这个回归数据我目前没有。

- **已掌握后还会不会复习？**
  会，只是移出重点题池，不是永久删除。做法是降权加拉长复习间隔，让它偶尔还能出现；如果再次答错就重新进入重点池。因为「掌握」是个当下判断，人是会遗忘的，一刀切删掉等于假设能力只增不减。

**坑**

- 不要说 SM-2 完全由 LLM 驱动，简历明确强调零 LLM 参与调度计算。
- 不要把业务阈值包装成科学定律。

## Q50. 长期记忆如何支持纠错、遗忘和隐私保护？

**面试官为什么问**

用户画像涉及简历、能力和行为数据。对方会看你是否只考虑“记住”，没考虑错记和删除。

**30 秒口播**

长期记忆必须可查看、可追溯、可修改、可删除。每条画像应记录来源回合和更新时间，用户或后续证据可以触发纠正；检索和 Prompt 只使用当前有效版本。删除时不仅删主表，还要清向量索引、缓存和派生摘要。敏感字段要最小化收集、按租户隔离并限制日志输出，不能因为“个性化”就永久保存全部原始对话。

**深水区备料**

- 区分用户明确提供的事实和模型推断，后者需要更低默认信任和明显标记。
- 记忆写入、读取、修改和删除均应记录审计事件。
- 向量库删除通常需要稳定 memory ID，不能只靠文本匹配。
- 备份和异步索引会让“删除完成”变复杂，需要定义 SLA 和软删/硬删流程。
- 多租户必须在查询过滤、向量 namespace、对象存储路径和缓存 key 四处隔离。

**大概率追问**

- **用户要求删除后，备份怎么办？**
  这是「删除完成」最难兑现的地方。在线路径好办——主表、向量索引、缓存和派生摘要按稳定 memory ID 一起清；但备份和异步索引里的副本没法立刻消失。实际做法是定义清楚 SLA：在线数据即时删，备份按保留期自然过期，并且承诺删除后的数据不再进入任何检索和 Prompt。我不会对用户说「已彻底删除」，那是做不到的承诺，该说的是删除的边界和时限。

- **模型推断的画像要不要展示给用户？**
  要，而且必须标明这是推断而不是用户说过的事实。区分的理由是两者可信度不一样——用户自己填的目标岗位是事实，模型从三道题答错推出来的「并发基础薄弱」是推断，后者默认应该有更低的信任权重和更容易的修改入口。展示它的代价是用户可能不认同这个判断，但那正好是纠错的机会，藏起来只会让错误的画像一直影响出题。

- **如何防止跨用户召回？**
  四处都要隔离，只在数据库加 `user_id` 是不够的：查询层强制过滤、向量库按 namespace 或 payload filter 隔离、对象存储路径带租户前缀、缓存 key 带用户维度。最容易漏的是后两个——缓存 key 忘了带 user_id 就是典型的串号事故，而且它只在并发时偶发，测试很难抓到。工程上更可靠的做法是让过滤发生在数据访问层而不是每个业务查询里，靠人记得写 where 迟早出事。

**坑**

- 不要只说数据库加 `user_id` 就完成隔离。
- 不要默认原始对话都可以长期保存。
