# 02 Agent 核心与模型调用（10 题）

## Q11. 你怎么定义 Agent？它和普通聊天机器人有什么区别？

**面试官为什么问**

这是岗位基础题。对方想知道你是否把“接了大模型”都叫 Agent，以及你能否说清目标、状态、工具和控制循环。

**30 秒口播**

我把 Agent 理解成一个由模型参与决策、能读取状态并采取外部动作的执行单元。普通聊天机器人通常是输入一段文本、生成一段文本；Agent 还会选择工具、更新状态、观察结果，再决定下一步。项目里 Planner、Researcher 这类角色是能力单元，真正控制它们何时运行的是 WorkflowEngine。也就是说，Agent 不等于整个系统，模型决策和确定性编排要分开看。

**深水区备料**

- 最小构成：目标/指令、模型、上下文状态、工具或动作空间、观察结果、停止条件。
- 可以区分“Agentic workflow”和“自由自治 Agent”：前者控制流显式，后者由模型多轮决定动作。
- DeepResearch 的普通角色统一实现 `Agent.step(Blackboard, RunContext)`，模型并不直接控制全局循环。
- `compose` 才允许 Coordinator 生成受约束流程，但仍要过白名单和资源上界校验。

**大概率追问**

- **Workflow 算不算 Agent？**
  不算，它是调度器不是能力单元。WorkflowEngine 里没有模型调用，它做的是按拓扑层派发节点、判断条件边、处理超时重试和合并状态——全是确定性代码。模型只在节点内部被调用。我刻意保持这个边界：如果连控制流都交给模型决定，出问题时就没有可以断言的地方了。

- **Multi-Agent 一定比单 Agent 好吗？**
  不一定，而且默认应该怀疑。每多一个角色就多一次调用、多一段延迟、多一个失败点，上下文还要在角色之间传递和衰减。我的项目里 quick 工作流就没有反思环节，简单问题不强制走多 Agent。判断标准是职责分离能不能换来可测试性、并发或者一道质量门——换不到就不该拆。

- **Agent 的停止条件怎么设计？**
  终止性必须写在代码里，不能靠 Prompt 说「最多两轮」。我的做法是三重上界：循环用 `for range(max_rounds)` 硬限，单步有 timeout 和最多 5 次尝试，全局有 TokenBudget。任何一个先到就停。除此之外还有语义上的提前退出——证据充分、没有新增子问题都会提前结束。关键区别是：语义退出是优化，硬上界才是保证。

**坑**

- 不要回答成“Agent 就是会调用工具的大模型”，状态和控制循环同样关键。
- 不要把角色类、工作流引擎和整个产品都混叫 Agent。
- 不要用“像人一样思考”这种无法验证的描述。

## Q12. 一个可上线的 Agent 应用通常有哪些层？

**面试官为什么问**

看你的视角是否停留在 Prompt 和模型调用，还是能覆盖数据、执行、治理和产品闭环。

**30 秒口播**

我一般拆成五层。最底层是模型和工具适配；上面是 Prompt、结构化输出和上下文；再上面是 Agent 能力与工作流；然后是状态、持久化、评估、权限和观测；最外层才是 API 和用户界面。项目里经常出问题的反而是中间几层，比如工具重放、上下文污染、状态恢复和指标口径，而不是模型 API 能不能调通。

**深水区备料**

- 模型层：provider 适配、超时、重试、流式、Token usage。
- 能力层：Planner、Researcher、工具 schema、结果模型。
- Runtime 层：Workflow、状态机、并发、预算、Checkpoint、取消。
- 治理层：Prompt Injection、工具权限、密钥、审计、评估、回归。
- 产品层：交互、澄清、实时进度、历史、配置、人工接管。
- 可用 DeepResearch 目录映射：`llm.py`、`agents/`、`workflow.py`、`persistence/`、`api.py`、`frontend/`。

**大概率追问**

- **哪一层最容易被低估？**
  状态和恢复那一层。Demo 阶段它完全不存在——跑一次出个结果就完了；但真跑长任务时，进程重启、实例切换、分支合并、取消传播全在这一层，而且这些问题只在特定交错下暴露，happy path 测不出来。我自己踩的最重的坑就在这里：并行分支合并丢数据，条件很窄，一般用例根本触发不了。

- **如何划分 Agent 和工具的职责？**
  工具是确定性的副作用出口，Agent 是决定要不要用它的判断者。分界线我画在「这件事需不需要理解自然语言」：需要理解的交给模型，能用函数算清楚的就写成工具或者干脆写成普通代码。特别要守住的是权限——工具自己校验权限，不能让模型说「我有权限」就放行。

- **小团队是否需要这么多层？**
  层是职责不是目录。小团队完全可以把治理层合进 API 层、把 Runtime 合进业务代码，但不能省掉「谁负责校验」「谁负责终止」这些职责——省掉的结果就是出事时找不到该改哪里。我的判断是：能合的是实现，不能合的是边界。反过来一上来就搭中台也是浪费，我自己这个项目也是先跑通再拆的。

**坑**

- 不要机械背“六层架构”，重点是每层解决什么失控问题。
- 不要一开始就上复杂中台，小业务可以合并实现，但职责边界仍应清楚。

## Q13. Function Calling 的完整执行循环是什么？

**面试官为什么问**

简历写了 18 个工具。对方会检查你是否只会把函数 schema 传给模型，还是理解选择、校验、执行、回填和终止。

**30 秒口播**

模型先根据用户目标和工具描述返回工具名及参数，服务端不能直接信任，要先做 schema 校验和权限检查，再执行真实函数。工具结果会以结构化消息回填给模型，让它决定继续调用还是生成最终答案。循环必须有最大轮数、超时和取消，写操作还要有确认或幂等控制。18 个工具真正难的不是注册，而是避免选错、越权和多轮调用失控。

**深水区备料**

- 工具 schema 要写清适用条件、参数单位、必填项和失败语义，避免工具间描述重叠。
- 参数验证用 Pydantic/JSON Schema；枚举、数值范围、字符串长度在程序侧限制。
- 读工具与写工具分级；高风险写操作增加用户确认、审批或 dry-run。
- 并行只适用于无依赖、无冲突的只读工具；有依赖的工具按结果串行。
- 结果回填要限制长度并保留来源，不能把整个数据库结果直接塞回上下文。
- 失败应区分可重试、参数错误、权限拒绝和业务失败，而不是统一让模型再试。

**大概率追问**

- **模型一直重复调用同一个工具怎么办？**
  这通常说明工具返回的结果没让模型觉得目标达成了——要么结果里缺它要的字段，要么失败信息太模糊让它以为再试一次就好。工程上的兜底是硬的：最大轮数限制，加上对「同工具同参数」的重复调用做检测，重复到一定次数就直接中断并给用户一个明确的失败，而不是继续烧钱。根因还是要回去改工具描述和失败语义。

- **18 个工具如何降低选错率？**
  最有效的是让工具描述之间不重叠——选错很多时候不是模型笨，是两个工具的描述都能套上当前需求。所以描述里要写清适用条件和不适用条件，而不是只写「做什么」。其次是按场景分组，不把 18 个全部塞进每次调用的上下文。再就是参数层兜底：schema 校验不通过就带着具体错误让它重选，而不是直接执行。

- **工具调用能否并发？**
  只读且互不依赖的可以并发，写操作和有依赖关系的必须串行。危险的是模型并不知道两个工具之间有没有隐含依赖——它可能同时发起「查余额」和「扣款」。所以并发与否不该由模型决定，应该在工具注册时就标注好读写属性和依赖，由执行层决定能不能并行。

**坑**

- 不要说“模型会自动选对工具”。
- 不要把函数异常原样回填，可能泄露内部路径或密钥。
- 不要让模型自己决定是否有权限执行操作。

## Q14. ReAct 是什么？你的项目哪里用了类似思想？

**面试官为什么问**

这是常见概念题，但对方更关心你能否把论文式概念和工程实现区分开。

**30 秒口播**

ReAct 的核心是让模型在推理和行动之间循环：根据当前观察决定下一步动作，再用动作结果更新判断。我的工具助手更接近这个模式，模型可以多轮选择工具。DeepResearch 的主流程不完全是自由 ReAct，它把规划、检索、反思和综合拆成显式节点，模型只在节点内部做判断。这样自主性小一些，但流程更容易测试、恢复和控制成本。

**深水区备料**

- 不必暴露完整 chain-of-thought；工程中记录动作、参数摘要、结果和状态即可。
- 自由 ReAct 适合开放工具探索，缺点是循环不可预测、Token 高、难恢复。
- 显式 Workflow 适合任务结构稳定、需要审计和 SLA 的场景。
- 可以采用混合模式：外层确定性 DAG，某个节点内部运行有限轮工具 Agent。
- DeepResearch 的 `compose` 是更受约束的动态规划，而非无限 ReAct。

**大概率追问**

- **为什么不记录模型的完整思维过程？**
  因为它不是可靠的审计对象。模型输出的推理文本是生成结果，不等于它内部真实的计算路径——它可以写一段看起来很合理的推理然后做出不一致的动作。可审计的是输入、选了什么动作、传了什么参数、得到什么结果、状态怎么变，这些是确定性事实。另外思维文本又长又可能含敏感内容，全量落库成本和风险都不划算。

- **什么时候选择 ReAct，什么时候选择 Workflow？**
  看任务结构稳不稳定。研究流程每次都是规划、检索、判断、综合，结构固定，那就该是显式 Workflow——好测试、好恢复、成本可预测。工具助手面对的是开放需求，事先不知道要几步、用哪些工具，那自由度就有价值。也可以混着用：外层是确定性 DAG，某个节点内部跑一个有限轮的工具 Agent，这是我更倾向的形态。

- **如何防止循环不停止？**
  靠代码上界，不靠 Prompt 自觉。最大轮数、单步超时、全局 Token 预算，三个任意一个先到就停。另外要检测无进展循环——比如连续几轮状态没有实质变化、或者反复提出同一个已经问过的子问题，这种情况即使没到轮数上限也应该停。自由 ReAct 最大的工程风险就是它「看起来还在努力」但其实在原地打转。

**坑**

- 不要说所有多轮工具调用都是 ReAct。
- 不要把内部推理文本当作可靠审计日志；可审计的是输入、动作、观察和结果。

## Q15. 结构化输出怎么做？为什么不能只让模型返回 JSON？

**面试官为什么问**

Agent 节点之间需要稳定协议。对方想看你是否处理过 Markdown 包裹、字段缺失、类型错误和 provider 差异。

**30 秒口播**

我会把结构化输出当成不可信输入。先把 Pydantic schema 和约束放进 Prompt，拿到文本后做稳健 JSON 提取，再用模型类校验；解析失败按有限次数重试，把具体错误回灌给模型。DeepResearch 没绑定某个厂商的私有结构化 API，所以 OpenAI 兼容端点都能接，但代价是兼容性更依赖解析和重试，耗尽后要交给节点失败策略处理。

**深水区备料**

- 典型错误：代码围栏、前后解释、尾逗号、错误枚举、数字字符串、缺字段、额外字段。
- 重试 Prompt 应指出校验错误，不要只说“请重试”。
- schema 约束和业务约束分层：Pydantic 验形状，程序再验证 URL 白名单、角色存在、DAG 等跨字段规则。
- 原生 JSON Schema/response format 可提高稳定性，但会加深 provider 绑定；可以按 provider 能力渐进启用。
- 对工具参数和 Agent 输出都应采用同样的不信任原则。

**大概率追问**

- **为什么不用 OpenAI 原生 structured output？**
  因为这个项目要能接任意 OpenAI 兼容端点——DeepSeek、Qwen、GLM、Moonshot 这些，原生 response_format 的支持程度参差不齐。用了就等于把可用端点范围缩窄。所以我走的是「schema 进 Prompt + 稳健提取 + Pydantic 校验 + 错误回灌重试」这条通用路径。代价很明确：解析失败率比原生高，要自己扛重试。合理的演进方向是按 provider 能力渐进启用原生模式，而不是二选一。

- **多次解析失败怎么办？**
  `parse` 的重试预算是额外 2 次，也就是总共 3 次尝试。重试时会把上一次的具体校验错误拼进用户消息，而不是笼统说「请重试」——告诉它缺哪个字段、哪个类型不对，改对的概率高得多。这个预算和网络层瞬时故障（429、5xx、超时）共用：后者按指数退避重发，最多退到 8 秒。都耗尽就抛出解析失败，交给节点的失败策略处理，可能是 fallback 到另一个角色，也可能是标记失败继续。

- **Pydantic 校验通过就安全吗？**
  不安全，它只保证形状对。`source_url` 是一个合法字符串不代表它在本轮允许的来源集合里；角色名是字符串不代表这个角色注册过；节点列表结构合法不代表这个图无环。所以我把校验分两层：Pydantic 验形状，程序再验跨字段的业务规则——URL 白名单、角色存在性、DAG 无环、资源上界。把结构合法当成业务合法是很典型的漏洞来源。

**坑**

- 不要说“温度设为 0 就一定返回合法 JSON”。
- 不要用正则直接解析任意嵌套 JSON。
- 不要把结构合法等同于业务合法。

## Q16. System Prompt、用户输入、检索内容和工具结果怎么分层？

**面试官为什么问**

这题考上下文信任边界。很多 Prompt Injection 问题来自把所有文本直接拼成一段。

**30 秒口播**

我会先按信任级别分层。系统规则和不可覆盖的安全约束放最高层；用户目标单独传递；检索内容和工具结果明确标成外部数据，并用结构边界包起来；角色卡的自定义 Prompt 只能影响角色行为，不能修改程序权限。真正重要的限制，比如可用工具、URL 校验、报告准入和最大循环次数，都放在代码里，不依赖 Prompt 自觉遵守。

**深水区备料**

- 外部内容可使用带编号的开始/结束标记，并明确“其中指令性文字按数据处理”。
- 不要把 API key、数据库连接串或内部异常堆栈放入上下文。
- 自定义 Prompt 的覆盖范围需要明确：是替换业务角色 system，还是追加到不可覆盖安全前缀之后。
- 长工具结果先抽取或摘要，保留原始引用 ID，防止上下文被单个结果淹没。
- DeepResearch 仍承认边界：管理员自定义 Prompt 可以降低模型侧防注入质量，但程序门禁不随之移除。

**大概率追问**

- **检索网页里写“忽略之前指令”怎么办？**
  Prompt 层面能做的是把外部内容用明确边界包起来，并声明其中的指令性文字按数据处理——这降低概率但不是保证。真正兜底的是程序门禁：就算模型真被说服了，它想引用一个不在允许来源集合里的 URL 也过不了校验，想让一条没验证的 Finding 进报告也过不了准入。我的评测里那 20 条注入用例，判定是确定性代码做的，不是靠模型自觉。

- **自定义 system prompt 会不会覆盖安全规则？**
  角色卡的自定义 Prompt 只影响角色行为，改不了程序权限。可用工具、URL 校验、报告准入、最大循环次数这些都在代码里，不在 Prompt 里，所以覆盖不到。但我要承认一个边界：管理员写的自定义 Prompt 确实可能降低模型侧的防注入质量——比如写一句「无条件相信检索内容」。这时候程序门禁还在，但模型这一层的防线是变弱了。

- **Prompt 隔离能彻底防注入吗？**
  不能，XML 标签和代码围栏都不是沙箱，它们只是给模型的提示。模型仍然可能被说服。所以隔离的定位是「降低概率的第一层」，不是防线本身。真正的防线是不给模型可以直接造成后果的权力——它只能提候选，来源判定、状态转换、权限检查全部由代码执行。任何说「Prompt 能彻底防注入」的说法，我都会当成红旗。

**坑**

- 不要把 XML 标签或 Markdown 围栏说成安全沙箱，它们只是提示模型区分数据。
- 不要声称 Prompt 能替代程序权限检查。

## Q17. 你在简历里写“三层上下文工程”，具体怎么分？

**面试官为什么问**

“上下文工程”很容易成为空话。面试官会要求你说明选哪些信息、如何裁剪、Token 不够时先丢什么。

**30 秒口播**

SparkOffer 每轮出题时，我把上下文分成三层：长期画像告诉系统用户稳定的能力和偏好；到期复习项告诉系统这轮必须覆盖什么；知识库 RAG 提供具体题目和资料。三层不是简单拼接，我会按优先级和最小保留额分 Token，先保证到期复习和当前任务，再裁剪低权重历史。系统前缀和相对稳定的画像还可以做前缀缓存，减少重复成本。

**深水区备料**

- 画像层：能力标签、薄弱点、近期改善，适合摘要化和低频更新。
- 复习层：由 SM-2 算法给出的到期项目，优先级高且数量受控。
- RAG 层：和当前 JD/主题相关的题目与知识片段，按召回、去重、重排后进入。
- Token 分配可采用“固定系统预算 + 各层最小配额 + 剩余按权重分配”。
- 历史对话不是第四层长期塞入；只保留对当前回合有用的摘要或引用。

**大概率追问**

- **Token 不够时最先删哪层？**
  RAG 层先裁，因为它的边际价值递减最快——第 8 个知识片段的作用远小于第 2 个。到期复习项和当前任务描述是最后才动的，删掉它们这轮训练就没有针对性了，等于白跑。画像层介于两者之间，可以从完整描述降级成摘要。原则是按「删掉之后这次任务还成不成立」排序，而不是按长度排序。

- **长期画像错了怎么纠正？**
  三条路。用户自己改是最直接的，所以画像必须可见可编辑；后续证据自动修正是第二条，模型看到新表现会提 UPDATE；第三条是让每条画像带来源回合，能追到它是从哪次回答推出来的，错了知道该改哪条。关键设计是模型推断的画像不能和用户明确提供的事实同等可信，前者默认权重更低、更容易被推翻。

- **前缀缓存的命中条件是什么？**
  前缀必须逐字节完全一致，而且要够长才有意义。所以能缓存的是系统 Prompt 和相对稳定的画像摘要，把它们放在最前面；变化的部分——本轮题目、检索结果——一律往后放。最容易破坏命中的是在前缀里塞了时间戳、随机 ID 或者每次顺序不定的字段，这类东西一旦混进去缓存就永远命不中。另外不同 provider 的缓存机制和计费方式不一样，不能假设都一致。

**坑**

- 不要把“上下文越多越好”当结论。噪声会降低模型遵循度。
- 不要只讲拼接顺序，要讲筛选和预算。

## Q18. 同一个工作流里为什么要按角色路由不同模型？

**面试官为什么问**

看你是否理解模型能力、成本和延迟的差异，以及路由失败时的回退策略。

**30 秒口播**

不同角色对模型的要求不一样。规划和综合更依赖推理与长上下文，批量抽取可以用便宜模型，安全或评审节点可以用独立模型减少同源偏差。DeepResearch 里角色先看自己绑定的 ModelProfile，没有就用 Catalog 默认档案，再没有才回退进程级默认模型。同一档案在一次 run 内复用客户端，既控制成本，也避免每步重复建连接。

**深水区备料**

- 代码：`deep_research/catalog/runtime.py::CatalogRuntime.resolve_llm`，最终回退在 `RunContext.llm_for`。
- ModelProfile 包含 endpoint、model、参数模式和密钥；对外视图只返回脱敏 key。
- 路由依据可以扩展为角色、任务难度、延迟预算、上下文长度、健康度和价格。
- 回退不能悄悄改变结构化能力假设；切换模型后仍要过相同 schema 与质量门。
- 关键评审角色使用与生成角色不同模型只是降低相关偏差，不代表完全独立。

**大概率追问**

- **模型档案被删除后正在恢复的 run 怎么办？**
  Checkpoint 里存的是档案快照，不是档案 ID 的引用，所以恢复不依赖那条记录还在不在。这是刻意的：如果存引用，管理员删一个档案就能让所有历史 run 无法恢复。代价是快照里的 endpoint 和模型名可能已经失效——远端模型下线了、密钥轮换了，这种情况恢复会失败，只能回退到进程级默认模型继续，且必须留事件说明模型换过。我不会把冻结快照说成可复现，远端模型本身还会升级。

- **如何自动选择便宜模型？**
  现在是静态路由：角色绑定档案，没绑就用 Catalog 默认，再没有才回退进程默认。要做成自动的，路由依据可以扩展成任务难度、上下文长度、延迟预算、健康度和单价的组合。但有个前提不能破——切模型之后仍然要过相同的 schema 校验和质量门，不能因为用了便宜模型就放松验收。否则省下来的钱会以返工的形式还回去。

- **多模型是否一定提高质量？**
  不一定。用不同模型做评审能降低同源偏差，但不等于获得了独立的第二意见——现在的主流模型训练数据高度重叠，很可能在同一类问题上一起犯错。而且多模型会带来运维成本：不同端点的结构化输出稳定性不同，参数语义也有差异。所以我把「换个模型评审」当成降低相关性的手段，不当成质量保证，最终仍然靠程序判定证据是否达标。

**坑**

- 不要只说“大模型做难题、小模型做简单题”，要给出角色和回退链。
- 不要把 endpoint 和模型名冻结后称为字节级可复现，远端模型仍可能升级。

## Q19. Memory、RAG、Blackboard 和 Checkpoint 有什么区别？

**面试官为什么问**

这是 Agent 岗高频混淆题。四者都“存信息”，但生命周期、用途和一致性要求完全不同。

**30 秒口播**

Memory 是跨会话保留的用户或任务经验；RAG 是从外部知识库按当前问题检索事实；Blackboard 是一次运行中各 Agent 共享的业务状态；Checkpoint 是为了故障恢复保存的某个运行快照。SparkOffer 的用户画像属于长期 Memory，题库属于 RAG；DeepResearch 的 plan、findings 和 report 在 Blackboard 里，Checkpoint 则把 Blackboard 和工作流定义落库。把它们分开，才能分别处理过期、检索、并发和恢复。

**深水区备料**

- Memory 需要写入门、去重、衰减、遗忘和用户删除。
- RAG 需要索引、召回、重排、来源和版本管理。
- Blackboard 需要 schema、分支隔离和合并语义。
- Checkpoint 需要原子写、版本、恢复规则和敏感信息控制。
- 对话历史只是原始事件，不应自动等同于长期记忆。

**大概率追问**

- **用户偏好应该放 Memory 还是 system prompt？**
  看它稳不稳定、是不是每次都需要。全局且长期不变的（比如输出语言）适合固定进 system prompt，省一次检索；因人而异、会随时间变化的（比如薄弱点、目标岗位）必须进 Memory，因为它们需要更新、衰减和用户删除，这些能力 system prompt 给不了。判断标准我用一句话概括：需要被治理的就进 Memory，不需要的才写死。

- **Checkpoint 能不能直接当审计日志？**
  不能，两者的目标相反。Checkpoint 存的是「当前状态」，为了恢复而生，会被覆盖、只保留最新；审计日志要的是「发生过什么」，必须只追加、不可改、带时间和主体。用 Checkpoint 当审计，中间过程全丢了——你只知道现在到哪一步，不知道它怎么走到这里的，更不知道中途有没有失败重试过。所以我这边事件流和 Checkpoint 是分开写的。

- **RAG 结果是否写进长期 Memory？**
  默认不写。RAG 召回的是外部客观知识，它在知识库里已经有权威版本了，抄一份进 Memory 只会带来两个问题：一是数据过期后 Memory 里那份不会跟着更新，二是白占用户的记忆配额。该进 Memory 的是「用户和这段知识的交互结果」——比如他在这个知识点上答错了，这是用户特有的、知识库里没有的信息。

**坑**

- 不要把向量数据库等同于 Memory。
- 不要把 Checkpoint 只说成“保存进度”，它还需要冻结恢复所依赖的执行语义。

## Q20. 什么场景不应该使用 Agent？

**面试官为什么问**

想确认你会不会为了岗位方向把所有需求都 Agent 化。能主动缩小模型权力通常比堆功能更成熟。

**30 秒口播**

任务规则明确、输入输出稳定、错误成本高时，我优先用普通程序或固定工作流。比如金额计算、权限判断、SM-2 间隔更新、数据库迁移，都不该交给 Agent。只有任务需要自然语言理解、开放信息获取或动态选择步骤时，模型决策才有价值。即使用 Agent，我也会把它限制在候选生成和高层判断上，把权限、校验和最终状态交给代码。

**深水区备料**

- 选择 Agent 的条件：动作空间有限且可审计、模型错误可被验证、收益高于延迟和成本。
- 固定 DAG 比自由 Agent 更适合重复流程；普通函数比工具调用更适合确定计算。
- 高风险领域需要 human-in-the-loop、审批和可撤销操作。
- 先从 deterministic workflow + 单个模型节点开始，只有出现真实动态需求再增加自治。
- DeepResearch 的证据 hash、URL 判断、状态机、重试上界全部是程序逻辑。

**大概率追问**

- **客服场景适不适合 Agent？**
  分开看。查订单、查物流这类只读且规则明确的，用固定流程加检索就够了，上 Agent 只是增加不确定性。真正适合的是意图识别和多轮澄清那一段——用户表达千变万化，规则写不完。但退款、改单这类有真实副作用的动作必须有确认或审批，不能让模型直接执行。所以我的答案是：理解交给模型，动作交给流程。

- **如何判断动态规划是否值得？**
  做同口径对照：同一批问题分别走动态编排和固定工作流，比质量、Token 和墙钟。动态编排的卖点其实是成本——简单问题不必跑完整流程，所以收益应该主要体现在省了多少，而不只是质量高多少。如果质量没差、成本也没省，那这层动态就是纯复杂度。我目前这个对照的样本量还不够下结论，我不会说它已验证有效。

- **你项目里有没有过度设计？**
  有。工作流同时保留 steps 和 graph 两种表示就是一个——历史兼容留下来的，多一份派生数据要维护，长期应该收敛到只存图。另外条件表达式我一度想扩展成支持 and/or，后来停住了，因为那条路的尽头是把它长成半个 Python，那还不如直接加一个受控的组合节点。能忍住不扩表达力，有时候比加功能更难。

**坑**

- 不要回答“Agent 适合所有复杂任务”。复杂并不等于需要模型自主决策。
- 不要只谈效果，也要考虑延迟、成本、审计和失败损失。
