# 检索档案、角色与提示词

## 从界面配置

1. 打开角色广场的“检索资源”，在 API Key 池选择渠道，添加一个或多个 Key。优先级数字越小越先使用；Key 可以改备注、调整优先级、更换或停用。
2. 内置 Tavily、Brave、Serper、Grok、OpenAlex、arXiv 档案可直接使用。需要隔离凭据时，复制为专属档案并勾选所用 Key；需要外接搜索模型时，新建档案并填写协议、完整端点和模型。
3. 在设置页选择“默认检索档案”。该页面不再重复保存搜索密钥。
4. 新建或编辑研究角色，默认继承全局检索档案；取消继承后可以选择一个或多个专属档案。角色卡片会显示绑定关系。
5. 在检索档案上测试服务。联网模型的测试同时检查引用和可获取的网页正文。新建角色后还需要在工作流中选择该角色，创建角色本身不会自动替换工作流节点。

## 配置优先级

| 层级 | 行为 |
| --- | --- |
| 角色的 `search_profile_ids` | 非空列表覆盖全局默认；`null` 表示继承。研究角色不接受空列表。 |
| 全局 `search_profile_ids` | 设置页保存的默认档案列表。 |
| 旧版 `search_backends` | 未选择默认档案时映射到相应内置档案，兼容已有配置。 |
| 内置档案的 Key | 使用同渠道的启用 Key，按优先级、创建时间排序；池为空时使用环境/兼容运行配置凭据。 |
| 自定义档案的 Key | 仅使用显式绑定的 Key，不自动借用其他档案、渠道或环境中的凭据。 |

多个档案并发检索并合并去重；同一档案的多个 Key 是主备关系。凭据/配额错误触发切换；协议错误不会被当作额度耗尽。全部凭据不可用时明确报错，不再尝试另一个隐藏的全局 Key。

内置档案使用 `builtin:tavily` 等稳定 ID。它们不需要迁移已有 Key 或生成重复凭据。自定义档案可以共享已选 Key，也可以使用完全独立的 Key 集合。

## 外接搜索模型

| 档案协议 | 请求与要求 |
| --- | --- |
| Responses 联网模型 | 完整端点，例如 `https://服务地址/v1/responses`；发送 `model`、`input`、`tools: [{type: "web_search"}]`。服务必须实现这个联网工具。 |
| Chat Completions 搜索模型 | 完整端点，例如 `https://服务地址/v1/chat/completions`；发送 `model`、`messages`。必须使用服务端自带联网能力的搜索模型。 |
| Grok Web Search | 内置 Responses 联网协议；专属档案可覆盖端点与搜索模型。 |

识别的引用结构包括 `citations`、`search_results`、Responses 输出 annotations、嵌套 `url_citation` 和 Chat 消息 annotations。普通聊天模型生成的正文或 Markdown 链接不会自动变成已验证来源。不支持以上协议或需要特殊请求参数的服务仍需增加对应适配器。

引用 URL 会由独立、无模型凭据的 HTTP 客户端获取原文。只读取公开 HTTPS 页面，检查重定向目标，限制并发、超时与正文体积。私有模型端点沿用项目的 `ALLOW_PRIVATE_PROVIDER_URLS` 配置；引用网页仍不允许访问私网。

模型生成的回答不作为网页原文。页面抓取失败、付费墙、二进制/PDF 或体积超限时保留引用 URL，但原文为空，不能通过逐字证据验证。PDF 专用全文能力仍由既有学术检索链提供。

角色的“模型档案”负责理解资料、提取事实等推理；“检索档案”负责获取资料。这两个模型可以不同，也可以指向同一个服务商，但职责和凭据绑定分别配置。

## 提示词

新角色默认 `append`：内置角色模板后追加领域与风格指令。旧角色迁移为 `replace`，保留原先替换角色模板的语义。

两种模式都会保留固定行为契约、全局规则及结构化输出要求。研究者的 URL、原文引用与数值校验由程序执行，不能通过替换提示词关闭。结构化补全仍使用 JSON Schema、Pydantic 校验及有限重试。

“预览最终提示词”由后端与运行共用的渲染函数生成，分别展示默认模板、固定契约、全局规则及基础 system prompt。具体任务执行时仍会加入当前问题、来源、前序结果和适用的工作流上下文；预览不冒充某次尚未运行请求的完整记录。

自定义指令最多 8000 字符。修改指令不会改变行为模板对应的执行逻辑，也不会自动授予网络、文件或命令执行能力。

## 运行、恢复与迁移

- 新运行保存角色绑定、提示词模式、检索端点与模型、默认档案以及按优先级排序的 Key ID。checkpoint 不保存密钥。
- 恢复使用冻结的档案定义和顺序，不采用后来修改的角色、端点或默认选择。仍从凭据库读取当前密钥，支持轮换与撤销；已删除、渠道改变或全部停用的凭据明确失败。
- 专属检索与默认检索都经过同一个来源快照记录器和证据验证流程。事件记录角色名与所选档案 ID。
- 显式注入 `SearchTool` 的 Python 集成仍可替换默认检索；角色的专属绑定继续优先生效。
- 旧 checkpoint 没有保存的检索信息无法追溯恢复，兼容加载会使用旧 `search_backends` 配置；不会把后来选择的新档案默认为旧任务的原始配置。
- Alembic `0024` 给旧 Key 标记 Tavily；`0025` 增加检索档案表和角色配置字段。已有 Key 值、优先级及角色提示词不重写。后端正常启动时运行现有的升级流程。
- 前端旧搜索密钥 API 字段仍保留兼容，环境变量也继续有效；新界面统一从角色广场维护凭据。密钥加密沿用已有 `CATALOG_ENCRYPTION_KEY` 配置。

## 验证边界

协议和运行路由使用模拟服务验证，数据库升级在临时 SQLite 数据库上验证；没有使用用户真实 Key 发起付费请求。生产 PostgreSQL、第三方服务账号额度及真实端点连通性仍需在对应部署中验证。

## 运行前可靠性检查

新建研究页的“检查角色与检索配置”只读取当前工作流、角色卡片、检索档案和启用 Key，不会发起联网请求；它会列出每个角色实际使用的模型与检索档案，并在缺少凭据时阻止提交。档案和 Key 管理区显示使用位置，停用前可看到受影响的角色或默认配置。最终端点连通性、引用正文和额度仍应使用“测试档案”，因为预检不会产生付费请求。

同一 URL 被多个检索档案返回时，系统保留配置顺序优先的可用正文，并在运行事件中记录内容变体哈希；一个渠道失败不会掩盖其他渠道结果。Key 池会按 HTTP `Retry-After` 或渠道错误进入临时冷却，并限制同一凭据的并发请求；健康状态只在同一进程/事件循环内共享，worker 多进程需要各自观测。
