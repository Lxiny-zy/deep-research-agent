# 场景实现与交付质量审计

日期：2026-10-04。只读审计：打开已保存的真实样本产物、原始论文和数据独立核对，阅读代码，
运行离线测试和临时探针；没有新增模型调用，没有修改代码。对照当时场景验收计划中的“必须交付的结果”
和“质量通过标准”（现并入 [后续改进计划](IMPROVEMENT_PLAN.md) 第 3 节）。

## 结论

- **实现**：八类场景的链路（输入、执行、质量门、交付、恢复）都已接通，相关离线测试通过，
  均判为“基本健全但有缺口”。缺口主要不在流程，而在质量门：不少场景专属要求只写在提示词里，
  或检查方式过窄，错误内容能通过全部门禁。
- **产物**：文件可打开，各格式内容一致，逐字引文能在原文找到，抄录的数值基本准确。但推理层面
  的错误——公式写反、比较口径反转、把原文写明的内容说成“未给出”、过度断言——以及用户点名
  内容的缺失，都没有被拦下。整体尚不满足“内容真实可信、论据充分有出处”的要求。
- **证据基础薄**：每类只有 1–2 个真实样本，大多是首次失败后的恢复。sc54、sc60、sc72 的恢复
  由验收脚本驱动，不是产品路径。多数样本早于 10-04 的完成契约，没有按新契约复核。

## 质量门缺口

以下均已在代码中确认，或用临时探针复现：

- **幻灯片**：空备注被渲染为“（无备注）”并计为有备注（`workbench/delivery/pptx.py:373`、
  `:398-405`），备注检查永远不会触发。溢出检查在分页之后进行、阈值与分页相同，也不会报警。
  讲稿固定为 2–4 句，不读汇报时长。渲染器没有插入图表的路径。
- **思维导图**：去重只查同一父节点下完全相同的标签（`workbench/mindmap_contract.py:59-62`）；
  关系只查是否为空；标签只有 240 字上限；PNG 只拒绝边长超过 30,000 像素的图。
- **同行评审**：`review` 门只检查是否给出 1–10 分（`workbench/gates.py:178-182`）；缺陷分级只
  写在提示里；没有方法覆盖检查；正文退化为摘录时仍会追加评分。
- **文献综述与精读**：
  - 覆盖是否充分完全由模型判定；“未给出”“缺陷”类断言不回查全文。
  - 交付表格由模型直接写成 Markdown（`workbench/writers.py:57`）。代码透视表和“未报告”约定
    只存在于旧报告导出链路（`report/assemble.py` → `report/pivot.py`），且只对带结构化实体
    的发现生效。
  - 行内公式、书目、公式与原文是否一致、用户点名的主题，都没有门禁。
  - 整个片段可以当作“逐字引文”，sc60 有 4 条超过 3,000 字。
- **PDF 章节解析**：重解析 DAUHST 时，Introduction 吞掉了第 2 章方法，表头“Method”被当成
  章节，参考文献并入结论（`tools/oa_pdf_fulltext.py:165-189`）。
- **问答**：
  - 机械问题和断言问题共用 2 轮修订，断言核验要等机械检查通过后才做
    （`workbench/qa.py:484-557`）；不保留最好的一版，失败时整答降级。
  - 产品里没有“继续修订回答”的入口，未通过稿只被验收脚本读取。
  - 绑定任务的问答要求有论文原文（`workbench/qa_api.py:402`），开放研究无法基于已核验发现
    追问。
  - 降级输出不经模态规则核验，sc82 的降级回答仍包含被拒的断言。
- **研究**：
  - 发现级核验缺少模态规则。
  - 只检查依据在引用范围内，不检查依据是否对应该句。
  - 写作步骤没有中间检查点，sc82 恢复时首轮写作约 23 万 token 作废。
  - 只读到摘要的关键来源没有在报告中披露。
- **数据分析**：
  - 配对判断靠正则（`workbench/analysis.py:423-428`），问题里出现“成对删除”或“同一批样本”，
    就会把物种比较换成两列不同单位的配对 t 检验。
  - 分组样本量拦截只认特定句式，“各组 n=151”可以通过；数值检查只看是否出现在台账里，两组
    均值对调也能通过。
  - 缺前提检验、Welch 方法、事后比较、分层相关和异常值/哨兵值检测。“?” 会让整个任务失败，
    且提示错误；重复测量和多表没有支持。
- **完成判定**：任何门禁不是 pass（包括文体告警）都进入待复核（`workbench/completion.py:153-155`）。
  按当前首次通过率，部署后多数任务可能停在待复核。

## 对后续计划的影响

1. 在新增真实任务之前，先修“错误内容能通过门禁”的问题；否则新样本只会产生更多假通过，
   且一次研究任务约耗 150 万 token。
2. 问答收敛优先级应前移：线上问答记录 fallback 8 条、done 4 条，而问答是最高频的交互入口。
3. 部署 `2b204ea` 前须决定哪些告警阻止完成，并在进入待复核前先自动定向修复。
4. 真实验收改为按产品路径运行：每类至少 2–3 个新输入，记录新契约下的首次结果；
   脚本驱动的恢复单独标注，不计入产品可用性。
5. 生产双 worker 需要先核定资源：部署日志显示主机约 1.8 GB 内存，swap 已用 0.5–0.76 GB；
   而 compose 默认上限为 API 2g、每个 worker 2g、数据库 1g。

本审计依据的样本数量少，结论只说明当前样本暴露的问题，不代表全部输入。
