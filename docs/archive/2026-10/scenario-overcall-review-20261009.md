# 其他任务场景的过度调用与过分谨慎审查

这是优化前的审查记录。2026-10-10 已完成相应代码优化与回归验证，当前实现见[优化说明](scenario-overcall-optimization-20261010.md)；本文的探针及调用数据对应其保存的优化前源码指纹。

日期：2026-10-09。

**结论：仍有同类问题，主要集中在返工不收敛、局部失败扩大为整篇处理、逐段触发全文检查，以及轻量任务沿用统一质量流程。** 本次直接问答分流解决了普通问答和论文追问的默认路径；其他任务的执行链没有随之整体变轻。

本次以当前本地工作区为准：`HEAD=ed97c2772fac0e9540541cd4398ad27e5f193e56`，包含最新的直接问答、模型调度等未提交修改。检查覆盖工作台调研、综述、精读、审稿、幻灯片、思维导图、数据分析及公共终稿检查。没有连接实验室服务器或验证远端部署，也没有修改业务代码。

这里把“过度调用”限定为可以避免的重复生成、重复判定或必然被丢弃的工作；“过分谨慎”指局部问题影响超出必要范围，或任务强度未随用户目标调整。正式科研任务中的事实核验本身有必要。

## 1. 高优先级：返工只看次数，缺少内容层面的停止条件

影响：工作台调研、综述、精读、审稿、幻灯片、思维导图和数据分析的写作循环。

[`write_with_revisions`](../deep_research/workbench/revision.py#L288) 默认允许首稿加两轮修订。其[停止条件](../deep_research/workbench/revision.py#L316)是检查通过、不可修订或次数耗尽，没有检查“正文是否与上一版相同”“同一组问题是否持续没有改善”。它会保留问题最少的一版，但保留最佳版本并不会阻止后续无效调用。

**离线复现：** 写作者连续返回完全相同的正文，检查器连续返回同一个可修订问题，最终仍执行 **3 次写作、3 次评估**。

此外还有一层独立的[交付前自动修复](../deep_research/workbench/completion_repair.py#L90)。因此，`max_revisions` 当前控制的是写作者内部循环，不能视为整个任务的返工上限。

**离线复现：** `max_revisions=0` 时，带有可修复正文问题的任务仍发生 **2 次正文生成**，其中一次来自交付前修复。修复仍失败后才进入 `needs_review`。这个行为也被现有[回归测试](../tests/test_completion_auto_repair.py#L27)明确保留，属于当前策略，不是偶然的网络重试。

默认两轮写作修订与一次交付前修复可以叠加；局部编辑、核验、协议重试又各自消耗请求。因此，“最多两次返工”无法直接说明整次任务的调用成本。

**建议：** 在正文及证据均未变化时立即停止重复修订；对持续相同的问题增加无进展判断。写作循环与交付前修复共用任务级修订额度，并明确提供“禁止自动修订”的配置语义。

## 2. 高优先级：局部问题仍会升级为整篇生成

影响：长篇调研、综述、精读、审稿，尤其是幻灯片和数据分析报告。

通用写作者已经支持按段落修订，但[局部编辑抛出普通异常后](../deep_research/workbench/writers.py#L363)，仍会继续调用完整写作方法，重新生成正文。直接问答及严格问答最近收紧的局部修订边界，并没有统一覆盖这里。

**离线复现：** 一个段落需要修改，局部编辑失败后，共发生 **2 次完整正文生成、1 次局部编辑尝试、2 次正文评估**。探针中的编辑异常由替身直接产生；真实编辑若已请求模型，该请求还要另计。

两种交付物的粒度更粗：

- **幻灯片：** [通用局部修订明确排除 slides](../deep_research/workbench/writers.py#L442)，[`SlideWriter.write`](../deep_research/workbench/writers.py#L1141)每次请求整个 `SlideDeck`。单页事实或备注问题也可能重生成整份演示稿。
- **数据分析：** [修订回调](../deep_research/workbench/analysis.py#L1224)继续完整生成报告，尚无对应的段落编辑分支。

表格问题和需求覆盖问题也会[关闭段落修订](../deep_research/workbench/writers.py#L466)。其中确实存在需要调整整体结构的情况，但当前处理粒度没有进一步区分单个表格、单页内容和全文结构。

**建议：** 给幻灯片建立按页、要点、讲稿的编辑接口，给数据报告复用段落编辑。局部编辑失败后优先保留已有正文及问题记录；只有确认需要改变整体结构，且仍有共同预算时，才升级为整篇生成。

执行权丢失、预算耗尽和写作进度错误已有专门的中止处理，本次没有把这些分支误判为必然触发完整重写。

## 3. 高优先级：全文核验按段落串行触发，建议也要先付出判定成本

影响：同行评审最明显；也涉及精读、综述中的缺失断言，以及带引用的导图问题。

[`requires_fulltext`](../deep_research/workbench/fulltext_review.py#L36)除了识别明确的缺失断言，还会根据“不足、缺点、缺陷、weakness、limitation”等章节上下文触发检查；带引用的 `question` 单元也会触发。

[`SupportReviewer.review`](../deep_research/workbench/support.py#L453)逐个处理单元。每个命中的单元先通过模型[判断核验目标](../deep_research/workbench/fulltext_review.py#L283)，必要时再分批扫描原文，之后还有引用支持核验。相同文献下的多条意见没有在这个入口合并为一次目标判定。

**离线复现：** “不足”章节中的 **6 条纯建议**，模型最终全部判为非事实性内容，却仍发生 **6 次 `FullTextTarget` 判定 + 1 次支持核验，共 7 次模型逻辑调用**。原样再次检查时新增调用为 **0**，说明缓存有效；首次逐段判定的开销仍然存在。

还有一处需要细分的保守边界：[事实性批评也要求完整覆盖所评价文献](../deep_research/workbench/fulltext_review.py#L409)。探针中已找到支持批评的原文，来源不完整时仍返回 `uncertain`；换成完整来源才通过。对一份较长的完整材料，首段已有支持证据，仍进行了 **1 次目标判定 + 5 次原文批次检查**。

“整篇论文缺少某项实验”需要完整文本核对，这个要求合理。优化空间在于进一步区分：原文明示的局限、范围有限的事实陈述、对全文的缺失判断、纯建议。当前这些内容容易进入同一条较重的入口。

**建议：** 合并同一文献下多个单元的目标判定和原文读取；将来源版本、命题及评价范围作为复用依据。全文缺失判断继续要求完整覆盖，范围有限的陈述则绑定对应证据和限定条件。纯建议的判定尽量并入现有批次。

## 4. 高优先级：数据分析会先生成已经注定被替换的正文

影响：同一受试者多次测量、同一场景下多种方法等重复观测数据。

统计阶段已经能够[识别重复观测](../deep_research/workbench/analysis_inputs.py#L37)，并明确保留描述统计、停止不受支持的推断检验。这些信息在[正文生成之前](../deep_research/workbench/analysis.py#L1115)就已存在。

但执行仍继续经过正文生成与质量检查；到[最终处理阶段](../deep_research/workbench/analysis.py#L1340)，只要结果含“检测到重复测量”提示，就无条件用统计摘要替换正文。随后又对[替换后的正文执行核验](../deep_research/workbench/analysis.py#L1375)。

**离线复现：** 用户只要求描述统计，数据准备已识别重复观测；在让正文评估通过的受控条件下，仍发生 **1 次完整正文生成、2 次正文核验入口调用**，生成的描述性说明最终被替换。这里的 2 次是核验方法调用数，不等同于固定 2 次模型请求。

不把重复观测当作独立样本，是正确的统计约束。当前问题是这个约束还导致了可避免的生成工作，并使纯描述任务也整篇回退。

**建议：** 在统计结果产生后决定交付路径。对于描述统计任务，保留合格正文并附加确定性的推断限制说明；如果已决定只能交付统计摘要，就直接生成摘要，省去必然被替换的自由正文。

## 5. 中优先级：单个终稿引用问题仍可能替换整份正文

影响：使用公共终稿检查的报告类任务。

[`validate_body`](../deep_research/report/validation.py#L260)在终态默认模式下，只要存在问题就替换整个正文。前面的修订循环能降低触发概率，但修订未完成、预算耗尽或最终仍有机械错误时，这个行为仍然存在。

**离线复现：** 两个正常引用的段落后增加一个不存在的 `[99]`，唯一问题为 `invalid_citation`，最终正文中的“分析”和“结论”章节都被素材摘要替换。

通用写作者会[保存未获批准的原稿](../deep_research/workbench/writers.py#L662)，因此不能把它描述为原稿永久丢失。不过，用户主交付中的论述和结构确实整体退化了。

**建议：** 按错误影响范围处理：能定位到独立段落的错误，隔离该段并保留已核验部分；引用映射整体失效等全局问题再使用整篇回退。移除错误引用时必须一并处理其事实断言，不能留下失去依据的陈述。

## 6. 中优先级：轻量档和调用预算尚未覆盖整条执行链

影响：快速调研、快速综述、简短汇报、概念导图、小规模数据分析。

[`TierSpec`](../deep_research/workbench/tiers.py#L16)及其[覆盖参数](../deep_research/workbench/tiers.py#L55)只调整子问题数、反思轮数、每次检索结果数。`quick` 工作流会减少检索后的补洞环节，但写作质量策略仍使用统一的、默认偏严格的 [`QualityPolicy`](../deep_research/workbench/quality.py#L38)。

因此，选择轻量或快速可以减少检索工作，却不意味着减少后续全文检查、支持核验和修订轮数。对简短解释或小型交付物，这种差异会直接影响使用体验。

当前生产代码中，`ModelCallBudget` 的实例化入口位于 [QA API](../deep_research/workbench/qa_api.py#L373)，报告任务没有对应的整次模型请求额度。报告任务已有阶段轮数、[超时](../deep_research/execution_policy.py#L37)和恢复次数约束，缺的是累计请求数与跨阶段修订额度；不能把它们描述为完全没有执行边界。旧 [`max_tokens`](../deep_research/config.py#L173)字段也已经明确不再用于执行限额。

**建议：** 将检索深度与交付核验强度分别建模，按任务目标选择适当策略；再加入所有角色、模型检索及 HTTP 重试共同消耗的请求额度，并为最终交付预留额度。具体数值应通过真实任务测量确定，本次不推算统一的节省比例或延迟。

## 各场景的判断

| 场景 | 当前判断 | 最值得处理的部分 |
| --- | --- | --- |
| 普通问答、论文追问 | 默认直接回答路径已修正 | 保持 direct / verified 的明确边界 |
| 课题调研、文献综述 | 仍有过度调用风险，快速档也会遇到 | 无进展返工、两层修订额度、局部失败整篇生成 |
| 论文精读报告 | 核验有必要，局部失效的影响仍偏大 | 缺失断言核验、局部修订失败、整篇摘要回退 |
| 同行评审 | 全文核验的调用放大最明显 | 按意见批量处理，区分建议、原文局限与全文缺失判断 |
| 幻灯片 | 单页问题处理粒度偏粗 | 按页和讲稿修订，复用其余已核验页面 |
| 思维导图 | 已有节点编辑，问句核验仍可能较重 | 带引用问题的全文判定；需求覆盖失败后的整体重写 |
| 数据分析 | 有明确可避免的生成工作 | 提前处理注定回退的结果，保留合格描述统计正文 |
| 重连、恢复、重新导出 | 本次未发现普遍重新生成的同类问题 | 保持已有阶段记录、内容版本和纯渲染重试边界 |

思维导图已有[节点局部修订](../deep_research/workbench/writers.py#L1403)，不应与幻灯片一概视为每次重生成全图；但需要重做需求覆盖时仍会走完整写作分支。

## 最新代码中已经有效的优化

以下内容应保留，不能仅因代码中出现多个检查入口就认定为重复模型调用：

- **普通问答分流：** [`qa_direct.py`](../deep_research/workbench/qa_direct.py#L23)已有更紧的调用上限；严格核验是显式模式。
- **终稿缓存：** [`ProseReviewer.review`](../deep_research/workbench/prose_review.py#L534)可复用相同正文的记录，增加代码生成的参考文献不会自动重核验正文；需求覆盖也有自己的缓存。
- **公式本地比对：** [`FormulaReviewer`](../deep_research/workbench/formula_review.py#L369)已对可确定的公式结构做本地处理，仅未解决的情况请求模型。
- **文体建议降级：** [`assess_draft`](../deep_research/workbench/revision.py#L188)已避免单纯文体建议消耗正文返工额度。
- **材料与引用边界：** 固定材料任务跳过无下游用途的检索实体抽取；[写作引用下限](../deep_research/workbench/revision.py#L158)按可用来源调整；[表格核验](../deep_research/workbench/tables.py#L600)会复用未变单元。

这些优化能减少重复请求，但不能自动消除本次确认的首次调用成本、返工额度叠加和整体回退问题。

## 验证范围与改动顺序

新增了可重复运行的[离线探针](../artifacts/scenario-overcall-review-20261009/probe.py)，七项检查全部通过。另运行了 **74 项针对性回归，全部通过**，覆盖局部修订恢复、全文核验、公式核验、交付前修复和固定材料角色路由。结果、执行目标和源码 SHA-256 保存在[验证记录](../artifacts/scenario-overcall-review-20261009/validation.json)。

探针使用模型替身；数据分析探针还使用受控的通过型核验器，以单独检验确定性的最终回退分支。它们证明了当前控制流程和调用边界，没有测量真实模型的语义误判率、线上延迟或费用。现有回归通过也不代表调用策略已经合理，其中一些测试正是在保证上述现行策略。

建议下一轮按以下顺序改动：

1. **统一收敛与额度：** 相同正文停止返工，写作和交付前修复共用额度，明确零自动修订的含义。
2. **移除注定无用的工作：** 数据分析在写作前确定可交付范围与回退路径。
3. **缩小修改和降级范围：** 增加幻灯片、数据报告的局部修订，避免独立段落错误影响整份交付。
4. **合并全文核验：** 按文献和命题范围批量处理，保留真实全文缺失判断所需的完整性检查。
5. **补全场景策略和观测：** 分开检索深度、核验强度和总调用额度，记录每一阶段的请求次数、耗时、重试原因和有效修订比例。

优先处理这些控制流程，能够让模型请求更直接地服务于最终交付，同时保留必要的证据与统计约束。
