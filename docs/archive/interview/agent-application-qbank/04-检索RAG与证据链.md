# 04 检索 RAG 与证据链（10 题）

## Q31. 讲一下 SparkOffer 的 RAG 完整链路

**面试官为什么问**

简历给出了 Hit@K、MRR 和延迟。对方会先确认数据从文档进入索引，再从 query 走到上下文的全过程。

**30 秒口播**

文档侧先按内容哈希判断是否变化，只对新增或变更文档做切分和向量化，写入通过后台队列异步完成。查询侧会根据薄弱点把请求拆成多路并发查询，分别召回后用 RRF 融合，再做 0.85 语义去重和 Rerank，最后按上下文预算选片段。评测不是只看最终回答，而是先在 55 例人工相关性集上测 Hit@K、MRR 和 P50，确认检索本身没有被生成结果掩盖。

**深水区备料**

- 文档链：版本/内容 hash → chunk → embedding → Qdrant upsert；删除或更新要同步处理旧向量。
- 查询链：薄弱点/主题 → query rewrite 或 multi-query → 并发召回 → RRF → 语义去重 → rerank → Token 裁剪。
- 后台队列把上传响应和 embedding 计算解耦，但需要任务状态、失败重试和幂等文档 ID。
- 召回评测真值来自 55 例人工标注；Hit@K 看是否命中，MRR 对首个相关结果位置更敏感。
- 当前仓库没有 SparkOffer 源码，函数名和具体基础设施只按真实项目回答。

**大概率追问**

- **为什么先融合再 Rerank？**
  成本考虑。多路召回的候选里重复很多，先 RRF 融合再去重能把送进 Reranker 的候选数压下来，而 Rerank 是这条链上单位成本最高的一步。反过来先精排也能跑通，只是要为重复内容白付算力，具体顺序取决于候选规模和 rerank 单价。

- **chunk 大小如何确定？**
  没有通用答案，要在「片段够完整能独立回答问题」和「够小不稀释语义」之间试。方法上应该拿标注集扫几档大小和重叠比例，看 Hit@K 和 MRR 怎么变，而不是凭感觉定。具体用的参数得以 SparkOffer 仓库为准，我不凭记忆报数字。

- **文档更新后如何删除旧 chunk？**
  关键是 chunk ID 要可推导——由文档 ID、版本和分片位置组成，这样才能定位到该删哪些向量。安全的顺序是先写新版本、再切换可见版本、最后清理旧向量，避免中间出现检索空窗。如果删除和写入不在一个事务里，还需要补偿任务兜底孤儿向量。

**坑**

- 不要把向量检索直接等同于 RAG。
- 不要只讲模型生成，检索链路必须能单独评测。
- 不要编造 SparkOffer 的 chunk 长度、embedding 型号或队列实现。

## Q32. 为什么要做多路查询和并发召回？

**面试官为什么问**

想看你是否理解用户表达与知识库措辞不一致的问题，以及并发带来的成本和重复结果。

**30 秒口播**

一条用户 query 往往同时包含主题、薄弱点和具体约束，用单一检索式容易只覆盖一种表述。我会把它改写成几条互补查询，例如概念、场景和易错点，再并发召回。这样能提高召回，但不是越多越好，查询数要有限，并在后面做融合和去重，否则只会增加延迟、重复和向量库压力。

**深水区备料**

- 多路查询来源：规则模板、LLM rewrite、用户画像标签、同义词或实体扩展。
- 并发适合各路独立检索；通过连接池和 Semaphore 限制对 Qdrant/搜索服务的压力。
- 查询改写需要保留原始实体和硬约束，防止 LLM 扩写后语义漂移。
- 可以给原始 query 更高权重，避免改写完全替代用户表达。
- 评估时要比较 single-query 与 multi-query 的召回增益、P95 和调用成本。

**大概率追问**

- **查询改写本身用 LLM 会不会更慢？**
  会增加一次调用的延迟，所以不该所有请求都改写。可以先用规则模板和画像标签生成互补查询，只有复杂或表述模糊的请求才让模型改写。判断值不值得看的是改写带来的召回增益能不能抵掉那几百毫秒。

- **多路召回结果如何融合？**
  用 RRF 按名次融合，因为不同查询路的原始分数尺度不可比，直接加权相加会被某一路的分布带偏。融合后再做语义去重和精排。如果某几路明显更可信，可以给它们更高权重做 weighted RRF。

- **如何防止改写跑题？**
  改写时必须保留原始 query 里的实体和硬约束，比如时间范围、公司名、版本号，这些丢了就是另一个问题了。工程上的兜底是保留原始 query 单独作为一路，并给它更高权重，这样即使改写全跑偏，原始表述那一路还在。

**坑**

- 不要把“并发”说成免费，QPS 和连接数都会增加。
- 不要只报召回提升，不看延迟和重复率。

## Q33. RRF 是什么？为什么设置 `k=60`？

**面试官为什么问**

简历明确写了 RRF。对方通常会要求公式，并追问为什么不用原始相似度直接加权。

**30 秒口播**

RRF 是按排名融合多个结果列表，对文档的分数是各列表里 `1 / (k + rank)` 的累加。它不要求不同检索器的原始分数可比，所以适合融合多条 query 或稀疏、稠密检索。`k=60` 是常见的平滑参数，让前几名有优势，但不会让第一名把其他列表的共同信号完全压掉。这个值不是理论最优，应该在标注集上做敏感性验证。

**深水区备料**

- 例子：同一文档在两路分别排第 2、第 5，得分为 `1/(60+2)+1/(60+5)`。
- 优点：简单、稳健、不需要校准 BM25 与 cosine 的分数尺度。
- 缺点：忽略原始得分差距和查询质量；多个低质量列表也可能累计推高噪声。
- 可以对不同 query/检索器增加权重，形成 weighted RRF。
- `k` 越小越强调头部，越大越平滑；应关注 Hit@K/MRR 以及结果多样性。

**大概率追问**

- **RRF 和加权分数融合哪个好？**
  看分数可不可比。如果几路检索器的分数经过校准、尺度一致，加权融合能利用分差信息，理论上更精细；但 BM25 和 cosine 这类天然不可比，硬加权就是在拍系数。RRF 只用名次，牺牲了分差信息换来稳健，这也是它的主要缺点。

- **如果文档只在一路出现怎么办？**
  它只累加到一份 `1/(k+rank)`，天然弱于多路都命中的文档，这正是 RRF 想要的效果——多路共同认可是一种投票信号。风险是某些确实只有单一来源能召回的重要文档会被压下去，所以不能只看融合后的头部，必要时给特定检索路加权。

- **为什么不直接让 Reranker 排全部结果？**
  因为 Reranker 通常是 cross-encoder，要对每个候选和 query 做一次前向，成本随候选数线性涨。几百个候选全排一遍，延迟和费用都不划算。所以先用便宜的召回和融合把候选压到几十个量级，再让它精排。

**坑**

- 不要只背“RRF 能提高召回”，必须能写出公式。
- 不要把 `k=60` 说成固定标准答案。

## Q34. 语义去重和 Rerank 分别解决什么问题？顺序为什么这样安排？

**面试官为什么问**

多路召回后重复结果很多。对方会检查你是否理解去重、相关性重排和来源多样性的区别。

**30 秒口播**

语义去重解决的是多条 query 把同一内容召回很多次，Rerank 解决的是初始召回排序不够贴合当前问题。我先融合，再用 0.85 相似阈值合并近重复片段，减少送给 Reranker 的候选数；然后让 Reranker 在去重后的候选里做精排。去重不能只看文本相似，还要保留文档 ID 和来源，避免把不同来源的独立证据误合并。

**深水区备料**

- 去重可结合文档 ID、chunk overlap、归一化文本和 embedding cosine。
- 0.85 是项目阈值，不应称为通用最佳值；要在重复率与误合并率之间校准。
- Reranker 可以是 cross-encoder 或 LLM，但要限制候选数量控制成本。
- 检索相关性与来源独立性是两回事：相似内容可以都保留其 publisher 元数据用于交叉印证。
- 先 Rerank 后去重也可行，但会浪费算力；具体顺序由候选规模和模型成本决定。

**大概率追问**

- **0.85 怎么选？**
  在重复率和误合并率之间校准出来的，不是通用最佳值。阈值调低了会把讲同一主题但结论不同的片段错误合并，调高了去重就形同虚设。校准方式是拿标注集看不同阈值下有多少真重复被合并、多少独立内容被误伤。

- **两段文本很像但结论相反怎么办？**
  这正是纯相似度去重最危险的地方——「营收增长」和「营收未增长」在向量空间里可能非常近。所以去重不能只看相似度，要保留文档 ID 和来源元数据，来自不同来源的片段即使很像也不该合并。在 DeepResearch 那边，这类情况是靠跨论断矛盾标记来暴露的，而不是靠去重。

- **Reranker 失败时如何降级？**
  退回融合后的排序直接截断，宁可排序差一点也不要整条检索链断掉——检索是可降级能力，不是安全门禁。但降级必须留事件，否则线上质量下降了没人知道原因。

**坑**

- 不要把相似文本直接当同一事实。
- 不要在去重时丢掉来源和版本信息。

## Q35. 为什么用内容哈希做增量向量化？

**面试官为什么问**

考索引更新、幂等和成本控制。全量重建在演示数据上可行，真实知识库会很浪费。

**30 秒口播**

文件名和更新时间都不可靠，真正决定是否需要重建的是内容是否变化。我会对规范化后的文档内容计算 hash，和数据库记录比较；未变化就跳过 embedding，变化时生成新版本并替换旧 chunk。这样重复上传是幂等的，也能把向量化成本压到变更部分。后台任务还要用稳定的文档和 chunk ID，避免重试产生重复向量。

**深水区备料**

- hash 前要确定规范化规则，避免换行或元数据顺序导致无意义重建。
- 文档更新需要“写新版本 → 切换可见版本 → 删除旧向量”或事务外补偿，防止索引空窗。
- chunk ID 可由 `doc_id + version + chunk_index/content_hash` 组成。
- 失败重试必须 upsert，而不是盲目 insert。
- DeepResearch 也保存来源内容 hash，但用途不同：它用于证明证据校验时看到的网页快照，而不是知识库增量索引。

**大概率追问**

- **文档只改一段，能否只重算受影响 chunk？**
  可以，但前提是切分策略稳定——如果 chunk 边界随内容漂移，改一句话可能让后面所有分片全部错位，那就退化成全量重建了。可行的做法是按结构切分（章节、段落）让边界锚定在语义位置上，再对每个 chunk 单独算哈希比对。这比整文档哈希省，但实现复杂度也更高。

- **如何处理删除文档？**
  主表标删除的同时必须清向量索引，否则会出现「文档已删但检索还能召回」的幽灵结果，这在权限场景下是事故。所以需要稳定的 chunk ID 才能定位删除，不能靠文本匹配。异步索引和备份会让「删干净了」这件事变复杂，需要定义软删和硬删的边界。

- **hash 冲突需要担心吗？**
  SHA-256 级别的碰撞概率在工程上可以忽略，不值得为它设计防御。真正要担心的是另一头——规范化规则没定好，导致换行、空格或者元数据顺序变了就算内容变了，白白触发大量无意义重建。这个比碰撞常见得多。

**坑**

- 不要把 SparkOffer 的索引 hash 和 DeepResearch 的证据 hash 混为同一设计。
- 不要忽略旧向量清理和任务重试幂等。

## Q36. Hit@K、MRR 和 P50 分别说明什么？

**面试官为什么问**

简历写了具体指标，通常会被要求解释计算方式、数据集和为什么这些指标足够或不够。

**30 秒口播**

Hit@K 看前 K 个结果里有没有至少一个相关文档，适合衡量能不能召回；MRR 看第一个相关结果出现得多靠前，对排序更敏感；P50 是一半请求的检索延迟不超过这个值。我的 55 例人工集上 Hit@1 是 76.4%、Hit@3 92.7%、Hit@5 100%、MRR 0.86、P50 230ms。它只能证明这组题和知识库上的检索表现，还需要 P95、nDCG、重复率和最终回答指标补充。

**深水区备料**

- Hit@K：每个 query 只计 0/1，再对样本平均；多个相关文档时信息量有限。
- Reciprocal Rank 是 `1 / 首个相关结果排名`，MRR 是其均值。
- P50 容易掩盖长尾，生产环境更关心 P95/P99、超时率和并发退化。
- 相关性标注要说明粒度：文档、chunk 还是答案证据；标注标准变化会影响数字。
- 还应做消融：无 multi-query、无 RRF、无 rerank，确认每个组件的增益。

**大概率追问**

- **Hit@5 100% 是否说明 RAG 没问题？**
  不说明。它只说这 55 个 query 的相关文档都进了前五，既不代表排序好，也不代表最终答案对——模型完全可能拿到了正确资料还写错。而且 55 例的样本量很小，100% 更可能说明这批题对这个知识库偏简单，不是能力上限。

- **为什么没有 nDCG？**
  因为当时的标注是二元的「相关/不相关」，没有分级相关性，nDCG 的增益函数就退化了，算出来信息量有限。要用 nDCG 得先把标注升级成多级相关性，这个成本我当时没投。这是评测设计上可以补的一块。

- **P50 计不计 query rewrite 和 rerank？**
  必须说清边界，否则这个数没意义。同一条链路，只算向量检索和算完整的「改写→并发召回→融合→去重→精排」，差出来的可能是好几倍。报数字的时候我会明确它的计时起止点，而不是只甩一个 230ms。

**坑**

- 不要把 Hit@5 100% 说成答案准确率 100%。
- 必须准备延迟计时边界，否则 230ms 没有意义。

## Q37. DeepResearch 的逐字证据校验是怎么做的？

**面试官为什么问**

这是项目最有辨识度的机制。对方会判断它是真正的程序门禁，还是 Prompt 里要求模型带引用。

**30 秒口播**

Researcher 输出每条 Finding 时必须同时给 `source_url` 和 `evidence_quote`。程序先确认 URL 来自本轮允许的来源，再对网页原文和 quote 做 Unicode、空白、大小写等归一化，执行连续子串匹配；太短、拼接、改数字或跨来源的引用都会拒绝。通过后记录原文位置和内容 SHA-256。只有程序标成 verified 的 Finding 才能进入后续反思和综合。

**深水区备料**

- 代码：`deep_research/guardrails.py::EvidenceVerifier`、`_normalize_with_offsets`、`_normalized_span`。
- 归一化需要保留字符到原文 offset 的映射，才能在 UI 展示真实上下文位置。
- quote 有最小长度，防止“是的”等万能短句支持任意论断。
- URL 必须属于提供给模型的 source 集合，防止模型编造新链接。
- 内容 hash 锚定“校验当时看到的网页版本”，网页更新后仍可审计。

**大概率追问**

- **网页换了空格、大小写或全半角怎么办？**
  匹配前两边都做归一化——Unicode 规范化、空白折叠、大小写统一、零宽字符清理，然后在归一化后的文本上找连续子串。关键是归一化要保留字符到原文位置的映射，这样匹配成功后还能回原文取真实 offset，前端才能展示证据在页面里的实际上下文。

- **逐字存在就代表论断被支持吗？**
  不代表，这两件事必须分开。原文写「没有明显增长」，模型总结成「增长显著」，只要它引的那句话真在原文里，逐字关照样过。所以逐字关后面还有语义支持判定，让独立判断去看这段引用到底支不支持这个论断，输出限定在 supported/unsupported/uncertain 三个值里。

- **PDF/OCR 内容如何处理？**
  麻烦在于 OCR 的错字、连字符断行和栏位错乱会让逐字匹配失败，而这时候引用可能是真实的。稳妥的做法是保存解析后的规范化文本作为校验基准，并记录解析器版本，这样至少可复现。当前项目主要面向网页文本，PDF 这条链没有专门处理，这是明确的缺口。

**坑**

- 不要说逐字校验能判断语义正确。
- 不要说整个报告每句话都来自原文；门禁对象是结构化 Finding。

## Q38. 为什么逐字校验之后还要语义支持和矛盾检测？

**面试官为什么问**

想看你是否理解“引用真实”和“论断被引用支持”是两回事，也会追问模型重新进入验证链是否形成自证。

**30 秒口播**

逐字校验只证明这段话真实存在于来源里，不证明它支持 Finding。比如原文说“没有增长”，模型却总结成“增长明显”，quote 仍然能匹配。所以我在逐字门之后让独立结构化判断检查 statement 是否被上下文支持，再为通过的论断生成稳定 claim ID，做跨来源矛盾标记。模型只能提出 supported 或矛盾候选，最终状态转换和报告准入仍由程序执行。

**深水区备料**

- `SemanticEvidenceVerifier` 只处理已经 verified 的 Finding，并返回受限枚举和置信度。
- 语义上下文不能只给 quote，可带原文附近窗口，避免断章取义。
- `ClaimConsistencyVerifier` 输出 contradiction/corroboration 候选，代码校验 claim ID、阈值和关系冲突。
- 矛盾双方都标为 conflicted，不让模型静默选一边。
- 仍然存在模型误判风险，因此状态和证据必须可审计，不能声称消除幻觉。

**大概率追问**

- **验证模型和生成模型相同会不会共错？**
  会，这是真实存在的相关偏差——同一个模型误解了原文，验证时很可能同样误解。用不同模型能降低相关性，但不等于独立，它们的训练数据本来就高度重叠。所以我不把语义验证当保证，真正硬的是它前面那道确定性的逐字关。

- **语义验证失败时是 fail-open 还是 fail-closed？**
  fail-closed。验证异常或者返回 uncertain 时，这条 Finding 拿不到 supported，也就进不了报告准入。理由很简单：安全和状态转换上不能靠猜，宁可少一条材料也不能把没验证过的当验证过的。代价是模型抽风时报告会变薄。

- **如何判断哪一条矛盾论断更可信？**
  当前不判断，两边都标成 conflicted 交给用户看。因为在开放世界里判定谁对需要外部权威真值，系统手上没有——用多数票决定更危险，转载会让错误信息轻松取得数量优势。可以演进的方向是来源可信度分级和时间新鲜度，但那也只是排序参考，不是事实裁定。

**坑**

- 不要说“LLM 验证过所以一定正确”。
- 不要让验证模型直接改写 Finding 或决定删除证据。

## Q39. 多来源交叉印证如何判断“独立来源”？

**面试官为什么问**

多个 URL 不等于多个独立证据。对方会用同一媒体子域、转载和冲突来源追问你的计数方式。

**30 秒口播**

关系模型先提出哪些 claim 表达同一事实，程序再检查来源是否来自不同 registrable domain。同一机构的不同子域、IDN 和 punycode 别名不会重复计数；如果同一组里存在矛盾，冲突优先于佐证。严格双源模式下，只有至少两个独立发布方支持、关系状态完整且没有冲突的 Finding 才能进报告。

**深水区备料**

- 代码：`guardrails.py::publisher_identity`、`_registrable_domain`、`_with_corroboration`、`report_eligible`。
- `tldextract` 使用公共后缀语义识别 registrable domain，不能简单取最后两段。
- 域名独立只是发布方近似，不等于信息源真正独立；转载链仍可能重复。
- 冲突与佐证同时出现时标记 disputed，不能用多数票直接覆盖。
- 严格门禁默认关闭，以兼容只有单一权威来源的事实；按任务风险或设置开启。

**大概率追问**

- **Reuters 被多家媒体转载算几个来源？**
  按当前实现算多个，因为域名不同——这正是这套方法的已知弱点，我不会掩饰。域名独立只是发布方独立的近似，管不了转载链背后其实是同一个信源。要真正处理得做转载检测或者引入信源溯源，现在只能说它提高了门槛，不能说它证明了独立性。

- **政府官网只有一个来源怎么办？**
  这就是严格双源默认关闭的原因——很多权威事实本来就只有唯一发布方，强制双源会把最可信的材料挡在门外。所以它是按任务风险开启的选项，不是全局默认。开启时的代价就是这类单源事实进不了报告，需要用户知道这个取舍。

- **为什么不是所有任务默认双源？**
  因为它对可用性的伤害很直接：一半以上的合理论断可能因为找不到第二个独立发布方而被拒。安全门禁的强度应该匹配任务风险，做一个行业概览和做一个医疗结论，需要的证据门槛不一样。默认关闭、按需开启，比一刀切更实用。

**坑**

- 不要说“不同域名就一定独立”。
- 不要把交叉印证当事实真值证明，它只是提高证据门槛。

## Q40. 做了这么多门禁，还可能产生幻觉吗？

**面试官为什么问**

这是诚实度压力题。任何声称“解决幻觉”的答案都会继续被反例击穿。

**30 秒口播**

仍然可能。门禁主要降低伪造来源、错误引用和已知矛盾进入报告的概率，但来源本身可能错，语义验证模型可能误判，Synthesizer 也可能在连接句里引入新表述。我更准确的说法是：系统把高风险论断变成可验证、可追踪的结构化对象，并让不满足条件的材料默认进不了报告。它提高可控性，不是给事实正确率做绝对保证。

**深水区备料**

- 残余风险：来源权威性、网页时效、转载依赖、语义模型偏差、报告二次生成、覆盖不足。
- 缓解：来源评分、时间过滤、严格双源、引用覆盖指标、报告后 claim extraction 再验、人工复核。
- 对高风险领域可以生成“证据摘要 + 未决冲突”，而不是强行给单一结论。
- 确定性指标可监控逐字验证率、语义支持率、报告准入率、独立发布方和冲突数。
- 开放世界事实准确率需要人工标注或外部权威数据，不能用自建护栏用例替代。

**大概率追问**

- **如何验证最终报告没有新增无引用论断？**
  现在验证不了，这是我承认的缺口——门禁的准入单位是结构化的 Finding，报告生成阶段的连接性表述不在门禁范围内。要补的话，得在报告生成后再做一次 claim extraction，把抽出来的论断和已验证的 Finding 对齐，看有没有孤儿论断。这件事在我的优先级列表里，但还没做。

- **来源可信度如何建模？**
  当前没有建模，所有通过 URL 策略的来源在证据链里是等价的。可以做的方向是域名分级、发布时间新鲜度、是否原始信源、历史准确率，组合成一个可解释的分数。但要注意这类分数很容易变成偏见的载体，我不会让它自动决定删除证据，最多用于排序和提示。

- **医疗或法律场景能否使用？**
  不能直接用。这套门禁降低的是引用造假和已知矛盾的风险，它不判断医学结论是否正确，也没有专业知识库和资质审核。真要用在这类领域，得换成受监管的权威语料、加上专业人员复核，并且系统输出应该是「证据摘要加未决冲突」，而不是给出单一结论。

**坑**

- 禁止说“从根本上解决幻觉”。
- 不要用更多 LLM Judge 层数掩盖缺少真值数据的问题。
