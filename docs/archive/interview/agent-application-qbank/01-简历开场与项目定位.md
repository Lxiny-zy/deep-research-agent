# 01 简历开场与项目定位（10 题）

## Q01. 请做一个一分钟自我介绍

**面试官为什么问**

不是听你复述教育经历，而是看你能不能在一分钟内把“为什么适合 Agent 应用开发”讲清楚，并给后续追问埋下可控的入口。

**30 秒口播**

我本科是通信工程，现在在北京邮电大学读新一代电子信息技术。最近主要做了两个 Agent 应用：一个是 AI 面试训练平台 SparkOffer，我用 LangGraph、RAG 和长期记忆做跨会话训练闭环；另一个是 DeepResearch，我把复杂问题拆成多 Agent 工作流，重点做了编排、证据校验、意图门禁和中断恢复。两个项目一个偏业务产品，一个偏 Agent Runtime。我希望找的也是 Agent 应用开发岗位，因为我比较擅长把模型能力接进可测试、可观测、能上线的完整系统。

**深水区备料**

- 教育背景只用一句，不展开课程和成绩，除非对方主动问。
- SparkOffer 的价值是“用成熟框架快速做业务闭环”：LangGraph 状态机、长期画像、SM-2 复习、RAG 题库、工具助手。
- DeepResearch 的价值是“把运行时原语拆开做透”：`Agent.step`、Blackboard、Workflow、DAG、Checkpoint、租约、SSE、证据门禁。
- 代码落点：`deep_research/agents/base.py`、`deep_research/workflow.py`、`deep_research/orchestrator.py`、`deep_research/guardrails.py`。

**大概率追问**

- **两个项目里你投入最多的是哪个？**
  DeepResearch。SparkOffer 更多是用成熟框架把业务闭环拼起来，而 DeepResearch 的编排引擎、恢复机制和证据链是我一层层自己写的，出了 bug 也是我自己复现和修，所以我更希望被追这一边的细节。短板也直说：它没有真实用户规模，我拿不出线上 A/B 数据。

- **为什么一个用 LangGraph，一个选择自研？**
  目标不一样。SparkOffer 要的是尽快把面试训练闭环跑通，LangGraph 的状态机和 Checkpoint 正好够用，没必要重写。DeepResearch 我想验证自己能不能把这层做出来，而且它需要工作流以图数据落库、前端画布编辑、定义快照恢复，这些定制在框架里绕起来反而更费劲。不是因为 LangGraph 不好。

- **你更偏算法、后端还是全栈？**
  主线是后端和 Agent Runtime，前端能独立写完整功能但不是我的深水区。算法方面我做的是应用层的检索评测、阈值校准和评估设计，不是模型训练——基础模型和大规模分布式推理我没有经验，这个我不会往上靠。

**坑**

- 不要从姓名、学校一路念到技术栈，最后没说岗位匹配。
- 不要说“精通大模型”或“精通 Agent”，项目经历不足以支撑这种表述。
- 不要一次报十几个数字，开场只留两三个能继续展开的技术点。

## Q02. 为什么想做 Agent 应用开发，而不是传统后端或算法岗？

**面试官为什么问**

想确认你是不是只追热点，也想知道你对岗位边界是否清楚。Agent 应用开发既不是纯 Prompt 调参，也不是训练基础模型。

**30 秒口播**

我喜欢这个方向，是因为它刚好处在模型能力和软件工程之间。模型能做规划、抽取和判断，但真正落地还要解决状态、工具权限、失败恢复、成本和评估。我做两个项目时最投入的也不是单次回答效果，而是怎么让一次 Agent 运行可控、可查、可恢复。所以我更想做 Agent 应用层和运行时这一段，而不是去做预训练或只写普通 CRUD。

**深水区备料**

- 岗位能力可以拆成四块：模型调用与上下文、工具/RAG、编排与状态、评估与工程化。
- 你的证据：SparkOffer 证明业务闭环，DeepResearch 证明运行时和可靠性。
- 可以明确自己的短板：没有基础模型训练和大规模分布式推理经验；PyTorch 了解但不是简历主线。
- 可以说明兴趣点：受约束自主性，即让 LLM 做高层判断，确定性代码掌握权限、校验和终止条件。

**大概率追问**

- **Agent 应用开发和普通 LLM API 套壳的区别是什么？**
  套壳是一次请求换一次回答，出错了最多重说一遍。Agent 要处理跨步骤的状态、要调外部工具产生真实副作用、要在中途失败后能接着跑，这些都不是 Prompt 能解决的。我的判断标准很简单：如果去掉模型这个系统就没有可讲的工程，那基本就是套壳。

- **你认为这个岗位最难的部分是什么？**
  是给概率性的组件设计确定性的边界。模型每次输出都可能不一样，但用户要的是稳定可交付的结果，所以难点在于哪些交给模型、哪些必须锁死在代码里。我在项目里的做法是让模型只提候选，权限、状态转换、终止条件全部由程序裁定。

- **你做过模型微调吗？**
  没有。我的经验集中在应用层——上下文组织、检索、编排、评估和工程化，微调和预训练不在我的简历里，我也不会往这个方向包装。如果岗位需要，我了解 LoRA 这类方法的基本原理，但得从头学起。

**坑**

- 不要贬低传统后端。Agent 系统的大部分稳定性仍来自后端工程。
- 不要把“会调用模型 API”说成岗位核心竞争力。
- 没做过微调就直接说没有，把重点放在应用层能力，不要绕。

## Q03. SparkOffer 和 DeepResearch 两个项目是什么关系？为什么要做两个？

**面试官为什么问**

项目看起来都用了 Agent、RAG 和 SSE，对方会判断它们是不是同一个模板换皮，以及你的能力有没有递进。

**30 秒口播**

两个项目解决的问题不一样。SparkOffer 是面试训练产品，核心是跨会话的用户画像、题库检索、复习调度和多场景交互，所以我优先用 LangGraph、LlamaIndex 这些成熟组件把业务跑通。DeepResearch 更偏基础设施，我刻意把工作流、状态机、Checkpoint、证据门禁和恢复机制显式实现，验证自己是否真正理解 Agent Runtime。一个证明我会用框架做产品，一个证明我能解释框架下面发生了什么。

**深水区备料**

- SparkOffer 的状态跨会话延续，长期画像和掌握度直接影响下一轮出题。
- DeepResearch 的状态以单次研究任务为中心，重点是开放域检索的可追溯性和长任务恢复。
- 共同点：FastAPI、SSE、结构化输出、RAG/工具、评估。
- 差异点：SparkOffer 更重个性化学习策略；DeepResearch 更重编排正确性、证据安全和运行可靠性。
- 面试时可以把二者组织成能力递进，不要分别讲成两段互不相关的功能清单。

**大概率追问**

- **DeepResearch 为什么不用 LangGraph？**
  因为这个项目的目的之一就是把 Runtime 做透，用了框架反而达不到目的。另外它有几个具体需求：工作流要以图数据落库并支持前端拖拽编辑、run 创建时要冻结定义快照、并行分支要按我自己的三方合并语义汇合，这些在框架里做定制的成本不低。代价是并发、取消、恢复的正确性全得我自己扛，所以我配了离线测试和 chaos 演示兜底。

- **SparkOffer 中最难的业务闭环是什么？**
  是让训练结果真正影响下一轮出题。难点不在单个模块，而在把 LLM 抽取的能力信号、长期画像、SM-2 到期项和题库检索这几路信息按优先级装进同一个上下文，还要证明它比只按主题出题更好。所以我做了和仅主题、随机策略的离线对照，而不是只报 Judge 分数。

- **两个项目有哪些代码或设计可以复用？**
  直接复用的代码不多，可复用的是模式：结构化输出当不可信输入处理、SSE 流式链路、依赖注入 + 假实现做离线测试，这几套在两边是一致的。真正没法复用的是状态模型——SparkOffer 的状态跨会话延续，DeepResearch 的状态以单次 run 为中心，硬抽象成一套反而会拧巴。

**坑**

- 不要说 DeepResearch 比 LangGraph 更强。它只覆盖了项目需要的一小组原语。
- 不要把相同的 SSE、FastAPI 重复包装成两个核心亮点。
- 不要说“为了丰富简历做了两个项目”，要从问题和能力递进回答。

## Q04. 用一分钟讲清 DeepResearch 的完整链路

**面试官为什么问**

这是项目真实性的第一道筛选。能否说清输入、状态、控制流、模型、工具和输出之间的关系，基本决定后面会不会深挖。

**30 秒口播**

用户提交问题后，系统先做多轮指代消解、意图识别、槽位抽取和必要的澄清，再确定工作流。运行开始前会冻结工作流和角色配置。Planner 把问题拆成子问题，Researcher 按依赖并发检索，并把带来源逐字引用的 Finding 交给程序校验；Reflector 判断证据缺口并做有界补充，Synthesizer 只使用通过门禁的材料生成带引用报告。整个过程写状态机事件和 Checkpoint，通过 SSE 实时展示，进程异常后可以从已完成节点继续。

**深水区备料**

- API 前置链：`deep_research/api.py` 调用 `deep_research/intent/context.py`、`deep_research/intent/slots.py`、`deep_research/intent/readiness.py`、`deep_research/intent/routing.py`。
- 运行对象：`Blackboard` 保存业务态，`WorkflowRun/StepRun` 保存执行态，`RunContext` 提供 LLM、检索、设置和 Tracer。
- 编排入口：`DeepResearchAgent` 在 `deep_research/orchestrator.py` 组装依赖，`WorkflowEngine` 在 `deep_research/workflow.py` 解释线性步骤或图。
- 证据链：`SourcePolicy → EvidenceVerifier → SemanticEvidenceVerifier → ClaimConsistencyVerifier`。
- 恢复：Checkpoint 同时保存 Blackboard 和 workflow definition，恢复不依赖当前模板是否已经变化。

**大概率追问**

- **意图识别为什么放在创建 run 之前？**
  因为澄清如果发生在 run 创建之后，历史里就会留下一堆没真正执行的空任务，用户列表会很脏。放在前面还有个好处：明显的风险请求在花掉第一个 Token 之前就被拦下来了。代价是创建接口变成了可能需要多轮交互的形态，前端要处理澄清态。

- **逐字校验能解决幻觉吗？**
  不能，它只解决「这句话是不是真的出现在来源里」。原文说「没有增长」、模型总结成「增长明显」，quote 照样能匹配上，所以逐字关后面还要有语义支持判定和跨来源矛盾标记。即便这样也只是降低风险，来源本身是错的这种情况它管不了。

- **进程挂掉后具体怎么找到可恢复任务？**
  API 启动时和之后每 30 秒会扫一遍数据库，找那些状态还在运行中、但租约已经过期或者根本没有租约的 run。抢到租约的实例把它接过来，从 Checkpoint 里的 Blackboard 和定义快照继续跑。没有 Checkpoint 的 run 不会硬续，会直接标成 error，避免从头重放。

**坑**

- 不要把所有步骤都说成一个 Agent 在“自主思考”。控制流由 WorkflowEngine 决定。
- 不要说“每条报告句子都验证过”。实际准入单位是 Finding/论断，报告生成仍可能引入连接性表述。
- 不要遗漏程序性门禁，否则听起来只是普通的多 Agent 检索 Demo。

## Q05. 用一分钟讲清 SparkOffer 的核心闭环

**面试官为什么问**

简历第一项目通常会被默认视为主项目。对方会检查你能否把训练、评估、记忆、复习和再出题串成一个闭环，而不是罗列六个页面。

**30 秒口播**

SparkOffer 不是一次性问答，而是跨会话的面试训练系统。每轮回答后，LLM 负责逐题评价和抽取新的能力信号，系统把结果更新到长期画像和向量记忆，再由确定性的 SM-2 调度决定哪些薄弱点该复习。下一轮出题时，会把画像、到期复习项和题库 RAG 一起装进上下文，并根据弱项覆盖和难度分布做个性化调整。这样训练结果会真正影响下一轮，而不是每次重新开始。

**深水区备料**

- 三种编排不要混讲：简历面试用 LangGraph 五阶段状态机；专项训练是题库/RAG 流水线；助手是单 Agent + 18 个工具。
- 长期画像更新由 LLM 提出 ADD/UPDATE/IMPROVE/NOOP，存储和调度规则由程序维护。
- 记忆治理：0.75 语义去重、14 天半衰期、权重上限 30%、单用户 500 条上限。
- 个性化评估不能只报 Judge 分数，要说明和仅主题、随机策略做离线基线比较。
- 这里没有当前仓库代码可引用。被追到实现细节时应以 SparkOffer 真实仓库为准。

**大概率追问**

- **为什么用户画像更新要让 LLM 参与？**
  因为「这道题答错说明他哪块弱」是语义归纳，规则写不出来——同样一次错误，可能是概念没掌握，也可能只是表述不清。所以我让模型做归纳、提出 ADD/UPDATE/IMPROVE/NOOP 这类操作候选，但真正的写入、去重、权重和数量上限由程序控制。模型负责理解，数据库负责守规矩。

- **为什么 SM-2 不交给 LLM？**
  因为它的输入输出完全确定：给定回忆质量，下一次间隔就该是那个值，没有需要理解的语义。交给模型只会带来不可复现和难以解释——用户问「为什么今天让我复习这个」，我得答得出来。而且这类计算要能写回归测试，模型每次输出不一样就测不了。

- **如何证明个性化真的有效？**
  不能只报 Judge 分数，那样等于自己给自己打分。我的做法是和两个基线做离线对照：只按主题出题、随机出题，再比较弱项覆盖率和难度分布是否真的贴合用户当前水平。这个对照的局限是样本来自离线集，不等于真实用户的长期学习收益。

**坑**

- 不要把“长期记忆”说成把所有对话塞进向量库。
- 不要把画像、向量记忆和复习调度混成一个模块。
- 不能只说“根据用户情况个性化”，必须讲清下一轮输入具体发生了什么变化。

## Q06. 这两个项目中，你个人具体负责什么？

**面试官为什么问**

想区分个人完成、团队协作和借助开源组件完成的部分，也会顺带判断简历措辞是否过度包装。

**30 秒口播**

这两个项目的核心设计和主要实现都是我主导完成的。SparkOffer 我重点做了 Agent 流程、长期画像、RAG 检索评测和训练闭环；DeepResearch 我负责工作流引擎、证据链、意图识别、Checkpoint 恢复以及前后端联调。第三方框架和模型我会明确说是使用和集成，不会说成自己实现。开源协作方面，我也参与过 DeepSeek-Reasonix、AxonHub、NewAPI 等项目，但会按具体 PR 说明贡献范围。

**深水区备料**

- 准备三个可以现场打开的 commit/PR：一个核心功能、一个 bug 修复、一个测试或文档改进。
- DeepResearch 可展示的代码主线：`workflow.py`、`guardrails.py`、`persistence/sql_repository.py`、`intent/`、前端运行页。
- 对使用 AI 编码工具保持诚实：工具帮助生成和检索，但架构选择、验收标准、调试和最终责任由你承担。
- 若项目是个人项目，不要虚构产品、算法、测试团队；可以讲你如何模拟真实协作流程，例如 issue、测试门和代码审查。

**大概率追问**

- **哪段代码完全由你设计？**
  并行分支的三方合并和租约 fencing 这两块，从问题定义到算法到回归测试都是我自己推的。我可以现场讲清楚为什么是 base/current/branch 三方比较而不是简单覆盖，以及为什么每次受保护写入都要在同一事务里校验 owner——因为这两个决定都是我踩过坑之后改的。

- **使用 Codex/Claude Code 到什么程度？**
  用得不少，主要在检索代码、写样板和补测试上。但需求拆分、架构取舍、验收标准和最后的代码责任在我，我的标准是能不能解释边界、复现 bug、改实现并用测试证明。工具生成但我没验证过的东西不会写进简历。

- **开源贡献具体改了什么？**
  我会按 PR 说，不笼统报项目名。准备好的是问题背景、改动范围和验证方式，规模上多数是 bug 修复和文档/测试改进，不是核心架构级贡献——这个我不夸大。

**坑**

- “全部都是我做的”之后必须能承受任意模块追问。
- 不要把调用 LangGraph、Qdrant、Tavily 说成“自研”。
- 开源贡献不要只报项目名，至少准备 PR 链接、问题背景和改动结果。

## Q07. 你遇到的最难技术问题是什么？

**面试官为什么问**

看你能否定义问题、比较方案并验证结果。回答“模型不听话，所以改 Prompt”通常说明工程深度不足。

**30 秒口播**

我认为最难的是并行 Agent 对共享状态的合并。每个分支都从同一份 Blackboard 副本开始，可能既修改已有 Finding，又追加新结果；简单覆盖会丢掉兄弟分支的内容。我最后采用 base、current、branch 三方合并：只把 branch 相对 base 的变化应用到 current，列表还要区分基线改写和追加段。这个问题后来真的暴露过数据丢失，我修完后补了纯函数和端到端两层回归测试。

**深水区备料**

- 代码：`deep_research/workflow.py::_merge_parallel_value`、`_merge_parallel_sequence`、`_merge_parallel_blackboard`。
- 分支运行前深拷贝 layer base，避免并发原地写同一对象。
- append-only 列表可以合并双方增量；两边都改写基线时按元素差异覆盖，同时保留双方追加段。
- 这只是确定性的结构合并，不理解业务语义，也不是 CRDT。
- 测试：`tests/test_graph_workflow_run.py` 和 `tests/test_step_policies.py` 覆盖改写加追加、pop 加 append 等交错。

**大概率追问**

- **两个分支把同一元素改成不同值怎么办？**
  当前是确定性规则胜出，不是自动协商——按拓扑层内的稳定顺序合并，后合并的分支覆盖同一位置。我不会把它说成解决了冲突，它只保证结果可重复、不丢追加段。真要处理语义冲突，得引入字段级写集或者业务对象专用的 merge policy。

- **为什么不用锁？**
  因为分支是并发跑的，加锁就等于把并行退化成串行，那并行本身就没意义了。我的做法是每个分支在自己的深拷贝上跑，汇合时再做三方合并，冲突在合并阶段用确定性规则解决。代价是内存里会同时存在多份 Blackboard。

- **深拷贝大 Blackboard 会不会慢？**
  会，而且这是当前设计明确的成本——分支数和状态体积一起放大内存占用。现在的研究任务状态量还撑得住，所以我没有优化。真要处理更大的状态，方向是 copy-on-write 或者只拷贝分支会写的字段，而不是整份深拷。

**坑**

- 不要说“完全解决并发冲突”。同一字段的语义冲突仍只有确定性胜出规则。
- 不要把 asyncio 并发说成多线程并发。
- 不要只描述算法，要讲 bug 如何被测试锁住。

## Q08. 讲一个你真实修过的严重 Bug

**面试官为什么问**

这题在看调试方法和质量意识。真实 Bug 的复现、根因和回归测试，比“做了很多功能”更有区分度。

**30 秒口播**

有一次并行层里，一个分支改写了基线 Finding，另一个分支追加了新 Finding。旧合并逻辑发现基线被改写后，直接用后合并分支的整段列表覆盖，结果先合并分支的追加内容丢了。我的修复不是换个覆盖顺序，而是把列表拆成基线段和追加段：基线段按相对 base 的元素差异合并，两边的追加都保留。然后补了一个纯函数最小复现和一个真实并行 Agent 的端到端测试。

**深水区备料**

- 先说明为什么普通 happy path 没抓到：只有“双方都改写基线且都有追加”时触发。
- 用可控 Agent 和 `asyncio.Event` 构造确定交错，不使用 `sleep` 碰概率。
- 修复需要保持合并顺序确定，否则测试仍可能偶发。
- 同一轮代码审查还发现过重试退避组合上界缺失：字段各自合法，但 8 步指数退避可累计到数十小时，后来增加单步尝试和全流程最坏退避上限。

**大概率追问**

- **为什么测试一开始没覆盖到？**
  因为触发条件很窄：必须两个分支都改写了基线、而且都各自追加了新内容，少任何一个条件都不会暴露。原来的用例都是单分支追加或者单分支改写，走的是 happy path。这件事之后我写并发测试会先列交错矩阵，而不是只测「能跑通」。

- **如何确认修复没有引入新覆盖问题？**
  两层测试：一个是纯函数级的最小复现，直接对合并函数喂改写加追加的组合断言结果；一个是真实并行 Agent 的端到端用例，用 `asyncio.Event` 构造确定交错，不靠 sleep 碰概率。后者的价值是能验证合并顺序确实是稳定的，否则测试自己会偶发。

- **还有哪些并发交错没有覆盖？**
  嵌套场景覆盖得最薄——图分支里再套 team_fanout、然后在子流程里失败重试，这种多层交错我只测了单层。另外分支在合并中途被取消的路径也没有专门用例。我知道这几处是缺口，不会说测试已经覆盖全部并发情况。

**坑**

- 不要把 Bug 讲成“写错一个变量名”。要选能体现分析能力的问题。
- 不要说“补了单测所以以后绝不会再出问题”。
- 不要省略复现方式和失败断言。

## Q09. 简历上的这些数字怎么证明不是包装？

**面试官为什么问**

Agent 项目的指标很容易选软样本、混淆分母或让 Judge 自说自话。对方会检查你是否清楚每个数字到底测了什么。

**30 秒口播**

我会把数字分成三类。第一类是确定性测试数，比如后端默认 613 项、前端 139 项，可以直接收集和运行。第二类是自建离线评测，比如 20/20 注入拦截、18/20 风险请求拒识，我会同时说明分母、数据集和假模型边界。第三类是演示指标，比如 1.8 秒接管和 75% 重复 Token 节省，只代表固定 chaos 场景。我不会把自建集上的 100% 说成真实世界准确率。

**深水区备料**

- `python -m eval.intent_eval`：任务意图 75 条，准确率 78.7%，零 Token 判定 81.3%；风险 18/20，误伤 0/24。
- `python -m eval.adversarial`：注入和逐字引用为确定性代码；矛盾与交叉印证用脚本化关系 LLM，只测传播和门禁。
- `pytest --collect-only -m "not pg"` 与前端 `vitest --run` 可复核测试数量。
- SparkOffer 的 Hit@K、MRR、P50 必须能说明 55 例标注集、相关性真值和计时边界。
- 质量 Judge 适合相同模型、数据集、Prompt 下做相对比较，不适合当绝对真理。

**大概率追问**

- **为什么意图准确率只有 78.7% 还能上线？**
  因为这个模块优化的是成本和路由，不是安全。分类错了最多是工作流深度选得不合适，用户还能自己改；真正兜底的证据门禁和风险拒识是独立的，不受它影响。而且系统不强猜——置信度不够就弃权，交给 L3 或者回退默认 deep。

- **20 条注入是不是太少？**
  少，我不会拿它当通用免疫的证据。它的价值不在数量，而在这 20 条里有 4 类是首轮真被打穿的绕过——英文同义词、零宽字符拆词、中文把字句、URL 连字符——修完之后转成回归样本锁住。真要评估真实覆盖率，得引入外部红队集和真实网页样本。

- **75% Token 节省是否能代表成本节省？**
  不能直接等同。75% 是那个固定 chaos 场景下避免的重复调用比例，杀进程的位置换一下数字就变了；如果在 Synthesizer 中间杀，能省的比例明显更低。而且 Token 数不等于金额，不同模型单价差很多，所以我只把它当恢复机制有效的证据，不当成本承诺。

**坑**

- 不要只报百分比，不报样本数。
- 不要把管线召回率说成模型识别能力。
- 不要沿用已经变化的旧数字，面试前必须现场再跑一遍。

## Q10. 目前项目最大的不足是什么？

**面试官为什么问**

想看你有没有架构边界意识。成熟的回答不是“还可以优化性能”，而是能指出当前设计在哪个规模或信任模型下会失效。

**30 秒口播**

DeepResearch 现在最大的边界是执行任务仍然跑在 API 进程里的 asyncio 后台任务中。数据库有 Checkpoint、租约和多实例接管，所以进程挂掉能恢复，但它还不是完整的分布式任务队列，也不保证 exactly-once。下一步我会先把执行器拆成独立 worker，用持久队列承接 run，再补幂等工具调用、集中式事件总线和更完整的线上质量监控。这个改动比继续加 Agent 角色更重要。

**深水区备料**

- 当前 EventHub 是进程内对象；跨实例实时订阅需要 Redis Streams、NATS 或 Kafka 一类外部总线。
- 恢复是至少一次语义：已发出的外部工具调用可能重放，需要幂等键或操作日志。
- Catalog 默认模型目前缺数据库级部分唯一约束，并发设置默认值仍有竞态。
- 自定义 AgentCard 只能复用五种 behavior，不是任意插件系统。
- 多租户需要强制鉴权、RBAC、审计和资源配额；当前本地零配置模式不应被描述为 SaaS 安全模型。

**大概率追问**

- **为什么不一开始就上 Celery/Kafka？**
  因为当时没有能证明它必要的负载。进程内 asyncio 加数据库 Checkpoint 已经能演示恢复语义，部署和调试链都短得多，先把编排和证据链做对更重要。判断该换的信号也很明确：出现多实例、任务积压、需要独立扩缩容或者跨进程取消的时候，现在这套就不成立了。

- **你会怎么设计幂等工具调用？**
  给每次调用生成稳定的幂等键，比如 `run_id + node_id + action_index`，工具侧按这个键保存结果，重放时直接返回上次的响应而不是真的再执行一遍。对本身不可幂等的操作，就得靠 outbox 或者 prepare/commit 两阶段。前提是工具服务愿意配合，这不是编排引擎单方面能保证的。

- **哪个技术债优先级最高？**
  执行器拆出去这一项，因为它卡住的是架构上限，其他问题都能在现有结构里补。我的排序依据是「不改会不会限制系统能到的规模」，而不是实现起来有不有趣——所以我不会先去加更多 Agent 角色。

**坑**

- 不要说“项目已经生产级”。可以说具备生产化要素，但仍有明确缺口。
- 不要列十个无关 TODO，要挑一个最影响架构上限的问题讲透。
- 不要把承认边界说成自我否定，要同时给出演进顺序和原因。
