# 03 多 Agent 编排与工作流（10 题）

## Q21. 为什么要拆成多个 Agent，而不是一个大 Prompt 一次完成？

**面试官为什么问**

多 Agent 很容易只是增加角色名。对方想知道拆分是否解决了真实问题，以及额外成本是否值得。

**30 秒口播**

我拆 Agent 不是为了数量，而是为了把不同阶段的输入输出和失败边界固定下来。规划、检索、证据判断、反思和综合需要的上下文与模型能力不同，拆开后可以分别选模型、做重试、记录指标和限制权限。简单问题仍然走 quick 工作流，不强制多 Agent。只有当职责分离能换来可测试性、并发或质量门时，拆分才有意义。

**深水区备料**

- Planner 输出结构化 `ResearchPlan`；Researcher 消费子问题并输出 `Finding`；Reflector 只判断证据缺口；Synthesizer 只消费准入材料。
- 各阶段 schema 形成契约，避免一个超长 Prompt 同时规划、搜索、判断和写报告。
- 拆分成本：更多模型调用、更长延迟、状态协调、错误传播和观测复杂度。
- `quick` 省略反思，`reviewed` 增加 Critic，说明多 Agent 数量由工作流需求决定。
- 单 Agent 更适合短、低风险、工具少的任务；固定流水线比自由群聊更适合研究场景。

**大概率追问**

- **如何证明多 Agent 比单 Agent 更好？**
  只能用对照实验，不能靠直觉。我的做法是同一组用例分别跑 quick 和 reviewed/deep，比较 Judge 四维分、Token 和墙钟——如果质量提升很小但成本翻倍，那这个拆分就不值。目前这套对照跑在自建用例上，样本量不足以支撑通用结论。

- **角色拆太细会有什么问题？**
  每多一个角色就多一次模型调用、多一段延迟，还多一个可能失败和需要观测的点。更麻烦的是上下文要在角色之间反复传递，信息在序列化和摘要中衰减，容易出现每个角色都做对了但整体跑偏。所以我的默认是能合就合，只有职责分离能换来可测试性或并发时才拆。

- **Critic 会不会只是增加一次模型调用？**
  有这个风险，如果 Critic 只会说「写得不错」那它确实就是纯成本。避免的办法是让它输出结构化的、可以驱动后续动作的判断，而不是自由点评。它到底值不值，还是得用 reviewed 和 quick 的对照数据说话。

**坑**

- 不要说“多个 Agent 可以互相讨论，所以一定更准确”。
- 不要把同一个模型换不同 Prompt 就夸成真正独立专家。
- 必须承认需要用质量、Token 和墙钟对照来验证收益。

## Q22. Agent、Blackboard、RunContext 三个对象为什么要分开？

**面试官为什么问**

这是 DeepResearch 的核心抽象。对方在看你是否理解能力、业务状态和运行依赖三者的边界。

**30 秒口播**

Agent 只负责能力，例如规划或检索；Blackboard 保存这次研究已经产生的计划、结果、反思和报告；RunContext 提供模型、搜索、配置、Tracer 这些运行依赖。这样 Agent 不需要彼此直接调用，也不需要自己管理数据库连接。引擎只按统一的 `step(bb, ctx)` 协议调度，状态可以序列化，依赖也能在测试里替换成 Fake 实现。

**深水区备料**

- 代码：`deep_research/agents/base.py` 中的 `Blackboard`、`RunContext`、`Agent` Protocol。
- Blackboard 核心字段：`query`、`plan`、`results`、`reflections`、`report`、`scratch`。
- `scratch` 为扩展状态保留空间，但内部 key 需要命名约定；引擎元数据使用下划线前缀。
- `RunContext.llm_for(agent_name)` 支持角色级模型路由；共享 Semaphore、Tracer 和 Settings 也从上下文传递。
- 如果 Agent 直接互相调用，控制流、超时和恢复会散落进角色实现，难以统一治理。

**大概率追问**

- **`scratch` 没有强 schema 会不会失控？**
  会，这是我承认的弱点。现在靠命名约定管着——引擎自己的元数据统一加下划线前缀，和业务 key 分开——但类型约束确实很弱，写错 key 只能在运行时发现。要收紧的话，应该给常用扩展点定义 TypedDict 或者 Pydantic 模型，而不是继续放任裸 dict。

- **为什么不用消息队列让 Agent 互相通信？**
  因为研究场景的本质是「渐进丰富同一份状态」，不是「互相发通知」。用黑板的话，状态天然是一个可以整体序列化的对象，Checkpoint 和恢复都简单；换成消息传递，我还得额外维护每个 Agent 的局部状态和消息顺序。代价是所有角色都耦合在同一个状态结构上，加字段要考虑全局影响。

- **RunContext 会不会变成上帝对象？**
  有这个倾向，它现在装了 LLM、检索、Settings、Tracer 和共享 Semaphore。我的边界是：只放「运行期依赖」，不放业务状态——业务状态一律进 Blackboard。真要继续长下去，应该按用途拆成几个更小的协议再组合，而不是一直往里塞。

**坑**

- 不要说 Blackboard 是全局单例，它属于单次 run。
- 不要把 RunContext 当业务状态保存进报告。
- 需要承认 `scratch` 灵活但类型约束较弱。

## Q23. 为什么把 Workflow 设计成数据，而不是直接写 Python 流程？

**面试官为什么问**

想看你是否理解声明式工作流的产品价值和代价，而不是只说“方便扩展”。

**30 秒口播**

工作流变成数据后，节点、条件边、Join 和可靠性参数都能落库、版本化和在前端编辑，同一套引擎可以执行内置模板和用户流程。创建 run 时把 definition 冻结，之后模板变化也不会影响历史任务。代价是所有可表达能力都要先设计成受控原语，还要做图校验和兼容迁移，灵活性不如直接写 Python。

**深水区备料**

- `Step` 支持普通 Agent、`reflect_loop`、`compose`、`team_fanout`，以及 timeout、retry、fallback、failure policy。
- `Workflow` 同时支持线性 `steps` 和图 `nodes/edges`；自定义定义还保存 viewport 与 version。
- 数据化带来的能力：数据库存储、React Flow 编辑、乐观锁、审计、definition snapshot、API 创建运行。
- 约束：不能表达任意 Python 条件或任意插件代码；需要白名单角色和安全条件语言。
- 当前保存层保留 steps 与 graph 双表示，用服务端归一化实现渐进兼容。

**大概率追问**

- **为什么同时存 steps 和 graph？**
  历史加兼容原因：早期定义只有线性 steps，图编辑器是后加的，老记录不能一刀切失效。现在保存时以 nodes/edges 为准，服务端按拓扑结果重算 steps，两个表示都由服务端归一化生成，不信任客户端提交的一致性。代价是多一份派生数据要维护，长期应该收敛到只存图。

- **如何做工作流版本迁移？**
  两条线：存量数据用 Alembic 迁移改结构，运行中的 run 靠创建时冻结的 definition 快照，不受模板变化影响。所以改模板不会把正在跑的任务改坏。真正麻烦的是新增控制原语——老引擎不认识新节点类型，这种情况得给定义带版本号并保留旧分支的解释逻辑。

- **任意复杂逻辑怎么表达？**
  表达不了，这是声明式设计换来的代价。条件只支持路径取值和简单比较，连 and/or 都没有，复杂判断得拆成多条边，或者让上游 Agent 先算好一个标志位写进 scratch。如果真出现必须写代码才能表达的分支，那说明它该是一个新的引擎原语，而不是把条件语言扩成半个 Python。

**坑**

- 不要说“新增任何流程都不用改代码”。新增控制原语仍需改引擎。
- 不要忽略声明式系统的校验和迁移成本。

## Q24. DAG 是怎么调度的？为什么按拓扑层执行？

**面试官为什么问**

这是并发和依赖处理的核心实现题。对方会追问环、条件边、失败和恢复如何影响调度。

**30 秒口播**

保存工作流时先用 Kahn 算法做拓扑分层。入度为零的节点组成一层，层内可以并发，执行完再降低后继入度；层间保持依赖顺序。每个并行节点拿同一份层起点 Blackboard 的深拷贝，层末再合并回主状态。这样并发范围清楚，Checkpoint 也可以按层写，代价是同一层节点不能实时读取兄弟节点刚产生的数据。

**深水区备料**

- 图算法：`deep_research/orchestration/graph.py::graph_topo_layers`。
- 校验：重复 ID、悬空边、弱连通、环；节点声明顺序用于同层稳定排序。
- 执行：`deep_research/workflow.py::_run_graph`，用 `asyncio.gather` 跑层内节点。
- 条件只读取上一层已经合并的主 Blackboard；如果节点依赖兄弟输出，应显式建边让它进入下一层。
- 区分研究子问题 DAG：LLM 生成的子问题依赖有环时会降级为并行，而用户工作流图有环直接拒绝。

**大概率追问**

- **为什么不做节点完成即触发的事件驱动调度？**
  因为按层执行让并发范围和 Checkpoint 边界都很清楚——一层跑完合并一次、写一次快照，恢复时也好对齐。事件驱动理论上墙钟更短，但状态合并的时机会散落在各处，恢复语义要复杂得多。代价就是同层里快的节点得等慢的，这是我明确接受的取舍。

- **一层中有一个节点很慢怎么办？**
  当前就是整层一起等，这是按层调度的直接代价。能缓解的是节点级 timeout——慢到超时就按失败策略处理，不会无限拖住整层。真要根治得改成事件驱动调度，那是另一套恢复语义了。

- **环为什么一处拒绝、一处降级？**
  因为来源不同，能承担的后果也不同。用户在画布上画出来的环是配置错误，保存时就该拒绝并告诉他哪里有问题，让错误停在编辑阶段；而子问题依赖是 LLM 生成的，运行时才发现有环，这时候拒绝等于整次研究白跑。所以后者破环降级成并行，牺牲依赖上下文保住可用性。

**坑**

- 不要说层内共享同一个可变 Blackboard。
- 不要把 Kahn 排序说成能自动解决业务依赖错误。
- 不要混淆工作流 DAG 和子问题 depends_on DAG。

## Q25. Researcher 如何处理有依赖的子问题并发？

**面试官为什么问**

简历写了并行检索。对方会判断你是否只是对所有问题 `gather`，还是理解依赖、上下文传递和并发上限。

**30 秒口播**

Planner 生成的子问题可以带依赖。Researcher 先按依赖关系调度：没有前置依赖的先并发，后续问题会把已完成前驱的结果摘要带入检索和抽取。并发由 run 级共享 Semaphore 限制，不会因为图分支或 team 嵌套把并发倍增。如果模型给出循环依赖，子问题层会破环降级成普通并行，保住任务可用性。

**深水区备料**

- 调度代码：`deep_research/scheduler.py::research_dag`；Researcher 在 `deep_research/agents/researcher.py` 消费。
- 依赖上下文只传必要摘要，避免把所有前驱原文重复塞入每个后继 Prompt。
- `asyncio.gather` 负责并发等待，Semaphore 约束真正昂贵的 LLM/搜索操作。
- 单个子问题失败不应取消全部研究；成功结果继续进入报告，但失败必须留下事件。
- 破环是 best-effort 策略：牺牲依赖上下文，不牺牲整次研究。

**大概率追问**

- **前驱失败时后继怎么办？**
  后继照跑，但拿不到前驱的结果摘要，等于降级成没有依赖上下文的独立检索。我不让一个子问题的失败取消整次研究，因为其余结果仍然有价值。前提是失败必须留下事件，不能静默吞掉——用户要能看出这份报告是在材料不全的情况下生成的。

- **并发数怎么设置？**
  不是拍一个数，要看 provider 的 rate limit、连接池上限和平均延迟一起定。设太高会撞 429 反而更慢，设太低浪费等待时间。我的做法是先测各阶段耗时找出瓶颈在哪，再调这个值，而不是默认拉满。

- **如何避免依赖上下文越来越长？**
  只传前驱结果的必要摘要，不把原文整段塞进每个后继的 Prompt。否则链条越深上下文膨胀越快，既贵又容易让模型抓不住重点。代价是摘要会丢信息，所以摘要里要保留引用 ID，需要时能回查原始 Finding。

**坑**

- 不要说墙钟时间永远等于最慢一条，存在依赖层和并发限流。
- 不要把任务失败静默吞掉，必须区分失败隔离和忽略错误。

## Q26. ANY、ALL、SUCCESS_ALL 三种 Join 有什么区别？

**面试官为什么问**

图工作流的汇聚语义很容易只做一个“所有前驱完成”。这题检查你是否处理条件路由与失败隔离的组合。

**30 秒口播**

ANY 表示任一入边激活就执行，适合 A/B 条件分支最后汇合；ALL 要求所有入边条件都激活，适合必须多路同时满足的节点；SUCCESS_ALL 在 ALL 基础上还要求前驱都成功，适合输入必须完整的汇总节点。这里要区分“边是否激活”和“前驱是否成功”，因为默认失败隔离允许失败节点结束后流程继续。

**深水区备料**

- 条件路由中未选择的分支不是失败，而是未激活；因此默认用 ALL 会让很多汇聚点永远跳过。
- 失败节点可以属于 active nodes，但不会进入 successful nodes。
- `SUCCESS_ALL` 为聚合器等完整输入节点提供硬门槛。
- 运行代码在 `workflow.py` 的图执行入边判断；定义模型在 `orchestration/types.py`。
- 恢复时条件跳过可能重新评估，预算跳过则是终态，两者不能混为同一 SKIPPED 语义。

**大概率追问**

- **ANY 会不会让节点太早执行？**
  会，这正是 ANY 的语义——任一入边激活就走。所以它只适合那种「几条互斥分支最后汇合到同一个收尾节点」的场景。如果节点真的需要多路输入都齐了才有意义，就不该用 ANY，该用 ALL 或者 SUCCESS_ALL。

- **条件边没有命中时状态是什么？**
  是未激活，不是失败。这个区分很关键：未激活说明流程根本没选这条路，是正常的；失败是选了但执行出错了。混淆这两者的直接后果就是默认用 ALL 的汇聚点会永远等不到条件分支，整个流程静默卡住。

- **失败节点算不算完成？**
  算结束，但不算成功。默认的失败隔离允许节点失败后流程继续，所以它会出现在已激活节点集合里，但不会进入成功集合。SUCCESS_ALL 就是为了这个场景存在的——聚合类节点需要的是「前驱都成功」这个硬门槛，光是「都结束了」不够。

**坑**

- 不要把 ALL 解释成“所有前驱成功”，那是 SUCCESS_ALL。
- 不要忽略条件未激活和执行失败的区别。

## Q27. 条件表达式为什么自研一个小解释器，不直接用 `eval`？

**面试官为什么问**

考不可信输入处理和依赖取舍。工作流条件来自前端或模型生成，直接执行会形成代码注入。

**30 秒口播**

条件只需要读取 Blackboard 路径并做简单比较，没有必要开放 Python。我的解释器只支持点路径、`last/length` 这类只读虚属性、六种比较运算和 JSON 字面量；不支持函数调用、属性写入和任意表达式。解析失败返回不激活，而不是让异常炸掉整层。表达力确实有限，但换来安全、可序列化和前后端一致。

**深水区备料**

- 代码：`deep_research/orchestration/conditions.py`。
- 支持形态：`state.reflections.last.is_sufficient == false`、`state.results.length >= 1`。
- 字面量只接受 JSON 的字符串、数字、布尔和 null，未加引号的任意文本被拒绝。
- `eval` 的风险不是只靠正则就能消除；安全来自根本没有调用和写操作。
- 不支持 and/or；复杂逻辑应拆边或由上游 Agent 预计算 scratch 标志。

**大概率追问**

- **为什么不用 simpleeval 一类库？**
  那类库的思路是在 Python 表达式上做减法，靠黑名单裁掉危险能力，历史上被绕过的先例不少。我需要的表达力其实很窄——取个路径的值、比一下大小，做加法比做减法安全得多。另外自己实现还能保证前后端对同一条件的解释完全一致，以及条件本身可序列化落库。

- **路径不存在时为什么不报错？**
  因为条件求值发生在流程执行途中，抛异常会炸掉整层，而路径不存在往往只是上游还没写这个字段，属于正常情况。所以取不到就返回不激活，语义上等价于「这条边的条件没满足」。代价是写错 key 不会立刻暴露，只会表现为分支一直不走，这个我在保存时用条件语法校验兜一部分。

- **如何扩展复合条件？**
  优先不扩。需要 and/or 的场景，我倾向于拆成多条边串起来，或者让上游 Agent 把复杂判断算成一个布尔标志写进 scratch，条件只读那个标志。真要支持，也应该是加受控的组合节点，而不是让表达式语言一点点长成 Python。

**坑**

- 不要只说“用正则防注入”。
- 不要为追求表达力逐步把它扩成半个 Python。

## Q28. 并行分支如何合并 Blackboard？

**面试官为什么问**

这是判断你是否真正写过并行工作流的深挖题。简单的最后写入获胜通常会丢结果。

**30 秒口播**

每个分支都从同一个 base 深拷贝开始执行，合并时比较 base、当前主状态和 branch。branch 没改的字段保留 current；字典按 key 递归；列表如果只追加，就保留两边追加；如果改写了基线，则按元素差异更新基线段，同时保留双方追加。它保证常见结构变化不丢，但不理解业务语义，真正冲突时仍是确定性规则，不是自动协商。

**深水区备料**

- 代码：`workflow.py::_merge_parallel_value`、`_merge_parallel_sequence`。
- 需要 deep copy，不然 branch 修改会污染 base，三方比较失去基准。
- 合并顺序按拓扑层内稳定顺序，确保结果可重复。
- 成功分支应先合并再传播 fail-fast 异常，避免失败兄弟抹掉已完成产出。
- 可演进方向：字段级写集、copy-on-write、业务对象专用 merge policy。

**大概率追问**

- **同一 Finding 两边改成不同内容怎么办？**
  按拓扑层内的稳定顺序，后合并的分支覆盖同一位置——是确定性规则胜出，不是自动协商。我不会说它解决了冲突，它只保证同样的输入一定得到同样的结果，不会随机丢数据。真要处理语义冲突，得引入字段级写集或者按业务对象定制 merge policy。

- **为什么不用数据库事务或锁？**
  因为这是单次 run 内存里的状态合并，不是跨进程的持久化竞争，套事务等于把并行退化成串行。持久层那边确实有事务和租约 fencing，但那解决的是另一个问题——旧实例写不回脏数据。两层各管各的。

- **大对象深拷贝如何优化？**
  可以走 copy-on-write，或者只拷贝分支声明会写的字段而不是整份状态。现在没做是因为研究任务的状态量还撑得住，过早优化会让合并逻辑更难验证。这是我知道但暂时接受的成本。

**坑**

- 不要称为 CRDT。
- 不要声称解决了语义冲突。
- 不要忘记失败尝试也要在副本上运行，成功后才提交。

## Q29. 反思循环怎么设计，如何保证不会死循环？

**面试官为什么问**

“Reflector 自动补洞”是常见卖点。对方会追问它是否只是让模型反复说“不够”，以及成本是否有硬上限。

**30 秒口播**

Reflector 不直接重做整次研究，它只根据当前计划和已验证证据判断哪些子问题还缺材料，并把增量问题写入 `pending_sub_questions`。Researcher 下一轮只处理这些补洞项。循环用 `for range(max_rounds)` 控制，默认轮数很小；证据充分、没有新问题或预算耗尽都会提前停止。终止性来自代码上限，不依赖 Prompt 里让模型自觉收敛。

**深水区备料**

- `reflect_loop` 是 WorkflowEngine 的控制原语，不是 Reflector 自己递归调用。
- 增量子问题通过 Blackboard scratch 传递，避免重跑整个 plan。
- 生成工作流中的反思轮数还要经过 `max_rounds_cap` 校验。
- TokenBudget 耗尽时非终端反思步骤可跳过，保住已有材料进入 Synthesizer。
- 质量收益必须用 reviewed/deep 与 quick 的对照评估，不能假定多一轮一定更好。

**大概率追问**

- **模型每轮都生成不同问题会怎样？**
  那循环就退化成了持续烧钱——每轮都有新问题，永远显得「还不够」。所以终止性不能建立在模型自觉收敛上：`for range(max_rounds)` 是硬上限，预算耗尽也会停。另外新增问题要和已有子问题做去重，避免换个说法的同一个问题被反复提出来。

- **反思是否应该由另一个模型执行？**
  用不同模型能降低同源偏差——同一个模型容易觉得自己产出的材料已经够了。但这只是降低相关性，不是真正独立的第二意见，两个模型可能在同一类问题上一起犯错。所以我不会把「换了个模型」当成质量保证，最终还是靠程序判定证据是否达标。

- **如何判断新增问题是否重复？**
  最简单是对已有子问题做文本或语义相似度比对，超过阈值就丢弃。要更稳的话，应该比对问题背后的实体和意图，而不是字面表述——「2024 年营收多少」和「去年收入情况」字面差很远但实质是同一个。这块目前做得比较粗，是可以继续加强的地方。

**坑**

- 不要用“Prompt 要求最多两轮”证明终止性。
- 不要把反思说成模型在检查自己的真实思维过程，它只检查结构化产物。

## Q30. Coordinator 动态编排和 team_fanout 有什么区别？

**面试官为什么问**

两者都看起来是“动态多 Agent”。对方会检查你是否理解受约束规划和 Map-Reduce 分工。

**30 秒口播**

Coordinator 解决的是“这道题该走哪些步骤”，它根据问题生成一份受约束 Workflow，校验失败会自修复一次，再不行就回退内置 deep。team_fanout 解决的是“同一阶段如何分团队并行”，每个团队拿隔离子 Blackboard 做一个 focus，最后由 Aggregator 汇总。前者动态决定控制流，后者是固定的 Map-Reduce 执行原语，状态隔离和失败语义不同。

**深水区备料**

- 动态 Workflow 上界：最多 8 步、角色白名单、禁止递归 compose/team_fanout、反思和重试有上限、必须以报告角色收尾。
- Coordinator 的 LLM 输出只是 `GeneratedWorkflow` 数据，没有直接执行权限。
- team 子流程用新 Blackboard，团队之间不共享 scratch；完成后串行合并 findings，再做跨团队一致性校验。
- 单团队失败返回空结果并继续，Aggregator 仍可基于其余团队产出。
- 当前数据驱动 AgentCard 不会自动进入 Coordinator 生成白名单，这是明确边界。

**大概率追问**

- **Coordinator 生成非法流程怎么办？**
  先把校验错误回灌给它自修复一次——大多数问题是引用了白名单外的角色或者步数超了，模型看到具体错误通常能改对。改完还不合法就直接回退内置 deep，不再继续试。这里的关键是它的输出只是一份待校验的数据，没有直接执行权限，所以最坏情况是浪费一次调用，不是跑出一个危险流程。

- **team_fanout 为什么不用主 Blackboard 分支副本？**
  因为团队要的是彻底隔离——每个团队盯一个 focus 独立研究，互相看到对方的中间状态反而会干扰。所以团队用全新的 Blackboard，scratch 不共享，完成后串行合并 findings 再做跨团队一致性校验。代价是团队之间无法在过程中互补，只能在汇总阶段发现分歧。

- **动态编排如何评估收益？**
  和固定工作流做同口径对照：同一批问题分别走 compose 和内置 deep，比质量、Token 和墙钟。动态编排的卖点是简单问题不必跑完整流程，所以收益应该体现在成本上而不只是质量上。目前这个对照的样本量还不足以下结论，我不会把它说成已验证有效。

**坑**

- 不要把 Coordinator 说成可以调用任意代码。
- 不要说团队之间会自由对话；当前是隔离研究后汇总。
