## 一、设计思路总述

系统的可靠性目标一句话：**进程可以在任意时刻被 kill -9，重启后另一个（或同一个）实例能安全接管、从最近 checkpoint 续跑，且历史数据、事件流对外表现一致**。围绕它的关键决策如下（问题→方案→备选与取舍→代价/边界）：

**1. 仓储协议 + 双实现。** 问题：编排器与 API 都要读写运行数据，但测试不能依赖数据库。方案：`ResearchRepository` 用 `typing.Protocol` 定义（repository.py:67），结构化满足、无需继承；`InMemoryRepository`（memory_repository.py:34）与 `SqlRepository`（sql_repository.py:76）两实现。**内存版是协议的参考实现**（repository.py:9 明示）：它用最少代码表达每个方法的语义（如 save_events 的覆盖式、lease 的条件转移），SQL 版必须对齐它——test_repository.py:41 用 `params=["memory","sqlite"]` 让两实现跑同一套用例强制行为等价。备选：只留 SQL 版 + mock——但 mock 只验证调用不验证语义。代价：新增方法必须写两遍并补对齐测试。

**2. 每写方法独立事务 + expire_on_commit=False。** 问题：async 下 ORM 惰性加载在 commit 后失效会炸。方案：每个写方法 `async with self._sm() as s, s.begin()` 独立短事务（sql_repository.py:87 等），sessionmaker 统一 `expire_on_commit=False`（db.py:47），commit 后对象仍可读，转 DTO 内联完成。备选：长事务贯穿整个 run——SQLite 单写者下会把库锁死。代价：跨方法没有原子性，所以「终局产物」专门提供单事务的 `replace_artifacts`（sql_repository.py:245）兜底。

**3. checkpoint 粒度 = 层/步骤边界，语义 = at-least-once。** 问题：断点续跑存多细？方案：引擎只在根流程每个 step（线性 workflow.py:577-578）/每层图节点完成后（workflow.py:781-782）把整个 Blackboard 序列化为 checkpoint（workflow.py:356-383），经 `checkpoint_sink` → `save_orchestration` 落库（orchestrator.py:453-457）。备选：每次 LLM 调用后写——写放大严重、且黑板中间态不是一致快照。取舍：崩溃点到上一 checkpoint 之间的层会**整层重跑**，LLM 调用是 at-least-once，不是 exactly-once；这是明码标价的边界，靠层粒度把重复上限锁死在一层内。

**4. 租约（owner/TTL 120s/心跳 60s）+ fencing 条件写。** 问题：两个实例同时认为自己拥有一个 run（脑裂）。方案：`workflow_run` 行带 `lease_owner/lease_expires_at`（orm.py:212-215）；acquire 是条件 UPDATE「无主或已过期才写入」（sql_repository.py:374-390）；心跳每 60s 续约（api.py:56, 735-758），**续约失败立即 cancel 执行任务**（api.py:754-756）；关键写全部先过 `_owned_workflow_row`——一条 no-op UPDATE 带 owner+未过期条件，rowcount=0 即抛 `LeaseLostError`（sql_repository.py:114-139），空更新的意义是让 PostgreSQL 锁行、SQLite 先取写锁，把「校验租约」和「受保护写」放进同一事务的锁内。备选：单调 fencing token——见下。代价：TTL 是崩溃检测窗，接管前必须等满（防脑裂的安全窗，不是恢复开销，chaos_demo.py:280-281 特意打印区分）。

**5. 为什么还不是单调 fencing token。** owner 是每次尝试新生成的 uuid4（api.py:877, 940），值域上不会 ABA 复用；且条件里带 `lease_expires_at > now`，过期的旧主连自己的写都会被拒。真正的边界：这套 fencing 只保护**同一个 DB 内的写**；若未来有跨存储副作用（对象存储、外部计费），需要单调递增 token 让下游也能拒旧写。另一边界是它信任各实例时钟大致同步（now 由应用侧生成，sql_repository.py:375）。

**6. 启动恢复扫描 + 孤儿处理。** 问题：崩溃 worker 留下的 pending/running run 谁接管？方案：lifespan 启动即扫一遍 + 每 30s 周期扫（api.py:57, 396-404），分页 1000 拉全部候选（api.py:58, 316-324）；对每个候选先 acquire lease，**拿到后必须重读 detail**——第一次读只是候选识别，fencing 后重读才能防止「用过期 checkpoint 恢复」或「重启一个刚完成的 run」（api.py:342-351，测试 test_api.py:701）；有 checkpoint → prepare_resume 续跑，无 checkpoint → 置 error（孤儿无从续，api.py:352-359）。租约检查始终是跨实例仲裁者，扫描只是发现机制。

**7. 定义快照 vs 现行定义。** 问题：自定义工作流可被编辑/删除，恢复时用哪份？方案：创建 run 时把 workflow 定义整份快照进 `workflow_run.definition`（api.py:887-899），恢复时 `Workflow.model_validate(existing_execution.definition)` 优先（orchestrator.py:444-445）；run 参数（max_rounds 等）也快照进 checkpoint 的 `_run_settings`，恢复时还原而非用当前全局配置（orchestrator.py:53,126；api.py:187-200，测试 test_api.py:826）。代价：快照会「过时」，但可复现性 > 新鲜度。

**8. SSE：跨实例订阅 / 终态回放 / 心跳。** 本实例有 EventHub 则走实时流，静默期每 15s 发 `: keep-alive` 注释行防反代掐连接（api.py:61, 498-529）；**非属主实例**不硬拒：轮询持久化状态（0.5s），run 终态后等最多 2s 宽限让终态事件落库，回放 DB 事件、过滤旧 attempt 的异型终态、缺失时合成终态事件（api.py:59-60, 531-594）。resume 时先 `prepare_resume` 原子地「置 running + 删旧终态事件」（sql_repository.py:150-162），并把历史事件（剔除终态）种回新 tracer 再回放给订阅者（api.py:771-784），否则客户端会把上一 attempt 的 done 当真提前断流。

**9. EventHub 无 await 间隙的回放一致性。** `stream()` 里「回放 buffer → 注册订阅队列」全程同步无 await（observability.py:161-170），publish 也是同步调用（Tracer sink），单线程事件循环下两者不可能交错——迟到订阅者不丢不重。队列上界 1024（observability.py:138），慢消费者满了丢当条（publish 不阻塞，observability.py:146-149）；close 哨兵**必达**：QueueFull 时弹一条腾格再放 None（observability.py:151-159）。

**10. SQLite→PostgreSQL 兼容。** 同一套 ORM/仓储跨两库：JSON 列、String(36) uuid、`DateTime(timezone=True)`；SQLite 侧 PRAGMA 补齐生产语义——WAL 并发读写、busy_timeout 15s、foreign_keys=ON 让 CASCADE 真生效（db.py:32-41）；fencing 的空更新在 PG 是行锁、在 SQLite 是库级写锁，语义同样成立。PG 集成测试单独标 `@pytest.mark.pg`（test_repository.py:717）。

**11. 迁移的向后兼容手法。** 0011：先回填 NULL 时间戳再收紧 NOT NULL（20260721_0011:30-46）——「先修数据后加约束」。0014：对账旧 create_all 库——迁移内嵌**历史 schema 快照**而非 import 现行 ORM metadata（否则未来表会被历史迁移提前建出，20260722_0014:30-36），幂等补列、重编号重复 sub_question 后才建唯一约束（:496-539），downgrade 留空（:552-555）。启动时 `prepare_sqlite_schema` 对无 alembic_version 的遗留库 stamp 到 0013 再升级，让 0014 统一修复（db.py:56-83）；连接串经 `config.attributes["database_url"]` 显式传入 env.py 而非改写进程级环境变量（db.py:139-142, env.py:28-29），迁移在 `asyncio.to_thread` 里跑避免嵌套事件循环（db.py:144）。

**12. chaos 演示的度量方法。** 全离线假后端（DR_DEMO_FAKE_BACKENDS，api.py:611-674），每次调用 sleep 2s 并计 1000 模拟 token；先跑对照 run 得完整基线，chaos run 在 step-3 `step.started` 瞬间硬杀，等 TTL+3s 后重启；**接管耗时 = 重启进程 → 首个 `workflow.resumed` 事件**（chaos_demo.py:294-297，实测 ≈1.8s）；**节省占比 =（对照总 token − 恢复后新增 token）/ 对照总 token**（chaos_demo.py:304-306，实测 ≈75%）。诚实声明：token 是按调用计量的模拟值（报告头自带此声明，chaos_demo.py:310），75% 的真实含义是「免于重跑的后端调用占比」——每次调用等权时两者数值相同。

## 二、题库（32 题）

### A. 基础档（7 题）

**A1. 仓储接口为什么用 Protocol 而不是 ABC 基类？**
- 考点：结构化子类型、解耦。
- 参考答案：`ResearchRepository` 是 `typing.Protocol`（repository.py:67-68），两实现无需 import 基类、无继承耦合；类型检查器按方法签名结构化匹配。行为一致性不靠继承靠测试：test_repository.py:41 把 memory 与 sqlite 参数化跑同一套用例。
- 追问链：Protocol 检查发生在什么阶段？→ 静态（mypy）+ 测试；运行时不校验。→ 若两实现语义漂移谁兜底？→ 参数化测试。
- 陷阱：别说「Protocol 有运行时强制」；它默认没有。

**A2. `expire_on_commit=False` 干什么用？不设会怎样？**
- 考点：async SQLAlchemy 陷阱。
- 参考答案：db.py:47。默认 commit 后所有 ORM 实例过期，下次属性访问触发惰性刷新；async session 里同步惰性 IO 会抛 `MissingGreenlet`。设 False 后 commit 完仍可安全读（如 create_run 里 flush 后拿 `run.id`，sql_repository.py:90-112）。
- 追问链：那数据会不会读到旧值？→ 每方法独立短事务，对象生命周期不跨事务，风险可控。
- 陷阱：与「脏读」无关，这是 ORM 对象过期策略。

**A3. SQLite 启动时设了哪些 PRAGMA，各解决什么问题？**
- 考点：SQLite 生产化。
- 参考答案：db.py:32-41——`journal_mode=WAL`（读写并发，读者不阻塞写者）、`busy_timeout=15000`（并发 run 落库时排队而非直接抛 database is locked）、`foreign_keys=ON`（SQLite 默认关外键，开了 `ondelete=CASCADE` 才真级联，delete_run 才能一条 DELETE 清子表，sql_repository.py:435-439）。
- 追问链：为什么 journal_mode 可配（环境变量白名单，db.py:22,35-37）？→ 某些网络文件系统不支持 WAL。
- 陷阱：忘了 foreign_keys 默认 OFF 是最常被追问的点。

**A4. token 事件为什么不落库？**
- 考点：事件分级。
- 参考答案：token 增量是瞬态渲染数据，只发实时 sink 不进 events 列表（observability.py:106-110）、不进 EventHub 回放缓冲（observability.py:141-142）；回放时正文可由 report 事件全量恢复。落库的是有限的非 token 事件，seq 即顺序（orm.py:166 唯一约束 uq_event_run_seq）。
- 追问链：迟到订阅者看不到打字机效果怎么办？→ 接受，回放展示最终内容。
- 陷阱：别说「为了省磁盘」——核心是回放语义只需最终态。

**A5. save_events 为什么是覆盖式（先删后写）？**
- 考点：写语义选择。
- 参考答案：sql_repository.py:303-322，与内存版对齐（memory_repository.py:130-135）。事件在 run 结束时一次性整表落库（orchestrator.py:368-379 finally 里），第二次保存（resume 后）不会撞 (run_id, seq) 唯一约束；seq=下标保证回放有序。
- 追问链：那 run 进行中崩溃事件丢吗？→ 事件流丢（重放靠 resume 时种回 DB 里上一次的 events，api.py:771-784），但 checkpoint/产物不丢。
- 陷阱：覆盖式 + 租约参数（lease_owner）配合才安全，僵尸实例覆盖会被 fencing 拒绝。

**A6. delete_run 如何保证不删掉进行中的 run？**
- 考点：删除与租约协作。
- 参考答案：先看本实例 live map（api.py:1171），再对有编排行的 run 试 acquire_lease，拿不到＝别的实例在跑，返回 409（api.py:1143-1165，测试 test_api.py:310）；拿到后删除，CASCADE 连租约行一起消失。无编排行的遗留 run 若还是 pending/running 也按 leased 处理（api.py:1148-1152）。
- 追问链：为什么删除也要抢租约而不是只看 status？→ status 可能是崩溃残留，租约才是跨实例事实。

**A7. get_run 为什么全用 selectinload？**
- 考点：async 加载策略。
- 参考答案：sql_repository.py:496-514。async 下惰性加载不可用（见 A2），selectinload 一次预取 sub_questions/results.findings/report/tags/orchestration.steps，再内联转 Pydantic DTO；避免 N+1 与 MissingGreenlet。
- 追问链：为什么不 joinedload？→ 一对多集合 joinedload 行数爆炸，selectin 是集合关系惯用解。

### B. 进阶档（8 题）

**B1. checkpoint 到底在哪些时刻写？内容是什么？**
- 考点：断点续跑核心。
- 参考答案：三类时刻——①根流程每步/每层完成后（workflow.py:577-578 线性、781-782 图）；②终态（成功 finally workflow.py:604-616、失败/取消 except workflow.py:582-598）；③内容 = 整个 Blackboard 的 JSON（含 plan/results/report/scratch）+ workflow 定义快照 + 步骤状态表（workflow.py:366-383），并把 tracer 的 total_tokens/estimated/elapsed 塞进 scratch `_runtime_metrics`（workflow.py:361-365），恢复时 `restore_metrics` 还原（orchestrator.py:239-245, observability.py:54-61）——预算与耗时账目跨 attempt 连续。
- 追问链：终态 checkpoint 抛 LeaseLostError 为什么吞掉？→ 租约已被继任者接管，终态写不进去是预期，不能掩盖原始异常（workflow.py:595-598）。
- 陷阱：说「每次 LLM 调用都 checkpoint」就错了。

**B2. 租约三个参数（TTL 120s / 续约 60s / 扫描 30s）之间的约束关系？**
- 考点：参数推理。
- 参考答案：TTL=120s（sql_repository.py:374 默认）、心跳 60s（api.py:56）、恢复扫描 30s（api.py:57）。约束：心跳间隔 < TTL/2，容忍一次续约失败/延迟不丢锁；扫描间隔 < TTL，保证 TTL 过期后最多再等一个扫描周期就被接管；接管最坏延迟 ≈ TTL + 扫描间隔。
- 追问链：TTL 调小行不行？→ 崩溃检测更快，但 GC 停顿/慢 SQL 更易误杀活主（续约失败即 cancel，api.py:747-756）。
- 陷阱：TTL 不是恢复耗时，是防脑裂安全窗（chaos_demo.py:280-281 专门区分）。

**B3. `_owned_workflow_row` 的「空更新」到底在防什么？**
- 考点：fencing 实现细节。
- 参考答案：sql_repository.py:114-139。UPDATE ... SET lease_owner=owner WHERE owner=me AND 未过期——值没变（no-op），但 PostgreSQL 会锁住匹配行、SQLite 会先取写锁；于是「校验租约」与随后的受保护写在**同一事务的锁保护下**串行化，另一实例的 acquire_lease 必须等本事务提交后才能改租约行。rowcount=0（owner 不符或过期）→ 抛 LeaseLostError。测试：test_repository.py:181。
- 追问链：为什么不 SELECT ... FOR UPDATE？→ SQLite 不支持 FOR UPDATE，空更新是两库统一的取锁写法。
- 陷阱：不是为了改数据，是为了拿锁 + 原子校验。

**B4. prepare_resume 为什么必须原子？**
- 考点：resume 的可见性。
- 参考答案：sql_repository.py:150-162 单事务内「fencing 校验 + status 置 running + 删除旧 attempt 的 ORCHESTRATOR done/error 事件」。若不原子：SSE 非属主路径可能读到「status=running 但旧 done 事件还在」，把旧终态回放给客户端提前断流；或反之。测试：test_repository.py:231、test_api.py:166,907。
- 追问链：resume 端点为什么 202 之前就要 prepare_resume？→ 客户端拿到 202 后立即重连流，必须已看到新 attempt（api.py:956-958 注释）。

**B5. 启动恢复扫描完整流程口述一遍。**
- 考点：恢复路径全景。
- 参考答案：api.py:308-394——分页拉 pending/running（1000/页）→ 跳过本实例 live 中的 → 读 detail，无编排行直接置 error → 生成新 owner uuid，acquire_lease 失败跳过（别人在跑或 TTL 未到）→ **重读 detail**（fencing 后快照才可信）→ 状态已终态/checkpoint 为空则放弃（空 checkpoint 置 error 释放租约）→ prepare_resume → 建 EventHub → create_task(_execute) 移交租约。失败路径统一在 finally 归还租约、清 live（api.py:387-394，测试 test_api.py:563）。
- 追问链：为什么每 30s 还要再扫？→ 启动时 TTL 可能未到期，崩溃 worker 的租约在启动后才过期（api.py:310-313 注释）。

**B6. 恢复时的运行参数从哪来？为什么不用当前全局配置？**
- 考点：快照一致性。
- 参考答案：创建 run 时把 max_rounds/max_tokens 等七个字段快照进 checkpoint scratch `_run_settings`（orchestrator.py:53,126；api.py:62-70），恢复时 `_settings_for_resume` 还原（api.py:187-200）。否则管理员中途改配置会让同一 run 的两个 attempt 行为不一致（预算突然变小把 run 憋死）。密钥不快照——密钥轮换后应可用新密钥续跑。测试：test_api.py:826。
- 陷阱：注意「非密钥快照、密钥用现行」这条分界。

**B7. SSE 心跳为什么两层？15s 是怎么定的？**
- 考点：长连接工程。
- 参考答案：本地流路径经中转队列 `wait_for(…, 15s)` 超时发 `: keep-alive` 注释行（api.py:505-526）——LLM 一步可静默到 600s，反代（nginx 默认 60s）会掐空闲连接；远端轮询路径同样按 15s 节流心跳（api.py:543-548）。注释行是 SSE 协议规定客户端必须忽略的帧。测试：test_api.py:496。
- 追问链：为什么不用 EventSource 自动重连兜底？→ 重连有间隙、且要靠回放补齐，keep-alive 更平滑。

**B8. 非属主实例的 SSE 为什么不直接 404 / 空流？**
- 考点：跨实例流。
- 参考答案：api.py:489-594。事件是终态整表替换持久化（B-A5），非属主实例做不了 token 级实时，但必须挂住连接：轮询状态 → 进行中就心跳等待 → 终态后等 ≤2s 宽限（等终态事件落库）→ 回放 DB 事件，过滤旧 attempt 异型终态、必要时合成终态帧；轮询中发现状态回到 running（被 resume）就整轮重来（api.py:558-575）。测试：test_api.py:112,150,166。
- 陷阱：宽限期是因为「status 更新」与「事件落库」是两个事务（finalize 与 save_events 分离，orchestrator.py:336-379）。

### C. 深入档（9 题）

**C1. EventHub 迟到订阅者为什么保证不丢不重？给出证明思路。**
- 考点：并发推理。
- 参考答案：observability.py:161-170。stream() 内「把 buffer 逐条 put → 把队列加入 _subscribers」之间没有任何 await；publish 是同步函数（作为 Tracer sink 被同步调用）。单线程事件循环上，同步代码段是原子的——publish 要么整体发生在注册前（事件已进 buffer，被回放），要么整体在注册后（直接进队列），不存在既错过回放又错过实时的交错。close 后订阅者也能拿到回放 + 哨兵（observability.py:168-169，测试 test_event_hub.py:75）。
- 追问链：多线程还成立吗？→ 不成立，这是显式依赖 asyncio 单线程模型的设计；跨线程需加锁。
- 陷阱：能说出「无 await 间隙」四个字才算答到点上。

**C2. 慢消费者会怎样？close 哨兵为什么必达？**
- 考点：背压策略。
- 参考答案：队列上界 1024（observability.py:138）；满时 publish 丢当条不阻塞（observability.py:146-149）——阻塞会拖垮整个 run 的执行协程，不可取；丢的非 token 事件由 run 详情接口兜底。close 时若队列满，先 get_nowait 弹一条腾格再放 None（observability.py:151-159），保证订阅者不会因收不到哨兵永久挂起。
- 追问链：为什么回放切片是 `[-(1024-1):]`？→ 给哨兵留一格，put_nowait 不会因满而抛（observability.py:165-167）。

**C3. 优雅关停为什么必须先停 recovery loop？顺序推演。**
- 考点：关停顺序因果。
- 参考答案：api.py:441-457。顺序：cancel recovery_task 并等它结束 → 快照并 cancel 其余后台任务 → engine.dispose()。若先快照任务：恢复扫描可能在快照之后又移交一个新 _execute，逃过取消，进而在 engine dispose 后继续发 SQL。测试：test_api.py:596。
- 追问链：被 cancel 的执行任务落库状态吗？→ 不置 error——CancelledError 直接 re-raise（api.py:787-791），run 保持 running + checkpoint，让下一次启动恢复接管；测试 test_api.py:1060。

**C4. `_execute` 的 finally 为什么把清理放进独立 task 再 shield？**
- 考点：取消语义细节。
- 参考答案：api.py:830-847。第二次 task.cancel()（如关停时）会打断正在 await 的 finally 清理；把清理放进独立 task、循环 `await asyncio.shield(cleanup_task)`，即使外层收到 CancelledError 清理仍跑完（心跳取消、租约释放、LLM/搜索连接池关闭、hub.close、live 清理），最后再补抛 CancelledError 保留取消语义。测试：test_api.py:863。
- 陷阱：直接 `shield(coroutine)` 不够——shield 被取消时协程若无人 await 仍可能中断；shield 的是**独立 task**。

**C5. 恢复/resume 为什么都要「获取租约后重读」？构造一个不重读会坏的场景。**
- 考点：TOCTOU。
- 参考答案：api.py:342-351、945-954。场景：扫描先读到 run（checkpoint 版本 N），此刻旧 worker 还活着，又写了 checkpoint N+1 并 finalize 成 done，随后 TTL 过期；扫描此时才抢到租约——若用第一次读的快照，会用过期 checkpoint N 重启一个已完成的 run。重读发生在 fencing 之后，旧 worker 再也写不进来，快照才可信。测试：test_api.py:701, 786, 739（并发 resume 只有一个赢）。

**C6. 图模式恢复：为什么条件跳过是「暂定」而预算跳过是「终态」？**
- 考点：恢复语义分叉。
- 参考答案：workflow.py:673-688。条件跳过（`_INCOMING_CONDITIONS_SKIP_REASON`）源于上游失败/条件不激活——恢复重跑时上游可能成功，本节点资格改变，所以要重新判定；预算跳过是终态，因为恢复会经 `_runtime_metrics` 还原 token 累计与预算（B1），预算在上个 attempt 耗尽这次仍是耗尽。测试：test_checkpoint_resume.py:168。
- 追问链：同一 node 多个历史 StepRun 取哪个？→ 最新一次（test_checkpoint_resume.py:207）。

**C7. 并行层里一个节点失败、兄弟节点成功，为什么必须把成功输出 merge 进失败 checkpoint？**
- 考点：并行失败隔离 + 持久化正确性。
- 参考答案：workflow.py:768-779。gather 抛异常时先 cancel 未完成任务、`return_exceptions=True` 收尾，再 merge 成功兄弟的黑板增量。因为成功节点已被 runtime 标 SUCCEEDED（持久化的运行时状态），恢复时会**跳过**它；若其输出不在 checkpoint 里，跳过即永久丢失产物——状态与数据必须一起落。
- 陷阱：这是「状态机说做过了、数据却没存」的经典一致性坑。

**C8. 迁移 0014 为什么不 import 现行 ORM metadata？0011 的手法叫什么？**
- 考点：迁移工程。
- 参考答案：0014 内嵌截至 0013 的历史 schema 快照（20260722_0014:29-36 注释）：历史迁移若引用 live metadata，未来新增的表/列会在这条历史迁移执行时被提前建出，破坏后续迁移的前提；且整条迁移幂等（inspector 探测后补列/补约束），补唯一约束前先重编号重复 (run_id, idx)（:496-539），downgrade 保持 schema 不回退（:552-555）。0011 是「先回填后收紧」：UPDATE NULL→now() 再 alter NOT NULL（20260721_0011:30-46）。
- 追问链：遗留 create_all 库怎么进入迁移轨道？→ prepare_sqlite_schema 检测无 alembic_version 且有表 → stamp 到 0013 → upgrade head 让 0014 统一对账（db.py:72-83）；曾被错误 stamp 到 head 的库也测过（test_repository.py:488）。

**C9. alembic 连接串为什么走 config.attributes 而不是改环境变量？**
- 考点：全局状态卫生。
- 参考答案：db.py:139-142 注释 + env.py:28-29。临时改写 `os.environ["DATABASE_URL"]` 会与任何并发读环境变量的代码产生隐式全局耦合（测试并行、同进程多库）；attributes 是 per-Config 的显式传参。另两处细节：URL 里 `%` 转义 `%%` 防 ConfigParser 插值炸（env.py:29），upgrade 在 `asyncio.to_thread` 跑（db.py:144）——alembic 内部 `asyncio.run` 不能嵌在已运行的事件循环里。

### D. 压力档（8 题）

**D1. kill -9 之后，到底会不会重复调 LLM、重复扣费？**
- 考点：诚实说清 at-least-once。
- 参考答案：**会，有界地会。** checkpoint 在层边界写（B1），崩溃点落在「层内某次 LLM 调用完成后、层 checkpoint 前」时，恢复会整层重跑，这一层的 LLM 调用重复执行、重复计费——语义是 at-least-once，不是 exactly-once。上界 = 一层的工作量；已 checkpoint 的层被跳过（chaos 演示实测跳过率对应 75% token 节省）。做不到 exactly-once 的根因：LLM 调用是外部副作用，无法与本地事务原子提交；要逼近它得做请求级幂等键 + 结果缓存，成本远超一层重跑的期望损失。token 账目上不会双记：恢复从 checkpoint 里的 `_runtime_metrics` 续算（workflow.py:361-365），重复调用产生的是**真实的新消耗**，账目如实反映。
- 追问链：那两个实例会不会同时重复调？→ 不会，租约互斥（D2）。→ 怎么把重复窗口做小？→ checkpoint 更细粒度（写放大取舍）或子问题级结果缓存。
- 陷阱：说「不会重复」是错的；说「重复无上界」也是错的。

**D2. 两个实例同时写同一个 run 会怎样？推演一遍。**
- 考点：脑裂推演。
- 参考答案：分三幕。①同时抢：acquire_lease 是条件 UPDATE「owner IS NULL 或已过期」（sql_repository.py:374-390），DB 串行化两条 UPDATE，一个 rowcount=1 赢，一个 rowcount=0 输，输家不启动（test_repository.py:635；并发 resume 只启动一个：test_api.py:739）。②旧主假死后复活（GC 停顿超 TTL，B 已接管）：A 的心跳续约条件 `owner=A AND 未过期` 失败 → 发终止事件并 cancel 自己（api.py:747-756，test_api.py:957）；即便 cancel 前 A 还有一次在途写，`_owned_workflow_row` 的空更新在同事务锁内校验 owner=A 失败 → LeaseLostError，写被拒（sql_repository.py:114-139，test_repository.py:181）。③A 在 B acquire 的同瞬写：空更新先锁行，B 的 acquire 等 A 事务提交；A 提交后 B 才改 owner，此后 A 一切 fenced 写被拒。结论：受保护写不可能交错；结合 D3 说明非 fenced 中间写为何也无害。
- 陷阱：推演时忘掉「过期的旧主连自己的写都过不了 `lease_expires_at > now` 条件」这一层。

**D3. 我看 save_result / save_plan / save_sources 根本没带 lease_owner——僵尸实例的脏写怎么办？**
- 考点：真实短板 + 补偿设计。
- 参考答案：承认：中间产物写方法确实未 fencing（sql_repository.py:164-243 无 lease 参数）。防线在终局：`replace_artifacts` 是**带 fencing 的单事务整体替换**——删光 plan/results/report 再按继任者的黑板重写（sql_repository.py:245-301，orchestrator.py:503-512 注释「final derived artifacts are one unit」）；僵尸的中间脏写会被继任者的终局替换整体覆盖，不会进入最终可见状态。事件同理：save_events 覆盖式 + fencing。真正的残余窗口：run 进行中读详情接口可能短暂看到僵尸的中间行——只影响进行中的展示，不影响终态一致性。测试：test_repository.py:150（replace 幂等）。
- 陷阱：直接否认「有未 fencing 的写」会被当场翻代码打脸；正确姿势是承认 + 讲补偿机制。

**D4. 为什么不是单调递增的 fencing token？这里有没有 ABA？**
- 考点：分布式基本功。
- 参考答案：经典单调 token（Chubby/ZK 风格）防两件事：ABA（同一持有者标识被复用）与下游旧写（token 随请求带给外部系统）。本系统：owner 每次尝试都是新 uuid4（api.py:877,940），不存在值复用意义上的 ABA；且所有受保护写都发生在**同一个 DB**、都经条件写校验，DB 本身就是仲裁者，不需要把 token 带给第三方。所以 uuid + TTL 条件写在当前架构内与单调 token 等强。边界（要主动说）：一旦出现跨存储副作用（对象存储写文件、外部计费接口），DB 条件写鞭长莫及，就必须换单调 token 让下游可比较新旧；另外条件里的 now 来自应用时钟（sql_repository.py:375），多实例时钟漂移会放大/缩小 TTL 窗口，生产应配 NTP 或改用 DB 时钟。
- 陷阱：背「必须单调 token」教条而说不出「为什么这里 uuid 够用、什么时候不够」。

**D5. SQLite 能撑生产吗？**
- 考点：技术选型的分寸感。
- 参考答案：分场景答。单实例（桌面版/单容器）：能——WAL 读写并发 + busy_timeout 15s 排队 + foreign_keys 级联（db.py:32-41），写入本就低频（层边界 checkpoint + 终态整表事件），单写者模型完全够。多实例：不能也不该——租约仲裁要求所有实例共享同一个库，SQLite 是进程内文件库，跨机共享（NFS）锁语义不可靠；此时切 `postgresql+asyncpg`，同一套仓储代码直接可用（URL 切换即可，条件写在 PG 语义更强：行锁而非库锁），PG 路径有独立集成测试（test_repository.py:717）。诚实边界：JSON 列在 SQLite 无索引查询能力、事件表大了整表覆盖写会变慢——真上量应改追加式事件 + 增量 seq。
- 陷阱：一刀切答「能」或「不能」都丢分。

**D6. 事件回放会不会丢、会不会重？**
- 考点：把「哪条通道什么语义」拆开说。
- 参考答案：分三条通道。①持久化回放（GET /events、终态 SSE）：不丢不重——终态整表覆盖写 + (run_id, seq) 唯一约束 + 按 seq 排序（sql_repository.py:303-322, orm.py:166）；但**进行中崩溃**则该 attempt 未落库事件丢失，resume 时从 DB 种回上一次的事件（api.py:771-784）弥补展示连续性。②进行中实时 SSE：at-most-once——慢消费者队列满丢当条（observability.py:146-149），刻意用丢换不阻塞执行；断线重连经 EventHub 缓冲回放补齐（1024 上界，超长 run 截尾）。③token 事件：纯瞬态，无订阅者直接蒸发，设计如此（A4）。重复：同一订阅同一事件不会重；resume 场景客户端会再次收到历史事件（种回 + 回放），靠剔除旧终态防止「重复终态」引发的断流（api.py:774-782）。
- 陷阱：不区分通道就答「不丢不重」必被追杀。

**D7. 为什么不用 Celery / 消息队列？**
- 考点：架构自洽性。
- 参考答案：先说本质：Celery 解决的是「任务分发 + 独立 worker 池」，本系统刻意选了**进程内 asyncio 任务 + DB 租约**。理由：①负载是 IO 密集的 LLM/检索长调用，asyncio 单进程并发绰绰有余，不需要 CPU 型 worker 池；②可靠性诉求（崩溃恢复）靠 checkpoint + 租约 + 恢复扫描已闭环，broker 的 ack/redelivery 与之重复；③部署形态是零依赖单件交付（SQLite 同理，还有 PyInstaller 桌面版，api.py:76-78）——引 Redis/RabbitMQ 是为中间件本身引入新的可用性问题；④Celery 对 asyncio 原生支持一直别扭。诚实代价：执行与 API 同进程，重研究任务会与请求争事件循环；无法独立横向扩容「计算面」；恢复延迟受 TTL 约束（Celery redelivery 也有 visibility timeout，本质同类）。什么时候该换：多租户高并发、需要独立 worker 弹性伸缩时，把 `_execute` 剥成独立 worker 进程，仓储协议不用动——这是协议抽象预留的迁移路径。
- 陷阱：把「没用 MQ」说成疏漏；正确姿势是「同一问题的另一种闭环 + 明确的换轨条件」。

**D8. 1.8s 接管、75% 节省——怎么测出来的？可信吗？**
- 考点：度量诚实性。
- 参考答案：先讲方法（chaos_demo.py）：完全离线假后端（DR_DEMO_FAKE_BACKENDS=1，api.py:618-674），每次 LLM/检索调用 sleep 2s、计 1000 模拟 token；四阶段——对照 run 拿完整基线 → chaos run 在 step-3 的 step.started 事件瞬间 `proc.kill()`（Windows 上即 TerminateProcess，等价 kill -9，chaos_demo.py:116-120）→ 等 TTL 120s+3s 余量 → 重启。**1.8s** = 重启进程时刻到 SSE 上首个 `workflow.resumed` 事件的间隔（chaos_demo.py:294-297；resumed 事件在 runtime.restore 发出，runtime.py:23-25），衡量的是「扫描发现 + 抢租约 + 加载 checkpoint」的接管开销，**不含** 120s fencing 等待——报告里两者分开打印（chaos_demo.py:316-318）。**75%** = (对照总 token − 恢复后新增 token) / 对照总 token（chaos_demo.py:304-306）。可信度要主动交代三点：①token 是按调用等权的模拟计量，不是真实计费 token（报告标题自带声明，chaos_demo.py:310）；因为每次调用等权，75% 的**真实含义是免于重跑的后端调用占比**——这个占比是真实执行路径测出来的（哪些节点跳过、哪些重跑是真实的 checkpoint 行为）；②1.8s 依赖 --delay 参数与本机性能，量级（秒级）可信、小数位不必较真；③演示可复现：单命令、临时 SQLite、无网络无 key。
- 陷阱：把 75% 说成「省了 75% 的钱」——真实 LLM 调用 token 分布不均（synthesizer 最贵），实际节省比例取决于断点位置；诚实说法是「调用占比」。

**（附加压力）D9. 续租失败为什么直接 cancel 任务而不是降级成只读继续跑完？**
- 考点：设计立场。
- 参考答案：api.py:747-756。续约失败意味着本实例可能已不是属主，继续跑会：①白烧 LLM 费用（结果写不进去，所有 fenced 写会 LeaseLostError）；②与接管者并发调用外部 API 造成真实世界重复副作用。cancel 是止损：checkpoint 已落库到最近层边界，接管者从那续跑。降级只读没有意义——研究的产出必须落库才有价值。注意 cancel 路径不置 error（api.py:787-791），run 保持可恢复。

**可靠性五件套口诀「照·档·栏·跳·扫」**
- **照**（快照 checkpoint）：层边界写整块 Blackboard + 定义快照 + 计量（workflow.py:356-383）
- **档**（租约 lease）：owner uuid + TTL 120s，条件写转移（sql_repository.py:374）
- **栏**（围栏 fencing）：空更新锁行校验 owner+未过期，失败抛 LeaseLostError（sql_repository.py:114）
- **跳**（心跳 heartbeat）：60s 续约，失败即 cancel 止损（api.py:735-758）
- **扫**（恢复扫描 recovery scan）：启动 + 每 30s，抢锁后重读再续跑，无 checkpoint 置 error（api.py:308-404）

**三句兜底话术（承认边界）**
1. 「LLM 调用是 at-least-once——重复上界是一层，exactly-once 需要请求级幂等键，成本不划算。」
2. 「中间产物写没 fencing，但终局 replace_artifacts 是带 fencing 的单事务整体替换，僵尸脏写活不到终态。」
3. 「执行在 API 进程内、没有独立 worker——这是单件交付的取舍；要横向扩容时把 _execute 剥出去，仓储协议不用改。」
