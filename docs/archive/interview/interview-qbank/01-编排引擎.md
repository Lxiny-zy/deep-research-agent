## 一、子系统设计思路总述

### 1.1 解决什么问题

原始版本的编排器把「Planner→Researcher→Reflector→Synthesizer」写死在代码里：新增角色要改编排器、换流程要改代码、LLM 无法在运行时自己组队。本子系统把**控制流从代码降维成数据**：一个 `Workflow` 就是一串 `Step`（Pydantic 模型，workflow.py:44-71），引擎 `WorkflowEngine`（workflow.py:322）是一个无状态解释器，逐步解释 Step、对同一块 `Blackboard`（agents/base.py:26-41）加工，直到产出报告。数据流是：编排器组装 `RunContext` → 选一份 Workflow（公共模板仅 `deep`、`quick`、`hsi_review`，另有内部兼容流程或用户自建图）→ 引擎执行 → 黑板上的 plan/results/report 落库（orchestrator.py:459-468）。

每次运行都在引擎启动前经过全局意图/风险门禁；`guarded` 只是历史兼容别名，不是门禁开关，也不在产品 UI 或自动路由中出现。默认 `DR_ORCHESTRATION_MODE=planner-driven`，`framework/06_global_rules.md` 作为共享系统上下文注入内置、自定义和 planner-authored 的每个 Agent。

在这个地基上叠了四层能力：L1 声明式线性流程；L2 按任务类型路由不同模板（workflows.py:60）；L3 Coordinator 运行时生成流程（compose 原语，workflow.py:822）；L4 多团队并行 map-reduce（team_fanout 原语，workflow.py:885）。此外支持 DAG 图执行（分层并行 + 条件边 + 三种 Join，workflow.py:618）、checkpoint/断点续跑、token 预算、单步重试/超时/降级/失败隔离。

### 1.2 关键设计决策（问题 → 方案 → 备选与取舍 → 代价/边界）

**① Workflow-as-Data vs 代码定义流程**
- 问题：流程写死在编排器里，新增流程/角色都要改核心代码，LLM 更不可能生成"代码"来编排。
- 方案：Workflow/Step 是纯 Pydantic 数据（workflow.py:44-71），引擎按名字从注册表解析角色（registry.py:34-38）。新增流程只是多声明一份数据（workflows.py:38-42 的 reviewed 就是 `DEEP.steps + critic` 一行）。
- 备选：像早期 LangChain 一样用代码链组合。取舍：数据可校验（validate_workflow）、可持久化（checkpoint 里存 definition）、可被 LLM 生成（GeneratedWorkflow）、可被前端拖拽编辑——这四件事代码定义都做不到或很难做。
- 代价：表达力受限于引擎支持的原语集合（agent/reflect_loop/compose/team_fanout + 条件边），任意控制流（如 while-true）刻意不支持——这同时也是「可证终止」的来源。

**② 黑板模式 vs 消息传递**
- 问题：多角色如何共享中间产物？
- 方案：单一共享 Blackboard，所有角色实现统一协议 `async step(bb, ctx) -> Blackboard`（agents/base.py:75-85），引擎只搬黑板不理解语义；新角色的私有数据挂 `scratch` 不污染核心 schema（base.py:38-39）。
- 备选：Actor/消息传递（如 AutoGen 的对话式）。取舍：黑板让引擎与角色彻底解耦（引擎不需要知道 Planner 输出是什么类型）、checkpoint 只需序列化一个对象、调试时看一眼黑板就是全量状态；消息传递适合开放式对话，但状态分散、快照/恢复困难。
- 代价：并行分支写同一逻辑黑板会有竞争——所以引擎在并行处强制「隔离副本 + 显式合并」（见⑥），黑板模式的代价被转化成了一个明确的合并算法问题。

**③ 条件表达式解释器为什么不用 eval**
- 问题：图的边需要条件（如 `state.scratch.route == "a"`），条件来自用户/前端/LLM，属于不可信输入。
- 方案：手写 40 行的小语言（orchestration/conditions.py）：一条正则限定 `路径 [比较符 JSON字面量]` 形态（conditions.py:9），路径解析是**全函数**——dict 取 `last`、对象取 `length` 一律返回 None 不抛异常（conditions.py:12-25），字面量只接受 JSON（conditions.py:38-48）。
- 备选：`eval`/`ast.literal_eval` + 表达式库（如 simpleeval）。取舍：eval 是 RCE，直接被测试拒绝（test_workflow_conditions.py:30-34 里 `__import__('os').system('x')` 抛 ValueError）；引第三方表达式库则引入攻击面与依赖。40 行换来可枚举的安全边界。
- 代价：表达力弱（无 and/or/函数调用）。运行期仍可能暴露非法字面量——引擎兜底为「该边按不激活处理 + 发警告事件」，不让单条坏边经 asyncio.gather 炸穿整个 run（workflow.py:697-716，test_graph_workflow_run.py:221-260）。

**④ 三种 Join 语义**
- 问题：DAG 汇聚节点在「前驱被条件跳过 / 前驱失败」时到底该不该跑？一个语义满足不了所有场景。
- 方案：节点级 `join_mode: any | all | success_all`（graph.py:20；求值在 workflow.py:718-728）。any＝任一入边激活即跑（条件路由的汇聚点）；all＝所有入边条件都激活才跑（严格会师，test_graph_workflow_run.py:293-330 验证一条分支被跳过时 synthesizer 也跳过）；success_all＝在 all 之上还要求所有前驱**执行成功**（失败隔离默认 continue，失败节点仍算"激活"，success_all 给需要完整输入的节点如 aggregator 一个更严格的门槛）。
- 备选：LangGraph 式默认全量 join。取舍：与「条件边 + 失败隔离」组合时必须区分「没被路由到」和「跑了但失败」，单一语义会导致要么汇聚点永远等不齐、要么拿着残缺输入硬跑。
- 代价：用户要理解三种语义的差别；默认 any 在「全分支都被跳过」时会静默跳过下游（有 skip 状态可查）。

**⑤ 失败隔离模型**
- 问题：一个角色抛异常，是炸穿整个 run 还是继续？
- 方案：默认 `failure_policy="continue"`——单步失败被捕获、step 进入显式 FAILED 状态、发 error 事件后继续（workflow.py:567-576）；可选 `fail_fast` 向上抛并把 run 终态置 FAILED。层级化隔离：步骤级（重试→fallback_agent→隔离）、团队级（单团队失败返回 None 不拖垮兄弟，workflow.py:914-916）、边级（条件求值失败按不激活）。失败事件挂在角色自己的 Stage 而非 ORCHESTRATOR——后者是运行终态信号，会让 SSE 提前断流；用户自建名为 orchestrator 的角色卡还会被降级到 STEP_ORCHESTRATOR 兜底（workflow.py:497-515，test_workflow.py:142-166）。
- 备选：全有全无（任何异常即失败）。取舍：研究场景里「12 个子问题挂 1 个」不应损失其余 11 个的产出；尽力而为的报告比完美主义的失败更有用。
- 代价：continue 语义下下游可能拿到不完整输入——这正是 success_all join 与 require_report 兜底（workflow.py:579-580）存在的原因；失败绝不静默，状态机与事件流都留痕。

**⑥ 并行分支深拷贝 + 元素级合并**
- 问题：DAG 同层节点并发跑，都写一块黑板 = 数据竞争。
- 方案：每层先做 `layer_base = bb.model_copy(deep=True)` 快照（workflow.py:664），每个节点在快照的深拷贝上跑（workflow.py:671），gather 后用**三方合并**（base/current/branch，类似 git merge）把每个分支相对快照的增量应用回主黑板：dict 按 key 递归、list 识别 append-only 增量、破坏性改写按元素 diff 覆盖且不抹掉兄弟分支的追加段（`_merge_parallel_value`/`_merge_parallel_sequence`，workflow.py:88-174）。
- 备选：(a) 加锁串行写——并行失去意义；(b) 只允许 reducer 声明的 key 合并（LangGraph channel 方案）——对自由 scratch 区不友好；(c) last-write-wins——会丢数据。
- 代价：合并算法有真实的复杂度和曾经的 bug：本次审查发现「两个分支同时改写基线前缀且各自追加」时，后合并分支会覆盖掉先合并分支的追加段（高危：并行合并丢数据），已修复为「基线段按 branch 相对 base 的逐元素差异覆盖 + 双方追加段都保留」（workflow.py:148-164），并补了单元与端到端回归（test_graph_workflow_run.py:109-158）。这是「承认边界」的最好素材：并行状态合并本质上没有免费午餐，语义冲突（两分支把同一元素改成不同值）只能确定性地取一个并保留另一方增量。

**⑦ token 预算的软语义**
- 问题：反思循环 + 自组合可能无限烧 token；但预算一到就硬杀，用户连部分报告都拿不到。
- 方案：软预算。TokenBudget 只做判断不做统计（token_budget.py:9-41），唯一真相源是 tracer 的累计 token（workflow.py:477-481 每步前 update，取 max 保证单调）；耗尽时**跳过非终端步骤但仍执行终端角色**（synthesizer/aggregator，workflow.py:560-565、483-485），产出尽力而为的报告。跳过是显式 SKIPPED 状态而非静默消失。
- 备选：硬预算（抛异常终止）。取舍：研究产品的用户价值在报告；且「检查点在步骤边界」意味着预算天然是步骤粒度的软限制，无法在 LLM 调用中途精确掐断。
- 代价：可能超支一个步骤的量（检查在步骤开始前，步骤内不检查）；terminal 步骤本身也花 token。测试锚点：test_budget_enforcement.py:43-57（planner 后耗尽→研究被跳过→仍出报告）。

**⑧ Coordinator 动态编排的校验兜底**
- 问题：让 LLM 现场生成流程（L3），LLM 可能输出未注册角色、无限递归的 compose、超长流程、恶意重试参数。
- 方案：生成物只是数据（GeneratedWorkflow，workflow.py:201-208），执行前必须过 `validate_workflow`（workflow.py:256-319）白名单校验：步数≤8、只准引用已注册角色、禁止 compose/team_fanout（杜绝自指递归）、反思轮数≤max_rounds、单步重试≤5 且全流程最坏退避总时长≤120s、必须以终端角色收尾。防线是三层：Coordinator 端「错误回灌自修复一次」（coordinator.py:77-91）→ 引擎端校验失败回退内置 DEEP（workflow.py:860-870）→ 零产出时有界重规划 max_replans 次（workflow.py:837-852）。终止性 = 步数上限 ∧ compose 深度≤1（workflow.py:831-835）∧ 重规划上限 ∨ 预算耗尽。
- 备选：信任 LLM 输出 / 用 prompt 约束。取舍：prompt 是概率保证，校验器是确定性保证；自主性必须以「失控时确定性回退到已知安全流程」为底。
- 代价：白名单会拒绝一些"创意但合法"的流程；回退 DEEP 意味着自组合失败时行为退化为默认流程（但永远出报告）。

**⑨ 与 LangGraph 的对比定位**
- 问题：为什么不用 LangGraph？
- 方案定位：这不是通用框架，是**领域引擎**——原语（reflect_loop/compose/team_fanout）直接对应研究场景的模式；校验器带领域语义（"必须以能产报告的角色收尾"是 LangGraph 不会有的规则）；条件语言、预算软语义、失败隔离粒度都为「尽力而为出报告」这一产品目标服务。自研的第二个动机是可讲清每一行的正确性来源（状态机、合并算法、终止性证明都有对应测试）。
- 诚实边界：LangGraph 的 channel+reducer、时间旅行调试、人在环、子图生态更成熟；本引擎不支持任意循环图（DAG only，循环表达为 reflect_loop 原语）、条件语言表达力弱。如果是通用平台选型，我会认真评估 LangGraph；这里的目标是深研究产品 + 展示引擎工程能力。

## 二、题库（31 题）

### A. 基础理解（8 题）

### Q1.1 【基础】用一分钟讲清这个引擎的执行模型。
**考点**: 整体架构表述能力。
**参考答案**: Workflow 是数据：一串 Step 或一张 DAG（workflow.py:66-71）。引擎是无状态解释器（workflow.py:322-323 注释「无状态，可复用；所有运行态都在传入的 Blackboard 上」）：线性模式逐个 Step 执行（`_run_steps`，workflow.py:530）；图模式先 Kahn 拓扑分层（graph.py:92-148），层内并发、层间串行（`_run_graph`，workflow.py:618）。每个 Step 按名字从注册表解析出角色（registry.py:34），调用统一协议 `step(bb, ctx)`（base.py:85），黑板逐步累积 plan→results→reflections→report。每步结束写 checkpoint（workflow.py:577-578），运行生命周期由 OrchestrationRuntime 状态机记录并转成 SSE 事件（runtime.py:17-115）。
**追问链**: ① 引擎无状态那状态在哪？→ 黑板（业务态）+ WorkflowRun（运行态），都可序列化。② 嵌套执行（compose/team）怎么区分根？→ `_run_depth` 计数，只有根 run 做 start/finish/checkpoint（workflow.py:531、554）。
**陷阱提示**: 不要说"引擎调度线程"——是 asyncio 单线程并发，层内用 `asyncio.gather`。

### Q1.2 【基础】Step 模型里有哪些执行策略字段？各自默认值？
**考点**: 对核心数据结构的熟悉度。
**参考答案**: workflow.py:59-63：`timeout_seconds`（None，上限 3600）、`max_attempts`（1，字段级上限 10）、`retry_backoff`（0.5s，指数退避基数，上限 60）、`failure_policy`（continue/fail_fast，默认 continue）、`fallback_agent`（None，主角色重试耗尽后的降级角色）。执行顺序是：带超时执行→失败则指数退避重试（`retry_backoff * 2**attempt`，workflow.py:443）→重试耗尽走 fallback→仍失败按 failure_policy 处理。
**追问链**: ① fallback 也超时怎么办？→ 同一个 timeout 也约束 fallback（workflow.py:457-458；test_step_policies.py:181-210）。② 字段上限 10/60 与校验上限 5/120s 为什么不一致？→ 见 Q4.4（本次审查修复的缺口）。
**陷阱提示**: 重试是对**主角色**的，fallback 只执行一次，不参与重试循环。

### Q1.3 【基础】黑板（Blackboard）上有哪些字段？scratch 是干什么的？
**考点**: 共享状态设计。
**参考答案**: base.py:26-41：`query`、`plan`、`results`、`reflections`、`report` 五个核心字段 + `scratch: dict` 自由区。scratch 的设计意图是「新角色挂私有数据不改核心 schema」——例如 Coordinator 把生成流程写进 `scratch["composed_workflow"]`（coordinator.py:62），reflect_loop 经 `scratch["pending_sub_questions"]` 给 researcher 传补洞子问题（workflow.py:947），引擎自己也用 `scratch["_compose_depth"]`、`scratch["_runtime_metrics"]` 存元数据。
**追问链**: ① scratch 没 schema 会不会失控？→ 引擎内部 key 带下划线前缀约定；条件语言对任意形态做全函数解析兜底。② 为什么黑板是 Pydantic？→ checkpoint 就是 `bb.model_dump(mode="json")`（workflow.py:373），恢复即 model_validate。
**陷阱提示**: 别说"黑板是全局单例"——每个 run 一块，团队子流程还有隔离子黑板。

### Q1.4 【基础】公共内置模板有哪些？新增一条要改多少代码?
**考点**: L2 路由与可扩展性论据。
**参考答案**: 产品界面只展示三种公共模板：deep（完整深度研究）、quick（快速查询）和
hsi_review（AI4S/HSI 文献审查）。其余 `brief`、`fact_check`、`monitoring`、`teams`、`auto`
以及历史 `guarded` 仍保留在注册表，供旧 checkpoint、CLI 或 planner 兼容使用，但不作为公共模板，
也不承担全局安全门禁。新增一个模板只需在 `workflows.py` 声明 `Workflow` 并加入注册表，
无需修改引擎或编排器；未知流程名仍回退 deep，避免拼写错误打断运行。
**追问链**: 新增角色呢？→ 实现 `step(bb, ctx)` 协议 + `@register("name")` 装饰（registry.py:21-31），流程里写名字即可。
**陷阱提示**: 回退语义要说清是「静默回退+默认流程」，不是报错——这是可用性取舍。

### Q1.5 【基础】条件表达式支持什么语法？举个真实用例。
**考点**: 条件语言细节。
**参考答案**: 形态是 `路径 [op JSON字面量]`（conditions.py:9 正则）：路径点分、可含虚段 `length`/`last`；op 为 ==/!=/>/>=/</<=；无 op 则取 truthiness。字面量只接受 JSON（true/false/null/数字/带引号字符串，conditions.py:38-48）。真实用例：`state.scratch.route == "a"` 做路由（test_graph_workflow_run.py:73-106），`state.reflections.last.is_sufficient == false`、`state.reflections.length >= 1`（test_workflow_conditions.py:14-17）。比较遇到类型不匹配（TypeError）返回 False 而非抛异常（conditions.py:74-75）。
**追问链**: `state.` 前缀必须写吗？→ 可省，解析时剥掉（conditions.py:31-32）。
**陷阱提示**: 不支持 and/or——需要复合条件就拆成多条边或在角色里预计算一个 scratch 标志位。

### Q1.6 【基础】DAG 是怎么变成执行顺序的？环怎么处理？
**考点**: 图算法基础。
**参考答案**: `graph_topo_layers`（graph.py:92-148）做 Kahn 分层：入度为 0 的节点组成一层，层内按节点声明顺序排序保证确定性（graph.py:127-130、145），执行完减邻居入度。校验包括：节点/边 id 重复、悬空边、弱连通性（graph.py:112-126）、以及 `visited != len(nodes)` 判环直接拒绝（graph.py:146-147）。注意区分另一处 DAG：子问题依赖调度 `scheduler.research_dag` 遇到环是**破环降级为纯并行**（scheduler.py:36-39）而非拒绝——因为那是 LLM 产出的 depends_on，拒绝会牺牲整次研究，降级只牺牲上下文传递。
**追问链**: 为什么两处环策略不同？→ 工作流图是用户构建物，坏了该报错让他改；子问题依赖是模型产出的 best-effort 提示，坏了应容忍。
**陷阱提示**: 别混淆这两个 DAG，面试官可能故意用"你的 DAG 有环怎么办"钓这个混淆。

### Q1.7 【基础】StepRun 状态机有哪些状态？为什么要显式状态机？
**考点**: 运行时可观测模型。
**参考答案**: 8 个状态（types.py:24-32）：PENDING→READY→RUNNING→{SUCCEEDED, FAILED, RETRYING, CANCELLED}，RETRYING→RUNNING，PENDING/READY 还可直接 SKIPPED。转移表硬编码（types.py:35-49），非法转移抛 ValueError（types.py:64-66）。显式状态机的价值：① 预算跳过/条件跳过是显式 SKIPPED 而非"步骤消失"（workflow.py:559-561 注释）；② 每次转移发事件（runtime.py:60-82），前端进度条与断点续跑都消费它；③ RUNNING 转移自增 attempt 并盖时间戳，重试历史可审计。
**追问链**: RETRYING 为什么不能直接到 FAILED？→ 最后一次尝试失败发生在 RUNNING 态（重试循环 break 后由外层 fail_step 处理）；RETRYING 只是等待退避的中间态。
**陷阱提示**: SKIPPED 携带原因（error 字段复用存 reason，runtime.py:76-78），恢复逻辑靠它区分「预算跳过（终态）」和「条件跳过（可重评）」（workflow.py:674-684）。

### Q1.8 【基础】checkpoint 里存了什么？何时写？
**考点**: 持久化语义。
**参考答案**: `_checkpoint`（workflow.py:356-383）存三样：黑板全量 JSON（业务态）、workflow definition（流程定义——恢复时不依赖代码里的模板还在）、以及 `scratch["_runtime_metrics"]` 里的累计 token/耗时（workflow.py:361-365，保证续跑后预算不清零）。写入时机：根 run 每个步骤/每层执行后（workflow.py:577-578、781-782）、终态（成功/失败/取消）时。失败/取消路径写终态 checkpoint 时若遇 `LeaseLostError`（租约已被继任者接管）会吞掉它、保留原始异常向上（workflow.py:586-598；test_step_policies.py:347-408）。
**追问链**: 为什么失败也要 checkpoint？→ 恢复时要知道哪些步骤已成功（跳过重跑），并保住失败前兄弟分支的产出（见 Q3.4）。
**陷阱提示**: 团队子流程不写根 checkpoint——`is_root` 判定 + 嵌套步骤用 `nested-{uuid}` id 避免与未来根步骤混淆（workflow.py:554、689-693；test_team_fanout.py:227-303）。

### B. 设计权衡（9 题）

### Q2.1 【权衡】为什么选黑板模式而不是消息传递？
**考点**: 多智能体通信架构。
**参考答案**: 三个理由。① 解耦：引擎只搬黑板不解析语义，角色协议统一为 `step(bb, ctx)`（base.py:75-85），旧版每个角色签名不同（Planner.run(query) / Reflector.run(query, results)），通用引擎根本无法调度。② 快照与恢复：黑板是单一 Pydantic 对象，checkpoint = model_dump 一行（workflow.py:373）；消息传递的状态散落在各 agent 邮箱里，快照要收集全网。③ 可调试：任意时刻黑板即全量状态。代价我主动承认：并行写共享状态有竞争，解法是「分支深拷贝 + 三方合并」（workflow.py:664-671、88-174）——把隐式竞态转化为显式合并算法。
**追问链**: 什么场景消息传递更好？→ 开放式多轮协商（agent 间对话本身是产物）；本系统角色间是流水线加工关系，黑板更贴合。
**陷阱提示**: 别把黑板说成"没有缺点"——面试官等着你自己讲并行竞争问题。

### Q2.2 【权衡】条件解释器 40 行自研 vs eval/第三方表达式库，怎么想的？
**考点**: 安全意识 + 依赖取舍。
**参考答案**: 条件来自前端拖拽/LLM 生成，是不可信输入，eval 等于把 RCE 焊进引擎——测试里显式验证 `__import__('os').system('x')` 被正则拒绝（test_workflow_conditions.py:30-34）。第三方库（simpleeval 等）攻击面与维护风险仍在。自研的关键设计是**全函数路径解析**（conditions.py:12-25 注释）：黑板形态由角色运行时决定，对 dict 取 last、对象取 length 都可能发生，解析失败一律 None（falsy）而不抛异常——因为异常会经引擎的 asyncio.gather 炸穿整个 run。引擎侧还有第二层兜底：运行期才暴露的非法字面量按「边不激活 + 警告事件」处理（workflow.py:700-716）。
**追问链**: ① 为什么字面量只认 JSON？→ 无歧义、无注入面；未加引号的字符串直接报错（conditions.py:48），倒逼生成方规范。② 表达力不够怎么办？→ 复合逻辑下放给角色写 scratch 标志位；宁可语言弱也不开洞。
**陷阱提示**: 别说"正则保证了安全"就完——正则只限形态，真正的安全性来自「路径解析只读、字面量只 JSON、无任何调用语法」三件事叠加。

### Q2.3 【权衡】三种 join_mode 的设计动机，为什么一种不够？
**考点**: 汇聚语义与失败/条件的交互。
**参考答案**: 因为「入边条件跳过」和「前驱失败但被隔离」是两个正交维度。any（默认）：任一入边激活即跑，适合条件路由后的汇聚（A/B 只走一边，synthesizer 仍要跑）。all：所有入边条件都激活才跑——test_graph_workflow_run.py:293-330 里 route="a" 时 b 分支未激活，all-join 的 synthesizer 被 SKIPPED，这对"必须双路会师"的对比类流程是正确语义。success_all：在 all 之上再要求前驱都 SUCCEEDED（workflow.py:723-726 检查 `successful_nodes`）——失败隔离默认 continue，失败节点仍算"激活"，需要完整输入的节点（如聚合器）用它守门。判定代码在 workflow.py:718-728。
**追问链**: 为什么默认 any 不是 all？→ 与条件路由组合时 all 会让大多数汇聚点永远跳过，any 是研究场景的最小惊讶默认。
**陷阱提示**: 记清"激活"的定义：source 在 active_nodes（跑过且未被跳过）且边条件为真（workflow.py:697-703）。失败节点 active=True 但不进 successful_nodes（workflow.py:736-746）。

### Q2.4 【权衡】失败隔离为什么默认 continue？下游拿到残缺数据怎么办？
**考点**: 可用性 vs 正确性。
**参考答案**: 产品目标是「尽力而为的报告」：12 个子问题挂 1 个不应损失其余 11 个。隔离是分层的：步骤级 try/except + FAILED 状态 + error 事件（workflow.py:567-576）；团队级单团队返回 None（workflow.py:914-916，test_team_fanout.py:62-71 验证一个团队检索故障、报告仍有引用）；边条件级按不激活。残缺数据的防线：① success_all join 给关键节点守门；② 引擎级 `require_report=True` 兜底——流程走完没报告直接抛（workflow.py:579-580，编排器开启 orchestrator.py:466）；③ 失败全部留痕（状态机 + 事件），不是吞异常。需要严格语义的步骤显式声明 fail_fast。
**追问链**: fail_fast 时并行兄弟怎么办？→ gather 抛出后取消未完成任务，但**已成功兄弟的产出会先合并进失败 checkpoint**再抛（workflow.py:770-779），恢复时不丢（test_step_policies.py:250-280）。
**陷阱提示**: 别说"失败被忽略"——是"失败被隔离且显式记录"，两个词的差别面试官很在意。

### Q2.5 【权衡】token 预算为什么是软语义？会不会超支？
**考点**: 资源治理设计。
**参考答案**: 软语义 = 耗尽时跳过非终端步骤、但仍执行 synthesizer/aggregator 产出部分报告（workflow.py:560-565、483-485）。理由：硬杀让用户血本无归，软停保住已花 token 的价值。真相源单一：tracer.total_tokens，TokenBudget.update 取 max 保证单调（token_budget.py:31-37），避免和 charge() 双重计数。会超支：检查点在步骤边界（每步开始前 `_exhausted()`），单步内部不掐断，最坏超支一个步骤的量 + 终端步骤本身的消耗——这是「精确性换简单性」的自觉取舍。测试：test_budget_enforcement.py:43-57，5k 预算被 10k 的 planner 打爆后，RESEARCHER 不出现、报告仍产出、终态事件仍发。
**追问链**: 为什么不在 LLM 客户端层掐？→ 请求发出前无法精确预知响应 token；步骤边界是语义完整的最小回滚单元。
**陷阱提示**: 记住 `_runtime_metrics` 随 checkpoint 持久化（workflow.py:361-365）——否则断点续跑预算清零，等于变相无限预算。

### Q2.6 【权衡】并行合并为什么要三方合并（base/current/branch）而不是简单 last-write-wins？
**考点**: 并发状态合并算法。
**参考答案**: 因为分支改的是「相对快照的增量」，直接覆盖会丢兄弟分支成果。算法（workflow.py:88-174）：每层先深拷贝 layer_base 快照，各分支在自己的副本上跑；合并时对每个值比较 base/current/branch——branch 没改（==base）保留 current；dict 按 key 递归；list 若是 append-only（前缀==base）就把追加段接到 current 后；破坏性改写则按元素 diff 覆盖基线段、同时保留双方追加段。效果：root 写 items=["root"]，left/right 各 append，合并后 ["root","left","right"]（test_step_policies.py:282-308）；一支 pop 一支 append 也不丢（test_step_policies.py:310-344）。last-write-wins 在第一个测试里就会丢掉先合并分支的元素。
**追问链**: 冲突（两分支把同一元素改成不同值）怎么办？→ 无法自动语义合并，确定性地让后合并的 branch 改写生效、但双方追加段都保留（workflow.py:152-164）——见 Q3.3 的修复故事。
**陷阱提示**: 说清楚这是**结构合并不是语义合并**，别吹成 CRDT。

### Q2.7 【权衡】team_fanout 为什么用隔离子黑板，而 DAG 并行节点用共享黑板+合并？
**考点**: 两种并行模型的区分。
**参考答案**: 语义不同。DAG 并行节点是**同一研究的不同侧面**，天然要共享上文（plan、已有 results），所以共享快照+合并。team_fanout 是 **map-reduce**：每个团队研究一个独立 focus，子黑板从零建（`BB(query=task.focus)`，workflow.py:908-909），团队之间零耦合——隔离即是失败隔离（单团队异常返回 None）也是正确性隔离（不会互相污染 pending_sub_questions）。gather 后**串行**把各团队 results 并入父黑板（workflow.py:919-921，注释明确"避免并发写父黑板的竞态"），跨团队做一次 claim 一致性校验（workflow.py:922-928，test_team_fanout.py:162-181 验证跨团队矛盾被抓到），再由 aggregator 综合。
**追问链**: 子任务从哪来？→ 优先 scratch["subtasks"]（Coordinator/Planner 显式产出），否则 plan 的每个子问题一队，受 max_teams 截断（workflow.py:873-883）。
**陷阱提示**: 团队内部流程可被 SubTask.steps 覆盖，默认只有一个 researcher 步（workflow.py:83）。

### Q2.8 【权衡】并发限流为什么是 run 级共享信号量而不是团队/节点级？
**考点**: 并发放大问题。
**参考答案**: 若每个并行分支各建 `Semaphore(max_concurrency)`，K 个分支总并发被放大为 K×max_concurrency。引擎在 run 入口把一把信号量挂到 ctx（已存在则沿用，嵌套子流程共用同一把，workflow.py:517-525），昂贵操作（检索/LLM）在角色内部取这把锁。同时刻意**不**在 team_fanout 层持锁跨整个子流程——子流程内 researcher 会再取同一把，团队数≥max_concurrency 时会自锁死（workflow.py:903-906 注释）。两个测试钉死行为：5 团队并行峰值 ≤2（test_team_fanout.py:211-224）、3 个并行 researcher 节点×各 3 子问题峰值 ≤2（test_graph_workflow_run.py:189-218）。
**追问链**: 为什么挂 ctx 不挂引擎实例？→ compose/team 会嵌套调用 self.run，ctx 是贯穿所有嵌套层的载体；角色单测无引擎也能自建。
**陷阱提示**: "限流不改变产出（无死锁、报告照常生成）"是测试断言原文（test_team_fanout.py:222），可直接引用。

### Q2.9 【权衡】重试为什么在黑板副本上做（candidate 模式）？
**考点**: 失败尝试的副作用隔离。
**参考答案**: 角色是原地改黑板的，失败尝试可能已写了半截数据；直接在原黑板重试会把脏数据带进下一次尝试。所以每次尝试先 `bb.model_copy(deep=True)` 出 candidate，成功才 `_commit_blackboard` 逐字段拷回（保持对象身份不变，调用方持有的引用仍有效，workflow.py:437-450、194-198）。fallback 同样在新副本上执行（workflow.py:454-456）。测试：失败尝试的 scratch 追加被丢弃，最终只有成功尝试的输出（test_step_policies.py:124-139、163-178）。
**追问链**: 深拷贝黑板贵不贵？→ 黑板是文本型研究数据（幅度 KB~MB），每步一次深拷贝相对 LLM 调用延迟可忽略；真到瓶颈可换 copy-on-write。
**陷阱提示**: `_commit_blackboard` 保持 target 身份是刻意的——`bb is initial` 的断言（test_step_policies.py:138）保证编排器外层引用不失效。

### C. 深挖追问（8 题）

### Q3.1 【深挖】compose 的终止性怎么证明？
**考点**: 递归编排的有界性。
**参考答案**: 四个上界叠加。① 深度：`scratch["_compose_depth"]`≥1 直接跳过嵌套 compose（workflow.py:831-835），且 validate_workflow 禁止生成流程里出现 compose/team_fanout（workflow.py:295-296）——静态+动态双保险，测试验证生成里塞 compose 会被拒绝并回退（test_compose.py:108-117）。② 步数：生成流程 ≤MAX_GENERATED_STEPS=8（workflow.py:75）。③ 循环：reflect_loop 轮数 ≤max_rounds（默认 2，config.py:72），且反思判充分/无新子问题即 break（workflow.py:935-938）。④ 重规划：零产出时至多 max_replans 次（默认 1），预算耗尽立即停（workflow.py:837-852，注释明确「终止性 = 重规划上限 ∨ 预算耗尽 ∨ 有产出」）。
**追问链**: 生成流程内部再放 reflect_loop 呢？→ 允许，但轮数受同一 max_rounds_cap 校验（workflow.py:301-302），仍有界。
**陷阱提示**: 别说"LLM 不会生成递归"——要说"即使生成也会被校验拒绝"，确定性防线优于概率信任。

### Q3.2 【深挖】断点续跑的恢复语义：哪些步骤跳过、哪些重跑？
**考点**: recovery 一致性。
**参考答案**: 恢复用 `resume_run` 注入历史 WorkflowRun（与 initial_run 互斥，workflow.py:346-347），线性模式按 node_id（step-N）匹配，SUCCEEDED/SKIPPED 直接跳过（workflow.py:536-552）。图模式更精细（workflow.py:674-688）：SUCCEEDED 是终态；SKIPPED 要看原因——**预算跳过是终态**（续跑恢复了原 budget 与计数器，结论不变），**条件跳过是暂定的**（失败前驱在恢复中可能成功，改变本节点资格，`_INCOMING_CONDITIONS_SKIP_REASON` 哨兵区分，workflow.py:84）。FAILED 步骤自然重跑。嵌套步骤 id 用 `nested-{uuid}`，不会在恢复时误匹配未来的根步骤（test_team_fanout.py:259-302）。累计 token/耗时随 `_runtime_metrics` 恢复（workflow.py:361-365）。
**追问链**: 恢复后黑板从哪来？→ checkpoint 的 model_validate；definition 也在 checkpoint 里，不依赖代码模板未变。
**陷阱提示**: 「条件跳过可重评、预算跳过不可」这个不对称是加分点，讲出理由（预算计数器被恢复）而不是背结论。

### Q3.3 【深挖】讲讲那个并行合并丢数据的 bug 和修复。
**考点**: 真实 debug 深度（加分题）。
**参考答案**: 场景：两个并行分支都对基线 results 做了**原地改写**（各自跑 claim consistency 替换基线 Finding）并**各自追加**新结果。旧逻辑在「branch 改写了基线前缀」时整段以 branch 为准，会把先合并分支（current）的追加段抹掉——高危数据丢失。修复（workflow.py:148-164）：识别出「双方都改写基线前缀」的情形后，基线段按 branch 相对 base 的**逐元素差异**覆盖到 current 之上，然后双方各自超出基线长度的追加段都保留。回归测试两层：纯函数单测直接测 `_merge_parallel_sequence`（test_graph_workflow_run.py:109-121，断言 rewrite 生效 + L、R 追加都在），端到端测两个 RewriteAppendAgent 并行分支（test_graph_workflow_run.py:139-158）。这是 2026-07 全库审查确认的 3 个高危 bug 之一。
**追问链**: 语义冲突（同一元素被改成两个不同值）最终谁赢？→ 后合并的 branch 赢，确定性但非语义正确——诚实承认这是结构合并的边界，语义冲突应由上游设计避免（如各分支只改自己产出的元素）。
**陷阱提示**: 主动讲这个 bug 比藏着好——"我修过引擎的合并算法"是真实工程信号。

### Q3.4 【深挖】fail_fast 抛出时，已成功的并行兄弟节点产出去哪了？
**考点**: 失败路径下的数据持久性。
**参考答案**: gather 抛异常后引擎先取消未完成任务，然后 `asyncio.gather(*tasks, return_exceptions=True)` 收齐所有已 settle 的结果，把**成功兄弟的产出合并进主黑板**再抛（workflow.py:768-779）。注释写明理由：成功兄弟已是持久运行态（SUCCEEDED），若产出不进失败 checkpoint，恢复时会因状态是 SUCCEEDED 跳过该节点、产出永久丢失。测试：fail_fast 分支炸掉后，checkpoint 里仍有 fast 节点写入的 `result:fast`（test_step_policies.py:250-280）；被取消的兄弟状态是 CANCELLED、失败节点 FAILED、run 终态 FAILED（test_step_policies.py:214-247）。
**追问链**: CancelledError 里步骤状态怎么收敛？→ `_execute_with_policy` 捕获后若步骤还在 READY/RUNNING/RETRYING 就转 CANCELLED 再 re-raise（workflow.py:468-475）。
**陷阱提示**: 这是「隐性数据丢失」类 bug 的预防设计，能讲出「状态说做过但数据没了 → 恢复跳过 → 永久丢」这条因果链就是满分。

### Q3.5 【深挖】Coordinator 生成流程的三层防线具体怎么走？
**考点**: LLM 输出治理的纵深。
**参考答案**: 第一层在 Coordinator 内（coordinator.py:71-92）：structured output 生成 GeneratedWorkflow → validate_workflow 不过 → 把错误列表回灌 prompt 自修复**一次** → 仍不合法或网络/解析炸了 → 返回 DEEP 步骤副本。第二层在引擎 `_generate`（workflow.py:855-871）：拿到 scratch["composed_workflow"] 后**再校验一遍**（不信任角色层已校验——角色可被数据驱动卡片替换），失败发事件并回退执行内置 DEEP。第三层是零产出重规划（workflow.py:837-852）：生成流程跑完 `bb.results` 为空 → 写 replan_hint 回灌（coordinator.py:60 一次性 pop）→ 重生成，至多 max_replans 次，预算耗尽即停。测试各覆盖一层：自修复恰好一次（test_compose.py:74-104，gw_calls==2）、嵌套 compose 拒绝+回退（108-117）、零产出重规划（120-150）。
**追问链**: 为什么引擎要重复校验？→ resolver 可注入 DB 角色卡片，Coordinator 实现可被替换，引擎是最后一道不可绕过的门。
**陷阱提示**: 白名单只暴露 _ROLE_HINTS 里的内置角色进 prompt（coordinator.py:59），prompt 约束和校验器是两回事，别混为一谈。

### Q3.6 【深挖】reflect_loop 的数据流：补洞子问题怎么传给 researcher？会重复研究吗？
**考点**: 循环原语内部机制。
**参考答案**: workflow.py:931-948：每轮 reflector 评估最新黑板，产出 Reflection；若 `is_sufficient` 或无 `new_sub_questions` 立即 break；否则把新子问题写 `scratch["pending_sub_questions"]`，researcher 读到它就**只研究这批增量**而不是重跑全 plan（注释「经 scratch 传递，不重研已做过的」）。轮次记录进 `scratch["reflection_rounds"]` 供落库标 origin="reflection"。上界 `step.max_rounds ?? settings.max_rounds`（默认 2）。三个终止条件：充分 / 无新问题 / 轮数耗尽——再叠加引擎级预算跳过（预算耗尽时整个 reflect_loop 步骤被 SKIPPED）。
**追问链**: reflector 每轮都说不充分怎么办？→ 轮数硬上限兜底，见 Q4.3。
**陷阱提示**: pending_sub_questions 是「命令式接口藏在 scratch 里」，被问到耦合可以承认：这是黑板模式的约定式契约，靠测试而非类型保证。

### Q3.7 【深挖】validate_workflow 的「终端角色收尾」规则为什么存在？图模式怎么校验？
**考点**: 领域校验规则。
**参考答案**: 没有能产报告的角色（synthesizer/aggregator，workflow.py:81）流程就白跑；报告角色不在**末尾**同样错——test_workflow.py:101-105 注释点破：「报告角色存在但不收尾：会在研究结果写入前生成空报告」。线性版要求报告角色索引恰为最后一位（workflow.py:242-253）；图版 `validate_workflow_graph_terminal` 要求唯一出度为 0 的终端节点、且它就是唯一的报告节点（workflow.py:218-239）。terminal_roles 可扩展：用户自建 behavior=synthesize 的角色卡可计为终端（test_workflow.py:110-113），编排器把 catalog 的 terminal_roles 注入引擎（orchestrator.py:467）。预算软语义也依赖同一集合（`_is_terminal`，workflow.py:483-485）——终端角色是「耗尽仍执行」的白名单。
**追问链**: 为什么 aggregator 也算终端？→ teams 流程以 team_fanout（内部收尾于 aggregator）结束，报告由 aggregator 产出。
**陷阱提示**: 记住 terminal 集合一鱼三吃：校验收尾、预算豁免、require_report 的前提。

### Q3.8 【深挖】OrchestrationRuntime 和引擎是什么关系？为什么单独抽一层？
**考点**: 关注点分离。
**参考答案**: runtime.py 是**纯生命周期记录器**，模块注释自述「deliberately owns no scheduling policy」（runtime.py:3-5）：它维护 WorkflowRun/StepRun 状态机、每次转移发事件、承接 checkpoint 写入；调度策略（顺序、并发、重试、跳过）全在引擎。抽层的收益：① 状态机可独立测试（test_orchestration_runtime.py）；② 事件流成为前端 SSE 与持久化的统一 seam——引擎经 `_emit_runtime_event` 把 workflow.started/step.retrying/checkpoint.saved 等桥接到 tracer（workflow.py:385-387）；③ restore/adopt 两个入口区分「恢复既有 run」和「接管预持久化 run」（runtime.py:23-36），引擎构造器保证两者互斥（workflow.py:346-347）。
**追问链**: start 被重复调用怎么办？→ 已 RUNNING 则幂等返回现有 run（runtime.py:39-40），嵌套 run 因此不会重置根状态。
**陷阱提示**: 别把它说成"调度器"——它一行调度逻辑都没有，这正是设计意图。

### D. 压力与陷阱（6 题）

### Q4.1 【压力】这不就是重复造 LangGraph 的轮子？
**考点**: 自研正当性，考验诚实与定位。
**参考答案**: 先承认重叠：状态图、条件边、checkpoint、恢复，LangGraph 都有，通用平台选型我会认真评估它。但这是**领域引擎**不是通用框架，三点差异化：① 原语是研究领域的——reflect_loop/compose/team_fanout 直接编码「反思补洞 / LLM 自组合 / map-reduce 团队」三个模式，LangGraph 里要自己用低层原语搭；② 校验带领域语义——「必须以能产报告的角色收尾」「生成流程禁止自指」「全流程最坏退避 ≤120s」这些规则通用框架不会替你写（workflow.py:256-319）；③ 预算软语义、失败隔离粒度、"尽力而为出报告"贯穿引擎每个分支，这是产品语义不是框架语义。此外自研让我能对每个正确性性质给出测试证明（合并算法、终止性、限流不放大），这本身是这个项目要展示的能力。也诚实承认差距：不支持任意循环图（循环只能表达为 reflect_loop）、没有时间旅行调试、条件语言表达力弱、没有人在环原语。
**追问链**: ① 生产上你会选哪个？→ 看约束：团队生态/人力选 LangGraph，需要深度定制校验与预算语义、或依赖审计严格的场景自研可控。② LangGraph 的 reducer 和你的合并谁好？→ reducer 要求每个 key 预声明合并函数，类型安全但对自由 scratch 区不友好；我的三方合并零声明但只有结构语义——是声明成本与语义精度的互换。
**陷阱提示**: 千万别贬低 LangGraph 或假装没听过；「先承认、再差异化、最后给边界」的顺序不能乱。

### Q4.2 【压力】你的引擎正确性怎么保证？没有形式化验证吧？
**考点**: 工程正确性方法论。
**参考答案**: 没有形式化验证，靠四件事。① 状态机非法转移直接抛（types.py:64-66），运行态不可能悄悄进入未定义状态；② 关键性质各有钉死行为的测试：合并不丢数据（test_graph_workflow_run.py:109-158）、失败尝试副作用隔离（test_step_policies.py:124-139）、并发限流不放大（两处 peak≤max_concurrency 断言）、取消传播（scheduler.py:64-65「取消必须向上传播，不可吞」+ test_step_policies.py:214-247）、租约丢失不掩盖原始异常（test_step_policies.py:347-408）；③ 终止性是构造性的：所有循环都有硬上限（见 Q3.1），不依赖运行时监控；④ 后端默认离线基线 613 项测试全绿，且经过一轮多 agent 全库审查——审查确实发现了 22 个 bug（含 3 个高危，其一就是引擎的并行合并丢数据），说明测试不是万能的，但「审查发现→修复→补回归」这个闭环在运转。诚实边界：并发交错空间没有穷举（没做模型检测），合并的语义冲突只有确定性策略没有正确性保证。
**追问链**: 怎么测并发时序类 bug？→ 用 asyncio.Event 精确控制交错（如 FailAfterSignalAgent 等 sibling 完成后才炸，test_step_policies.py:63-71），不是靠 sleep 碰运气。
**陷阱提示**: 主动说出"审查发现过 bug"反而加分；说"我的测试覆盖了所有情况"必死。

### Q4.3 【压力】反思循环会不会死循环？reflector 永远说不充分呢？
**考点**: 终止性追问。
**参考答案**: 不会，四层上界与 LLM 的判断**无关**。① 轮数硬上限：`for rnd in range(rounds)`（workflow.py:935），rounds 默认 settings.max_rounds=2（config.py:72），负数被 Settings 校验拒绝（config.py:89-90）；LLM 说一万次"不充分"也只跑 2 轮。② 提前退出：充分 / 无新子问题即 break（workflow.py:938）。③ token 预算：耗尽时非终端步骤（含整个 reflect_loop）被 SKIPPED（workflow.py:560-565）。④ 生成流程里的 reflect_loop 轮数受校验器 cap（workflow.py:301-302），LLM 不能生成 max_rounds=999。关键句：终止性来自 for-range 的结构，不来自对模型行为的假设。
**追问链**: 每轮补洞产生的新子问题会指数增长吗？→ 单轮内交给 researcher 的只是该轮增量（pending_sub_questions），且总轮数有界，最坏是「轮数×单轮子问题数」线性量，researcher 内部还有并发信号量限流。
**陷阱提示**: 别答"reflector 的 prompt 让它最多提两个问题"——prompt 是软约束，面试官要听的是结构性硬上限。

### Q4.4 【压力】Coordinator 生成的流程失控怎么办？说一个你真实堵过的口子。
**考点**: 治理纵深 + 真实审查素材。
**参考答案**: 常规防线见 Q3.5（白名单校验→自修复→回退 DEEP→有界重规划）。真实堵过的口子：**重试预算缺口**。Step 字段级约束是 max_attempts≤10、retry_backoff≤60s（workflow.py:60-61），单看每个字段都"合法"；但早期 validate_workflow 不检查它们的**组合**——一个字段全合法的生成/自建流程，8 步×(max_attempts=10, backoff=60) 的最坏指数退避是每步 60×(2^9−1)=30660s，整个流程能合法地空转数十小时。本次审查发现后加了两条校验（workflow.py:76-79、288-314）：单步 max_attempts≤MAX_STEP_ATTEMPTS=5；全流程最坏退避总时长 Σ retry_backoff×(2^(attempts−1)−1) ≤MAX_TOTAL_BACKOFF_SECONDS=120s，公式与引擎实际退避实现（`retry_backoff * 2**attempt`，workflow.py:443）逐项对齐。测试 test_workflow.py:116-139：30s×5 次=450s 被拒，5s×3 次=15s 通过。教训是：**逐字段校验≠流程级安全，资源上界要对"最坏执行成本"建模**。
**追问链**: 还有类似的组合型口子吗？→ 同类思路已覆盖：步数×轮数（max_steps + max_rounds_cap）、嵌套深度（compose 禁入生成流程）；timeout_seconds 单字段 cap 3600s 是已知的下一个可收紧点（当前依赖步数上限间接约束总时长）。
**陷阱提示**: 这题的正确姿势是「讲缺口的发现过程和建模思路」，不是背常数；把 120s 说成"精确科学"是过头——它是拍的运维上界，可配置成本很低。

### Q4.5 【压力】并行分支的深拷贝黑板，数据量大了不会成为性能瓶颈？
**考点**: 性能诚实度。
**参考答案**: 承认是 O(分支数×黑板大小) 的拷贝成本，且合并也是逐元素比较。为什么现在可接受：① 黑板是文本型研究数据（findings/报告），量级 KB~MB，而每个并行节点至少含一次网络检索或 LLM 调用（秒级），拷贝的毫秒级开销不在关键路径；② 拷贝换来的是无锁并发+失败尝试隔离两个正确性性质，用锁换性能会引入更贵的顺序化。真到瓶颈的演进路径：黑板字段级 copy-on-write、合并只 diff 已知写入的字段（引擎可从 StepRun 记录角色声明的写集）、或大对象（原文快照）出黑板改存引用。没测过压测数字就不报数字。
**追问链**: checkpoint 每步一次 JSON 序列化呢？→ 同理由；且 checkpoint_sink 是注入的 async 回调（workflow.py:331），可换成节流/异步批量写而不改引擎。
**陷阱提示**: 别顺口编"实测 xx ms"——没有就说没有，给出量级论证和演进路径更可信。

### Q4.6 【陷阱】图模式的条件边在并行层里读的是哪个黑板？有没有一致性问题？
**考点**: 并发下的条件求值一致性（自曝边界题）。
**参考答案**: `edge_active` 里 `evaluate_condition(edge.condition, bb)` 读的是**主黑板 bb**（workflow.py:703），即上一层合并完成后的状态——同层兄弟的写入发生在各自副本上、层末才合并，所以同层节点的条件求值互相不可见、结果确定，这是「层间串行」保证的一致性模型。真正的边界在于：条件只能引用**前一层已合并**的状态，想根据同层兄弟的实时输出做路由是不支持的——这类依赖应显式建边，让目标节点落到下一层。另外恢复语义上条件跳过是暂定的（可重评，见 Q3.2），因为前驱恢复成功后条件可能翻转。
**追问链**: 如果条件读了个角色没写过的路径？→ 全函数解析返回 None → falsy → 边不激活、节点 SKIPPED，不炸 run（test_graph_workflow_run.py:264-289）。
**陷阱提示**: 这题容易答成"条件读的是节点自己的副本"——错；也别声称支持同层数据流路由，引擎明确不支持，承认并给出"显式建边"的正确用法。

## 三、本模块速记

1. **一句话定位**：控制流即数据——Workflow 是 Pydantic 数据，引擎是无状态解释器，状态全在黑板与 WorkflowRun 上（workflow.py:322）。
2. **能力分层**：L1 声明式线性 → L2 模板路由（公共 3 条，另有内部兼容流程）→ L3 compose 自组合 → L4 team_fanout map-reduce；再加 DAG 图执行（Kahn 分层并行）。所有层共享启动前的全局意图门禁与 planner-driven 规则上下文。
3. **四个控制原语**：agent / reflect_loop / compose / team_fanout；后两个禁止出现在生成/自建流程里（防自指递归）。
4. **硬上限一组数**：生成流程 ≤8 步、单步重试 ≤5 次、全流程最坏退避 ≤120s、compose 深度 ≤1、反思轮数默认 2、重规划默认 1 次、并发默认 4（workflow.py:75-79 + config.py:72-80）。
5. **三种 Join**：any（任一激活）/ all（条件全激活）/ success_all（还要前驱全成功）——条件跳过与失败隔离是两个正交维度，所以一种语义不够（graph.py:20，workflow.py:718-728）。
6. **失败隔离三层**：步骤级（重试→fallback→FAILED 隔离）、团队级（单队失败返回 None）、边级（条件求值失败按不激活）；失败留痕不静默，require_report 兜底。
7. **并行合并**：层快照深拷贝 + base/current/branch 三方合并；本次审查修复高危 bug——双分支改写基线时先合并分支的追加段被覆盖，现按元素 diff 覆盖且双方追加均保留（workflow.py:148-164）。
8. **预算是软的**：真相源是 tracer 累计 token，耗尽跳过非终端步骤但仍跑 synthesizer/aggregator 出部分报告；`_runtime_metrics` 随 checkpoint 持久化，续跑预算不清零。
9. **Coordinator 三层防线**：错误回灌自修复一次 → 引擎重校验失败回退 DEEP → 零产出有界重规划；终止性=步数∧深度∧轮数∧重规划上限∨预算。
10. **正确性证据**：8 状态显式状态机（非法转移即抛）+ 后端 613 项默认离线测试基线 + 全库审查 22 bug（3 高危）修复闭环；诚实边界：无形式化验证、合并只有结构语义、条件语言无 and/or。
