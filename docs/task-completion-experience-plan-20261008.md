# 任务完成体验升级方案

这次建议把“用户拿到可用结果”作为调度目标，优先改模型调用决策、任务收敛和结果呈现。现有角色体系、工作流与证据校验可以保留，不需要先增加更多 Agent。

本文是设计建议，尚未实施。上一轮核验与前端修复仍是本地改动，尚未部署到 Aliyun。

## 1. 现在的调度为什么显得奇怪

2026-10-08 通过 Aliyun 只读查询确认：

| 观察 | 对完成体验的影响 |
| --- | --- |
| 只配置了一个模型档案，名称为 `deepseek`，实际模型标识为 `gemini-3.8-flash`，默认 `reasoning=high`，输出容量 20,000 token | 配置名称容易误导；不同工作主要共享同一模型与默认推理配置。模型标识是渠道配置值，不据此推断底层真实供应商 |
| 案例任务的 60 次请求全部使用同一个模型标识：规划 1、研究 14、核验 43、反思 1、写作 1 | 有角色分工，但这个任务没有实际体现多模型选择；43 次核验也并非都在检查同一件事 |
| 模型选择采用“角色专属档案 → 默认档案 → 运行默认模型” | 没有在这个入口根据具体操作难度、结构化输出能力、延迟和调用失败类型做选择 |
| 已有请求级推理策略，但调用方需要主动接入 | 漏接的简单检查会继承高推理。案例中一致性核验一次消耗 19,201 个思考 token，最终输出截断 |
| 研究分支并发上限 4，同渠道模型请求并发上限 2；研究任务同时运行上限 1，当前运行方式为 inline | 配置里的“4 并发”不能直接理解为 4 个模型请求同时工作。需要分别解释任务队列、分支依赖和渠道排队 |
| 案例任务按 `[1,1,2,1]` 分为四层；调度代码等待整层结束才处理下一层 | 依赖已满足的后续节点可能被同层的无关慢节点拖住。应按依赖就绪启动，而不是按整层推进 |
| 摘录修复、写作返工、交付修订有各自的次数和停止条件 | 单个环节看似合理，合起来可能重复检查原稿，缺少统一的“这一步是否能改善结果”判断 |

案例耗时 13 分 48 秒，最终待复核。最值得优先解决的是高推理误用、无效修订以及串行等待；现有数据尚不能证明换成某个新模型就一定更快。

## 2. 用户最终应该获得的体验

默认采用“先给有依据的结果，随后完善”。

1. **开始时说清交付内容。** 例如“先确认 JEV 指代，再给出代表论文、方法对比和研究方向”。会改变研究对象的歧义要尽早确认；能独立进行的背景准备继续执行。
2. **运行中持续显示成果。** 资料就绪后先展示已核验的关键结论和来源，明确标为阶段结果；不能把未经核验的流式草稿直接称为可用答案。
3. **把结果状态与处理状态分开。** “已有初步答案，正在补齐方法比较”比单一百分比更有用。用户随时能读已有结果、补充条件或停止后续工作。
4. **完成时直接给下一步。** 已完成就阅读、复制、下载；部分内容不足就列出具体缺口，提供“只补充缺失资料”“修订这几段”“重试 PDF”等对应动作。
5. **故障时保留最好版本。** 后续某次检查或文件生成失败，不覆盖已经可用的内容。原始草稿、已核验结果和最终报告需标识清楚。

“可用但有缺口”不等于任务完成。如果用户明确要求完整比较、指定章节或必需文件，这些缺失仍须标为未完成，不能靠降低标准把状态改绿。

## 3. 第一优先级：按具体工作调模型

新增统一的请求决策入口。角色继续负责业务，具体操作决定模型配置、推理强度、队列优先级和失败后的动作。

| 具体工作 | 默认执行方式 | 什么情况值得升级 |
| --- | --- | --- |
| 任务分类、检索词、字段提取 | 支持结构化输出的快速配置、低推理 | 格式问题先按协议修复；涉及研究对象歧义时尽早确认 |
| 引文匹配、编号、重复来源、已知格式校验 | 程序直接处理 | 不为确定性问题额外调用模型 |
| 普通摘录是否支持结论 | 快速核验配置、批量处理、低推理 | 确有语义冲突且原文齐全时，转精确复核 |
| 方法对比、研究方向、报告综合 | 经评测选出的写作配置，默认适中推理 | 多来源矛盾、复杂推导或关键结论需要深入分析 |
| 复杂公式、关键结论争议 | 有相应能力的深入复核配置 | 只携带相关完整依据，不重新审查整份报告 |
| 导出与排版 | 程序执行；必要时局部格式修复 | 文件生成失败走渲染恢复，不重跑研究 |

短期只有一个模型也能落地：同一模型对应快速核验、常规写作、深入复核三类请求配置。未来有多个模型时再按评测结果绑定，不要求用户为每个角色手工挑模型。

选择顺序建议为：

**满足本操作的输入、输出和能力要求 → 用户明确指定的约束 → 可用渠道与健康状态 → 经评测的质量、延迟和费用。**

保留现有固定角色绑定作为明确覆盖项；自动策略不能静默绕过用户锁定。实际使用的模型、配置来源及升级原因应写入诊断记录，普通任务页只显示对用户有意义的动作。

不要让另一个大模型为每一次调用先做“该用哪个模型”的判断。第一版用明确的操作类型、能力配置和失败分类，减少额外调度开销。

## 4. 第二优先级：让任务能够收敛

建议复用现有交付契约和修订检查点，集中决定下一步动作：继续收集、开始写作、补充一项证据、修改某几段、交付已有结果或等待用户补充信息。

- 每次追加工作必须关联具体未完成项。例如“方法对比缺少某篇论文的实验设置”，不能只说“再反思一次”。
- 相同的问题、证据和正文没有变化时，禁止再次发起同一内容核验。服务恢复后的重试需要单独说明原因。
- 新增证据优先重新检查依赖它的结论；改一段话优先检查该段及受影响的表格、比较和覆盖项。影响范围扩大时才扩大复核。
- 跨阶段共用一份问题清单和修订账本，避免“写作已检查一次，交付又从头开始一次”。保留现有次数上限，同时记录新证据、问题数量与严重性是否改善。
- 缺少原文就补原文或删去无法支持的断言；不能靠升级模型证明不存在的证据。一次局部失败也不应阻止其他可修复内容前进。
- 降级输出必须明确缺口和来源范围。不能用素材摘要冒充用户要求的完整综述。

缓存绑定至少包含正文或结论、证据内容与来源版本、核验规则版本、模型配置及引用关系，并隔离任务权限。复用通过的结果不能让旧依据覆盖新事实；失败和不确定状态不能变成通过。

## 5. 第三优先级：减少真实等待，而不只是增加并发

### 依赖就绪即运行

现有 DAG 已经能描述依赖，第一步是取消整层等待。例如节点 D 只依赖 B，B 完成就可以启动 D，不必等与 D 无关的 C。仍保留运行上限、取消传播、租约检查和结果顺序，防止重复执行。

### 请求队列体现用户正在等待什么

在现有渠道限流与任务公平调度之上，增加请求级优先级：正在交互的短请求、能产生第一份可用答案的工作、必需的收尾工作优先；可选扩展靠后。对等待时间做加权，避免长任务一直被插队。

同一渠道的并发上限 2 应继续作为硬约束，先测队列时间、渠道延迟和 429，再决定是否增加。创建更多本地角色或同凭据档案不能绕过渠道容量。

### 失败分类决定下一步

| 失败 | 默认动作 |
| --- | --- |
| 渠道繁忙、429 | 显示排队状态，遵循退避；存在获准的可用渠道时切换 |
| 结构化输出不合协议 | 做有上限的协议修复；记录是格式问题，不误报为证据缺失 |
| 思考或输出截断 | 使用合适推理配置，按完整语义单元分批；不原样重发同一大请求 |
| 来源快照冲突 | 固定可用版本或调整相关断言；保留证据限制 |
| 单段引用不足 | 只补证据或修订该段，随后检查受影响内容 |
| 可选文件生成失败 | 交付可用正文，单独重试文件；必需文件失败则明确仍未完成 |

不要用固定总 token 上限强行终止所有复杂研究。操作上限和收敛检查用于阻止无效循环，任务深度及必需交付仍由用户目标决定。

## 6. 前端只保留能指导用户行动的信息

主区域建议显示：

> 已确认 8 篇相关论文，当前可阅读 3 条有依据的初步结论。正在补齐方法对比，尚缺 1 篇论文的实验设置。

用户看到的是真实工作状态：排队中、检索中、核对引用、修订局部、生成文件。若显示分母，必须来自已确定的工作清单；无可靠估计时不显示倒计时或停在 99%。

结果页以可用内容为主，问题默认合并成少量可操作项。一次正文问题引发 HTML、Word、PDF 三种格式都未生成，应展示“先修正文，之后可生成三种文件”，而不是四条同义错误。

“继续”需要具体：

- 补齐缺失资料：复用现有检索、结论和正文。
- 修订不支持的段落：只处理相关段落及依赖。
- 重试文件：只进入文件生成流程。
- 停止后续工作：保留已生成内容和实际未完成项。

已有保存、断线重连和独立内容修订能力应继续复用。第一版可以由现有状态推导更清楚的展示状态，无需先重构整套数据库状态机。

## 7. 推荐落地顺序与验收

| 顺序 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 0 | 发布上一轮已验证的核验阻塞与前端修复，建立基线 | 来源冲突不再导致无效修订；已结束任务不显示 99%；真实模型验收与代码回归分开记录 |
| 1 | 统一按操作选择推理配置，模型档案显示真实标识，增加排队与执行耗时记录 | 快速检查不意外继承 high；不静默更换用户锁定模型；能解释每次升级 |
| 2 | 阶段结果展示、问题去重归因、明确的继续动作 | 用户能在终稿前读到有依据的内容；重试文件不重跑研究；刷新不丢结果 |
| 3 | DAG 就绪调度、按渠道限制的请求优先级 | 满足依赖即可启动；取消后不产生孤立调用；前台短请求不被可选扩展长期阻塞 |
| 4 | 跨阶段增量核验和统一修订决策 | 相同输入没有无因重复检查；修改证据会使关联缓存失效；保留最好的有效版本 |

核心指标按问答、精读、综述分别统计：首次可用结果耗时、任务满足约定的比例、待复核比例、端到端 p50/p95、排队耗时占比、相同输入重复调用数、每轮修订减少的问题、继续操作复用成功率。

质量底线同时评测：引用不支持、来源版本混用、漏检关键数字及遗漏用户必需交付，不能为了提速而恶化。耗时目标应在同任务、同证据和同渠道条件下比较；不提前承诺固定降幅或统一完成秒数。

**优先建议：先统一调用策略，再提供阶段结果和精准继续，之后优化请求排队与增量核验。** 这样用户先感受到任务能够解释、能够恢复、能够完成，而后再通过数据选择是否需要增加新模型。
