# 任务场景可用性与交付验收计划

更新：2026-10-03。最新要求明确为：项目面向长任务，成本、token 和单次任务耗时不作为优化目标；优先保证真实任务能够恢复、完成，并交付内容正确、证据充分、格式可用的最终产物。当前工作顺序调整为：任务级质量收敛、长任务健壮性与自动恢复、多任务并发隔离、真实线上验收。耗时、调用次数和 token 仅用于识别卡死、无效循环和重复工作，不以减少调用为由降低质量要求。历史修复记录用于追溯，不直接决定下一步。

## 目标与当前边界

让用户在每个功能入口提交真实材料后，能够看到明确进度、得到符合该任务要求的结果、查看引用并下载可用产物；出错时能理解原因并恢复。交付对象是综述、精读结论、分析报告、评审意见、汇报材料等，版式遵循学术规范，不新增论文投稿流程。

现有实现与大量自动回归不能证明所有场景都已可用。真实状态以 [质量矩阵](REAL_TASK_QUALITY_MATRIX.md) 的样本和失败记录为准。用户负责浏览器手动验收，开发侧负责接口、模型链路、文件内容与导出验证。

先覆盖缺少真实验证的模块，避免继续集中于单个论文样本。保留当前已经完成且可以复核的读取和证据，只补真实缺口。实际顺序为：同行评审、汇报幻灯片、自动研究、新版多输入导图；随后补齐综述、精读、连续追问与数据分析的首次完成验证。共用阻断出现时先修复，再继续未覆盖模块。

| 思维导图 | 多份材料与指定主题 | 可用的交互/导出文件、正确概念层级与关系、覆盖用户主题，不能只有事实堆积 |
| 文献综述 | 指定多篇文献；另测开放检索 | 跨文献主题综合、比较条件、结论与局限，不能用证据摘录清单代替综述 |

| 数据分析 | 有说明的真实或公开数据，含缺失/异常情况 | 分析方法与数据相符，可复核统计、图表、解释及可打开的数据/报告文件 |

## P2：按任务建立严格质量收敛

2026-10-04 本地已将新契约任务的完成状态与实际交付绑定，新增待复核状态，并支持格式重试
后补齐完成记录；冻结契约与新格式可读取性检查已验证。具体证据与历史兼容边界见
[完成状态与交付记录](DELIVERY_COMPLETION_20261004.md)。这不代表下列每类真实任务已通过。

`done` 应表示该任务的必需质量门已经通过，而不只是工作流运行到了末尾。允许保留可下载的草稿或带警告版本，但必须与最终完成状态区分。质量检查失败时复用已通过的证据和段落，只对失败单元执行定向补读、重写或重渲染；连续多轮没有实质改善时停止自动循环，明确进入需要复核的状态，不得通过降低事实要求、删除必要内容或忽略警告换取通过。

所有场景共用的最终质量门：

- 结论能够回到已读取的原文、数据或用户材料，引用编号、具体依据和来源文件一致；关键主张无依据时必须明确说明，不能补写成事实。
- 用户要求的主题、章节、比较对象、数据范围和交付格式均有覆盖；材料缺失与模型遗漏必须区分。
- 正文、表格、图、公式、书目和导出文件使用同一份定稿快照；PDF、Word、HTML、PPTX、XLSX 等承诺格式可打开且内容一致。
- 确定性检查与模型复核均通过；涉及统计、数值、实验条件和比较关系时，必须执行专门的一致性校验。
- 失败后恢复不能重复已经成功的昂贵步骤，也不能丢失已核验证据、用户配置、输入范围或历史上下文。

| 场景 | 下一阶段必须提升 | 质量通过标准 |
| --- | --- | --- |
| 自动研究与资料库研究 | 提高首次完成率、检索召回、背景材料密度、冲突来源处理和复杂图示证据绑定 | 新问题首次运行可形成完整报告；每项核心结论有充分来源；检索或读取失败被明确暴露；恢复后不重复已完成子问题 |
| 文献综述 | 加强跨文献主题综合、比较条件、分歧与局限分析，避免退化为证据摘录清单 | 主题覆盖与用户范围一致；主要观点有多文献支撑；相互冲突的结论分别呈现；公式、行内引用和书目可用 |
| 论文精读 | 完善书目信息、全文摘要边界、跨页和多片段证据、图表坐标轴、公式及实验条件读取 | 方法、实验设置、主要结果和适用边界均可定位到原文；不能把局部片段表述成全文结论 |
| 学术问答与精读追问 | 提升多轮指代、比较问题、按需补读、冲突来源和无依据拒答 | 新会话连续多轮保持正确上下文；复用已有材料；新增读取范围可解释；最终回答简洁且每项引用可定位 |
| 同行评审 | 扩大完整方法覆盖，区分关键缺陷、一般问题和表达建议，防止虚构缺陷 | 贡献、优点、缺点、评分和修改建议彼此一致；每项事实性批评均能回到论文；建议具体可执行 |
| 数据分析 | 强化变量语义和分析范围、统计前提、缺失值、异常值、多表、重复测量及分组口径 | 统计量可独立复算；总体与分组口径不混淆；方法满足数据前提；XLSX 保留原始范围、样本构成和未分析字段 |
| 汇报幻灯片 | 优化面向听众和时长的叙事、页面密度、讲稿、图表组织和公式呈现 | PPTX 可实际打开和演示；每页承担明确叙事功能；关键图表与原数据一致；讲稿能够支撑目标时长 |
| 思维导图 | 改善概念层级、关系类型、去重、长标签、超宽/超长画布和分支定位 | 导图表达关系而非事实堆积；节点无明显重复；标签可读；HTML/PNG/Markdown 内容一致且可导航 |
| 共用来源阅读与 PDF 定位 | 多依据选择时清理旧定位状态，并扩展扫描件、旋转页、重复引文、多文档和超长 PDF | 用户选择具体依据前不显示旧页为新结果；唯一完整引文准确定位；不能可靠定位时明确失败而不是猜测 |

文档附件与资料库上传已在本地扩至 64 MiB，并以实际 18.9 MB PDF 检查 HTTP 输入、解析和原件读取；任务附件使用原始字节传输，避免 Base64 膨胀。表格分析入口仍为 16 MiB，其他解析资源边界仍有效；更大输入和生产代理容量待相应验收。跨页证据、复杂公式、超长表格和多文献布局按实际失败样本推进。仅有配色、间距或措辞偏好的调整排在阻断问题之后。

## P3：长任务健壮性与多任务并发

2026-10-04 本地进展：已接入任务/档位尝试期限、独立总期限、持久化有界恢复、worker 有界
退出及 API 渲染容量隔离；配置与测试边界见 [本轮记录](LONG_TASK_RECOVERY_20261004.md)。
下列条目仍作为完整验收要求，生产拓扑切换、公平调度和最终交付质量绑定并未因此完成。

当前代码已经具备独立 worker、数据库租约 fencing、周期续租、checkpoint 恢复、毒任务熔断、全局运行上限、共享供应商并发限制和有界阻塞线程池。下一阶段不以简单增加线程数为方案，而是完善 API/执行进程隔离、持久化调度、恢复粒度和资源分级。

### P3.1 生产执行拓扑

- 生产环境从 `inline` 切换为 `worker`：API 只负责鉴权、入队、状态读取、取消和下载，长任务由独立 worker 执行；API 重启不得中断研究任务。
- 在资源允许的生产环境运行至少两个 worker 副本；单 worker 崩溃或更新时，由其他副本在租约过期后接管。真正跨主机部署前，必须先提供共享且具备一致性保证的产物存储。
- worker 停止时先停止领取新任务，再等待在途任务；超过优雅退出期限后允许进程退出，由新 worker 从最近 checkpoint 接管。记录退出原因和接管延迟。
- 文档渲染与研究执行分级隔离。PDF、PPTX、XLSX、复杂图示生成不得占满 API 的阻塞执行槽；后续可拆为持久化交付队列。

### P3.2 长任务期限与自动恢复

- 原默认完整任务期限为 3,600 秒。现已增加各任务/档位独立尝试期限与整个任务最终期限；保留已有配置的正数覆盖，深度任务可使用更长窗口，具体默认值与升级方式见本轮记录。继续验证长任务真实恢复和交付，不能仅靠延长期限宣称完成。
- 区分“单次尝试期限”和“整个任务最终期限”。worker 崩溃、供应商瞬时错误、网络抖动、租约丢失和可恢复渲染错误自动重试；输入无效、确定性质量失败和连续无进展才进入终态。
- checkpoint 至少覆盖规划完成、每个子问题完成、来源读取与核验完成、定稿完成和各交付格式完成。接管后只重做最后一个未提交的幂等单元。
- 自动恢复必须保留原始输入、任务模板、档位、模型/检索配置快照、材料、统计范围、证据绑定和累计运行指标；不能在恢复时重新路由成另一类任务。
- 设定有上限的恢复次数和“连续无进展”检测。限制用于防止永久卡死和错误循环，不作为节约成本或减少质量复核的手段。

### P3.3 多任务调度与资源隔离

- 保留数据库范围的全局 `MAX_ACTIVE_RUNS` 和 `MAX_QUEUED_RUNS`，增加按任务重量、优先级和身份的公平调度；不能让多个超长自动研究永久占满全部执行槽。
- 分别限制服务级任务并发、单任务内部并发、供应商并发、命令执行并发和文档渲染并发。任何一层达到上限时应排队或明确拒绝，不能无限创建协程、线程或子进程。
- 任务领取继续使用条件租约和 fencing，确保并发 worker 不会双重执行或由旧 owner 覆盖新结果；幂等键必须覆盖创建、恢复、问答请求和交付重试。
- 问答、状态查询、取消和进度流不得被长任务或大型交付文件生成阻塞。必要时为交互请求保留独立容量。
- 供应商限流、冷却和密钥故障在 API 与所有 worker 之间共享；单个供应商或密钥故障不应拖垮其他可用路径。

### P3.4 可观测性与验收

- 任务详情和运维状态记录：排队时长、当前步骤、最后进度时间、最后 checkpoint、worker/租约 owner、尝试次数、恢复原因、无进展轮次和交付格式状态。
- 本地代码验收继续使用固定模型/检索响应，不启动真实压力测试。本轮基线为场景、worker 与队列测试 `80 passed`；恢复、共享协调、问答幂等和并行分支测试 `78 passed, 9 skipped`，跳过项为本轮未配置 PostgreSQL 的参数化分支。
- 线上压力与故障验收由用户后续执行：同时提交不同重量任务，重启 API，终止一个 worker，模拟供应商超时，并并发请求交付文件；检查无双重执行、无结果串写、可恢复、交互接口可用且最终产物通过任务质量门。
- 耗时、调用次数和 token 继续记录，但只用于发现卡死、重复读取、无效重写和未复用 checkpoint；不设置会提前终止高质量交付的累计 token 预算。

## 每轮产出与进度口径

- 在质量矩阵记录输入、代码版本、首次结果、恢复结果、可打开产物及剩余问题；保留失败，禁止用最终 pass 覆盖首次失败。
- 优先级按影响排列：无法提交/执行/取回结果、上下文错误、重要事实错误、必要交付缺失优先；非阻断显示问题随后处理。
- 不以“新增多少检查规则/测试/文档”作为项目主要进度。汇报哪些任务已实测可用、哪些失败、下一项能解除什么阻断。
- 本次部署已获授权；后续批次按用户当时的发布指令执行，不将本次授权视为持续自动部署授权。
