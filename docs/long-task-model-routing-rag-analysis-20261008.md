# 长任务模型调度、角色卡片与文档检索分析

2026-10-08。基于当前源码、Aliyun 只读查询，以及任务 `606e1a66-bed1-4730-a308-f15cc0c0f65e` 的模型调用事件、冻结配置和写作记录。

本轮完成分析和角色机制验证，没有实施下述调度或 RAG 升级，没有修改线上配置。上一轮核验与任务页修复仍是本地变更。

## 结论

1. **角色卡片机制已接入长任务引擎，但这条线上任务没有使用自定义卡片。** 当前数据库中保存的卡片数为 0，任务冻结快照中的 `cards` 也为空。实际工作由内置规划、研究、反思、综述写作等角色完成。
2. **调用次数多确实有可优化的结构性原因。** 最明确的一处是表格逐格串行核验：18 个单元对应 18 次模型请求，每次输入约 2,000～2,300 token。不能笼统归因于文档切块，也不能认为所有核验都是重复。
3. **当前已有检索增强流程，主要使用关键词和 BM25，没有文档 embedding 检索。** 上传、论文精读和资料库检索不是完全相同的路径。
4. **建议先改调用批处理、角色绑定和上下文组织，再试点混合检索。** 向量检索对跨语言、同义表达和多论文资料池有价值，但不能直接解决逐格核验、串行依赖或无效修订。

## 一、模型为什么调用很多次，每次输入却不大

案例任务共有 60 次请求。以下以每个 `call_id` 的最终记录统计，未把开始和结束事件重复计算。

| 操作 | 请求数 | 输入中位数 | 输入范围 |
| --- | ---: | ---: | ---: |
| 研究计划 | 1 | 1,546 | 1,546 |
| 资料抽取 | 14 | 约 12,387 | 8,895～16,068 |
| 摘录支持关系核验 | 13 | 2,420 | 1,836～4,478 |
| 跨来源一致性与印证 | 2 | 约 7,246 | 6,745～7,746 |
| 反思 | 1 | 2,531 | 2,531 |
| 综述写作 | 1 | 11,685 | 11,685 |
| 表格及正文支持关系核验 | 21 | 2,161 | 2,035～19,274 |
| 公式核验 | 1 | 3,286 | 3,286 |
| 全文回查目标定位 | 4 | 约 4,154 | 2,202～6,105 |
| 覆盖检查 | 2 | 21,654 | 21,654 |

输入合计 **389,007 token**。总输入并不少，主要是分散在多次请求中；其中可能包含反复发送的规则、schema 和资料。同一文本出现多次会分别计入每个请求，不能把合计当成独立阅读的资料量。

所有请求使用同一配置模型标识 `gemini-3.8-flash`。档案显示名称为 `deepseek`，默认推理强度 `high`；部分调用主动覆盖为低推理。这是渠道配置值，不根据名称推断实际底层供应商或真实最大上下文能力。

### 已确认的细碎请求

`workbench/tables.py:595` 在表格审查记录失效时，遍历每个单元，新建一个 `SupportReviewer`，再执行 `review([unit])`。

案例中，18 条表格判断对应前 18 次 `SupportDecisions` 请求；它们从约第 578 秒连续返回到第 624 秒。之后还有 3 次输入约 1.25 万～1.93 万 token 的正文支持核验。因此，“21 次正文核验”这个汇总标签实际上混合了两种粒度。

逐格执行的原意是防止相邻单元借用彼此的引用。优化时必须保留这项约束：

- 将每个单元的 `unit_id`、允许使用的 `evidence_id` 集合、完整证据及判断结果绑定。
- 先按证据共享关系合批，在一批内一次返回多个单元的独立判断。
- 代码逐个验证返回 ID 完整性、证据归属和来源版本。某格只能由其允许的证据支持。
- 批大小受输入容量、输出容量和实际映射准确率共同约束，不能只追求填满上下文。
- 改动一格后，仅复核该格及受影响的比较关系。当前表格已有整体签名复用，但一处变化仍可能使整表重查，应在此基础上细化。

普通正文核验本身已有最多 16 个单元一批的机制，也会尝试把共享证据的单元放在一起。应复用并补齐其“每单元允许证据”的能力，避免再造一套无约束批处理。

### 小输入并不自动代表调度错误

一个复杂公式即使输入很短，也可能需要深入推理；一个已核验事实的格式转换则不需要。应按操作和判断难度选择配置，不按 token 数机械分档。

目前许多调用是独立的结构化任务，不会自动携带此前所有模型对话。阶段间主要通过任务状态、已核验发现和报告资料传递信息，综合写作通常也不会把全部原文重新发送一次。这个方向合理，但需要显式保存论文结构、方法关系、研究问题和未解决事项，避免“提取了很多孤立事实，却缺少整体理解”。

渠道报告的缓存命中 token 本例均为 0。代码已有稳定提示前缀和缓存相关支持，不能直接说项目没有缓存；还需区分前缀是否相同、渠道是否支持缓存、以及渠道是否完整上报。当前输入字段来自服务端 `prompt_tokens`，并没有在显示前扣掉缓存 token。

## 二、角色卡片究竟在哪里参与

运行链路是：

`工作流指定角色名 → CatalogRuntime.resolve_agent → 对应卡片或内置角色 → RunContext.llm_for → 角色绑定模型或默认模型`

卡片机制的有效行为已经由 22 项测试验证，包括提示词、命名模型绑定、完整任务执行及断点恢复。

但目前存在三个使用落差：

### 1. 新建卡片不会自动加入长任务

工作流需要引用卡片的角色名；或者保存与既有步骤相同名称的覆盖卡。创建一张名为“领域专家”的卡片，并不会让所有综述任务自动增加一次专家调用。

案例实际执行的是：附件读取 → 内置规划 → 内置研究 → 反思补充 → 专用综述写作 → 交付前修订。数据库与该任务快照没有自定义卡片，所以没有发生自定义角色分工。

### 2. 卡片行为范围与科研模板不对齐

当前 `CardAgent` 只包装 `plan`、`research`、`reflect`、`synthesize`、`critique` 五种基础行为，并通过 `self.system` 注入提示词。

而长任务还有 `survey_writer`、`paper_reader`、附件读取和内部核验等专用执行路径。它们不能简单等同于通用 `synthesize`，内部核验提示也不是由通用卡片提示统一驱动。虽然命名模型解析可以查询同名卡片的模型绑定，但直接用同名通用卡片替换专用写作者，可能改变原有模板执行行为。

因此，应把“选择执行器”与“调整这个执行器的专业要求、模型偏好”分开。

### 3. 长任务使用冻结配置

任务启动时保存卡片、模型等配置快照，恢复时使用原快照。运行中修改卡片不会自动影响已经开始的任务。这对可复现和恢复是必要的，但界面应明确说明“此修改对新任务生效”，并展示本次任务实际使用的版本。

### 建议的角色升级

保留内置执行器，为科研模板提供明确的配置位置，例如研究规划、证据抽取、综述综合、公式复核。卡片控制领域提示、允许的工具、模型偏好和输出要求，执行器继续负责模板与证据契约。

界面区分三种状态：**卡片可用、已绑定哪些工作流、本次任务实际参与**。新建后若未绑定，直接给出绑定入口；任务详情显示角色、操作、实际模型和配置来源。

不建议为了让卡片“参与”而让所有卡片轮流发言。每个额外角色都应对应一个必须完成的工作项，否则会进一步增加等待和调用次数。

## 三、当前文档如何分块

分块至少有以下几层，不能混为一个参数：

| 路径 | 当前规则 | 用途与局限 |
| --- | --- | --- |
| 资料库和上传文件 | 目标上限 3,600 字符，重叠 320 字符；尽量在后半段的段落或句末断开 | 保存文本片段、哈希、章节、页码和字符位置。这里是字符，不是 token |
| PDF / Office 预处理 | PDF 先解析章节及页码，Office 先解析相应结构，再进入上述文本切块 | 已有结构信息，但最终文本块不等于完整表格或完整公式语义单元 |
| 粘贴论文文本 | 按文本行组合成约 2,500 字符一组；没有上述重叠逻辑 | 单独超长行可能超过目标值，不能把 2,500 当作严格统一上限 |
| 精读中的超长上下文 | 原文能放下时整体提供；否则按 4,000 字符拆片，约三分之二空间保留稳定前缀，再选相关补充片段，补充候选上限 6 | 有节选提示；不同问题可复用前缀，但文档前部偏置及跨片关系值得评估 |
| 附件批次 | 根据实际输入容量、规则和问题长度，将多个来源片段组成一批 | 并不是每个 3,600 字符片段一定单独调用模型 |
| 全文缺失/批评核查 | 按剩余模型容量切块，单块最多 10,000 字符，重叠最多 600 字符，再组成模型批次 | 用于完整覆盖；可以先找反例，但不能凭少量未命中的块确认全文缺失 |

来源定位已有基础。更值得升级的是统一文档版本、父章节、子片段、表格/公式对象与阅读窗口之间的映射，而不是把所有地方的块大小统一改成一个数字。

建议采用“检索片段”和“阅读上下文”两层：

- 检索使用较小且稳定的子片段，便于精确召回与引用。
- 命中后展开到必要的父段落、相邻片段或章节，让模型看到足够上下文。
- 表格携带表头、单位、脚注和标题；公式携带变量定义与适用条件。超长对象允许专门分解，而不是机械截断。
- 每段依据绑定文档 ID、内容版本、来源位置与片段哈希。相同 URL 的不同快照不能静默合成一个版本。
- 单次请求的上下文由问题需求和证据完整性决定，不以填满最大窗口为目标。

## 四、是否应该引入 embedding / RAG

**有必要为混合检索预留并验证能力，但当前不应把“先建设独立向量库”作为解决完成慢的前置条件。**

### 当前已经有哪些能力

资料库搜索会读取当前项目内、纳入状态的片段，以关键词/BM25 加标题、章节、短语和覆盖度排序，先保证不同来源，再补足更多片段。默认请求 5 条，最多 20 条。

候选目前按资料创建时间倒序读取，最多 5,000 个块，再在 Python 中排序。资料量大后，旧文献可能在相关性排序之前就被排除，这是未来应改为索引检索的具体理由。

当前线上持久资料库只有 **1 个项目、1 份资料、33 个片段**；这不包含所有任务临时下载或上传的材料。案例任务 `project_id=null`，没有绑定项目资料库。只给现有资料库加 embedding，不会改变该任务的表格核验调用链。

### 向量检索适合解决的问题

- 中文问题查找英文论文中的同义概念。
- 问题措辞与原文表达差异较大。
- 多篇论文、多次任务反复检索同一批材料。
- 较大的资料池中，关键词检索召回不足。

embedding 无法代替证据真伪判断、数值核对、来源版本管理、任务状态调度，也不会自动把 18 次逐格核验合成一次。

### 推荐的混合检索链路

```mermaid
flowchart LR
  A[问题与任务范围] --> B[按权限和版本确定材料集]
  B --> C[关键词与 BM25 召回]
  B --> D[向量语义召回]
  C --> E[融合与去重]
  D --> E
  E --> F[必要时轻量重排]
  F --> G[展开父段落与必要邻接内容]
  G --> H[形成带位置的证据包]
  H --> I[抽取与局部核验]
```

关键词召回保留论文名、缩写、公式符号、数据集、数值等精确匹配优势；向量补足语义匹配。重排不是再让大模型逐块判断一遍，否则会重新制造细碎调用。

资料库、用户上传和任务临时获取的原文应通过同一检索接口访问，同时保持项目、用户、任务和文档版本隔离。临时材料不能未经选择就成为所有后续任务可见的公共资料。

### 阅读策略必须随任务变化

| 任务 | 推荐路径 |
| --- | --- |
| 定点查找一个定义或实验参数 | 混合召回，再展开相邻正文 |
| 单篇精读、方法完整解释 | 先建立章节与方法结构，必要章节完整阅读，检索用于定位细节 |
| 多篇论文综述 | 每篇先形成有出处的结构摘要，再按研究问题检索和比较 |
| 跨章节公式与实验比较 | 按依赖补齐公式、定义、设置及结果，不局限于向量前几个命中 |
| 断言某篇论文没有报告某项信息 | 核查当前取得的相关全文覆盖，不能把“向量没搜到”当成“全文不存在” |

### 基础设施建议

先定义可替换的检索接口和评测集。生产已有 PostgreSQL，可优先评估 pgvector，避免过早引入另一套独立数据库；不过当前数据库的可用扩展查询没有返回 `vector`，需要单独准备扩展或镜像升级，不能假设已经可直接启用。

embedding 模型应实测中文问题对英文论文、科研缩写及长段落的表现，并记录模型版本。更换 embedding 模型需要版本化重建索引，不能混用不兼容向量。只有规模、索引维护或检索延迟证明需要时，再评估独立向量服务。

## 五、长任务调度建议

将现有能力组织成四个清楚的层次：

1. **角色与工作流决定做什么。** 哪个执行器负责什么产物，哪些结论需要补证据。
2. **操作策略决定怎么调用。** 抽取、普通核验、综合写作、复杂推导分别使用适合的模型与推理配置；尊重显式模型锁定。
3. **上下文组装决定读什么。** 任务概要、已完成事项、相关完整证据和局部未解决问题，替代重复发送整个历史。
4. **请求队列决定何时调用。** 满足真实依赖即可进入队列，在渠道容量内优先推进用户正在等待的结果，并防止长任务饥饿。

当前研究分支上限 4、渠道请求上限 2，且 DAG 存在整层等待。先减少不必要的依赖、取消整层屏障、合批独立小检查，再考虑提高渠道并发。

模型升级也要按问题原因：

- 资料缺失：检索或读取原文，不能靠更强模型补事实。
- 确有复杂推理：在相关完整上下文中升级复核配置。
- 格式不合法：做有上限的结构修复，不重新研究。
- 输入/输出容量不足：按完整语义单元重新组织批次，不原样重发。
- 已知证据冲突：固定来源版本、修改相关断言，保留其他有效结果。

每次追加调用都应关联尚未完成的工作项。没有新增证据、输入变化、服务恢复或明确修订目标时，不发起同一检查的下一轮。利用现有冻结快照、局部缓存、修订检查点继续演进，不需要另造一套互相竞争的总控循环。

## 六、推荐顺序与验收

| 优先级 | 工作 | 验收 |
| --- | --- | --- |
| P0 | 表格核验合批，保留每格允许证据；同输入复用 | 同一案例显著减少细碎请求；相邻格的证据不能串用；遗漏、重复 ID 被发现 |
| P0 | 角色实际绑定可视化，区分卡片、执行器和操作模型策略 | 创建与绑定步骤明确；任务记录能解释哪些卡生效；修改不污染旧任务快照 |
| P1 | 文档版本与父子片段映射统一，上下文按问题拼装 | 表格、公式、跨章节关系不因切块丢失；来源冲突可定位 |
| P1 | DAG 就绪调度及受渠道限制的请求优先级 | 不等无关慢分支；取消和恢复不重复执行；前台交互不被可选任务长时间阻塞 |
| P2 | BM25＋embedding 的影子检索实验 | 同一材料集比较跨语言召回、必要章节覆盖、首次可用结果耗时和最终证据支持质量 |
| P2 | 经评测后决定向量存储与模型组合 | 以实测召回、质量、延迟和运维成本决定，不以增加模型数量或输入 token 为目标 |

建议统计每次请求的操作类型、单元数、输入证据数、输入/输出/思考 token、排队时间、执行时间、卡片版本、模型选择原因，以及是否复用了已有判断。这样才能区分“做了必要的细致核验”和“把同一件事碎片化重复执行”。

真实模型对比应使用固定资料快照和同一任务集，覆盖长 PDF、中文问英文论文、公式、复杂表格、角色覆盖、恢复任务和缺失原文。除了调用数和耗时，还必须检查引用支持与必需交付，不能通过少检查来制造提速。
