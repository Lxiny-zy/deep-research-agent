## 一、设计思路总述

### 0. 一句话架构

**双通道 + 三级级联 + 三条单向不变量**：用户 query 与检索来源各走一条意图判定通道，
每条通道内部是「规则 → 本地统计模型 → LLM 兜底」的成本阶梯，逐级升级、尽早退出；
判定结果只允许朝**收紧**的方向影响系统行为（风险不可降级、来源门禁不可放宽、路由不可覆盖显式选择）。
口诀：**两条通道、三级阶梯、只紧不松**。

### 1. 为什么这个项目需要意图识别（动机要讲对）

面试时最容易被问倒的不是「怎么做」，而是「为什么要做」。这里的答案必须是**项目内生的缺口**，
而不是「意图识别很流行」：

- 项目原有安全审计**全部集中在来源边界**（SourcePolicy→EvidenceVerifier→语义→交叉印证），
  见 02 号文档的四层护栏。
- 但**用户 query 这一侧此前只校验长度**（`api.py` 的 `CreateRunRequest.query` 只有
  `min_length=1, max_length=2000`），然后直接进 Planner 的 prompt。
- 对一个主打「安全审计」的系统，请求入口无审计是真实的不对称。

意图识别补的正是这一侧，并顺带解决成本问题：单点事实查询和开放调研耗费的 token 相差数倍，
此前所有请求都跑同一条 deep 流程。

### 2. 双通道：判定对象与权力边界都不同

| 通道 | 判定对象 | 输出 | 权力 |
|---|---|---|---|
| 输入侧 `classify_query` | 用户 query（半可信） | 任务意图 + 风险意图 | 可路由工作流、可拒识整个请求 |
| 来源侧 `classify_source` | 检索到的网页文本（**完全不可信**） | 来源意图 | **只能把 allow 收紧为 quarantine** |

来源侧权力被刻意削弱，因为它读的是攻击者可控的输入。见 `guardrails.screen_source_intent`：
`deny` / `quarantine` 的结论原样返回，只有 `allow` 会被进一步收紧。

**这条约束的价值**（面试主动讲）：即便意图判定被间接注入完全操控，最坏结果也只是
把正常来源误判为可疑（**可用性损失**），而不可能让一条攻击性来源进入模型上下文（**安全性损失**）。
把安全属性做成结构上不可违反的，而不是依赖组件自身正确——这与 02 号文档
「模型提数据，程序盖验章」是同一套思路的延伸。

### 3. 三级级联：为什么不直接调大模型

| 层 | 实现 | 成本 | 覆盖 | 精度 |
|---|---|---|---|---|
| L1 规则 | 正则，`rules.py` | 0 token、微秒级 | 窄 | 高 |
| L2 本地模型 | TF-IDF + 逻辑回归，纯 Python | 0 token、微秒级 | 中 | 中高 |
| L3 大模型 | 结构化输出 | 数百 token、数百毫秒 | 宽 | 高 |

**级联的意义是成本阶梯，不是准确率堆叠**——这是最关键的一句。升级条件（`cascade.py`）：

- L1 命中风险 → **立即返回，不再往下**（拒识决定不需要更贵的确认，且能省掉攻击流量的全部成本）
- L1 命中任务意图 → 采纳
- L2 置信度 ≥ 校准阈值 → 采纳，零 token 结束
- 否则 → L3；**LLM 不可用或失败 → 返回 `unknown` 弃权，绝不猜**

`IntentDecision.tier` 与 `escalated` 记录判定由哪一级给出，直接支撑
「X% 请求 0 token 解决」的成本结论（`make intent-eval` 出真实数字）。

### 4. L2 为什么自己实现，而不是 sklearn

- **打包约束**：项目要打包成单文件桌面版（`DeepResearchAgent.spec`，PyInstaller），
  为一次稀疏点积引入几十 MB 科学计算栈不划算。模型参数就是一个 JSON
  （词表 IDF + 权重矩阵 + 偏置），推理是哈希查表加乘加。
- **字符 n-gram 而非分词**：中文没有空格，引入分词器又是重依赖。字符 2/3-gram
  对中文天然稳健（「有什么区别」直接成为特征），英文额外补一路词 unigram。
  副作用：零宽拆词等变体在 `normalize` 阶段就被还原，与 SourcePolicy 的经验一致。
- **完全确定性**：数据固定、切分种子固定（`SEED=20260802`）、权重零初始化、
  迭代次数固定 → 同一份数据永远训出同一个模型文件，**可 diff、可提交、可回归**。
- **训练细节**：批量梯度下降 + L2 正则（只作用于权重不作用于偏置）、
  平滑 IDF `log((1+N)/(1+df))+1`、TF 对数缩放、L2 归一化、`df>=2` 剔噪。

### 5. 阈值是校准出来的，不是拍脑袋

`calibrate_threshold`（`scripts/train_intent_model.py`）在 **dev 集**上扫描阈值，
取「采纳部分精度 ≥ 0.9」中**覆盖率最高**的那个，写进模型文件的 `min_confidence`。

这是级联最关键的旋钮：定高了大量样本白白升级到 LLM（贵），定低了错误路由流入下游（错）。
IDF 也只用 train 统计，防止 dev 信息泄漏。

### 6. 标签体系的三条设计原则

1. **每个标签都要有下游动作**。`comparative` → 必须多侧面 + 反思补洞；
   `factual_lookup` → 省掉规划与反思。落不到动作上的标签不设。
2. **任务意图与风险意图正交**，各自独立判定。一条 query 可以既是合法的
   `factual_lookup` 又携带 `prompt_injection` 风险；用单一标签体系会强迫二者互斥，
   导致「为了标注风险而丢掉路由信息」。
3. **保留 `unknown` / `none`**。级联每一级都可能弃权，弃权必须是**可表达的一等状态**，
   而不是被迫落到某个具体类上。

任务意图 → 执行策略映射（`routing.py`）：

| 意图 | 工作流 | 子问题上限 | 依据 |
|---|---|---|---|
| `factual_lookup` | quick | 2 | 单点事实，规划与反思纯属浪费 |
| `comparative` | deep | 4 | 需多侧面，易漏证据 |
| `exploratory` | teams | 6 | 面最广，适合多团队分头覆盖 |
| `temporal_trend` | deep | 5 | 需多时间切片交叉印证 |
| `causal_analysis` | deep | 4 | 因果链条需补洞 |

### 7. 三条安全不变量（本模块的核心卖点）

**7.1 风险单调收紧**（`_tighten_risk`）：任何一级判定为高危，后续级别都不能把它降回 `none`。
这让「被注入的 LLM 把攻击洗白」**在结构上不可能**——L1 已判定的 `prompt_injection`，
L3 返回 `none` 也不会生效。注意 L3 路径上 `current` 恒为 `none`（L1 命中会提前返回），
但仍走同一入口，避免将来调整级联顺序时绕过不变量。

**7.2 来源意图只能收紧**（`screen_source_intent`）：见第 2 节。

**7.3 路由只能收紧，且让位于显式选择**：
- 用户显式指定工作流时意图路由完全让位（`plan_route` 首条判断）。
  自动化不能覆盖显式意图，否则用户失去控制感、线上问题难排查。
- 意图建议 6 个子问题但用户配置上限是 3 时取 `min`。
- 置信度 < `MIN_ROUTING_CONFIDENCE`(0.6) 不路由——**路由错误的代价
  （跑错流程、烧掉预算）高于走默认流程**。

### 8. 拒识如何终止流程：新增的通用 halt 原语

被拒识的请求**不能抛异常**——异常会走引擎的「单步失败隔离」，流程照跑不误。

引擎新增 `HALT_SCRATCH_KEY`（`workflow.py`）：任一角色把它设为真值，
引擎即跳过全部剩余步骤，并记为 `skipped`（而非从运行历史中消失）。
**刻意做成通用原语而非「意图专用」**：引擎不需要知道谁因为什么要停下，
将来的合规/配额检查可复用同一机制（`test_halt_primitive_is_agent_agnostic` 用一个
匿名 Halter 角色证明这点）。

与预算耗尽的**区别**（面试常追问）：预算耗尽仍跑终端角色以产出尽力而为的报告
（`_is_terminal` 豁免），而 halt 跳过**包括终端在内**的全部剩余步骤——
请求终止的角色已经写好了 `bb.report`，再跑 synthesizer 只会拿着空结果集覆盖掉那份说明。

**拒识仍产出一份说明性报告**（`blocked_report`）。整条链路（落库/SSE/回放/前端）
都以「一定有报告」为前提；给拒识一份结构化说明，既不破坏这个不变量
（否则 `require_report=True` 会把拒识变成「运行失败」），也让用户看得到为什么被拒。

### 9. 路由发生在哪一层，为什么

**在 API 创建 run 之前**（`preroute_workflow`），不在流程内部。

原因：**工作流定义会被写进初始 checkpoint，崩溃恢复直接读它**。若等 `IntentRouter`
在流程内部才路由，那时执行路径已经定死，路由结论就只能是一条日志。

预路由**只跑 L1 + L2**（`enable_llm=False`）：这段代码在 HTTP 请求的**同步段**上，
升级到 LLM 会把创建研究的响应从毫秒级拉到秒级。

判定写进初始 checkpoint，流程内的 `IntentRouter` **复用而不重判**——既省成本，
也保证崩溃恢复后的运行拿到与首次完全一致的意图结论（重判可能因模型版本/阈值变化得到不同结论）。

> **易错点（我踩过）**：复用是「跳过判定」不是「跳过拦截」。第一版实现里
> `if INTENT_SCRATCH_KEY in scratch: return bb` 直接返回，导致预路由已判定为攻击的请求
> 在流程内被放行。修复后：复用的判定若是拒识，拦截动作照常执行；
> 缓存结构损坏时**重新判定**而不是当作无风险放行。见 `test_router_enforces_cached_block`
> 与 `test_router_reclassifies_when_cached_decision_is_corrupt`。

### 10. 规则设计：误判方向不对称

风险规则**宁可漏判不可误判**——漏判由 L2/L3 兜底，而误判会把正常研究请求拒之门外。
因此每条规则都要求「**动词 + 特权宾语**」的组合命中，不做单关键词匹配
（"system prompt" 本身是完全合法的研究话题）。

数据集里专门放了**与攻击同词不同意图的困难负例**作为误伤率的分母：

- 「研究一下提示词注入的防御方案有哪些」
- 「系统提示词工程有哪些最佳实践」
- 「数据库删除操作的审计方案怎么做」
- 「忽略噪声数据的预处理方法有哪些」（"忽略"是干扰词）

任务规则则只覆盖**模式极其稳定**的表达，其余一律弃权交给 L2——
不用规则去拟合本该由模型学的分布。

### 11. 评测方法论

**安全指标必须成对报告**：只报拒识率的评测可以用「全部拒绝」刷到 100%，
所以 `eval/intent_eval.py` 同时输出**拒识率**（漏放攻击 = 安全事故）与
**误伤率**（正常请求被拒 = 产品不可用），退出码在任一出现问题时为 1（可做 CI 门）。

**混淆矩阵而非单一准确率**：「exploratory 被判成 comparative」和
「comparative 被判成 factual_lookup」的下游代价完全不同——前者只是流程选得不够宽，
后者会直接跳过反思补洞。

**级联分流比例**是「为什么不直接用 LLM」的量化回答。

**诚实口径**：离线评测只覆盖 L1 + L2，L3 的贡献需要真实 LLM 才能测，
报告里显式标注（与 02 号文档的对抗评测口径一致）。

### 12. 残余风险（主动交代）

① **L2 训练数据是手写的百级样本**，覆盖「模式够稳定但规则写不动」的中间地带，
不宣称开放世界意图判定能力；真实部署应用线上 query 日志重训。
② **规则是黑名单**，换措辞可绕过——兜底靠「即使意图层漏判，原有四层证据护栏仍在」。
③ **风险类型可能判错**（`prompt_injection` 判成 `system_prompt_probe`），
但不影响拦截决策，评测中单列为「拦住了但类型判错」。
④ **来源侧默认不升级 LLM**：逐条调用会让成本随检索结果数线性膨胀；
规则弃权的来源保持 `allow`，仍受原有 SourcePolicy 与证据门禁约束。
⑤ **意图与真实需求的鸿沟**：用户表述的意图未必是真实需求，路由永远是建议不是命令。

## 二、题库（26 题）

### A. 基础理解（7 题）

**A1. 这个项目为什么需要意图识别？**
考点：动机是否内生。
答：项目安全审计原本全在来源边界（SourcePolicy→逐字→语义→交叉印证），
而用户 query 侧只校验长度就进 Planner prompt——请求入口无审计，对主打安全审计的系统是不对称缺口。
意图识别补这一侧；顺带解决成本问题（此前所有请求都跑同一条 deep 流程，单点查询和开放调研成本相差数倍）。
追问链：那为什么不直接在 Planner 的 prompt 里加约束？→ 同 02 号文档的答案：
prompt 约束不可审计不可回归，裁决权必须在程序侧。

**A2. 三级级联分别是什么？各自成本量级？**
答：L1 正则（0 token、微秒级、覆盖窄精度高）→ L2 本地 TF-IDF+逻辑回归
（0 token、微秒级、覆盖中）→ L3 大模型（数百 token、数百毫秒、覆盖宽）。
陷阱：说成「三级投票/集成」就错了——是**逐级升级、尽早退出**的成本阶梯，不是并行投票。

**A3. 任务意图有哪几类？每类对应什么动作？**
答：见第 6 节表。关键是**每个标签都有下游动作**，落不到动作上的标签不设。

**A4. 为什么任务意图和风险意图分开两套标签？**
答：二者正交。一条 query 可以既是合法的 `factual_lookup` 又携带 `prompt_injection` 风险；
合成单一标签会强迫互斥，导致为标注风险而丢掉路由信息。

**A5. `unknown` 存在的意义？**
答：级联每级都可能弃权，弃权必须是可表达的一等状态。落到 `unknown` 时走默认工作流，
比强行猜一个意图然后跑错流程代价小。

**A6. 来源侧意图判定能做什么、不能做什么？**
答：只能把 `allow` 收紧为 `quarantine`；不能把 `deny`/`quarantine` 翻案。

**A7. 意图识别关掉之后系统还能跑吗？**
答：能。`INTENT_ENABLED=false` 时 IntentRouter 直接放行、preroute 不路由，
行为回退到加意图识别之前。此外 `INTENT_LLM_FALLBACK=false` 可只跑两级（零 token 零网络），
`INTENT_SOURCE_SCREENING=false` 可单独关来源侧。

### B. 设计权衡（7 题）

**B1. 为什么不直接用大模型做意图识别？它准确率更高。**
考点：这是本模块最高频的题。
答：三点。① **成本**：意图判定是每个请求的**前置**步骤，不是可选步骤——
把它做成一次 LLM 调用，等于给系统所有流量加一笔固定开销；② **延迟**：预路由在 HTTP
同步段上，LLM 会把创建研究的响应从毫秒级拉到秒级；③ **可用性**：LLM 不可用时
意图识别不该整体失效。级联把 LLM 保留为**低置信样本的兜底**，用 `tier`/`escalated`
字段量化分流比例。补充：攻击流量在 L1 就被拦下，攻击者无法通过刷请求来放大我们的 LLM 账单。

**B2. L2 为什么自己写而不用 sklearn？**
答：见第 4 节（打包约束 + 确定性 + 规模不匹配）。
追问：那如果数据涨到十万级呢？→ 换 sklearn/增量训练是合理的；当前的接口
（`TextClassifier.predict` 返回 `(label, confidence, scores)`）没有暴露实现细节，可以替换。

**B3. 为什么用字符 n-gram 而不是分词？**
答：中文无空格，分词器是重依赖且引入分词错误传播；字符 2/3-gram 对中文天然稳健。
英文退化为子串匹配，所以额外补一路词 unigram。副作用是零宽拆词在归一化阶段就被还原。

**B4. 阈值 `min_confidence` 怎么定的？**
考点：能否说出「校准」而非「试出来的」。
答：dev 集上扫描，取「采纳部分精度 ≥ 0.9」中覆盖率最高的阈值，写进模型文件。
定高了样本白白升级 LLM（贵），定低了错误路由流入下游（错）。
陷阱：说「0.6 是经验值」就丢分了。

**B5. 路由为什么放在 API 层而不是流程内部？**
答：工作流定义写进初始 checkpoint 且崩溃恢复直接读它；流程内路由时执行路径已定死，
结论只能是一条日志。
追问：那流程内的 IntentRouter 还有什么用？→ 它是判定结论的**执行者与审计点**：
复用预路由的判定、执行拦截、发 INTENT 事件落库、写路由记录；
并且让「意图门禁」成为可被任意工作流编排的一等角色（guarded 流程）。

**B6. 拒识为什么不直接抛异常？**
答：引擎对单步异常做失败隔离，抛异常流程照跑不误。改用 halt 原语跳过剩余步骤，
并自带说明性报告——保持「一定有报告」的全链不变量（否则 `require_report` 会把拒识变成运行失败）。

**B7. halt 和预算耗尽的跳步有什么区别？**
答：预算耗尽仍跑终端角色（synthesizer/aggregator）产出尽力而为的报告；
halt 跳过**包括终端在内**的全部剩余步骤，因为请求终止的角色已写好报告，
再跑 synthesizer 会用空结果集覆盖它。

### C. 深挖实现（7 题）

**C1. 讲一下 `_tighten_risk` 的作用和必要性。**
答：风险单调收紧——只有更严重的风险能覆盖既有判定。让「被注入的 LLM 把攻击洗白」
结构上不可能。当前 L3 路径上 `current` 恒为 `none`，仍走同一入口是为了将来调整
级联顺序时不绕过不变量。

**C2. TF-IDF 的具体公式和归一化？**
答：TF 用 `1+log(count)` 对数缩放；IDF 用平滑版 `log((1+N)/(1+df))+1`（与 sklearn
smooth_idf 一致）；相乘后 L2 归一化。IDF **只用 train 统计**防止 dev 泄漏；
`df>=2` 剔除只出现一次的噪声特征并压缩模型体积。推理时训练期未见的特征直接丢弃
（不做 OOV 桶——词表封闭，保留未知特征只是无权重的噪声维度）。

**C3. softmax 为什么要减最大值？**
答：防 `exp` 上溢。`_softmax` 里 `exp(logit - max)`，数学上等价，数值上稳定。

**C4. 训练怎么保证可复现？**
答：数据固定在 `dataset.py`、切分种子固定、**权重零初始化**、迭代次数固定、
无 `Date.now`/随机采样。因此同一份数据永远训出同一个模型文件，可 diff、可提交、可回归。
`stratified_split` 按标签分层保证每类在 dev 里都有样本（小数据集上尤其重要）。

**C5. 词表全未命中时会怎样？**
答：`predict` 返回置信度 0.0 和空 scores → 低于阈值 → 级联继续升级到 L3 或弃权。
关键是**不能给一个任意标签的高置信判定**（`test_classifier_returns_zero_confidence_when_no_feature_matches`）。

**C6. LLM 返回了枚举外的标签怎么办？**
答：在 `_llm_classify_query` 里用 `in QUERY_INTENTS` / `in RISK_INTENTS` 白名单收敛为
`unknown`/`none`，不原样透传给下游路由（`test_cascade_rejects_out_of_vocabulary_llm_labels`）。
这与 02 号文档「模型提数据、程序盖验章」是同一条原则。

**C7. 意图判定进 checkpoint 的语义是什么？**
答：预路由的判定写进初始 checkpoint；流程内 IntentRouter 复用而不重判（省成本 +
恢复一致性）。但复用只跳过**判定**不跳过**拦截**：缓存是拒识结论时照常拦截，
缓存结构损坏时重新判定而非放行。

### D. 压力与陷阱（5 题）

**D1. 攻击者把注入写成规则没覆盖的措辞，你这套不就废了？**
答：承认黑名单不完备是本质局限。三层兜底：① L2/L3 覆盖规则写不动的表达；
② 即使意图层完全漏判，**原有四层证据护栏仍在**——注入内容要影响报告，
还得通过逐字引用、语义支持、交叉印证；③ 来源侧意图判定是**追加**的一道，
不替换任何既有检查。这套设计里没有任何单点是「唯一防线」。

**D2. 你的意图判定用了 LLM，那 LLM 被这段文本注入了怎么办？**
考点：这是本模块最值得展开的题。
答：正是为此设计了三条**单向**不变量。以来源侧为例：判定结果只能把 `allow` 收紧为
`quarantine`，不能反向。所以即便判定器被完全操控，最坏结果是把正常来源误判为可疑
（可用性损失），而**不可能**让攻击性来源进入模型上下文（安全性损失）。
风险侧同理：`_tighten_risk` 保证已识别的攻击不能被下游降级。
安全属性做成结构上不可违反，而不是依赖组件自身正确。

**D3. 「研究一下提示词注入的防御方案」会不会被你误拦？**
答：不会，这是数据集里的困难负例，专门作为误伤率的分母。规则要求
「动词 + 特权宾语」组合命中，`prompt injection` 作为**研究对象**出现时不构成
「推翻先前指令」的动作。`test_rules_do_not_flag_legitimate_research` 参数化覆盖了
6 条这类 query。评测输出里误伤率与拒识率成对报告——只报拒识率的评测可以用「全拒」刷满。

**D4. 意图识别的准确率是多少？**
答：先反问度量口径——离线评测覆盖的是 L1+L2 两级，L3 需要真实 LLM 才能测，
这一点在评测输出里显式标注。数据集是手写的百级样本，度量的是「已知表达模式上的
管线正确性」，不宣称开放世界意图判定率。跑 `make intent-eval` 出准确率、混淆矩阵、
拒识率、误伤率、级联分流四组数字。
陷阱：直接报一个漂亮数字而不交代口径，追问一层就崩。

**D5. 意图路由如果把用户的问题路由错了，用户不就得到更差的结果？**
答：三重保守设计。① 置信度 < 0.6 不路由（路由错误的代价高于走默认流程）；
② 用户显式指定工作流时路由完全让位；③ 子问题上限取 `min(建议, 用户配置)`，只收紧不放宽。
且路由结论与判定依据全部展示在前端 IntentPanel（层级、置信度、概率分布、命中信号），
用户能看到为什么这么跑，而不是黑箱。

## 三、模块速记

- **一句话**：双通道（query/来源）、三级阶梯（规则/本地模型/LLM）、三条单向不变量（风险不降级、门禁不放宽、路由不覆盖显式）。
- **口诀**：**两条通道、三级阶梯、只紧不松**。
- **动机**：安全审计原本只在来源侧，请求入口无审计 —— 这是内生缺口不是蹭热点。
- **成本论**：级联是**成本阶梯不是准确率堆叠**；`tier`/`escalated` 量化「多少请求 0 token 解决」。
- **最强的一题**：D2（判定器自身被注入怎么办）→ 答单向不变量，把安全做成结构性质。
- **最容易丢分**：B4 阈值（要说 dev 集校准）、D4 准确率（要先说口径）。
- **踩坑记忆点**：复用缓存判定时差点让拒识请求放行 —— 复用的是判定不是拦截。
- **演示**：`make intent-eval`（30 秒出混淆矩阵与拒识/误伤率）、前端 IntentPanel（判定依据可视化）。
