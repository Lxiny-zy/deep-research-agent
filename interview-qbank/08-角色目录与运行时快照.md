## 一、设计思路总述

### 0. 一句话架构

这是一个把“可编辑控制面”安全翻译成“可恢复执行面”的模块：

**角色与模型数据化、工作流先归一再校验、运行开始前冻结语义、密钥只保留活引用、并发编辑用版本号拒绝覆盖。**

可以记成四句话：

1. **卡片决定角色语义**：`behavior` 复用内置执行逻辑，`system_prompt` 定制角色，`name` 是工作流引用与模型解析键。
2. **档案决定模型实例**：角色绑定档案优先，其次 Catalog 默认档案，最后回退进程级模型。
3. **流程保存前必须过服务端门禁**：图与线性步骤保持同步，角色、条件、DAG、终端报告角色和重试上界统一校验。
4. **一旦创建 run，执行语义不再追随控制面漂移**：工作流定义、角色行为、提示词、模型非密钥参数和终端角色都进入 checkpoint；密钥不落快照，恢复时按档案 ID 从受保护仓储重新取。

### 1. Catalog 不是普通 CRUD，而是系统控制面

Catalog 有四类全局实体（`persistence/orm.py:258-335`）：

| 实体 | 管什么 | 如何进入运行时 |
|---|---|---|
| ModelProfile | endpoint / model / 参数模式 / API key | `CatalogRuntime.resolve_llm` 按角色解析 |
| AgentCard | name / behavior / prompt / 模型绑定 | `CardAgent` 适配成统一 Agent 协议 |
| SearchKey | Tavily key / priority / enabled | 每次执行构造主备检索池 |
| WorkflowDef | steps / nodes / edges / viewport / version | 创建 run 时冻结为 WorkflowRun definition |

真正的设计问题不是“怎么增删改查”，而是：**这些会被用户修改的全局配置，怎样在不污染引擎、
不泄露密钥、不破坏恢复一致性的前提下影响一次具体运行。**

因此模块明确区分：

- **控制面**：Catalog 表与编辑 API，可以随时修改；
- **执行面**：单次 run 的 Workflow、CatalogRuntime、checkpoint 和 manifest；
- **转换边界**：创建 run 时完成工作流定义与角色语义快照，后台任务的流程与角色语义只消费已经冻结的执行输入
  （`api.py:1104-1147`，`orchestrator.py:100-117`）。

### 2. 数据驱动角色：扩展的是“角色配置”，不是任意代码

`CardAgent` 不动态执行数据库里的代码。它只允许五种 `behavior`：
`plan / research / reflect / synthesize / critique`（`catalog/dto.py:13-14`），
映射到五个已经实现并测试过的内置角色类（`agents/card_agent.py:19-26`）。

一张卡片只改变三件事：

- `name`：工作流引用名，也是 `ctx.llm_for(name)` 的模型选择键；
- `behavior`：委托哪一种内置 step 逻辑；
- `system_prompt`：非空时覆盖该行为的内置提示词，空值沿用默认
  （`agents/card_agent.py:33-52`）。

取舍很明确：

- 好处：新建“便宜模型研究员”“严苛综合者”不改引擎代码，行为契约仍可测试；
- 代价：它不是任意插件系统。新增全新的工具权限、状态结构或执行算法，仍需实现 Python Agent 并注册。

### 3. 三层解析优先级

角色与模型各有一条独立解析链：

**角色解析**

`启用的同名角色卡 → CardAgent → 内置 registry`

`CatalogRuntime.resolve_agent` 先查启用卡片，未命中才调用代码注册表
（`catalog/runtime.py:111-130`）。因此同名卡片可以有意覆盖内置角色；禁用卡片则不参与覆盖。

**模型解析**

`角色绑定档案 → Catalog 默认档案 → RunContext 默认 LLM`

前两级在 `CatalogRuntime.resolve_llm`（`catalog/runtime.py:174-202`），最后一级由
`RunContext.llm_for` 回退（`agents/base.py:44-72`）。同一档案在一次 run 内只构造一个 LLM client，
按 profile ID 缓存，避免每个步骤重复创建连接池。

**工作流解析**

`内置工作流 → 已启用自定义工作流 → deep 默认流程`

内置名称优先，所以创建自定义工作流时直接拒绝与内置同名
（`catalog_api.py:222-227`，`orchestrator.py:384-405`），避免“存得进去但永远选不到”的幽灵配置。

### 4. 同名覆盖后，终端角色语义必须按“最终生效行为”重算

“角色名叫 synthesizer”不等于“它一定产出报告”。用户可以创建一张同名卡片，把它的 behavior
改成 `research`。此时真正生效的是自定义研究员，内置 synthesizer 已被覆盖。

`terminal_roles_for_cards` 的算法是：

1. 只看启用卡片；
2. 先从内置终端集合移除所有被同名覆盖的名字；
3. 再把 behavior 为 `synthesize` 的自定义卡片加入终端集合
   （`catalog/runtime.py:40-50`）。

这个结果同时用于角色列表的 `produces_report`、保存工作流时的终端校验、运行时引擎的终态判断，
避免 UI、API 与执行器对“谁能收尾”各说各话
（`api.py:1290-1323`，`catalog_api.py:243-268`，`orchestrator.py:536-560`）。

### 5. 自定义工作流为何同时保存 steps 与 graph

`WorkflowDef` 同时保存：

- `steps`：兼容旧版线性工作流和列表式展示；
- `nodes / edges`：承载自由布局、分支、条件边和 join；
- `viewport`：只服务编辑体验；
- `version`：服务乐观并发控制
  （`catalog/dto.py:143-178`，`persistence/orm.py:313-335`）。

双表示的风险是漂移，所以 API 不信任客户端同时提交的两份数据，而是在
`_normalize_graph_payload` 中统一归一：

- 改图：合并未提交的旧 nodes/edges，校验节点、边、条件与 viewport，再按拓扑层重算 steps；
- 改 steps：生成兼容图；
- 只改 viewport：不碰执行语义；
- 旧记录只有 steps 时，第一次图更新先自动升级出 nodes/edges
  （`catalog_api.py:271-328`）。

测试覆盖了 edges-only、nodes-only、viewport-only、steps-only 和旧数据升级
（`test_workflow_def_api.py:310-436`）。

### 6. 保存门禁与运行门禁各守一层

保存自定义工作流时，服务端会：

1. Pydantic 解析 Step / Node / Edge；
2. 校验条件表达式；
3. 检查角色是否存在且已启用；
4. 禁止自定义流程递归使用 compose / team_fanout；
5. 限制反思轮次、单步重试和全流程最坏退避；
6. 要求所有图分支汇入唯一报告终端
   （`catalog_api.py:230-268`，`workflow.py:218-317`）。

运行时仍保留最后一道终端检查，并由 `WorkflowEngine(require_report=True)` 保证最终必须真的得到报告
（`orchestrator.py:536-565`）。这不是重复劳动：保存门禁保护正常入口，运行门禁防数据库被外部脚本修改、
历史脏数据或快照损坏。

### 7. 乐观锁：两层检查，前端保留草稿

自定义工作流每次更新都携带 `version`：

- API 先把提交版本与刚读取的当前版本比较，冲突返回 409；
- repository 再执行 `WHERE id=? AND version=?` 的条件更新，并把版本加一；
- 即使两个请求都通过了 API 预检查，数据库层也只允许一个成功
  （`catalog_api.py:535-565`，`catalog/repository.py:346-376`）。

前端收到 409 后不卸载编辑器，因此本地草稿仍在；它只刷新服务端版本号，让用户确认后可再次提交
（`frontend/src/pages/WorkflowBuilderPage.tsx:11-15,83-114`）。

边界：这不是多人协作合并。第二次提交仍可能覆盖对方字段，只是第一次覆盖不会静默发生。

### 8. 创建 run 时先冻结，再持久化，再启动后台任务

关键顺序在 `POST /api/runs`：

1. 解析最终 workflow；
2. 创建初始 WorkflowRun；
3. 自定义流程把完整 definition 写入 execution；
4. 把本流程可能触达的 Catalog 语义写进 checkpoint；
5. `repo.create_run` 持久化；
6. 最后才 `asyncio.create_task` 启动后台执行
   （`api.py:1104-1164`）。

这样即使进程在返回 202 后立刻崩溃，恢复器拿到的也不是一个“只记了流程名、需要重新查当前配置”的空壳，
而是已经冻结的工作流与角色语义。

`workflow_catalog_roles` 还会把不直接出现在普通 agent step 上的隐式依赖一起收集：
fallback、reflect_loop 的两种角色、team_fanout 的 aggregator/researcher、compose 可能生成的白名单角色，
以及证据验证角色（`orchestrator.py:78-97`）。

### 9. 快照为什么不放密钥

`CatalogRuntimeSnapshot` 保存 behavior、prompt、profile ID、模型名、endpoint、参数模式与终端角色，
但模型快照类型根本没有 `api_key` 字段（`catalog/dto.py:60-93`）。

恢复时采取“冻结语义 + 活凭据”的组合：

- 模型、temperature / reasoning_effort、endpoint 等从快照恢复；
- API key 按 profile ID 从当前 Catalog 的内部 Full 视图取出；
- 二者重新组装成运行时 ModelProfileFull
  （`catalog/runtime.py:224-267`）。

这解决两个冲突目标：

- checkpoint / manifest 可落库、可展示、可审计，而不扩大密钥泄露面；
- 运维可以轮换失效 key，不必修改历史 checkpoint。

代价也要主动说：如果 profile 被删除，或者恢复环境不再能按 ID 提供凭据，角色语义仍能恢复，
但原模型未必还能调用；系统可能回退默认 LLM，不能宣称字节级完全复现。

### 10. 密钥视图、空值语义与资源生命周期

密钥通过类型边界隔离：

- `ModelProfileView` 只下发“是否设置 + 尾四位”，`SearchKeyView` 只下发脱敏 hint；
- `ModelProfileFull` 仅供引擎内部；
- 表单更新时空字符串表示“保持原密钥”，显式 null 对不可空字段直接拒绝
  （`catalog/dto.py:17-43,96-140`，`catalog/repository.py:159-176,288-301`）。

连接资源也有明确所有权：

- CatalogRuntime 按 profile 缓存 LLM，并在 `aclose` 中尽力关闭全部 client；
- API 注入的搜索 key 池由调用方关闭；
- DeepResearchAgent 只关闭自己拥有的默认 LLM / SearchTool；
- 后台执行 finally 即使再次收到 cancel，也用独立 cleanup task + shield 完成释放
  （`catalog/runtime.py:186-213`，`api.py:728-759,852-897`）。

### 11. 残余风险（主动交代）

1. **单一默认档案不是数据库硬约束**：当前是事务内“先清零、再设默认”，顺序操作正确，但并发写入下仍可能出现两个默认；测试只覆盖顺序切换（`catalog/repository.py:130-176`，`test_catalog_repository.py:48-60`）。
2. **快照不包含凭据**：安全性更好，但删除 profile、迁移到没有同 ID 档案的环境后，精确模型恢复会退化。
3. **自定义 prompt 属于受信控制面**：同名卡片能替换内置 prompt；当前单用户 / 管理员部署可接受，多租户需要 RBAC、审批与不可覆盖的系统安全层。
4. **乐观锁不做三方合并**：409 防静默覆盖，不保证协同编辑体验。
5. **behavior 是封闭集合**：数据化扩展覆盖“同逻辑、不同提示词/模型”，不覆盖任意新工具与新算法。
6. **搜索 key 列表按执行尝试重新读取**：它是运维可用性配置，不在 Catalog 快照中；恢复前后可能使用不同 key 池。

## 二、题库（28 题）

### A. 基础理解（7 题）

**A1. 角色目录模块解决的核心问题是什么？**

- 考点：能否把 Catalog 讲成控制面，而不是 CRUD 页面。
- 参考答案：它把四类可编辑全局配置转换为引擎可消费的运行时依赖：角色卡变成 Agent，模型档案变成按角色解析的 LLM，自定义工作流变成 Workflow，搜索 key 变成主备检索池。真正的关键是控制面与执行面隔离：Catalog 可以继续变化，但已创建 run 使用冻结 definition 与角色快照（`api.py:1104-1147`，`orchestrator.py:100-117`）。
- 追问链：为什么不让每一步直接查 DB？→ 同一次 run 会受中途编辑影响，恢复也无法复现原语义，还会把数据库耦合进引擎热路径。
- 陷阱提示：只回答“可以创建角色和模型配置”没有讲到执行一致性。

**A2. 一张 AgentCard 是怎么变成可执行 Agent 的？**

- 考点：CardAgent 适配层。
- 参考答案：`CatalogRuntime.resolve_agent(name)` 先查启用卡片，命中后用 name、behavior、system_prompt 构造 `CardAgent`；CardAgent 从固定映射选内置实现，把委托实例的 name 改成卡片名以支持专属模型解析，非空 prompt 覆盖内置 system，`step` 则原样委托（`catalog/runtime.py:124-130`，`agents/card_agent.py:19-52`）。
- 追问链：为什么改委托实例的 name？→ 内置角色在 step 中调用 `ctx.llm_for(self.name)`，卡片名必须成为模型路由键。
- 陷阱提示：CardAgent 没有动态 import 或 eval 数据库代码。

**A3. behavior 有哪些值？它与角色名是什么关系？**

- 考点：身份与执行逻辑分离。
- 参考答案：五种 behavior 是 plan、research、reflect、synthesize、critique（`catalog/dto.py:13-14`）。角色名是可自定义的稳定引用键；behavior 决定复用哪套执行逻辑。多个不同名字可以共用 research 行为，但绑定不同模型和 prompt。
- 追问链：为什么 coordinator / aggregator 不开放成 behavior？→ 它们服务 compose / team_fanout 控制原语，不是普通卡片可安全替换的单步行为；自定义流程也禁止嵌套这两种顶层原语（`workflow.py:267-275,293-300`）。
- 陷阱提示：不要把 behavior 说成“角色权限”，当前没有工具级权限模型。

**A4. 某个角色最终用哪个模型？**

- 考点：三级模型解析。
- 参考答案：先看该启用卡片是否绑定 model_profile_id；没有或档案不可用时用 Catalog 的默认 profile；Catalog 也没有默认档案时，`resolve_llm` 返回 None，由 `RunContext.llm_for` 回退进程级默认 LLM（`catalog/runtime.py:174-202`，`agents/base.py:66-72`）。同一 profile 在一次运行内按 ID 缓存一个 client。
- 追问链：没有自定义卡片时默认 profile 生效吗？→ 生效，runtime 会独立加载默认 profile，测试见 `test_catalog_e2e.py:89-108`。
- 陷阱提示：不是“未绑档案就直接用环境变量”，中间还有 Catalog 默认档案。

**A5. 自定义工作流为什么有 steps、nodes、edges、viewport 四组字段？**

- 考点：兼容层与编辑态数据。
- 参考答案：steps 保留旧版线性协议和列表消费；nodes/edges 承载图拓扑、条件、join 与位置；viewport 保存画布视角，不参与执行；API 在每次写入时同步两种执行表示（`catalog/dto.py:143-178`，`catalog_api.py:271-328`）。
- 追问链：运行时优先哪个？→ Workflow 有 nodes 时走图执行，否则走 steps（`workflow.py:525-536`）；保存 API 会让两者保持同一语义。
- 陷阱提示：viewport 不是 checkpoint，也不应影响执行哈希的业务语义判断。

**A6. 创建 run 时冻结了哪些 Catalog 信息？**

- 考点：快照内容与时机。
- 参考答案：冻结本工作流可能触达的角色卡 name / behavior / prompt / profile ID，相关模型档案的非密钥参数、默认 profile ID 和有效终端角色；自定义 Workflow definition 也在后台任务启动前冻结（`catalog/runtime.py:53-95`，`api.py:1125-1147`）。随后快照进入 Blackboard scratch，运行与恢复都从它加载。
- 追问链：为什么连 terminal_roles 也存？→ 卡片以后可能改 behavior 或被删除，不存就会让同一图在恢复时突然被判成不同终端语义。
- 陷阱提示：SearchKey 与 API key 明文都不在这个快照里。

**A7. 快照不存 API key，恢复时模型怎么调用？**

- 考点：冻结语义、活凭据。
- 参考答案：快照保存 profile ID 与模型非密钥参数；恢复时按 ID 从 live Catalog 取 `ModelProfileFull.api_key`，再用冻结参数组装新的 Full 对象（`catalog/runtime.py:224-267`）。因此 key 可以轮换，checkpoint 不含秘密。
- 追问链：profile 被删了呢？→ 精确模型恢复失去凭据，可能回退 Catalog 默认或进程默认；这是安全选择带来的明确边界。
- 陷阱提示：不要声称“删除模型档案后仍能完全恢复原模型”。

### B. 设计权衡（7 题）

**B1. 为什么只允许五种 behavior，不允许上传任意 Agent 代码？**

- 考点：扩展性与安全/可维护性的边界。
- 参考答案：角色卡解决的是参数化复用：同一套已测试执行逻辑，换名字、prompt 和模型。任意代码插件会立刻引入依赖安装、进程隔离、工具权限、资源配额、签名和升级兼容问题，远超本地研究工具的需求。封闭 behavior 换来稳定协议和服务端可验证性；新增真正的新能力仍通过 Python Agent + registry 完成（`agents/card_agent.py:19-41`，`registry.py:21-42`）。
- 追问链：以后要做插件怎么办？→ 另建受版本管理的插件协议与沙箱，不把 system_prompt 字段伪装成代码扩展。
- 陷阱提示：不要把“无需写代码新建角色”夸成“无需代码扩展任意能力”。

**B2. 为什么允许同名卡片覆盖内置角色？**

- 考点：低侵入定制与风险。
- 参考答案：工作流不必改名或复制，只需建立同名卡片就能替换 prompt / model / behavior；解析器仍保持“卡片优先、注册表兜底”（`catalog/runtime.py:124-130`）。这让现有 deep 流程直接吃到定制 researcher。代价是覆盖可能改变终端与安全语义，所以 enabled、behavior 白名单、终端重算和保存/运行校验必须一起存在。
- 追问链：如何证明真覆盖到完整 run？→ `test_catalog_e2e.py:37-74` 用同名 researcher 卡片验证自定义 prompt 进入完整报告流程。
- 陷阱提示：同名覆盖是显式能力，不是名称冲突 bug。

**B3. 为什么终端角色不能简单写死为 synthesizer？**

- 考点：有效配置语义。
- 参考答案：自定义 behavior=synthesize 的卡片也能产报告；反过来，同名 synthesizer 卡片若改成 research，名字还在但已不产报告。终端集合必须从“内置集合减去被覆盖项，再加有效 synthesize 卡片”动态计算（`catalog/runtime.py:43-50`）。测试 `test_workflow_def_api.py:290-307` 锁住了同名覆盖后的校验。
- 追问链：为什么快照终端集合？→ 防恢复时因卡片变更而重新解释旧流程。
- 陷阱提示：判断终端看最终 behavior，不看 display_name 或字符串包含 “synth”。

**B4. 为什么不只存 graph，彻底删除 steps？**

- 考点：迁移成本与协议兼容。
- 参考答案：项目先有线性 steps，后有图编辑与并行调度；API、历史数据、测试和模板仍消费 steps。双写加归一化允许渐进迁移，旧记录首次图编辑还能自动升级（`catalog_api.py:286-323`，`test_workflow_def_api.py:411-436`）。代价是同步逻辑复杂，因此只能由服务端生成派生表示，不能信任客户端自行保持一致。
- 追问链：最终能否删 steps？→ 可以，但要先迁移所有历史 WorkflowDef、模板/API 消费者与 checkpoint schema，并给版本化读适配器。
- 陷阱提示：不要说 graph_to_steps 只支持单路径；当前保存路径用 `graph_topological_steps`，支持 DAG 拓扑展开（`orchestration/graph.py:92-152`）。

**B5. 前端已经阻止环和非法连接，为什么服务端还要全量校验？**

- 考点：信任边界。
- 参考答案：前端校验只改善交互，调用方可以绕过 UI，旧客户端也可能提交过时结构。服务端会重新解析节点/边、执行条件语法检查、拓扑排序、角色白名单、反思与重试上界、唯一报告终端；非法请求统一 422（`catalog_api.py:230-328`）。运行时再检查终端与实际报告，防数据库旁路修改（`orchestrator.py:536-565`）。
- 追问链：为什么保存时校验角色 enabled？→ 禁用卡片运行时不会被 CatalogRuntime 解析，保存进去只会在执行时 KeyError。
- 陷阱提示：数据库 JSON 列不会替你验证内部结构。

**B6. 为什么用乐观锁，不给整张工作流加编辑锁？**

- 考点：协作频率与系统复杂度。
- 参考答案：工作流编辑是低冲突、长思考、短提交场景。悲观锁要处理锁租约、浏览器崩溃、超时续约和管理员解锁；version CAS 只在提交时检测冲突，成本更低。API 预检查给友好提示，DB 条件更新封住 TOCTOU（`catalog_api.py:539-562`，`catalog/repository.py:349-373`）。
- 追问链：前端如何不丢草稿？→ 409 后编辑器保持挂载，只刷新 server version（`WorkflowBuilderPage.tsx:98-110`）。
- 陷阱提示：乐观锁防丢更新，不提供自动字段合并。

**B7. 为什么只快照工作流会用到的角色，而不是整个 Catalog？**

- 考点：最小快照原则。
- 参考答案：全量快照会把无关 prompt、模型元数据和未来新增卡片都塞进每个 checkpoint，增加体积与暴露面；真正影响运行的只有显式步骤和隐式控制依赖。`workflow_catalog_roles` 精确收集普通 agent、fallback、reflect_loop、fanout、compose 白名单和 evidence_verifier（`orchestrator.py:78-97`），`create_catalog_runtime_snapshot` 再只保留 required 交集（`catalog/runtime.py:53-95`）。
- 追问链：为什么默认 profile 仍总要带？→ 未绑定卡片与内置角色都可能经它解析模型。
- 陷阱提示：最小化的是非密钥语义快照；密钥本来就不进入快照。

### C. 深挖实现（8 题）

**C1. 只更新 edges 时，服务端如何保证 nodes、steps 和 viewport 不丢？**

- 考点：PATCH 式合并与归一化。
- 参考答案：`_normalize_graph_payload` 先看 `model_fields_set`。若只提交 edges，就从 existing 取 nodes；若旧记录还没有 nodes，则先由 existing.steps 生成兼容图。随后解析 Node/Edge、校验每条 condition、用 `graph_topological_steps` 重算 steps；viewport 未提交时沿用 existing.viewport（`catalog_api.py:286-323`）。回归测试覆盖非法边不落库、重排边后 steps 跟着变、只移动节点不丢边、只改 viewport 不改语义（`test_workflow_def_api.py:310-408`）。
- 追问链：为什么不能简单把请求 JSON merge 到 ORM 行？→ edges 改变会改变执行顺序，必须连带重算 steps 并重新过终端校验。
- 陷阱提示：这是语义合并，不是浅字典合并。

**C2. 两个客户端同时拿 version=3 更新，为什么不会都成功？**

- 考点：TOCTOU 与数据库 CAS。
- 参考答案：两者可能都通过 API 层“提交版本等于当前版本”的预检查，但 repository 的 UPDATE 带 `WHERE id=... AND version=3`，第一个成功后写 version=4，第二个 rowcount=0，抛 `WorkflowVersionConflictError`，API 翻译为 409（`catalog/repository.py:346-373`，`catalog_api.py:559-562`）。
- 追问链：为什么还要 API 预检查？→ 可以更早返回包含当前/提交版本的友好错误；正确性仍由 DB CAS 承担。
- 陷阱提示：只在 Python 里先读后写不能防并发覆盖。

**C3. 自定义工作流从点击“开始研究”到执行，完整链路是什么？**

- 考点：控制面到执行面。
- 参考答案：构建器保存时 API 归一化并校验，repository 持久化 WorkflowDef；`GET /api/workflows` 只暴露 enabled 定义供选择（`api.py:1233-1260`）；创建 run 时按 name 取定义，复制 steps/nodes/edges 到 `execution.definition`，再保存 Catalog 快照并持久化 run（`api.py:1125-1147`）；后台 agent 优先使用 existing_execution.definition，不再查 live WorkflowDef（`orchestrator.py:477-480`）；WorkflowEngine 有 nodes 就走图调度，否则走 steps（`workflow.py:525-536`）。
- 追问链：创建后立刻删除 WorkflowDef 会怎样？→ 已创建 run 不受影响，未来新 run 不再能选择它。
- 陷阱提示：执行器不是每个节点都回查 WorkflowDef。

**C4. 中断后角色卡被更新、禁用甚至删除，恢复为何还能保持原 prompt？**

- 考点：快照优先路径。
- 参考答案：恢复时 Blackboard scratch 已有 `_catalog_runtime`，`load_catalog_runtime(snapshot=...)` 直接从快照重建 enabled 的 AgentCardView，再构造 CardAgent，不读取 live card 语义（`catalog/runtime.py:224-267`）。因此 behavior、prompt 和 terminal_roles 保持原值。`test_catalog_resume.py:133-220` 对 update/disable/delete 三种变更都断言恢复仍收到 original prompt。
- 追问链：模型密钥也来自快照吗？→ 不，只有参数冻结，密钥按 profile ID live 读取。
- 陷阱提示：删除 card 可恢复角色语义，删除 profile 不保证原模型仍可调用。

**C5. 角色绑定的 profile 已不存在时，代码具体怎么降级？**

- 考点：解析细节与诚实边界。
- 参考答案：live 加载时，绑定 ID 查不到就不会进入 `_profiles`；`resolve_llm` 先尝试绑定 profile，拿不到后转向 Catalog default，仍没有则返回 None，`RunContext` 回退默认 LLM（`catalog/runtime.py:174-184`，`agents/base.py:66-72`）。快照恢复时也只会把能从 live repository 取到 secret 的 profile 组装进 runtime（`catalog/runtime.py:238-259`）。
- 追问链：为什么 FK 是 ON DELETE SET NULL？→ 新运行不会留下悬空绑定（`persistence/orm.py:291-294`）；历史快照仍保留旧 ID 供审计。
- 陷阱提示：降级能保证流程尽量可用，但可能改变模型，不能包装成严格复现。

**C6. `workflow_catalog_roles` 为什么要收集 fallback、reflect_loop 和 compose 的隐式角色？**

- 考点：静态依赖闭包。
- 参考答案：这些角色不一定出现在 `step.agent`：fallback 只在失败路径触发，reflect_loop 分别有 reflector/researcher，team_fanout 隐式依赖 aggregator 与 researcher，compose 运行后还可能生成五种白名单角色。若只快照表面 agent，首次执行可能正常，恢复走到罕见分支时却取到新配置或找不到卡片（`orchestrator.py:78-97`）。
- 追问链：为什么固定加 evidence_verifier？→ 它会参与研究证据验证，即使不作为用户可见工作流节点出现。
- 陷阱提示：快照依赖分析要覆盖失败路径和动态生成路径，不只是 happy path。

**C7. 同名 synthesizer 被 research 卡片覆盖后，系统在哪几层避免“假终端”？**

- 考点：跨层一致性。
- 参考答案：CatalogRuntime 先按覆盖后的 behavior 重算 terminal_roles；`GET /api/roles` 把 produces_report 返回 false；保存工作流时 terminal 校验拒绝把它当报告节点；运行时 WorkflowEngine 的 `_terminal_roles` 与最终 require_report 再兜底（`catalog/runtime.py:43-50`，`api.py:1290-1320`，`catalog_api.py:243-268`，`workflow.py:320-348`）。测试 `test_workflow_def_api.py:290-307` 验证这条链。
- 追问链：如果自定义 my-writer behavior=synthesize？→ 它会进入 terminal_roles，可作为唯一终端，测试 `test_workflow_def_api.py:241-287`。
- 陷阱提示：名字、UI 标签和行为模板三者不能混为一谈。

**C8. 搜索 key 池并发切换时，怎样避免在途请求继续撞旧 key？**

- 考点：无锁粘滞故障转移。
- 参考答案：池按 priority 获得 key 列表；每个 search 协程维护自己的 tried 集合，但每轮都读取实时全局 `_idx`，不固化入口起点。配额/鉴权类错误时，仅当全局下标仍指向失败 key 才推进，避免另一个协程把已完成的切换拨回；非配额错误直接上抛给步骤重试（`tools/tavily_pool.py:47-80`）。`test_tavily_pool.py:198-217` 锁住“在途请求跟随实时切换”的竞态。
- 追问链：为什么不加全局锁？→ 会把所有并发检索串行化；当前最坏只是切换瞬间少量残余请求打旧 key。
- 陷阱提示：字符串错误分类是启发式，不能声称覆盖所有 provider 错误类型。

### D. 压力与陷阱（6 题）

**D1. “这不就是给 prompt 套了一层数据库配置，算什么 Agent 扩展？”**

- 参考答案：如果把它说成通用插件系统，这个质疑成立。它实际解决的是更窄但真实的问题：在不改引擎和工作流协议的情况下，对已验证的五类 Agent 行为做“身份、提示词、模型”三维参数化，并让这些配置参与终端校验、checkpoint 恢复和资源管理。执行逻辑仍来自真实 Agent 类，不是 prompt 假扮能力（`agents/card_agent.py:19-52`）。全新工具与算法仍要写代码注册，这是有意保留的边界。
- 追问链：价值怎么证明？→ 同名 researcher 覆盖内置 prompt 的完整 E2E 测试、每角色模型解析、恢复快照三条链都已落地，不是只做了表单。
- 陷阱提示：先承认范围，再讲工程闭环，不要硬争“这是低代码平台”。

**D2. “快照不存 key，怎么敢叫可复现？”**

- 参考答案：要区分**执行语义可复现**与**外部服务字节级重放**。系统冻结 workflow、prompt、behavior、模型名、endpoint、参数模式、设置和哈希；key 是凭据，不是算法语义，放入 checkpoint 会把每份历史记录变成长期秘密副本。恢复时使用同 profile ID 的当前凭据，是安全与可运维性的取舍（`catalog/dto.py:69-93`，`catalog/runtime.py:224-267`）。即便保存 key，远端模型版本和采样也可能变化，所以不能声称 bit-for-bit 重放。
- 追问链：怎样进一步提高复现性？→ 保存 provider/model 版本指纹、响应原始记录或可选离线回放包；密钥仍由 secret manager 注入。
- 陷阱提示：不要用“安全”掩盖 profile 删除后的可用性缺口。

**D3. “你所谓单一默认模型有数据库约束吗？两个并发请求会怎样？”**

- 参考答案：当前没有 partial unique index。repository 在同一事务里先把所有 is_default 清零，再写当前行，顺序操作与普通使用正确（`catalog/repository.py:130-176`），但两个并发事务仍可能各自提交一个默认值；`get_default_profile` 只取 scalar，数据异常时结果也不确定（`catalog/repository.py:118-123`）。这是明确欠账。生产 PostgreSQL 应加 `UNIQUE ... WHERE is_default=1`，或把默认 profile ID 提升为单行设置并做 CAS。
- 追问链：现有测试覆盖什么？→ 只覆盖顺序切换，不覆盖并发写（`test_catalog_repository.py:48-60`）。
- 陷阱提示：不要把“事务”误说成“自动保证跨行唯一”。

**D4. “允许同名卡片覆盖内置角色，用户把安全 prompt 换掉怎么办？”**

- 参考答案：当前威胁模型把 Catalog 视为部署管理员控制面，不是普通终端用户输入；配置了 API_KEY 时，整组 Catalog 路由统一受鉴权依赖保护（`api.py:517-519`），本地零配置模式则仍应按单用户环境看待。系统能保证的是：behavior 白名单、工作流结构门禁、证据的程序性验证与最终报告要求不会因换 prompt 消失；但自定义 prompt 确实可能降低模型侧指令质量，这是配置者承担的风险。多租户化必须补强制鉴权、RBAC、审计日志、卡片版本审批和不可覆盖的 system safety prefix，而不是继续把管理员配置与用户 query 放在同一信任级别。
- 追问链：同名覆盖至少如何避免拓扑被悄悄破坏？→ 终端角色按有效 behavior 重算，并在保存与运行两层校验。
- 陷阱提示：程序性证据门禁仍在，不等于自定义 prompt 没有风险。

**D5. “前端 409 后只刷新版本号，再点保存不还是会覆盖别人？”**

- 参考答案：会，所以当前语义是“阻止第一次静默覆盖，并保留本地草稿让人决定”，不是自动合并。前端保持编辑器状态，只把 base version 更新到服务端最新值（`WorkflowBuilderPage.tsx:98-110`）；用户再次提交相当于明确选择自己的草稿获胜。多人实时协作需要展示 diff、三方合并或 CRDT，图结构尤其不能盲目字段合并。
- 追问链：为什么不自动合并 nodes/edges？→ 删除节点、改边与改终端角色存在强语义耦合，机械 union 很容易造环或复活已删除节点。
- 陷阱提示：把 CAS 说成“解决多人协作”会被追问击穿。

**D6. “运行期间删掉工作流、角色卡、模型档案或搜索 key，会发生什么？”**

- 参考答案：分时点回答。创建 run 后，workflow definition 与角色 behavior/prompt/terminal semantics 已冻结，删除 WorkflowDef 或 AgentCard 不改变这次 run；CatalogRuntime 初始化后，已构造的 profile client 也不再查 DB。中断后恢复时，角色语义仍来自快照，但模型 secret 需要 live profile：profile 被删可能回退其他 LLM；搜索 key 池则在每次执行尝试构造时重新读取 active keys（`api.py:648-659`），恢复前后可能变化。未来新 run 一律使用最新控制面状态。
- 追问链：为什么搜索 key 不冻结？→ 它是配额与可用性凭据，恢复时继续使用已耗尽 key 没有价值；manifest 只记录 search backend，不记录秘密。
- 陷阱提示：不同实体的冻结策略不同，不能笼统回答“全部快照了”。

## 三、模块速记

### 核心口诀

- **控制面四件套**：档案、卡片、Key、流程。
- **执行面四原则**：先校验、再冻结、密钥不落盘、版本拒覆盖。
- **角色解析**：卡片优先，内置兜底。
- **模型解析**：绑定档案 → 默认档案 → 进程默认。
- **恢复语义**：提示词与参数冻结，凭据按 ID 活取。
- **终端判断**：看最终 behavior，不看角色名字。

### 创建 run 的关键顺序

`解析流程 → 冻结 definition → 收集角色依赖 → 写 Catalog 快照 → 持久化 run → 启动后台任务`

顺序答错会暴露一个严重设计问题：如果先启动任务再快照，崩溃窗口里可能留下不可恢复或语义漂移的 run。

### 三个最值得讲的测试

1. `test_catalog_e2e.py:37-74`：同名 researcher 卡片在完整 deep run 中真实覆盖 prompt。
2. `test_catalog_resume.py:133-220`：卡片更新 / 禁用 / 删除后恢复，仍使用原 behavior 与 prompt。
3. `test_workflow_def_api.py:462-484`：过期 version 返回 409，旧客户端不能覆盖新版本。

### 30 秒电梯稿

“我没有让工作流引擎直接依赖数据库，而是在 Catalog 和引擎之间做了运行时适配层。
角色卡只参数化五种经过测试的行为模板，按角色绑定模型；自定义工作流保存时统一归一图和 steps，
服务端检查角色、DAG、条件、重试上界和唯一报告终端。创建 run 时先把工作流与角色语义写进 checkpoint，
持久化后才启动后台任务，因此后续修改或删除卡片不会改变中断恢复的语义。密钥刻意不进快照，
恢复时按 profile ID 取当前凭据；工作流编辑则用 version CAS 返回 409 防止静默覆盖。
它的本质是把可变控制面安全地翻译成可恢复执行面。”
