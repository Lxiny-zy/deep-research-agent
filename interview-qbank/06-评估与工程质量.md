## 一、设计思路总述

### 0. 一句话定位

这个项目的评估体系回答两个不同的问题：**「系统的逻辑对不对」**交给 613 项默认离线 pytest + 139 项前端 vitest（假后端、零密钥、CI 可跑）；**「系统的产出好不好、值不值」**交给 eval 层（LLM-as-judge 四维打分 × 公共模板与内部编排模式 × 质量/token/墙钟/预算四列对照）。两层职责分离，口诀：**「假后端测我的逻辑，真模型归评估层」**。

### 1. 为什么评估是编排能力的「变现」

- **问题**：项目同时提供三种公共模板，并保留 reviewed/auto/teams 等内部编排能力与预算门禁——但「功能列表」在简历上是廉价的，任何人都能写「支持多种工作流」。面试官真正想听的是：**多出来的复杂度换来了什么**。
- **方案**：`eval/run_eval.py` 把编排差异变成实验结论：对每个 workflow × case 组合跑完整研究并打分，采集三个硬指标——judge 四维均分、`agent.tracer.total_tokens`（Tracer 真值，run_eval.py:91）、`time.monotonic` 包住 `agent.run` 的墙钟（run_eval.py:82-84）；汇总表之外自动输出「X 相对基线 → 质量 ±a%，token ±b%，耗时 ±c%」的对照结论行（`_delta_lines`，run_eval.py:125-142），并可 `--output` 落盘为 markdown 结果文档（run_eval.py:175-229、240-243，默认写 `eval/results/<date>.md`）。
- **取舍**：备选是只演示「公共模板和内部编排模式都能跑通」——那是功能验证不是价值论证。对照实验的代价是要烧真实 token、要维护数据集，但它把「我实现了动态编排」升级成「实验表明动态编排在简单事实题上省 X% token 而质量仅降 Y%」——**前者是陈述，后者是结论**。这正是 UPGRADE_PLAN.md 升级项 4 的立意：「从功能列表到实验结论」。

### 2. LLM-as-judge：四维设计与自知的局限

- **问题**：研究报告质量没有可程序判定的标准答案，人工评每轮不可持续。
- **方案**：`eval/judge.py` 用 LLM 从四个正交维度各打 1~5 分——coverage（覆盖关键面）、groundedness（论断有引用支撑、可溯源）、depth（分析而非罗列）、coherence（结构可读性），Pydantic 强约束 `ge=1, le=5`（judge.py:15-24），`average` 为四维均值。三个防偏差细节：① **temperature=0.0**（judge.py:47），同一输入可复现；② system prompt 显式对抗长度偏差——「不要因为篇幅长就给高分；缺引用、空泛、跑题都要扣分」（judge.py:27-31）；③ 每条用例携带 `notes` 判分要点（dataset.py:24 注释「理想答案应覆盖的要点」）作为打分锚点，缓解 judge 凭感觉打分。judge 用**独立 Tracer**（judge.py:37），评审消耗的 token 不污染被评 agent 的成本统计。
- **局限（主动交代）**：judge 与被评 agent 走同一套 `Settings` 模型配置——存在自评偏好（self-enhancement bias）风险；单 judge 无 ensemble、无人工标注校准集、绝对分数不可跨模型比较。**核心防御是实验设计而非 judge 本身**：结论只取「同一 judge 同一温度下的相对差」（deep vs quick 的 delta），系统性偏差在做差时部分抵消；绝对分只做参考。

### 3. 数据集三分类：为对照实验「设计出区分度」

- **问题**：随机凑一堆问题跑对照，可能所有工作流分数都差不多——不是系统没差异，是**题目没有区分度**。
- **方案**：`eval/dataset.py` 共 13 条用例、三分类各有明确的「实验假设」（dataset.py:1-8 docstring 写明）：**简单事实型 4 条**（fact-*，如 Transformer 出处、GIL）——考察轻流程（quick）是否已够用、深流程多烧的 token 有没有换来质量，这是「动态编排省 token」结论的证据来源；**复杂多面型 5 条**（multi-*，如 Agent 框架对比、RAG vs 长上下文）——深流程/评审流程的主场，deep/reviewed 应在 coverage 和 depth 上拉开差距；**时效敏感型 4 条**（fresh-*，如近三月模型发布）——考察检索时效与来源标注，notes 里明写「罗列过时旧闻应扣分」（dataset.py:103）。每条 id 唯一、query/notes 齐全，且被测试锁住（test_eval_compare.py:159-164 断言三类齐备、≥10 条、id 唯一）。
- **取舍**：13 条偏小，统计功效有限——但每条都要跑多个公共模板/内部编排模式 × 真实 LLM，成本线性增长；当前规模够支撑「方向性结论」，不够支撑显著性检验，这一点如实说。

### 4. 预算受限质量曲线：把「预算门禁」从防御机制变成可调参数

- **问题**：TokenBudget 门禁（token_budget.py:9-26，orchestrator.py:442 接线）只是个安全带，单独存在时讲不出价值。
- **方案**：`--budget` 用 `dataclasses.replace(settings, max_tokens=budget)` 生成副本透传（run_eval.py:74，不就地修改原 settings，test_eval_compare.py:93-94 专门断言），与 API 的 per-run params 同机制（api.py:93）。跑「同一工作流 × 不同预算」（UPGRADE_PLAN.md:96-98 给出 15k/30k/不限三档命令）得到质量-预算曲线：回答「预算砍半质量掉多少」「多少预算后边际收益递减」——这是**成本意识**的直接证据，对应观测层的四维（质量/token/耗时/预算，EvalRow 四个字段，run_eval.py:45-53）。
- **成本数字的可信度**：token 不是估出来的——流式调用先按增量估算、拿到 provider 最终 usage 后 `reconcile_tokens` 校准为精确值（observability.py:87-92，`stream_options={"include_usage": True}`，test_llm_usage.py:59），事件带 `tokens_estimated` 标志区分「已校准/未校准」（observability.py:33）。

### 5. 离线测试哲学：DI + fakes 测「我的逻辑」

- **问题**：Agent 系统的测试常见两个极端——要么全 mock 到看不出测了什么，要么依赖真实 API 导致慢、贵、不稳定、CI 装不下。
- **方案**：两层职责分离。**系统逻辑是确定性代码**（路由、DAG 调度、checkpoint、证据门禁、预算、合并），用 DI 注入替身即可完整验证：`DeepResearchAgent` 构造器接受外部 `llm`/`search_tool`（orchestrator.py:206-210），`tests/fakes.py` 的 `FakeLLM` **按目标 schema 分发**预设结构化对象（ResearchPlan/FindingList/Reflection/语义决策/一致性报告，fakes.py:69-111）——关键设计是遇到未预设 schema 直接 `raise AssertionError`（fakes.py:112）：新增结构化调用必须显式建模，测试不会「默默通过」。`FakeSearch` 返回两条内容可被逐字验证的固定源（fakes.py:115-120），于是**整条研究流程可离线端到端跑通**。模型的「聪明程度」不属于这层，归 eval 层用真实 LLM 度量。
- **取舍**：fakes 可能与真实 API 行为漂移——缓解是把 provider 交互压缩在薄薄的 `LLM` 封装里，并对封装本身做协议级测试（test_llm_usage.py 用模拟 OpenAI 流 chunk 验证 usage 回填）；未做录制回放/契约测试，是诚实的边界。

### 6. 对抗评测与功能评测的关系（概述，详见 02）

功能评测（run_eval）问「报告好不好」，对抗评测（`eval/adversarial.py`）问「护栏顶不顶得住」——前者求好，后者防坏。方法论是**「红队 → 修复 → 锁指标」**：自攻找到 4 类绕过（同义词/零宽拆词/中文把字句/URL 连字符），修复后把探针转为回归用例，三项指标（注入拦截 20/20、伪引用拦截 13/13、矛盾召回 10/10，均 100%）在 test_adversarial_eval.py:122-133 **锁死为 1.0 并入 pytest**——对抗指标进 CI 防回归，而质量评分不进 CI（依赖真实 LLM、有随机性、烧钱）。这个「哪些指标锁进 CI、哪些留在离线评估」的划分本身就是取舍。

### 7. 质量门清单：一切绿灯可一键复现

`make lint`（ruff check + format --check + mypy，Makefile:11-14；ruff 启用 E/F/I/UP/B/ASYNC 含异步陷阱检查，pyproject.toml:13；mypy 对核心包 `disallow_untyped_defs`，pyproject.toml:15-21）→ `make test`（pytest -m "not pg"，613 项默认离线用例）→ `verify.bat` 四步迁移验证（upgrade head → **alembic check 断言 ORM 与迁移零漂移** → downgrade base 回滚验证 → 离线 pytest，verify.bat:11-26）→ CI 三 job（后端 lint+mypy+pytest、PostgreSQL service container 跑 `-m pg` 集成测试、前端 ESLint+tsc build+vitest 139 项，ci.yml）。

### 8. 还没做的（先于面试官说出来）

① **对照实验真实数字待跑**：框架与测试全就绪，但 `eval/results/` 目前只有 .gitkeep——公共模板与内部编排模式的对照、预算曲线的真实数字尚未产出（已有实数的是对抗评测 3×100% 与 chaos 的 1.8s/75%，UPGRADE_PLAN.md:47-51、69-73）；② **未统计行覆盖率**——用测试分层与关键路径清单代替覆盖率数字；③ **无线上评估**：无用户反馈信号、无 A/B、无漂移监控；④ judge 无 ensemble、无人工校准集；⑤ 已知功能缺口如实记在 CHANGELOG「Known limitations」（healthz 不查库、限流单进程等，CHANGELOG.md:53-60）——CHANGELOG 本身就是「工程演进叙事 + 诚实边界」的证据。

## 二、题库（25 题）

### A. 基础理解（6 题）

**A1. 介绍一下你这个项目的评估体系，分几层、各回答什么问题？**
- 考点：全局分层观。
- 参考答案：五层。① **功能正确性**：613 项默认离线 pytest + 139 项前端 vitest，假后端零密钥，测系统逻辑；② **产出质量**：`eval/run_eval.py` 用 LLM-as-judge 四维打分做公共模板/内部编排模式对照（质量/token/墙钟/预算四列）；③ **安全鲁棒性**：`eval/adversarial.py` 三类对抗用例打护栏拦截率，指标锁进 pytest（test_adversarial_eval.py）；④ **可靠性**：`scripts/chaos_demo.py` kill -9 恢复演示，产出接管耗时与续跑节省两个数字；⑤ **静态质量门**：ruff/mypy/eslint/tsc/alembic check（Makefile、verify.bat、ci.yml）。
- 追问链：哪些进 CI？（①③⑤全进；②不进——真实 LLM 有成本与随机性；④以注入钩子的冒烟测试形式进，test_chaos_demo_hook.py）→ 为什么这样划分？（CI 里的东西必须确定、快、免费；见 B7）。
- 陷阱提示：别只说「写了很多测试」——分层与「每层回答什么问题」才是答案骨架。

**A2. judge 的四个维度是什么？为什么是这四个？**
- 考点：评分设计。
- 参考答案：coverage（覆盖问题关键面）、groundedness（论断有引用支撑、可溯源）、depth（深度分析而非罗列）、coherence（结构可读性），各 1~5 分，Pydantic `ge=1, le=5` 强约束，`average` 取均值（judge.py:15-24）。四维对应研究报告的四种典型失败模式：漏面、编造/无据、堆料无分析、结构混乱。其中 groundedness 与本项目的证据链主线呼应——报告能不能溯源是核心卖点。
- 追问链：为什么不加「事实准确性」维度？（judge 自己也无法可靠核实事实——那需要检索对照，超出单次打分能力；准确性由证据链的程序验证在生成侧兜住）→ 四维会不会相关性太高？（coverage 与 depth 有相关，但方向不同：漏面 vs 浅析；承认未做维度独立性分析）。
- 陷阱提示：说不出四维的英文名或说成三维/五维，会显得没真跑过。

**A3. 数据集是怎么设计的？三类各考察什么？**
- 考点：数据集意图。
- 参考答案：13 条、三分类（dataset.py:15-17 常量、28-120 用例）：简单事实型 4 条考察「轻流程是否够用、深流程多烧的 token 是否值得」；复杂多面型 5 条是深流程/评审流程主场，考察多角度拆解与综合；时效敏感型 4 条考察检索时效与来源标注，「罗列过时旧闻应扣分」写进 notes（dataset.py:103）。每条带 `notes` 判分要点供 judge 锚定（dataset.py:24）。分类设计让对照实验有区分度——预期不同工作流在不同类上各有优势，而非一条总分定胜负。
- 追问链：13 条够吗？（够方向性结论，不够显著性检验——每条 × 多个对照流程 × 真实 LLM；当前命令覆盖公共模板与内部编排策略，成本约束下的取舍）→ notes 会不会泄露答案给 judge？（见 B2 追问）。
- 陷阱提示：条数说错（不是 10 也不是 12，是 13：4+5+4）；测试锁的是下限 ≥10（test_eval_compare.py:160）。

**A4. run_eval 跑一次输出什么？**
- 考点：对照框架的输出面。
- 参考答案：逐用例明细（四维分+均分+token+耗时+预算列）、按工作流汇总（均分/均 token/均耗时，`_summarize` run_eval.py:107-122）、相对基线的 delta 结论行（「auto 相对 deep → 质量 -x%，token -y%，耗时 -z%」，run_eval.py:125-142）；`--output` 落 markdown 结果文档：元信息（工作流、预算、用例分类计数）+ 明细表 + 汇总表 + 对照结论（format_markdown，run_eval.py:175-229），默认路径 `eval/results/<date>.md`（run_eval.py:240-243）。
- 追问链：token 数从哪来？（`agent.tracer.total_tokens`，run_eval.py:91，Tracer 真值非估算）→ 墙钟含不含 judge 打分？（不含，计时只包 `agent.run`，run_eval.py:82-84——评的是被测系统的耗时，不是评审的耗时）。
- 陷阱提示：说成「输出一个总分」就把对照框架讲丢了——对照结论行才是这个工具存在的理由。

**A5. 613 项默认离线测试为什么一个 API key 都不需要？**
- 考点：DI + fakes 机制。
- 参考答案：`DeepResearchAgent` 构造器接受注入的 `llm` / `search_tool`（orchestrator.py:206-210）；`tests/fakes.py` 的 `FakeLLM` 按目标 schema 分发预设对象——请求 ResearchPlan 给两个子问题、FindingList 给一条可验证发现、Reflection 判「已充分」、语义/一致性 schema 也有预设（fakes.py:69-111）；`FakeSearch` 返回内容与 FakeLLM 的 evidence_quote 逐字对应的固定源（fakes.py:115-120），保证假发现能通过真实的 EvidenceVerifier——于是从 API 到报告的全链路可离线端到端。conftest 只有一个极简 fixture（`max_rounds=1` 限反思轮数，conftest.py:8-12）。PostgreSQL 集成测试单独标 `@pytest.mark.pg`（pyproject.toml:26-28，test_repository.py:715），默认 `-m "not pg"` 跳过。
- 追问链：FakeLLM 遇到没预设的 schema 会怎样？（`raise AssertionError`，fakes.py:112——新结构化调用必须显式建模，防「默默通过」）→ 假数据怎么过得了真护栏？（FakeSearch 源内容与 quote 逐字一致，这是刻意设计：护栏在测试里是真的）。
- 陷阱提示：别说「mock 掉了护栏」——恰恰相反，护栏全程真实执行，mock 的只是 LLM 与搜索这两个外部 IO。

**A6. 你的质量门都有哪些？提交一次代码要过几道关？**
- 考点：工程规范。
- 参考答案：后端 `make lint` = ruff check + ruff format --check + mypy（Makefile:11-14）；ruff 启用 E/F/I/UP/B/ASYNC 六组规则（pyproject.toml:13，ASYNC 抓异步陷阱如阻塞调用）；mypy 对 `deep_research` 包 `disallow_untyped_defs`（pyproject.toml:15-21，tests/eval 不强制——务实分级）。迁移验证 `verify.bat`：upgrade head → `alembic check`（断言 ORM 与迁移无漂移）→ downgrade base（回滚可用）→ 离线 pytest（verify.bat:11-26）。前端：ESLint + `npm run build`（tsc 类型检查 + Vite 构建）+ vitest。CI 三 job：后端离线、后端 PostgreSQL service container、前端（ci.yml）。
- 追问链：为什么 downgrade 也要验？（回滚是迁移的另一半；不可回滚的迁移在生产事故时是死路）→ alembic check 抓过真问题吗？（时间戳列 NOT NULL 与 ORM 不一致那类漂移，CHANGELOG.md:109-110 记录了对应修复）。
- 陷阱提示：把 `npm run build` 只当打包——它同时是 tsc 类型门。

### B. 设计与权衡（7 题）

**B1. 为什么说「评估是编排能力的变现」？不做对照实验行不行？**
- 考点：评估的战略定位。
- 参考答案：不做也「能跑」，但公共模板与内部编排模式就只是功能列表——面试官/用户无法判断复杂度是否值得。对照实验把架构差异翻译成决策语言：deep vs quick 的质量差多少、贵多少、慢多少（`_delta_lines` 自动产出三个百分比）；auto（动态自组合）的卖点「简单问题省 token」只有在简单事实型用例上跑出数字才成立。方案→数字→结论的链路，是「我做了 X」与「X 带来了 Y」的区别。run_eval.py:1-9 的 docstring 直接写明这个动机。
- 追问链：如果跑出来 deep 并不比 quick 好呢？（那也是有价值的结论——说明该场景下轻流程即可，动态编排的路由价值反而更大；实验的意义在于接受任何一种结果）→ 结果会写进哪里？（`eval/results/<date>.md`，README/简历引用）。
- 陷阱提示：别把对照实验说成「证明 deep 最好」的工具——预设结论的实验是伪评估。

**B2. judge 为什么用独立 Tracer？temperature 为什么是 0？notes 给 judge 算不算泄题？**
- 考点：评估的隔离性与可复现性。
- 参考答案：① 独立 Tracer（judge.py:37）——judge 自己的 LLM 消耗若混进被评 agent 的 `total_tokens`，成本对照就被污染了；测量工具不能改变被测量。② temperature=0.0（judge.py:47）——评分要可复现，同一报告两次打分应一致；生成可以有创造性，评审不该有。③ notes 不是泄题是「判分标准」——它给 judge 的是「理想答案应覆盖的要点」（dataset.py:24），相当于阅卷评分细则；不给 notes，judge 对「覆盖度」维度只能凭自身知识判断，偏差更大。风险在于 notes 过时（时效类），承认需要维护。
- 追问链：temperature=0 就完全确定了吗？（不是——provider 侧仍有非确定性（如 MoE 路由、并发 batch），只是方差大幅降低；承认边界）→ judge 的连接泄漏怎么处理？（`Judge.aclose` 转发底层 LLM 关闭，test_eval_compare.py:168-185 专门测转发）。
- 陷阱提示：「泄题」质疑要接住——单点打分（非 pairwise）场景下评分细则是标准做法，真正要防的是把 notes 混入被测 agent 的输入。

**B3. 预算受限质量曲线有什么用？机制上怎么实现的？**
- 考点：成本意识 + 配置透传链。
- 参考答案：用途：回答「花多少钱够」——同一工作流跑 15k/30k/不限三档预算（UPGRADE_PLAN.md:96-98），看质量何时进入平台期，给出「预算砍到 X 质量只降 Y%」这类采购级结论；也验证预算门禁的降级行为是「优雅变浅」而不是「崩溃」。机制：`--budget` → `dataclasses.replace(settings, max_tokens=budget)` 生成副本（run_eval.py:74，原 settings 不被就地修改，test_eval_compare.py:80-94 断言）→ 每次运行 `TokenBudget(max_tokens=...)` 门禁（orchestrator.py:442、token_budget.py:9-26）——与 API 的 per-run params 完全同一条链（api.py:93），评估用的就是生产机制，不是评估专用后门。
- 追问链：预算超了会发生什么？（门禁在步间检查，跳过后续非必要步骤收敛到报告——详见 01/03 文档）→ 为什么用 replace 不直接改 settings？（settings 被并发/后续 run 共享，就地修改是隐性全局副作用）。
- 陷阱提示：「评估路径 = 生产路径」是这题的加分点，说成「评估时单独实现了限额」就反了。

**B4. 为什么坚持离线测试？真实 LLM 进 CI 不是更真实吗？**
- 考点：两层职责分离哲学。
- 参考答案：CI 测试的对象是**我写的代码**：DAG 调度、并行合并、checkpoint 恢复、证据门禁、预算、SSE——这些是确定性逻辑，用可预测替身测得又快又稳又免费（613 项默认离线用例可重复运行）。真实 LLM 进 CI 的代价：慢（分钟级/次）、贵（每次 push 烧钱）、**不稳定**（模型输出随机性导致 flaky，团队会开始忽略红灯——比没有测试更糟）、泄密面（CI 需要生产 key）。而「模型好不好」本来就不是单元测试能回答的问题，归 eval 层按需人工触发。类比：测支付系统不需要真扣款，mock 网关测自己的状态机，对账系统另测资金正确性。
- 追问链：fakes 与真实 API 漂移怎么办？（LLM 封装薄、协议面小；test_llm_usage.py 用模拟 OpenAI 流 chunk 结构测封装本身；承认没做契约测试/录制回放，是下一步）→ 有没有介于两者之间的？（nightly 用真实 LLM 跑小样本 eval 做回归哨兵——在「还缺什么」清单里，见 D6）。
- 陷阱提示：这题的反面陷阱见 D4——两题答案要一致。

**B5. 墙钟为什么用 time.monotonic？为什么不把 judge 的耗时也算进去？**
- 考点：测量方法的严谨性。
- 参考答案：`time.monotonic` 不受系统时钟回拨/NTP 校时影响，测 duration 的标准选择；`time.time` 在长跑期间被校时会产生负数或虚高。计时只包 `agent.run`（run_eval.py:82-84）：judge 是测量装置不是被测系统，它的耗时与被评工作流的用户体验无关；混进去会让「换个 judge 模型」改变耗时结论。测试用 `_StubAgent` 注入 sleep 验证墙钟至少覆盖 run 内延迟（test_eval_compare.py:66-76，断言留计时器精度余量 `>= delay * 0.5`）。
- 追问链：墙钟受网络波动影响怎么办？（单次墙钟噪声大，看均值与相对差；承认未做多次重复取中位数）→ 为什么断言是 `>= delay*0.5` 不是 `>= delay`？（Windows 计时器精度粗，严格断言会 flaky——测试稳定性优先于断言强度）。
- 陷阱提示：能讲出「断言放宽是为了防 flaky」说明真的维护过跨平台测试。

**B6. token 数字凭什么是「真值」？流式输出的 token 怎么统计？**
- 考点：观测精度设计。
- 参考答案：非流式调用直接取 provider usage。流式的两段法：流中先按增量估算计入（`add_tokens(estimated=True)`），流末拿到 provider 最终 usage 后 `reconcile_tokens(estimated, exact)` 把估算整体替换为精确值（observability.py:81-92）；请求时显式带 `stream_options={"include_usage": True}` 让 OpenAI 兼容端在最后一个 chunk 返回 usage（test_llm_usage.py:59）。事件携带 `tokens_estimated` 标志（observability.py:33），前端能区分「实时估算中」与「已校准」；test_llm_usage.py:41-58 断言观察到的累计值单调递增、最终收敛到 exact=17、标志复位。所以 eval 报表里的 token 列是 provider 结算口径，不是 tiktoken 估算。
- 追问链：为什么不直接等流结束再计？（实时性——前端要在流中看到成本累积；这是「先估后校」两段法的动机）→ 恢复的 run 怎么续算？（checkpoint 存累计值，`restore_metrics` 回填，observability.py:54-61）。
- 陷阱提示：说「用 tiktoken 数的」就把这个设计讲丢了。

**B7. 对抗评测指标锁进 pytest，质量评分却不锁——为什么区别对待？**
- 考点：CI 准入标准。
- 参考答案：进 CI 的断言必须**确定、快、免费**。对抗评测满足：注入/伪引用两项由确定性护栏代码产生（正则+逐字校验），矛盾召回用「按真值返回的假 LLM」度量管线传播正确性（adversarial.py:8-16 口径声明）——三项都无随机性，锁 1.0 合理（test_adversarial_eval.py:122-133），回归即红。质量评分依赖真实 LLM：有成本、有方差、分数漂移可能来自模型升级而非代码回归——锁死数值会制造无意义红灯。所以质量评估进 CI 的只有「机制」测试（test_eval_compare 的 10 项：行数、透传、渲染），数值留给人工触发的离线跑。
- 追问链：那质量回归怎么发现？（当前靠手动跑对照；改进是 nightly 小样本+阈值告警，见 D6）→ known_gap 机制是什么？（新发现的绕过可标探针如实报告漏检、不计入必拦截断言，adversarial_cases 设计——诚实与防回归兼容）。
- 陷阱提示：「所有指标都应该进 CI」是听起来正确的错误答案——flaky 断言的社会成本要讲出来。

### C. 深挖实现（6 题）

**C1. run_comparison 是怎么做到可离线测试的？**
- 考点：评估框架自身的可测性设计。
- 参考答案：两个注入点：`agent_factory: Callable[[Settings, str], DeepResearchAgent]`（run_eval.py:37、65）与鸭子类型的 judge（只要求 `score(query, markdown, notes)`，run_eval.py:39）。测试注入三种替身：FakeLLM+FakeSearch 的真 agent（测全链路）、`_StubAgent`（只带 run/tracer/aclose，测墙钟与预算透传机制，test_eval_compare.py:37-50）、`FakeJudge` 固定四维分（test_eval_compare.py:28-30）。于是 test_eval_compare 的 10 项测试离线验证：行数=用例×工作流、token/墙钟/预算列填充、replace 副本语义、渲染的 delta 计算（断言字符串 `token -33%`、`耗时 -50%`，test_eval_compare.py:122-123）、markdown 表格与结论行、目录自动创建。
- 追问链：`finally: await agent.aclose()` 为什么重要？（每 case 新建 agent，异常路径不关闭会泄漏连接池，run_eval.py:96-97）→ 明细行为什么每 case 重建 agent 而不是复用？（Tracer 归零、状态隔离——agent 单次使用语义）。
- 陷阱提示：「评估框架自己也有测试」是很多项目缺的一层——能主动讲出来是差异点。

**C2. FakeLLM 为什么「按 schema 分发」而不是按调用顺序返回？**
- 考点：fakes 的设计哲学。
- 参考答案：按顺序（side_effect 列表）的 fake 与调用序强耦合——编排一改（并行、条件跳过、重试）测试全崩，且失败信息是「第 3 个返回值类型不对」这种废话。按 schema 分发（fakes.py:69-111）表达的是**契约**：「无论谁在何时要 ResearchPlan，都得到合法的 ResearchPlan」——测试对执行顺序不敏感，恰好适配本项目「同一批角色被不同公共模板和内部编排模式以不同顺序编排」的现实。计数器（parse_calls/complete_calls/stream_calls）仍可断言调用量。未预设 schema 抛 AssertionError（fakes.py:112）是防御性收口。另有 `verified_finding` 工厂（fakes.py:24-46）供绕过 Researcher 的测试直接构造「已通过全部验证」的 fixture，语义状态齐全。
- 追问链：FakeLLM 的固定报告为什么带 `[1]` 引用标记？（下游引用渲染/证据 UI 测试依赖引用格式，fakes.py:59）→ 假数据怎么和 FakeSearch 配对？（quote 与源 content 逐字一致，保证真 EvidenceVerifier 放行）。
- 陷阱提示：这题答「因为方便」等于没答——顺序无关性与编排可变性的匹配才是理由。

**C3. test_eval_compare 测了什么、刻意不测什么？**
- 考点：测试边界的自觉。
- 参考答案：docstring 直接声明边界（test_eval_compare.py:1-5）：只验证对照**机制**——行采集、token/墙钟/预算列、汇总与 markdown 渲染、目录创建、数据集结构约束、judge 资源关闭；**不断言真实质量分数**，「真实数字由用户以真实 LLM judge 自行跑出」。这是把「框架正确性」与「实验结果」分开：前者可回归，后者是一次性实验产物。数据集测试锁结构不锁内容（三类齐备、≥10 条、id 唯一、notes 非空，test_eval_compare.py:159-164）——用例文本可自由迭代，结构契约不许破。
- 追问链：为什么不把一份跑好的结果 md 提交进仓库当 golden file？（结果随模型版本漂移，golden 会腐烂；结果文档带日期落 `eval/results/` 属实验记录不属测试资产）。
- 陷阱提示：能引用 docstring 里那句「不断言真实分数」说明读过测试——这类边界声明是刻意写的。

**C4. 对抗评测的执行器怎么保证「测的是真护栏」？（概述题，详细在 02）**
- 考点：评测有效性。
- 参考答案：三保证：① 被测链路与生产同一套代码——SourcePolicy → EvidenceVerifier → SemanticEvidenceVerifier → ClaimConsistencyVerifier 直接 import 调用（adversarial.py:26-34），无平行实现；② 假的只有两处 LLM 依赖且口径公开（adversarial.py:8-16）：语义验证假 LLM 只做前置条件、不计指标，矛盾判定假 LLM 按用例真值返回——因此矛盾召回度量的是管线（claim_id 关联/阈值/双向标记）而非模型；③ 防刷指标机制：伪引用用例要求来源本身 policy=allow（拦截必须归因 EvidenceVerifier）、2 条 is_control 对照必须放行（防「一拦全拦」）、矛盾用例含中立发现断言不误标。指标分母是 43 个目标用例（20 注入+13 伪引用+10 矛盾对），另有 2 个放行对照。
- 追问链：三项 100% 可信吗？（→ D3）→ 4 类绕过怎么发现修复的？（→ 02 文档第 7、8 节）。
- 陷阱提示：这题控制在概述层收口并指向 02，展开细节反而暴露不清楚题库分工。

**C5. chaos_demo 在评估体系里的定位是什么？（概述题，详细在 03）**
- 考点：可靠性评估。
- 参考答案：它是**可靠性维度的量化评估**：起 API 子进程（离线假后端 `DR_DEMO_FAKE_BACKENDS=1`），先跑对照 run 拿 token 基线，再在 deep 工作流中间层硬杀进程、等租约 TTL 过期后重启，输出两个数字——接管耗时 1.8s（重启→首个 workflow.resumed 事件）与断点续跑节省 75% token（对照 8000 vs 恢复新增 2000）（chaos_demo.py:1-19 流程，UPGRADE_PLAN.md:69-73 实测）。工程收口：演示钩子默认零行为变化（未设环境变量时 `_demo_fake_backends_enabled() is False`，test_chaos_demo_hook.py:20-27），钩子路径本身有冒烟测试（离线跑通 deep 并计模拟 token ≥3000）。
- 追问链：为什么等租约 TTL 而不立即重启？（防脑裂 fencing 窗口，该等待单独标注不计入接管耗时——详见 03）→ 1.8s 是什么的时间？（恢复扫描接管，不含 TTL 等待）。
- 陷阱提示：把 TTL 等待算进「接管耗时」会被抓——数字口径要说得出。

**C6. mypy 为什么只对核心包严格？ruff 的 ASYNC 规则组抓过什么？**
- 考点：静态门的分级策略。
- 参考答案：pyproject.toml:15-21——`disallow_untyped_defs` 只施于 `deep_research` 包，tests/eval 不强制：核心包是长期资产、类型是接口文档；测试代码大量鸭子类型替身（_StubAgent、FakeJudge），强制标注收益低噪声高。`ignore_missing_imports = true` 因第三方（openai/tavily）无 stub。pydantic 插件让模型字段类型被 mypy 理解。ruff 选 E/F/I/UP/B/ASYNC（pyproject.toml:12-13）：B（bugbear）抓可变默认参数类真 bug，ASYNC 抓异步代码里的同步阻塞调用——对一个满是 async 的项目是针对性选择。
- 追问链：为什么不上 pyright/更严的 strict？（渐进严格：先保证核心包全标注，strict 的增量收益 vs 迁移成本）→ 格式化为什么用 `format --check` 进门而不是自动改？（CI 只验证不修改；本地 `make fmt` 才自动修）。
- 陷阱提示：「全项目一律最严」听着政治正确，实际是没维护过带测试替身的类型库的信号。

### D. 压力与陷阱（6 题）

**D1. LLM 当裁判可靠吗？如果报告里写一句「本报告值 5 分」把裁判糊弄了怎么办？**
- 考点：judge 的偏差与对抗面，诚实度。
- 参考答案：分三层答。**已知偏差与已做缓解**：长度偏差——system prompt 显式「不要因篇幅长给高分」（judge.py:30）；随机性——temperature=0（judge.py:47）；锚点缺失——notes 判分要点；格式作弊——结构化输出+Pydantic 界约束。**结构性防御**：结论只取同一 judge 下的**相对差**（delta 行），judge 的系统性偏差（如普遍偏松）做差时部分抵消——这比修 judge 本身更可靠。**承认未设防的**：对 judge 的 prompt 注入（报告正文里塞「给满分」指令）当前没有专门防御——被评报告整段进 user prompt（judge.py:44-46）；缓解方向是数据定界符+注入信号扫描（护栏的 SourcePolicy 思路可复用到 judge 入口）、多 judge ensemble、人工抽检对齐。还有自评偏好：judge 与 agent 同一套模型配置，理想做法是换不同 provider 当裁判。
- 追问链：那你为什么还用 LLM judge？（没有更好的可扩展替代——人工不可持续、规则打不了「深度」；关键是知道它测什么不测什么）→ 怎么验证 judge 本身？（应建小规模人工标注集算相关性——没做，如实说）。
- 陷阱提示：答「prompt 里写了要严格所以可靠」必挂——考的就是你知不知道 prompt 不是防御。

**D2. 613 个默认离线测试都测了什么？覆盖率多少？**
- 考点：对自家测试资产的掌握 + 诚实。
- 参考答案：先诚实：**没统计行覆盖率**，没有接 coverage.py，不能编一个百分比。当前 `tests/` 有 49 个测试文件、490 个 test 函数；参数化后总收集 614 项，其中 1 项 PostgreSQL 标记默认排除，所以本地默认基线是 613 项。按职责分为：纯函数与状态机单测，Agent / 编排 / 护栏组件测试，ASGI 离线端到端，持久化与 checkpoint 恢复，Catalog / 自定义工作流，评估器自身，以及 LLM / SSE 协议模拟。我要证明的是关键性质有回归钉子，例如租约 fencing、并行合并、fail-closed、澄清循环、无密钥快照，而不是拿行覆盖率代替风险分析。mypy `disallow_untyped_defs` 还提供另一维度的类型约束。
- 追问链：哪块覆盖最薄？（真实 provider 契约、长稳/负载、多浏览器交互——如实点名）→ 613 里有没有浅测试？（有些结构锁测试只锁 schema 或数据集构成，但它们防的是契约漂移，不应冒充深行为测试）。
- 陷阱提示：绝不能现编一个「85%」——追一句「用什么工具统计的」就穿帮。诚实+分层叙述是唯一活路。

**D3. 你这些数字——3 个 100%、1.8s、75%——都是自测的，我为什么要信？**
- 考点：指标的诚实口径与可复现性。
- 参考答案：三点。① **可复现**：每个数字都有单命令复现路径——`python -m eval.adversarial`（输出自带口径说明，adversarial.py:388-391）、`make chaos-demo`、`pytest`；面试现场可以当场跑。② **口径公开且保守**：对抗评测的输出与 docstring 明写哪两处是假 LLM、矛盾召回度量的是管线不是模型判别力；chaos 的 1.8s 明确不含租约 TTL 等待；100% 的分母（20/13/10）如实标出——**是自建用例集上的 100%，不是真实世界的 100%**，用例集之外的新绕过随时可能存在（known_gap 机制就是为此设计的）。③ **锁进回归**：三项率值以断言形式锁在 test_adversarial_eval.py:122-133，CI 每次运行都在重新「自证」——这比一次性截图可信。反过来说：对照实验的质量数字我**还没跑**（eval/results/ 是空的），所以简历/README 里也没写——不掺没跑出的数，是这套数字可信的前提。
- 追问链：自建用例集会不会挑软柿子？（伪引用类理论上必 100%——确定性逐字校验，不是挑的；注入类的 4 个绕过恰恰是先漏检再修复的，过程记录在 UPGRADE_PLAN.md:47-51）→ 有第三方验证吗？（没有，欢迎面试官现场出对抗用例——这个姿态本身是答案）。
- 陷阱提示：护短或含糊会死——「100% 的边界在哪」必须自己先说。

**D4. 用假 LLM 跑通端到端测试，算不算自欺欺人？**
- 考点：测试哲学的辩护能力。
- 参考答案：不算，前提是想清楚**测试的断言对象**。这 613 项默认离线用例断言的是：调度器按 DAG 拓扑并行、条件边正确路由、checkpoint 能恢复出一致状态、未验证的 finding 进不了报告、预算超限优雅收敛、SSE 事件序完整——全是**我写的确定性逻辑**，替身只是让这些逻辑可执行，断言从不涉及「模型答得好不好」。真正的自欺欺人是反过来：用真实 LLM 跑测试然后断言「报告里包含某关键词」——那是在测模型的随机行为，绿灯红灯都不说明代码对错。当然有真实风险要认：① fakes 与真实 provider 行为漂移——所以 LLM 封装的协议面单独测（test_llm_usage 模拟 OpenAI 流 chunk 与 usage 结构），且封装刻意薄；② 「假数据恰好通过护栏」可能掩盖集成缝隙——所以护栏在测试里全程真实执行，FakeSearch 的内容是刻意构造成能被逐字验证的，而对抗评测又专门测护栏拒绝的路径。两层加起来：假后端测逻辑、真模型归 eval——各测各的，谁也不冒充谁。
- 追问链：有没有被 fakes 骗过的真 bug？（契约测试缺位是已认的坑；provider 差异类问题靠 runtime 的重试/解析容错兜，llm.py:114-128 的 retries 语义）→ 那 e2e 到底什么时候用真 LLM 跑过？（手动冒烟 + eval 层，不在 CI）。
- 陷阱提示：只答「业界都这么做」是零分——要能把「断言对象是什么」讲清楚。

**D5. eval/results 目录是空的——你所谓的「对照实验」是不是只有框架没有实验？**
- 考点：未完成项的坦然与规划。
- 参考答案：对，当前状态就是「框架完备、真实数字待跑」，我不回避：`eval/results/` 只有 .gitkeep。已就绪的是全链路机制——13 条三类用例、四维 judge、公共模板/内部编排模式对照、预算透传、markdown 落盘，且机制层有 10 项测试锁着；待做的是拿真实 LLM key 按 UPGRADE_PLAN.md:89-102 的命令清单跑多种编排对照、15k/30k/不限预算曲线和 auto vs deep。刻意的顺序：先把测量仪器造好、校准好（机制测试），再采数——反过来先跑数后补框架，数字口径会漂。已经产出真实数字的是另两项：对抗 3×100% 与 chaos 1.8s/75%——它们不依赖付费模型所以先完成。简历上我只写已跑出的数字。
- 追问链：预计跑一轮多少成本？（13 用例 × 多个对照流程 × 深流程多轮检索，量级估算要能现场给出——按每 run 万级 token 估约几十万 token 量级 + judge 开销）→ 跑出来结果不好看怎么办？（结论中性呈现；「reviewed 贵 40% 只好 5%」同样是有效结论，指导默认工作流选择）。
- 陷阱提示：假装跑过是最大的雷——这个目录状态 30 秒就能被验证。

**D6. 如果这套系统明天要上线服务真实用户，你的评估体系还缺什么？**
- 考点：离线评估与线上评估的鸿沟。
- 参考答案：按优先级五块。① **线上质量信号**：现在只有离线 judge——上线要有用户反馈（点赞/引用点击率/报告留存）、抽样送 judge 的持续评分、与离线分数的相关性校验；② **回归哨兵**：nightly 小样本真实 LLM eval + 阈值告警，抓「模型 provider 静默升级导致质量漂移」——这是纯离线测试永远抓不到的；③ **A/B 基础设施**：工作流/prompt 改动的灰度对照，现在的 run_eval 是离线批跑，没有流量分割与显著性检验；④ **SLO 与成本监控**：Tracer 有单 run token 真值，但没有聚合面板、没有成本告警、没有 P95 延迟目标；CHANGELOG 已如实记录的缺口也在这类——healthz 不查库、限流单进程（CHANGELOG.md:53-60）；⑤ **安全的持续红队**：对抗用例集是静态的，上线后要有新绕过的收集回流机制（known_gap 探针机制就是为此留的接口）与真实注入样本的蜜罐采集。另加负载/长稳测试与 judge 的人工校准集。总结：现在的体系回答「代码对、护栏硬、离线上限在哪」，缺的是「真实分布下持续地好」。
- 追问链：这些里先做哪个？（回归哨兵——成本最低、抓的风险最独特）→ 线上 judge 打分的成本怎么控？（抽样 + 只对可疑 run 全评）。
- 陷阱提示：只答「加监控」太空——每一项要能挂到现有代码的具体缺口上。

### 口诀与关键句

- **两层分离**：「假后端测我的逻辑，真模型归评估层」——断言对象永远是确定性代码。
- **评估即变现**：功能列表 → 对照结论；「我做了 X」→「X 换来质量 +a% / token -b%」。
- **judge 三防**：温度零、锚 notes、反长度偏差写进 prompt；**结论只信相对差**。
- **FakeLLM 铁律**：按 schema 分发（顺序无关）+ 未预设即 AssertionError（不许默默通过）。
- **CI 准入**：确定、快、免费——对抗指标锁 1.0 进 CI，质量分数留离线。
- **数字口径三件套**：可复现（单命令）、口径公开（分母与假 LLM 声明随输出打印）、锁回归（断言化）。
- **诚实清单**（先于面试官说）：无行覆盖率、对照真实数字待跑、无线上指标、无 A/B、judge 无 ensemble 无人工校准、对 judge 的注入未设防、known limitations 记在 CHANGELOG。
